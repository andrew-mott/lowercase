## Change C2 - Worker V2 core contract + fake collaborators, no runtime wiring - merged (PR #351)

### Discussion

**Naming pass done for Phase 1's vocabulary, following the existing `Port`-suffix convention** (checked directly: every real port in `packages/ports/src` is `*.port.ts`, and none double-prefix with an owning-entity name — the owning context comes from the file's package/folder location, not the type name itself):

- `JobExecutionPort` — the inbound port (`execute()`); `WorkerDispatchPort` — the engine's outbound counterpart (Phase 4). Both stay colocated in their owning component's own package per the plan's Illustrative File Shape, so neither needs a `Worker`/`Engine` prefix restated in the type name. Settled as a general pattern: entity + behavior + `Port` (`Job`+`Execution`, `Worker`+`Dispatch`, `Resource`+`Permit` below), only reconsidering a prefix if a port is ever promoted into the shared, flat `packages/ports` package.
- `ExecuteJobCommand`/`JobResult`/`JobExecutionOptions` — confirmed as-is. `ExecuteJobCommand` matches the existing `EngineMessage`/`*Msg` command-union pattern the engine's own reducers already use (`packages/components/engine/src/engine.types.ts`).
- **`ResourceAdmission` renamed to `ResourcePermitPort`; `AdmissionRequest`/`AdmissionGrant` to `PermitRequest`/`PermitGrant`.** "Admission" read as more institutional and less clearly conditional than "Permit." "Permit" also matches the vocabulary `review-results.md` already nudged limiter's own future coordinator toward (`PermitGrant`, `PermitDecisionSink`) — using it now means a real Phase 7 coordinator can slot in behind this same port later without a rename. "Resource" is kept as-is, deliberately the plan's own paired term against "Worker" in its "Two Different Limits" split (worker capacity vs. resource capacity) — the pairing is what disambiguates an otherwise generic word, not the word alone.
- **`WorkerLifecycleEventSink` confirmed fine, with one mechanical difference from this codebase's existing `EventSink` (`packages/ports/src/observability/observability-sink.port.ts`) worth keeping in mind during implementation.** The existing one is a generic bus-fed fanout target (`handle(event: AnyEvent)`, its own `start`/`stop`, attached via `ObservabilityTapPort`); Worker V2's is a direct-call outbound port for one component's own facts (`record(event: WorkerLifecycleEvent)`, no attach/detach, no bus involvement at all). Don't implement `WorkerLifecycleEventSink` as if it must satisfy the real `EventSink` interface — it can't and isn't meant to. Renaming the existing `EventSink` to `ObservabilityEventSink` for disambiguation is logged separately in `docs/todo.md`, not part of this Change.
- **No new artifact port invented — Worker V2 depends on the existing `ArtifactsPort` directly.** A narrow, write-only worker-scoped port was considered first, but checked against `worker.ts`'s actual current usage: `bindValueRefs` (`worker.ts:440`) genuinely reads via `getTextArtifact`/`getMarkdownArtifact`/`getJsonArtifact` for reference resolution, not just writing outputs/exports — so write-only was the wrong shape. `ArtifactsPort` already sits at the correct tier (interface only, zero I/O); its own bloat is real but separate, already-flagged future work (this initiative's own "Not yet scoped": `packages/artifacts`' infra-vs-application-component boundary) — its per-format methods (`putJson`/`getJson`/etc.) are expected to eventually collapse toward one generic, format-agnostic put/get. Inventing a new port shape now risks needing a redo once that happens; revisit then, not before.
- **`ProtocolExecutor`/`WorkerProtocolDeps` confirmed as-is.** Deliberately not reusing today's `ToolBinding`/`ToolInstancePort` vocabulary (`packages/ports/src/tools/tool-instance.port.ts`) — `ToolBinding` is registration/factory machinery being deleted outright (no registry in the target design), and `ToolInstancePort.invoke(event: unknown)` is event-coupled (takes/returns a `ToolEvent`), which `ProtocolExecutor` must explicitly not be. "Executor" continues the same thread as `JobExecutionPort`/`ExecuteJobCommand` rather than either old word, carrying none of the old registration/event-coupling baggage forward on purpose.

Naming is expected to get a further look once these types exist as real code — settled well enough to build against, not necessarily final once seen on the page.

**Scope checked against precedent, not resized**: matches the plan's own "First Useful Pull Request" sizing (types + inbound port + fake collaborators + focused tests, no runtime wiring, no changes to the current worker) and the same additive shape `events-refactor` Change C1 already used successfully.

Starting reference: [Worker V2 plan — Phase 1](../../../component-architecture/worker-v2/README.md#phase-1-core-contract-and-tests), whose own "First Useful Pull Request" section sketches this Change's scope closely.

### What actually landed

Built additively under `packages/components/worker/src/v2/` and `tests/v2/`, matching the plan closely — `job.contracts.ts` (`ExecuteJobCommand`/`JobResult`/`JobExecutionOptions`/`ArtifactRef`/`ProtocolRequest`), `worker-lifecycle.events.ts` (the `WorkerLifecycleEvent` union, keyed on `kind` not `type`, plus factory functions), the three ports (`job-execution.port.ts`, `resource-permit.port.ts`, `worker-event-sink.port.ts`), `protocol/protocol-executor.types.ts`, and `worker.ts`'s `WorkerV2`/`createWorkerV2`. One additive line in `src/index.ts` (`export * from "./v2/index.js";`), `worker.ts` and every existing `tests/*.test.ts` untouched.

`WorkerV2.execute()` reads as a flat sequence — validate → (pre-abort short-circuit) → record started → resolve refs (minimal, `artifacts.getJson` only, result intentionally unbound for Phase 1) → run the protocol → check its result → store outputs → check that result → record completed/failed → return — with `lifecycle.record()` calls kept exclusively in `execute()` itself, never inside a helper. The permit-acquire/protocol-invoke/permit-release sequence and its cancellation classification were factored out into `#runProtocol`/`#runProtocolWithPermit`: the inner method does acquire → invoke → release-in-`finally`, and the outer method classifies any resulting rejection by `signal?.aborted` (not error identity, since no adapter in this codebase shares a canonical `AbortError`) into a typed `ProtocolRunOutcome` (`{kind: "result"}` or `{kind: "cancelled"}`) that `execute()` pattern-matches on — collapsing what were originally two separate, near-identical `try/catch` blocks in `execute()` into one shared classification point. Output/export storage was similarly factored into `#storeExecutionOutputs`, returning a typed outcome rather than touching lifecycle itself. `failedResult`/`completedResult` join the existing `cancelledResult` as the three `JobResult`-construction sites.

`tests/v2/worker.test.ts` covers all 5 required scenarios plus two additional ones added during review — 10 tests total: success; expected (resolved, not thrown) protocol failure; two dedicated output-storage cases (`OUTPUT_STORE_FAILED`, and `EXPORT_VALIDATION_FAILED` while still retaining the already-stored primary output); thrown invariant failure; cancellation mid-permit-wait; and guaranteed-permit-release across four sub-cases (acquire itself failing, success, resolved protocol failure, and a thrown protocol error). All against hand-written fakes (`tests/v2/helpers/`) satisfying the real port interfaces with no `as unknown as X` casts, matching `packages/events/tests/helpers/mock-bus.ts`'s bar. `tests/v2/architecture.test.ts` mechanically enforces the exit condition (no `EventBusPort`/`QueuePort`/`EmitterFactoryPort`/`AnyEvent` import anywhere under `src/v2/`) rather than relying on discipline alone.

**Deltas from the plan, all concrete and worth remembering:**

- The architecture test's first pass checked _all_ source text for the four banned identifiers, not just imports — it produced a false positive on `worker-lifecycle.events.ts`'s own doc comment, which deliberately _names_ `AnyEvent` to explain why `WorkerLifecycleEvent` isn't compatible with it. Fixed by scanning only `import` lines, not full file text — a doc comment is allowed to mention a banned identifier while explaining a deliberate divergence from it; only a real import counts as a dependency.
- `tests/v2/helpers/fake-artifacts.ts`'s `ArtifactsPort.get()` (and the per-format `getJson`/`getText`/`getMarkdown`/`getBytes`/`getAuto` methods) needed several internal `as` casts to bridge a TS limitation: a stored entry's `format` and `value` genuinely correlate at runtime (written together as one `ArtifactPutInput` union member), but TS can't see that correlation once both are read back off a widened `Map` value. Same category of internal cast already accepted in `events-refactor`'s core (`emit.ts`'s correlated-generic-indexed-access casts) — correct by construction, confined to the fake's own read site, not load-bearing production logic.
- The original two-`try/catch` structure in `execute()` (one around permit acquisition, one around protocol invocation) was consolidated into one shared `try/catch` during review, once it was clear both blocks were classifying rejections identically — reduced duplicated cancellation-handling logic without changing behavior (re-verified against all test scenarios). Later factored further into `#runProtocol`/`#runProtocolWithPermit` as part of a broader pass moving orchestration detail out of `execute()` into named private methods, keeping only `lifecycle.record()` calls in `execute()` itself.

A naming question surfaced during review, resolved in favor of keeping `JobExecutionPort` as named rather than switching to something like `WorkerPort`: this codebase has two real, coexisting conventions for how an implementing class relates to its port's name — a dominant one where they share a root (`Worker`/`WorkerPort`, `Artifacts`/`ArtifactsPort`, `RunService`/`RunServicePort`, ~30 examples, always a single canonical implementer), and a second, equally real one for capability-shaped ports with swappable implementations, where they deliberately don't (`InMemoryQueue`/`QueuePort`, `FsArtifactStore`/`ArtifactStorePort`, `InMemoryEventBus`/`EventBusPort`). `JobExecutionPort` belongs to the second group by name (capability-first, not provider-first) even though Phase 1 only has one real implementer — the concrete, checked reason it can't simply be `WorkerPort` right now is that the name is already taken by old `worker.ts`'s own `WorkerPort` (`start`/`stop`/`stopAllJobWaiters`, the unrelated component-lifecycle shell), which stays alive and untouched through this Change. Once Phase 5 deletes the old worker and that name frees up, renaming `JobExecutionPort` to `WorkerPort` (keeping the port name stable, letting the implementer version — `WorkerV2`, eventually maybe just `Worker` again — vary) becomes a real, available option worth revisiting then, not a decision forced now.

Verified: `pnpm typecheck && pnpm vitest run` inside `packages/components/worker` (31/31 tests pass, including the 21 pre-existing old-worker tests, unchanged); `pnpm -w turbo run typecheck` (26/26 tasks pass) confirms the `index.ts` addition doesn't break any downstream consumer. `tests/` isn't covered by the package's own `pnpm typecheck` (the same pre-existing gap `docs/todo.md` already tracks, and this initiative's own "Not yet scoped" repo-hygiene item for this package) — verified separately, twice (after the initial build and again after the later refactor), with a temporary, uncommitted `tsconfig.typecheck.json`-style config to confirm the test files themselves are type-sound, then discarded rather than committed (that hygiene fix stays out of scope for this Change, per the initiative's own note).

## Change C3 - HTTP JSON vertical slice - merged (PR #352)

### Discussion

**Explicit departure from old code, stated up front**: nothing in `packages/tools/src/httpjson` or old `worker.ts`'s own binding/export helpers is being reused for style or structure — only the underlying _requirements_ were mined from them (and from `@lcase/json-ref-binder`, which genuinely is reused as-is, being already pure and unrelated to the worker). Where a fresh implementation happens to end up similar to the old one, that's fine; nothing old is being ported forward as a shortcut.

**Scope cut: `StepHttpJson` → `ExecuteJobCommand` translation is deferred to Phase 3.** This Change builds only the _internal_ portion — `ExecuteJobCommand.protocol` through reference materialization through `HttpJsonExecutor` — exercised in tests via a hand-built `ExecuteJobCommand`, not a real flow-step translation. The "Legacy Compatibility Adapter" (next Change) is where a real step definition becomes a command; Phase 2 doesn't need that to exist yet to prove the vertical slice.

**Reference binding — the substitution half is already a solved, reusable, pure function; only the value-fetching half is new.** `@lcase/json-ref-binder`'s `bindStepRefs<T extends StepDefinition>(refs, resolved, step): T` (and the `bindReference`/`resolveJsonPath` it's built on) already does ref substitution/interpolation generically, with zero I/O and zero worker dependency — it's not being rebuilt. What's genuinely new is `#resolveRefs` growing content-type-aware value fetching per `Ref` (params vs. steps scope, `text/plain`/`text/markdown`/JSON — the same real requirement old worker's `bindValueRefs` served, reimplemented fresh rather than copied) before handing the resolved map to `bindStepRefs`.

**Request/response contract — a template/resolved split, not `StepHttpJson` reused directly.** `StepHttpJson` itself is flow-authoring-shaped (carries `on`, `exports`, routing concerns) and must never reach `ProtocolExecutor` — the doc is explicit that a protocol executor must not decide engine progression. Real shapes, still to be named precisely when implemented:

- An unresolved, template-shaped `ProtocolRequest` for httpjson (ref placeholders still intact) — what `ExecuteJobCommand.protocol` actually carries.
- A resolved shape (post ref-binding, ready to send) that `HttpJsonExecutor.execute()` actually receives — narrower than `StepHttpJson`, just the wire-relevant fields (`url`/`method`/`headers`/`json`).

**Fetch semantics, several concrete corrections over old behavior, not just restyling — verified against the real old code, not assumed:**

- `parseInputBody`'s `if (!body) return;` is a real, confirmed bug (truthiness, not `!== undefined`) — a step sending `false`/`0`/`null` as a JSON body silently sends no body at all today. New code must check `!== undefined`.
- Old `getResponseBody` parses the response body _before_ checking `response.ok`, and a parse failure fully masks the real HTTP status (a 500 with a slightly malformed error body gets reported as "could not parse response," never as a 500). New code must not let body-parse failure hide status classification.
- `GET`/`HEAD` + a body is not just bad practice — `fetch` itself throws a `TypeError` for it. Must be validated and rejected as `invalid-request` before calling `fetch`, not left to surface as a raw platform exception.
- New, real hardening old code never had: validate the materialized URL via `new URL()`, restrict to `http:`/`https:` only. Default `Accept: application/json` and `Content-Type: application/json` (when a JSON body exists) unless already provided.
- Inject `fetch` itself as a plain function dependency on the executor, specifically so tests can be deterministic without real network calls.
- "Treat 2xx as success" is _not_ new behavior — `Response.ok` is already spec-defined as exactly that range; this is restating the existing check, not changing it.

**Response contract deliberately narrower than the old tool's, closing a rough edge this project already knew about.** `HttpJsonResponse = { status, body }` — no `ok`/`redirected`/`statusText`/final `url`/every header echoed back, unlike old `emitToolCompleted`'s full-`Response`-object dump. This is a direct fix for something already named as a known issue before this Change started (`CLAUDE.md`: "the full result payload currently riding inside the `job.<capability>.completed`/`failed` event... is one specific known rough edge"), not a new opinion introduced here. An empty 204/205 response produces `body: null`. On a _parseable_ non-2xx response, the response is still carried alongside the failure (`HttpJsonResult`'s `ok: false` branch can include `response`) so it can become the optional `output` on a failed `JobResult` — reusing the `output?: ArtifactRef` field Phase 1 already defined on the failed variant, not a new mechanism.

**Error taxonomy: two layers, and `JobExecutionError.code` tightens from Phase 1's plain `string` to a real closed union.** A protocol-specific `HttpJsonFailure` (`invalid-request` / `network` / `http-status` / `invalid-response`) gets mapped by `WorkerV2` into the portable `JobExecutionError`, whose `code` becomes a `JobExecutionErrorCode` literal union (`CANCELLED`, `TIMEOUT`, `INPUT_RESOLUTION_FAILED`, `HTTP_REQUEST_INVALID`, `HTTP_NETWORK_FAILED`, `HTTP_STATUS_FAILED`, `HTTP_RESPONSE_INVALID`, `OUTPUT_STORE_FAILED`, `EXPORT_RESOLUTION_FAILED`, `EXPORT_VALIDATION_FAILED`, `EXPORT_STORE_FAILED`, plus a code for resource-key resolution failure) — additive over Phase 1's existing codes, nothing breaks. Codes stay stable categories (never e.g. `HTTP_404`); raw exceptions, response excerpts, and URLs stay out of `JobExecutionError` entirely and belong to telemetry instead — `JobExecutionError` must stay safe to put into results and durable lifecycle facts. This is the same discipline `docs/todo.md`'s existing "real credentials aren't safe yet" item already demands elsewhere in the system, applied consistently here rather than reopened as a new question.

**`retryable` gets a narrow, explicit definition: "safe for the system to execute the entire job again automatically," not "this might be transient."** Conservative Phase 2 policy: cancellation, invalid input, invalid successful responses, and ordinary 4xx are never retryable; 408/429/5xx and network/timeout failures are retryable only for a read-only or explicitly-idempotent request (`GET`/`HEAD`/`OPTIONS` for now); output/export storage failures are never retryable (the external request already happened by that point). A timed-out `POST` is `retryable: false` — it may have already completed and had a real effect. **Phase 2 classifies but does not act on this** — no retry loop is built; matches the doc's own "Open Questions That Do Not Block Phase 1" already deferring when retry/backoff becomes real.

**Export declarations move onto `ExecuteJobCommand` properly — Phase 1's shape here was a genuine placeholder mistake, not a deliberate design.** `ExecuteJobCommand.exports?: Record<string, ArtifactRef>` is currently typed as already-resolved _hashes_, which makes no sense as an input to execution — a command needs export _declarations_ (path, format, optional schema) describing what to extract, not what was already extracted. This gets corrected in this Change, not carried forward.

**Resource-key derivation: neither purely command-supplied nor purely worker-hardcoded — a small injected policy function, worked out through real back-and-forth, not settled on the first pass.** Initial framing (command supplies a `resource.key` field outright) didn't survive the observation that the canonical key may only be knowable _after_ reference resolution (e.g. a templated URL). Final shape: `WorkerV2` owns _when_ to resolve the key (it's the only thing holding the materialized request at the right moment) but not the _policy_ for what counts as the same resource — that's a plain injected function, not a port (pure, no I/O):

```ts
type ResourceHint = { kind: "named"; name: string } | { kind: "derive" };
type ResourceKeyResolver = (
  request: ResolvedHttpJsonRequest,
  hint?: ResourceHint,
) => ResourceKeyResult;
```

A command may optionally carry a `ResourceHint` (an explicit named profile, e.g. for grouping multiple endpoints under one limit) with `{kind: "derive"}`/omitted falling back to a default origin-based policy (`http-origin:${new URL(url).origin}`). **Security rule, verified as a real instance of an already-known risk, not a hypothetical**: never derive a resource key from a resolved secret (an `Authorization` header value) — if account identity should affect limiting, the command carries a stable _credential profile name_ (e.g. `openai-primary`) as its hint, never the resolved secret itself. This is the same class of problem `docs/todo.md`'s "real credentials aren't safe yet" item already names for job payloads generally — one more concrete place it would bite if not handled deliberately here.

**Full execution sequence, reconciling everything above with what Phase 1 already built:** wait for worker capacity → record started → resolve artifact references → materialize the HTTP JSON request (bind refs into the template) → resolve the canonical resource key → acquire resource permit → start protocol timeout → execute request → release permit (unconditional `finally`, unchanged from Phase 1) → store output/exports → record terminal lifecycle fact → release worker capacity.

**Timeout and cancellation — two independently-sourced signals combined carefully, including a real race condition caught and fixed before it shipped.** The caller's `AbortSignal` (from `JobExecutionOptions`) threads through the worker-capacity wait, the resource-permit wait, and (combined with the worker's own timeout signal) the protocol call itself — timeout is scoped tightly, starting only immediately before the protocol invocation, not before. Since `AbortSignal.any()` can't report _which_ input signal actually fired, a small helper tracks the first cause explicitly (`"caller"` vs. `"timeout"`, recorded at the moment each source's own `abort` event fires, not reconstructed from final signal state afterward) — the naive "check both signals' current state, caller wins" approach was considered and rejected: a timeout that fires first, followed shortly by a caller abort before the rejection is even caught, would be misclassified as a cancellation under that approach. `CANCELLED` (`signal?.aborted`) and `TIMEOUT` (the worker's own deadline) are classified as distinct `JobExecutionErrorCode`s, never collapsed into one.

**Worker capacity and resource admission both get real local implementations in this Change, sharing one generic semaphore primitive internally, but kept as separate policies** (per the doc's own "Two Different Limits"). Worker capacity is exposed as `withWorkerCapacity(core: JobExecutionPort, config): JobExecutionPort` — a decorator, not internal `WorkerV2` state — applied automatically inside `createWorkerV2(deps, config)`. `WorkerV2`'s own class becomes module-private (only `createWorkerV2` exported) specifically so capacity enforcement can't be silently bypassed by constructing the raw class directly. `createWorkerV2`'s new `config: { maxConcurrentJobs: number; protocolTimeoutMs: number }` is **required, with no package-supplied defaults** — the runtime composition root must explicitly choose values (e.g. `1`/`60_000`). The worker-capacity wait is itself cancellable by the caller's signal, consistent with permit-wait cancellation: if aborted while still queued for capacity, resolves `CANCELLED` with zero lifecycle facts recorded (execution never reached `started`).

**Permit/capacity activity stays telemetry, not durable lifecycle facts — confirmed by direct precedent already in this codebase, not a new call.** The Event Migration Ledger already classifies today's `worker.job.dequeued` as Telemetry (owned by the queue consumer layer, not worker core); the doc separately states permit requests/grants "are not durable lifecycle facts under current requirements... they are debug telemetry." Worker-capacity wait/grant/release activity gets the same treatment, emitted by whichever piece does the actual waiting (the capacity wrapper, the permit adapter) — not routed through `WorkerLifecycleEventSink`. Also clarified in passing: the `supervisor` component sketched in Change C1's investigation is _not_ the mechanism for this — its primary shape is a sidecar to _external_ services the worker calls out to, not to the worker itself; it would only become relevant to worker's own telemetry in the separate, unscheduled scenario where worker itself becomes an out-of-process supervised component.

**Durability is explicitly out of scope here too, consistent with Phase 1's Reliability Boundary, not reopened.** `executionId` already exists as a forward-looking idempotency key; `WorkerLifecycleEventSink` is already a swappable port, so a durable implementation is a later adapter swap, not a rewrite. Recovering permit/semaphore state after a crash is real but explicitly Phase 7 territory.

Starting reference: [Worker V2 plan — Phase 2](../../../component-architecture/worker-v2/README.md#phase-2-http-json-vertical-slice).

### What actually landed

Built as designed, closely matching the discussion above — no significant deltas in shape, only two real bugs caught and fixed during implementation itself (beyond the two already-known old-code bugs the discussion set out to avoid repeating).

**New files** under `packages/components/worker/src/v2/`: `concurrency/semaphore.ts` (`createSemaphore`, the shared cancellable FIFO primitive), `worker-capacity.ts` (`withWorkerCapacity`), `job-result.factories.ts` (`cancelledResult`/`failedResult`/`completedResult`, extracted out of `worker.ts`), `execution-output-storage.ts` (`storeExecutionOutputs`/`tryStoreOutput`, extracted out of `worker.ts` in the later readability pass below), `resource-key-resolver.ts` (`defaultResourceKeyResolver`), `adapters/outbound/local-resource-permit.adapter.ts` (`createLocalResourcePermitPort` — moved here from `ports/outbound/` in the same pass, since it's a real implementation, not an interface, and didn't belong filed alongside the actual port definitions), `protocol/combine-for-protocol-run.ts`, `protocol/http-json/{http-json.types,materialize-http-json-request,http-json.executor}.ts`.

**Edited Phase 1 files** (real, necessary changes, not purely additive — as flagged going in): `job.contracts.ts` (`ProtocolRequest` is now the real httpjson template; `ExecuteJobCommand.exports` corrected to `Record<string, ExportRef>`; new `JobExecutionErrorCode` union; new `resourceHint?` field), `protocol/protocol-executor.types.ts` (`ProtocolResult`'s failure branch gained `payload?`; new `ResolvedProtocolRequest`; `ProtocolExecutor.execute()` now takes the resolved shape), `worker.ts` (`WorkerV2` un-exported/module-private, `execute()` rewritten to the full sequence, `#resolveRefs` grew real content-type-aware logic, output/export storage grew real logic and was later extracted to `execution-output-storage.ts`), `index.ts` (additive re-exports). `export-validation.ts` was reused verbatim, unedited, as planned.

**Two real bugs found and fixed during implementation, not anticipated in the discussion:**

- `HttpJsonExecutor`'s first draft caught _every_ `fetch` rejection — including one caused by the caller's or timeout's own abort — into a normal, resolved `{ok:false, error:{code:"HTTP_NETWORK_FAILED"}}` result. That would have silently defeated `WorkerV2`'s entire `combineForProtocolRun`-based `TIMEOUT`/`CANCELLED` classification for the real executor, since that classification only ever runs on a _rejected_ promise — an abort-caused failure needs to propagate, not resolve normally. Fixed by checking `signal?.aborted` in the catch and re-throwing when true. Caught while designing the executor's own test matrix, before it ever reached `WorkerV2`'s own tests — worth remembering as a real, non-obvious contract every future protocol executor must also honor.
- The hand-written `createFakeProtocolExecutor` test double didn't respect a passed `signal` at all — it just always ran `resultFn` to completion regardless of cancellation, which is not what any real `ProtocolExecutor` may do. This silently made the `TIMEOUT` test hang for the full 5-second Vitest default timeout the first time it ran. Fixed by making the fake genuinely race `resultFn`'s outcome against the signal firing, matching the real contract every executor must satisfy — a fake that ignores cancellation isn't a faithful stand-in for anything exercising cancellation behavior further up the stack.

**One planning gap closed during implementation**: the approved plan had no dedicated test file for `materializeHttpJsonRequest`'s own pure logic (method defaulting, header defaulting, GET+body rejection, URL validation, real `bindStepRefs` integration) — added `tests/v2/materialize-http-json-request.test.ts` to cover it directly rather than only indirectly through `worker.test.ts`'s end-to-end case.

**Readability pass after the first working version, once the whole slice was green.** `WorkerV2.execute()`'s original single-method shape (resolve refs → materialize → resolve key, each with its own inline `if (!ok) record+return failed`) was decomposed into `#prepareProtocolRun` (combining all three into one outcome, collapsing three near-identical failure branches into one) and `#finishFailedExecution`/`#finishCancelledExecution`/`#finishCompletedExecution` (each pairing "record the matching lifecycle fact" with "build the matching result," removing that repeated pair from every call site). The export/output-storage logic (previously one large `#storeExecutionOutputs` method) moved into `execution-output-storage.ts` as a set of small, focused, independently-testable functions (`storeDeclaredExports` → `storeDeclaredExport` → `storeJsonExport`/`storeTextExport`, a shared `storedArtifact`/`exportFailure` for the common result shapes). Verified behavior-preserving, not just by inspection — re-read in full against the original logic line by line, plus the entire repo's own verification suite (`pnpm format && pnpm build && pnpm -r test && pnpm typecheck && pnpm lint`) run clean afterward.

**Test suite**: 15 files, 82 tests total (up from Change C2's 8/31) — all passing, including the full original Phase 1 suite unchanged. New: `semaphore.test.ts`, `worker-capacity.test.ts`, `local-resource-permit.test.ts`, `combine-for-protocol-run.test.ts` (including the exact timeout-then-caller-abort race the discussion called out), `resource-key-resolver.test.ts`, `http-json-executor.test.ts`, `materialize-http-json-request.test.ts`. `worker.test.ts` grew from 10 to 18 tests — updated for the resolved-request assertion and real export storage, plus new coverage for `TIMEOUT` vs. `CANCELLED` distinctness, resource-key-failure short-circuiting, a parseable-failure-payload-as-output case, and one true end-to-end HTTP JSON job (fake `fetch`, real export) proving Phase 2's actual exit condition.

Verified: `pnpm typecheck && pnpm vitest run` inside `packages/components/worker`; `pnpm -w turbo run typecheck` (26/26 tasks); `tests/` typechecked separately via the same temporary, uncommitted sibling `tsconfig.json` approach as Change C2, then discarded.

## Change C4 - Legacy compatibility adapter - merged (PR #353)

### Discussion

Connects Worker V2 to the current engine unchanged: translate the current queued job event into `ExecuteJobCommand`, invoke Worker V2, translate `JobResult` back into the current completion/failure compatibility event. Starting reference: [Worker V2 plan — Phase 3](../../../component-architecture/worker-v2/README.md#phase-3-legacy-compatibility-adapter).

**Adapter placement: worker's own package, not `packages/runtime`, despite the plan doc's own illustrative shape pointing there.** The doc's "Illustrative File Shape" sketches `legacy-queued-job.adapter.ts` under `packages/runtime/src/worker-v2/`, labeled "Possible integration code," not a requirement. Checked `packages/runtime`'s actual current contents directly: it's entirely thin `create*`/wiring functions today (`create-services.ts`, `wire-functions/create-{artifacts,limiter}.ts`, `registries/*.ts`) — nothing adapter-shaped with real translation logic. That, plus the precedent Change C3 already set (`local-resource-permit.adapter.ts` living in `v2/adapters/outbound/`, not in `packages/runtime` or even `ports/`), settles this: the real implementation belongs in `packages/components/worker/src/v2/adapters/inbound/`, with `packages/runtime` doing only construction and start/stop.

**File shape** (verified against a second model's review, not taken as-is):

```text
packages/components/worker/src/v2/adapters/inbound/
  legacy-httpjson-queue-consumer.ts   # the stateful reserve-loop/lane runner
  legacy-httpjson-job.mapper.ts       # pure translation functions, no I/O

packages/runtime/src/worker-v2/
  create-worker-v2.ts                 # construct + wire + start/stop only
```

Splitting the pure mapping logic (queued-event → `ExecuteJobCommand`, `JobResult` → compat event data) out of the stateful consumer loop matches this codebase's existing preference for separating pure functions from the I/O shell around them (`materialize-http-json-request.ts` in Change C3 is the same pattern).

**Current machinery, verified by reading old `worker.ts` directly rather than assumed.** The real inbound path is not a bus subscription to `job.<capability>.queued` — it's `QueuePort.reserve(toolId, workerId)`, pulled in a per-tool loop (`startToolJobWaiters`), and every reserved job then goes through `packages/components/limiter`'s `slot.requested`/`slot.granted` dance before `handleNewJob` actually runs it. Since Worker V2 already owns its own local capacity (`withWorkerCapacity`) and resource permit mechanism built specifically to replace exactly this, the new inbound adapter bypasses the old limiter component entirely — reserve straight off the queue, hand straight to Worker V2, let its own gating do the work.

Also confirmed only one real queue lane exists to reserve from today: the engine's planner (`step-planned.planner.ts`) hardcodes `toolid: "httpjson"` unconditionally — the flow step's own optional `tool` field (`StepCapCommonFields.tool?`) isn't wired into routing at all currently. No dynamic tool/lane discovery is needed; the adapter reserves from the single fixed `"httpjson"` lane.

**Queue backpressure — a real gap surfaced via a second model's research, verified before accepting.** Confirmed directly against `InMemoryQueue`'s own source (`packages/adapters/src/queue/inmemory.queue.ts`): `reserve()` removes an event immediately (`shift()`), and both `ack()`/`nack()` literally `throw new Error("Method not implemented.")`. A naive "reserve in a loop, fire off `execute()` without awaiting, reserve again immediately" adapter would let Worker V2's own capacity semaphore become a second, uninspectable, non-durable queue — every job past `maxConcurrentJobs` would sit as a promise in the semaphore's in-memory FIFO waiter list instead of remaining safely in the queue. That distinction matters specifically because the queue is meant to be swappable later (a Redis Streams consumer group keeps claimed-but-unacked entries in a durable, reassignable Pending Entries List; an in-memory promise array has none of those properties) — an adapter that firehoses the queue today would need real rework to ever sit in front of a durable queue later, not just a swap.

Fix: bounded intake via `maxInFlightJobs` concurrent consumer lanes, each running `reserve → translate → await worker.execute() → await compat publish → reserve next`. `maxInFlightJobs` is the adapter's own required config number — deliberately not read off Worker V2's `maxConcurrentJobs` (same decoupling precedent as `ResourcePermitPort`'s adapter config being independent of `WorkerV2Config` in Change C3). For this Change's wiring, `packages/runtime`'s composition sets `maxInFlightJobs` equal to `maxConcurrentJobs`, but they stay two separate knobs mechanically.

Worth naming explicitly: this isn't new machinery, it's a faithful re-expression of what old worker's `startToolJobWaiters` already does today — reserving whenever `activeJobCount < maxConcurrency` and refilling as jobs complete is exactly an N-wide concurrent reservation window; N independent lanes achieve the same effect. Preserves existing intake behavior rather than inventing something new, consistent with this Change's "connects... unchanged" framing.

Worker V2's own capacity semaphore (`withWorkerCapacity`) stays in place alongside the lane bound, not made redundant by it: this compat adapter's lanes mean the semaphore is never actually contended on _this_ path (intake is already capped at `maxInFlightJobs`), but Phase 4/5's `WorkerDispatch` will call Worker V2 directly in-process with no lane-bounded adapter in front of it — the semaphore remains the real enforcement point there. Two guards, two different callers, not defense-in-depth for its own sake.

A defining test for this: preload more jobs than `maxInFlightJobs`, block execution, assert only `maxInFlightJobs` were actually reserved off the queue (the rest remain queued), and assert completing one job causes exactly one more reservation.

**Resource keys stay out of the queue/lane design entirely — reaffirming, not revising, Change C3's existing shape.** Resource keys are an admission dimension resolved inside Worker V2 after reference resolution, not a delivery-routing dimension the adapter should know about; a queue-per-resource-key was considered and rejected for exactly that reason. A real fairness caveat this bounded-lane design introduces: if every reserved job in a lane window happens to wait on the same constrained resource, jobs for other resources can sit stuck behind them. Matches the plan doc's own "Future Fanout Warning" already anticipating this — explicitly not solved in this Change; later options include a bounded scheduling window, separate pending/executing limits, or a shared admission coordinator (Phase 7 territory).

**`local-resource-permit.adapter.ts`'s two known long-term limits reaffirmed, one already known and one new.** Cross-worker coordination not existing yet is already-known Phase 7 territory. The per-key `Semaphore` map never evicting idle keys is a real, previously-unnoticed gap — logged to `docs/todo.md` rather than fixed here, since cardinality is low today (one local worker, a handful of origins).

**Remote-queue shape, named for later, not actionable now.** A future Redis Streams-backed queue adapter would need to: read only when it holds in-flight credit, acknowledge only after terminal result delivery succeeds, leave/requeue failed deliveries per an explicit retry policy, reclaim abandoned reservations, and expect duplicate execution/delivery (consumer-group semantics, not exactly-once). Likely its own package (e.g. `packages/adapters/worker-redis-streams`) so the worker package doesn't acquire a Redis dependency merely by existing — the host/runtime would still only wire it. Not designed, not started; named so it isn't rediscovered from scratch in Phase 6.

**Event taxonomy: the compat `job.<capability>.completed`/`.failed` event is a Result/Reply, not a Lifecycle event — resolved directly from the plan doc's own categories, not by convention alone.** The "Current Event Migration Ledger" classifies it as "Split result and lifecycle event": `JobResult` is the result that advances engine control flow, and Worker V2's own `WorkerLifecycleEventSink.record()` call (already built in Change C2) is the _separate_ durable lifecycle fact — both exist, they're just no longer the same event. The "Results And Replies" section names this adapter's exact role: _"a compatibility adapter may temporarily publish an old completion event"_ / _"engine control flow consumes the result contract, not worker lifecycle fanout."_ Since it's a Result, not a Lifecycle fact, it doesn't get a `WorkerLifecycleEventSink`-shaped port — no new outbound port for this Change. `legacy-httpjson-job.mapper.ts` produces the compat event's `data` payload as a pure function; `legacy-httpjson-queue-consumer.ts` performs the actual `emit()` call directly.

Broader point worth keeping for future ports/adapters work: the plan doc's four-category taxonomy (Commands / Results and Replies / Lifecycle Events / Telemetry) classifies interactions by semantic role, not by whether they're literally realized as a bus event. Commands and Results can be a plain in-process call or a real wire event depending on deployment — the doc's own example: `worker.slot.requested` is today a real bus event, but in the target design it's just a plain `acquire()` method call once local. Lifecycle Events and Telemetry are the categories meant to stay consistent regardless of mechanism. Same principle as CLAUDE.md's existing heuristic: _"adapter/mechanism choice must never change observability semantics."_

**`architecture.test.ts`'s import ban needs narrowing.** Change C2 banned `EventBusPort`/`QueuePort`/`EmitterFactoryPort`/`AnyEvent` imports anywhere under `src/v2/`. This adapter genuinely needs `QueuePort`, `EmitterFactoryPort`, and `AnyEvent` to do its job. Scope narrows to exclude `adapters/` — core (`worker.ts`, `ports/`, `protocol/`, `concurrency/`, `job-result.factories.ts`, `execution-output-storage.ts`, `resource-key-resolver.ts`) keeps the existing ban unchanged.

**Type mapping confirmed clean — no new types needed either side.** `job.contracts.ts` and old `worker.ts` both import `Ref`/`ExportRef` from the same `@lcase/types`. The real `job.httpjson.queued` event's data schema (`JobHttpJsonSubmittedDataSchema` — `{url, method?, headers?, body?, args?, refs: Ref[], exportRefs?: Record<string, ExportRef>}`) maps onto `ExecuteJobCommand.protocol` + `.refs` + `.exports` almost field-for-field (rename `exportRefs`→`exports`).

**Response event fidelity — also cleaner than expected, checked against the real schema rather than assumed.** `job.httpjson.completed`/`.failed`'s data schema (`JobCompletedDataSchema`/`JobFailedDataSchema`) is already narrow: `{status, output: string | null (a hash), exportHashes?: Record<string,string>, message?}` — not the "full raw payload" rough edge CLAUDE.md flags elsewhere (that must be a different code path; unresolved footnote, not blocking here). Mapping is direct: `output.hash`→`output`, each export's `.hash`→`exportHashes`, `error.message`→`message`. One real, accepted loss: the old schema has no field for `JobExecutionErrorCode`/`retryable` — both get dropped in this translation. Not a regression (old worker never had typed codes either), just a ceiling this specific compat event can't raise; not worth widening the old schema to fix now.

**`executionId` has no old-event equivalent — decided as a temporary mapping, not a permanent one.** Old queued events carry `jobid`/`runid`/`stepid`/`flowid`/`traceid`/`spanid`, nothing named `executionId`. Since this compat path has no retry loop (one queued job = one execution attempt), the mapper reuses `jobId` as `executionId`. This needs an explicit code comment at the mapping site stating it's a temporary choice, not a decision that `executionId` should permanently equal `jobId` long-term.

**MCP gap named and accepted, not solved.** Old `worker.ts` is expected to be fully retired at this Change's composition root (no runtime switch/feature flag — see below). Worker V2 doesn't support MCP until Phase 5. Between this Change and Phase 5, an `mcp` step would have nothing consuming its queue lane at all. Accepted as a known, deliberate gap: MCP is already treated as semi-dead/non-primary in this codebase, not worth keeping old worker alive in parallel just to cover it.

**No runtime switch between old worker and Worker V2 — a deliberate divergence from the plan doc's own Phase 3 scope line ("provide a runtime switch that selects old worker or Worker V2 for the proven path").** Old worker is being retired outright at this Change's composition root instead. Matches this project's own stated engineering principle (`CLAUDE.md`: "don't use feature flags or backwards-compatibility shims when you can just change the code") and the fact that old worker has no long-term future to preserve a toggle back to.

**Outbound event emission: the new `emit(bus, type, data, options)` helper (`packages/events/src/core/emit.ts`), not `EmitterFactoryPort.newJobEmitterFromEvent(...).emit(...)` — revised from the initial plan on the user's own steer, verified before adopting.** `EmitOptions`'s `fromEvent: AnyEvent` field (`packages/events/src/core/scope.ts`) derives trace/span correlation from an inbound event exactly the way `newJobEmitterFromEvent` did, but the dependency shrinks from the 12+-method `EmitterFactoryPort` to plain `EventBusPort`. Real, not just stylistic: this is the codebase's newer, actively-preferred event-emission mechanism (the old per-domain `EmitterFactory` pattern is `CLAUDE.md`'s own acknowledged rough edge), and it drops the need for a hand-written `fake-emitter-factory.ts` test double entirely — a small, genuinely-typed `EventBusPort` fake (modeled on `packages/events/tests/helpers/mock-bus.ts`) is enough.

## Change C5 - Engine migrates to `WorkerDispatch` - merged (PR #354)

### Discussion

Changes the local engine-to-worker interaction: engine gets an engine-owned outbound port, a local adapter calls Worker V2's inbound port directly, and the engine advances its own state from the returned result instead of waiting on a bus event. Starting reference: [Worker V2 plan — Phase 4](../../../component-architecture/worker-v2/README.md#phase-4-engine-workerdispatch).

**This is a shim for how the engine locally reaches the worker, not an engine redesign.** The engine itself hasn't been refactored to the port-driven "invoke directly locally, or emit as transport when remote" model — this Change bridges the engine into calling Worker V2 directly for the httpjson path, without changing how the engine's own reducer/planner/effect loop works internally. A full engine refactor (treating dispatch the way this initiative treats worker) is expected later, not now.

**No engine machinery needs inventing — this already has a precedent inside the engine itself.** Today, `stepPlannedPlanner` (`step-planned.planner.ts`) builds `EmitJobHttpJsonSubmittedFx`/`EmitJobMcpSubmittedFx` effects with everything a job needs (url/method/headers/body, refs, exportRefs, scope); the handler fires the event onto the bus and forgets, and a separate `engine.ts` subscription to `job.*.completed`/`.failed` re-enters the loop later via `JobFinishedMsg`. Calling the new port directly and enqueuing a result message when the promise settles is the exact shape already used by `GetFlowDefFx`/`FlowDefResultMsg` (`get-flow-def.effect.ts`): an async effect handler calls a port directly, builds a result message, `deps.enqueue(message); deps.processAll();`. Phase 4 is that pattern applied to job execution, not a new one.

**Events are not going away — checked before assuming otherwise.** Initially reasoned that since nothing besides the engine itself subscribes to `job.*.submitted`/`.completed`/`.failed` (grepped observability, replay, run-history projection — confirmed empty), the bus round-trip could just be dropped once the engine no longer needs it for control flow. That was too narrow: `ReplayEngine` (`packages/replay/src/replay.ts`) reads via `EventStorePort.iterateAllEvents(runId)`, backed by `JsonlEventLog` (`packages/adapters/src/event-store/jsonl.store.ts`) — a generic, type-agnostic store keyed only on runid. Anything published on the bus with a runid lands there and is what feeds the UI's event graph. What's legacy here is specifically the _mechanism_ — the engine learning a result by subscribing to a bus event, because it hasn't been refactored to call an outbound port directly. The event itself, as a durable observability fact, is not legacy and stays. Worker V2's `WorkerLifecycleEventSink` is still console-only (Change C4, explicit placeholder) — not wired into `EventStorePort` — so today the compat `job.httpjson.completed`/`.failed` bus event is what's actually carrying this fact into the durable log and the UI graph. Retiring that event outright would go dark on job-level history until something bridges the lifecycle sink to durable storage; not this Change's problem to solve, but the reason the event keeps publishing rather than getting cut.

**Double-processing hazard, resolved.** If `job.httpjson.completed`/`.failed` keep publishing on the bus _and_ the engine advances state directly from the new port's return value, `engine.ts`'s existing wildcard subscription (`job.*.completed`/`job.*.failed`) would still catch the httpjson compat event and enqueue a second `JobFinishedMsg` for the same job — double-emitting `step.completed`/`.failed`, which nothing downstream is built to absorb twice. Fix: narrow that subscription to `job.mcp.completed`/`job.mcp.failed` explicitly, since mcp still needs the old bus-mediated path (see below). httpjson's compat completion event keeps publishing for the event log/UI graph, but nothing subscribes to it for control flow once this lands.

**MCP stays on the old path — but that path is already broken, not merely untouched.** Confirmed by direct inspection: Change C4 deleted `createInProcessWorker(...)` (old `worker.ts`'s construction) from `packages/runtime/src/runtime.ts` entirely and replaced it with `createWorkerV2Compat`, which only wires the httpjson-specific legacy consumer. Nothing in current runtime wiring constructs a consumer for `job.mcp.queued` at all — mcp jobs have had no consumer since Change C4 merged, not "still functioning via the old path." Worker V2 has no MCP executor regardless (Phase 5), so there's nothing to route mcp jobs to even if a consumer were revived. Leaving this as-is for Change C5 is still the right call — reviving old-worker construction just to cover mcp would be real scope creep, and mcp is already treated as semi-dead/non-primary in this codebase — but logged to `docs/todo.md` as a found gap distinct from Change C5's own scope, rather than silently assumed to still work.

**A second model's research on this port and its adapter, verified claim by claim rather than adopted wholesale:**

- **Confirmed and load-bearing**: `createWorkerV2Compat()` (`packages/runtime/src/worker-v2/create-worker-v2.ts`) constructs the real Worker V2 instance and then hides it — only the wrapped `legacy-httpjson-queue-consumer` gets returned; nothing in `packages/runtime` currently holds a reference to the raw `execute()`/`JobExecution` port. This isn't a style critique — Phase 4 cannot call Worker V2 directly without restructuring this file to expose the callable core separately from the self-running legacy consumer. Real, necessary, in scope for this Change.
- **Naming — reasonable, left open.** The doc's own `WorkerDispatch` name arguably undersells that the method awaits a terminal result rather than firing-and-forgetting a submission. `JobExecutorPort`/`LocalWorkerJobExecutor` (or similar) was proposed as a replacement. Checked for a collision with existing "dispatch" usage in `ports`/`engine`/`worker` — none found. Not settled; naming decided at implementation time rather than here.
- **Adopted: a separate package for the local adapter, not `packages/adapters` and not inside either component's own package.** This adapter is different in kind from Change C4's: Change C4's compat adapter lived inside `packages/components/worker`'s own `v2/adapters/` because it only had to know about worker plus generic bus/queue infrastructure — not about a second component's core. This adapter has to import both the engine's port language and worker's `JobExecution` port directly. Housing it inside either component's own package (even in an adapters/ subfolder mirroring Change C4's pattern) would give that package a real dependency on the other component's package — undercutting Phase 4's own exit condition ("engine and worker cores do not import each other") at the package level, not just the folder level, and working against ever running them as separate processes later. `packages/adapters` was considered and rejected too — that tier is understood as infrastructure-backed port implementations (Prisma repositories, `FsArtifactStore`, `InMemoryQueue`), not a home for adapters that bridge two components' cores directly; folding this in would blur what that tier means. A third, small package depending on both, while `packages/components/engine` and `packages/components/worker` depend on neither each other, is the shape being adopted — tentatively under something like `packages/integrations/engine-worker`, explicitly **not** a commitment to a broader "integrations" package tier. This is the first time two components have been joined directly (that boundary has held for a long time); the taxonomy question this raises is real but deliberately left open until more cases like it exist, per existing ADR practice (decide once proven, not before).
- **Declined: the modules/hosts runtime restructuring.** The research also sketched splitting `packages/runtime` into `modules/`+`hosts/` with discriminated host configs (monolith/engine-only/worker-only), for long-term deployment flexibility. Phase 4's actual exit conditions don't require any of that — it's a separate, larger lift from wiring one new port, and matches `CLAUDE.md`'s own guidance to keep engine changes incremental unless a larger rewrite is explicitly intended. Consistent with the already-logged long-term direction (runtime/component decomposition into standalone deployable pieces), but not this Change's work; the research's own scoping note agreed ("For Phase 4, only implement the monolith composition").

**`JobFinishedMsg`'s shape stays as-is — minimal engine change is the deliberate goal for this Change.** It still carries a full `AnyEvent` (`JobCompletedEvent | JobFailedEvent`), and the reducer/planner (`job-finished.reducer.ts`/`job-finished.planner.ts`) only ever read `.event.runid`/`.stepid`/`.data.{status,output,exportHashes}` — `jobId` itself is read nowhere in either. The new port's result gets adapted into that same existing message shape rather than introducing a cleaner plain-fields message and updating the reducer/planner to match; that cleanup is expected as part of a future, fuller engine refactor (this initiative gave the worker that treatment; the engine is expected to get an equivalent pass later, not folded into this Change).

**`EmitJobHttpJsonSubmitted`'s effect handler is untouched.** Still fires `job.httpjson.submitted` onto the bus unchanged — kept for the same observability reason as the completion event, and left for the same future engine refactor to reconsider, not touched opportunistically here.

### What actually landed

Built largely as planned, with several real refinements and one important correction found only once implementation started.

**Package placement revised again, mid-plan-review, before any code was written.** The plan's first draft proposed a per-pair `packages/integrations/engine-worker` package (its own `package.json`, needing a new `pnpm-workspace.yaml` glob entry). The user's own steer during plan review — "these things are small, maybe they don't deserve their own package yet" — led to a flatter shape: one `packages/integrations` package (`@lcase/integrations`), structured exactly like `packages/adapters` already is (per-concern subdirectories under `src/`, each with its own `package.json` `exports` subpath, e.g. `./engine-worker`). Sits directly under the existing `packages/*` workspace glob — no new glob entry needed at all. A future second joiner becomes a sibling subdirectory/subpath here, not a new package, until there's a real reason to split further.

**A cleaner split than planned: `LocalWorkerJobExecutor` ended up with zero side effects, not two responsibilities.** The plan's first draft had the adapter both translate _and_ publish the compat `job.httpjson.completed`/`.failed` event, requiring it to also carry `EventBusPort` and full `JobScope` fields it otherwise has no use for. Realized while wiring it up: `packages/events/src/core/emit.ts`'s `buildEvent()`/`publishEvent()` split (build-and-validate, then separately publish) means the _same_ `AnyEvent` object the new engine effect already has to build (to satisfy `JobFinishedMsg`'s unchanged shape) can just also be published — one object, two uses, right there in the effect handler, which already has `bus` in `EffectHandlerDeps`. `LocalWorkerJobExecutor` (`packages/integrations/src/engine-worker/`) ended up a pure translator: `JobExecutionRequest → ExecuteJobCommand`, call `worker.execute()`, `JobResult → JobExecutionOutcome`, nothing else. No bus dependency, no compat-event knowledge at all. The "two jobs bolted onto one adapter" seam the discussion above anticipated didn't end up needing to exist.

**A real double-execution hazard, found and fixed before it could ship, not after.** Since `job.httpjson.submitted` keeps publishing (kept for observability) and the router was never taught otherwise, it would have kept turning that into `job.httpjson.queued` — and if Change C4's legacy consumer kept running too, the same job would execute twice. Fixed both ways, per explicit instruction: `create-worker-v2.ts` no longer constructs or starts the legacy consumer for the monolith path at all (`createWorkerV2Core` exposes the raw `JobExecutionPort` directly instead), and `NodeRouter.route()` gets a small, commented, temporary guard skipping `capid === "httpjson"` before it ever reaches `queueJob()`. **Correction from the plan's own wording**: the plan assumed `job.httpjson.queued` messages would "accumulate, unconsumed" as a small accepted leak. Actually cleaner than that — since the router's guard returns _before_ calling `queueJob()`, httpjson jobs are never enqueued at all. No leak, not even a small one.

**`RuntimeContext.worker`/`SystemServiceDeps.worker` needed a genuine no-op, and it turned out to need touching only one function, not three.** `createWorkerV2Core`/`createNoopLegacyWorker` (`packages/runtime/src/worker-v2/create-worker-v2.ts`) replace Change C4's `createWorkerV2Compat`. The plan expected `apps/http-server`'s and `apps/cli`'s own service-construction code would need the same swap — turned out both `createServices()` and `createRuntime()` (`packages/runtime/src/{create-services,runtime}.ts`) already delegate to the same `makeRuntimeContext()`, so fixing that one function covers every app automatically. Less diff than planned, found by reading the actual call chain rather than assumed.

**One accepted, documented divergence: `job.httpjson.submitted`'s `jobid` and the real dispatch's `jobid` no longer match.** `EmitJobHttpJsonSubmittedFx`'s handler generates its own `"job-" + randomUUID()` internally (unchanged, per the "don't touch it" decision); `ExecuteHttpJsonJobFx` needs its own `jobId` to build both the `ExecuteJobCommand` and the `JobScope` its compat event uses, generated independently in `step-planned.planner.ts`. Previously these were the same value (one event, one `jobid`, reused end to end). Now they're two independent ids for the same logical job — a small, real correlation regression in the event log, accepted as the direct, unavoidable cost of keeping `EmitJobHttpJsonSubmittedFx` untouched while adding a fully separate dispatch path alongside it.

**Verified with a real, live end-to-end run through the actual engine, not just fakes.** Beyond the new unit/integration tests (below), a temporary scratch test called `makeRuntimeContext()` directly with real Prisma-backed artifacts, a real in-memory bus/queue, and no fakes anywhere — then published a real `run.requested` event (bypassing `RunService`/Prisma's run repository, which the engine's own state machine doesn't need) for a one-step httpjson flow hitting `https://swapi.tech/api/people/1`. Confirmed via the full event trace: `job.httpjson.submitted` publishes (kept), the run advances entirely through the new `ExecuteHttpJsonJobFx` → `LocalWorkerJobExecutor` → Worker V2 path with zero queue involvement, Worker V2's own `job-execution-started`/`-completed` lifecycle facts fire through the console placeholder sink, `job.httpjson.completed` publishes exactly once (observability preserved, no double-processing), `job.httpjson.queued` never fires at all (confirming the router guard), and the run reaches `step.completed`/`run.completed`/`flow.completed` for real. Test file, its temp artifacts directory, and the ad hoc `lcase-db/replay` directory it needed were all discarded after — matching the "temporary, uncommitted, then deleted" precedent already used in Change C2/3/4.

## Change C6 - Repo-hygiene + dead-code removal - merged (PR #355)

### Discussion

Phase 5 as originally written ([Worker V2 plan — Phase 5](../../../component-architecture/worker-v2/README.md#phase-5-complete-the-worker-surface)) bundled four differently-sized things into one Change: removing the old worker/tool-registry, adding MCP through the V2 protocol-executor shape, settling generic binary/response capture, and migrating remaining job event families. Discussing it surfaced that this bundling doesn't hold up, and the initiative's Change index/roadmap (`INITIATIVE.md`) was revised accordingly — this Change is now scoped to only the part that's genuinely ready.

**The old worker is already fully dead, verified by grep, not assumed.** `new Worker(` and imports of the old (non-`v2`) `@lcase/worker` export only appear in `packages/components/worker`'s own test suite (`worker.test.ts`, `registration.test.ts`, `exports.test.ts`, `export-refs.test.ts`, `params.test.ts`) — nothing in `packages/runtime` constructs it. Change C5's `createNoopLegacyWorker()` swap already severed the last real wiring. Same for `ToolRegistry` (`packages/tools/src/tool.registry.ts`): its only consumers are the old `worker.ts` and that same test suite. `tool-registry.temp.ts` and `tool.factory.temp.ts` are already fully commented-out. So Phase 5's own exit condition ("remove the old worker when no runtime path uses it") is already true today — this is pure deletion, not gated on MCP or binary capture also being ready.

**MCP is dropped from this Change, not just deferred casually — it's a real rewrite, not a mechanical port.** `packages/tools/src/mcp/mcp.tool.ts` carries its own doc comment admitting it "needs to be rewritten," implements bidirectional producer/consumer streaming against `AnyEvent`/`ToolDeps`/emitter-factory shapes that don't exist in Worker V2's protocol-executor contract (plain protocol-in/protocol-out, no streaming), and has a live bug on its error path (`return {} as ToolEvent<"tool.failed">` — discards the real emitted failure event). Mapping this onto Worker V2 is its own design problem, not something that fits "add MCP through the same protocol-executor shape" as httpjson did. Zero users, zero real MCP flows run today, so there's no urgency forcing the question. MCP's near-term fate (postpone further work vs. land limited support) is deliberately punted to Change C10, alongside the broader multi-protocol HTTP expansion — **not a decision to remove MCP from the project.** The stated intent is to eventually support MCP and other protocols; this is purely a sequencing choice. Until then: `mcp` stays a valid step type in `packages/specs`/`packages/types`/the workbench UI (untouched — purging it would be a real cross-package change with no upside today), and the router still silently queues `job.mcp.*` with nothing consuming it, exactly as broken as it's been since Change C4 (already logged in `docs/todo.md`, not a regression this Change introduces or needs to fix).

**Binary/generic response capture is also dropped from this Change — it belongs to the artifacts refactor (Changes C7-C9), not here.** Today's httpjson executor only content-type-sniffs JSON vs. not; there's no real binary artifact storage path. Real binary support is now motivated by a concrete, named use case (an STT → LLM → TTS flow) and by the worker's own future need for a more flexible HTTP transport (Change C10) — no longer purely speculative — but it's an artifacts-API concern first, not something to bolt onto worker cleanup.

**What's actually in scope**: delete the old `worker.ts`, `ToolRegistry`/`tool.registry.ts`, `tool-registry.temp.ts`, `tool.factory.temp.ts`, and their now-orphaned test files, once confirmed nothing else references them. Combine with `packages/components/worker`'s repo-hygiene pass — the same treatment `events-refactor` Change C3 gave `packages/events`: a real `tsconfig.typecheck.json` so `tests/` actually gets type-checked, `clean-dist`/`clean-node-modules` scripts, a real ESLint config replacing the `echo lint` stub, then an actual clean/reinstall/rebuild/lint pass fixing whatever surfaces.

## Change C1 - Worker/tools investigation — history, current shape, refactor direction - merged (PR #350)

`packages/components/worker`'s `Worker` class (`worker.ts`, ~700 lines) has been a known refactor target for a while — grew organically to support advancement elsewhere rather than getting a deliberate design pass of its own, the same shape of problem `EmitterFactory` was before its own refactor. This Change is that pass: understand the actual history and current shape before planning any change.

### Discussion

**Rate limiting/concurrency history — why two mechanisms coexist in `worker.ts`.** Worker originally had its own local, per-tool concurrency limiter — the simplest thing that worked, before any global coordination existed. But concurrency/rate limits are really two problems at once: a worker's own local capacity, and a genuinely global resource limit (e.g. a rate-limited external API) that only makes sense coordinated _across_ workers, especially once workers can scale beyond one instance. Several attempts at the global half followed — an early "resource manager" concept, then `packages/scheduler` (abandoned; separate history, not re-litigated here) — before landing on `packages/limiter` as the real global mechanism, coordinating via the bus (`limiter.slot.granted` etc., per `CLAUDE.md`'s limiter description).

`packages/limiter` initially only implemented **concurrency**, not rate limiting. Real rate limiting was always meant as a following, event-driven addition to it — mirroring the concurrency slot-grant flow — but that follow-up was never built. That gap is exactly what the still-scaffolded `rate-limiting` initiative is for.

That leaves `worker.ts`'s local `handleRateLimit` — old code, predates `packages/limiter` itself — as the _only_ rate-limiting protection actually in place today (concurrency is superseded by `packages/limiter`'s global coordination, but rate limiting isn't yet). It exists specifically because the worker calls out to arbitrary external endpoints (websites/APIs) and needs some protection against hammering them, even a crude one. **Not yet resolved: whether this Change should touch `handleRateLimit` at all**, given removing it would remove the system's only real rate-limiting protection until `rate-limiting` (a separate, not-yet-picked-up initiative) actually builds the real thing inside `packages/limiter`.

**Confirmed**: the dead/commented-out direct call to `handleNewJob` in `startToolJobWaiters` is exactly that leftover — worker used to run jobs on its own directly; once concurrency coordination moved to `packages/limiter`, the call site switched to the bus round-trip (`requestSlot` → `limiter.slot.granted` → `handleGranted` → `startWaitingJob` → `handleNewJob`) and the old direct call was left commented out as reference rather than deleted.

**`WorkerContext`/`ToolWaitersCtx` (the whole `startToolJobWaiters` machinery) is a real, deliberate redo candidate, not just incidental mess.** It was built carefully — deferred promises (`Deferred<void>`/`capacityRelease`) so waiting for capacity doesn't require polling the queue, active-job-count tracking per tool, per-tool concurrency (`maxConcurrency`, still read from each tool binding's own declared `spec.maxConcurrency` in `#buildToolCtx`) — but the design is considered unfinished/not fully correct despite that effort, and is now overloaded: one context object tracking tool registration state, per-tool active/waiting job counts, concurrency limits, and the worker-local rate-limit state (`rateLimitPolicy`/`rateLimitTs`) all at once. Broader pattern named, not specific to this one piece: a number of methods on `Worker` were added over time simply because some other part of the system came to depend on them existing, not from a deliberate design pass — consistent with the initiative's own framing of `worker.ts` as something that grew to support advancement elsewhere.

**`tool-registry.temp.ts`/`tool.factory.temp.ts` are a kept-as-reference v1, superseded by the real `tool.registry.ts`'s v2.** V1 had no concept of a "binding"; v2 introduced bindings and the rules around how tools are registered/tracked and invoked (new instance vs. reused singleton, etc.) — real, deliberate design work across several iterations, not settled even by v2. Whether the `.temp.ts` files still accurately reflect how invocation used to work, or have drifted since, is unconfirmed.

**Export storage hardcoded to `httpjson` only is neglect, not a deliberate exclusion.** Best understanding: the `mcp` step type has just never been revisited since it was first built, and it's unclear whether it even supports `exports` the way `httpjson` does (uncertain if MCP's response shape is JSON-compatible the way exports expects). Consistent with `mcp` being treated elsewhere as the non-primary, less-trusted step type.

**The double `enableSideEffects` check in `emitJobStarted` is believed to just be a mistake, not intentional** — not worth further investigation on its own.

**The binary/response-capture gap traces to `httpjson` specifically, not a generic-artifacts limitation.** `packages/artifacts` was always meant to be generic (the `bytes` format exists from early on), but the `httpjson` step type was built JSON-only to get the simplest path working first, and was never extended past that. The worker's own `storeJsonArtifact`/`storeTextArtifact`/`storeMarkdownArtifact` convenience methods, built early alongside that same simplest-path effort, ended up as the _only_ way the worker ever interacts with artifact storage — never revisited or extended (e.g. no `storeBytesArtifact`) even as the artifacts layer underneath grew more generic.

**A real fork in direction, raised mid-walkthrough: possibly sidestep `worker.ts` entirely rather than refactor it in place** — the same shape of move as `events-refactor` (new `emit()` core built additively, proven in one domain, old `EmitterFactory` never touched). Instinct, not yet a decision: draft what a worker should be from first principles, then figure out how to build toward it, rather than trying to incrementally fix the existing ~700-line file. Not yet confirmed as the actual plan — see note in Change framing above.

**Confirmed, not just a hunch: `worker.ts` should be rebuilt from scratch, not incrementally patched** — same shape of move as `events-refactor` (new core built additively, old file untouched, proven out in one real path before migrating). Every finding above (dead code, dual rate limiters, tool-queue keying inconsistent with its own stated intent, `WorkerContext`/`ToolWaitersCtx` overload) confirmed as real, longstanding, and known — not new information, just now written down and traced precisely instead of felt.

**A settled reframe on scope, resolving an earlier "is event-driven architecture even worth it here" tangent**: this project deliberately pursues event-driven design, deterministic replay, and swappable infrastructure as goals in their own right (see `INITIATIVE.md`'s new Design principles section) — that isn't in question. What's actually in scope to fix is accreted implementation mess (duplicate/dead mechanisms, request/response interactions forced through pub/sub where a direct port call would do) that exists independent of that philosophy, not the philosophy itself.

**New component idea: a reusable control-plane/sidecar piece, separate from both the worker and the tool/protocol layer.** Keeps the worker thin and transport-only (no lifecycle or health awareness, consistent with the earlier sidecar/TTS conclusion — the worker still just dispatches to a reachable endpoint). This new piece instead owns: starting/stopping a colocated process, heartbeat/health reporting (feeding a future system dashboard), for the user's own hand-built services (e.g. a local LLM). Resurrects the earlier-deferred "worker-level liveness"/tool-author-SDK threads from the `architecture-boundaries` worker-tool-extensibility research, but correctly relocated to its own dedicated component instead of folded into the worker or a tool binding.

**Dual-use motivation, not scope creep**: the same start/stop/heartbeat mechanism built for a user-authored service sidecar (LLM/TTS/STT) is plausibly the same control-plane shape needed later if `engine`/`worker`/`limiter` themselves ever get split out of process — building it now for a real, concrete case (the STT/LLM/TTS pipeline this project originated from) is practice for that exact swappable-infra mechanism, not a detour from it. Not yet scoped as a Change; a real idea to carry forward.

**Working name: `supervisor`.** Rough responsibility sketch (not designed in detail, deliberately deferred — this belongs to its own future component/initiative, not this Change): health/readiness, capacity/concurrency _announcement_ rather than enforcement (limiter still owns actual enforcement — this resurrects the old worker-adjacent "managed tools" idea but in a different flavor, decoupled from the worker), start/stop/observe of the colocated process, identity, status, optional metrics later, lifecycle control. Some responsibilities may be optional or shaped differently for internal system components (engine/worker/limiter, if ever split out) vs. external user-authored services. Prior real-world precedent: an earlier LAN setup used Redis Streams with some kind of heartbeat reporting, imperfectly understood/executed at the time. Current instinct: report over the bus (events), not a persisted HTTP connection — consistent with everything already read via SSE in the workbench today, so status/control could surface there (or anywhere else that reads the same event stream) for free. Concrete motivating case: monitoring/controlling processes across multiple machines on the user's own LAN, not a hypothetical.

**Pushback on the "direct port call, not a bus round-trip" framing above — correction, not a compromise.** The bus-mediated worker↔limiter slot handshake was a deliberate, deliberately-hard-won boundary decision (one of the few places this project stuck strictly to bus-only communication, specifically so the component could move out of process without a rewrite) — consistent with this initiative's own Design principles, not something to collapse for simplicity. **Resolution: make the coordination _mechanism_ swappable via a port, not fixed to either direct calls or the bus.** A new port (not yet named precisely — something like `SlotRequesterPort`, `requestSlot(resource): Promise<Grant>`) that `Worker` depends on, with (at least) two adapters: a bus-mediated one (today's request/wait-for-`limiter.slot.granted` dance — correct if limiter is ever genuinely out of process) and a direct in-process one (today's actual deployment reality). This is the same ports/adapters pattern already used everywhere else in this codebase (`ArtifactStorePort`/`FsArtifactStore`, `QueuePort`/`InMemoryQueue`), just applied to this one interaction, which never got it. Checked precisely: no requester-side port exists today — `LimiterPort` ([limiter.port.ts](../../../../packages/ports/src/limiter/limiter.port.ts)) is limiter's own self-driven-component shell (`handleSlotRequested`/`handleSlotFinished`/`emitResponse`/`start`/`stop`), not something a caller invokes.

**Refinement: adapter choice must never change observability semantics.** The two adapters may only vary the coordination mechanism (how the request reaches the decision, how the answer comes back) — never whether an event gets recorded. Limiter's _core_ (decision + emission) always runs and always emits the grant event regardless of which adapter triggered it; the direct adapter gets its answer via a resolved return value (decoupled from whether anything is listening to the emitted event), the bus adapter gets its answer by subscribing to that same event. Existing code already leans this way and doesn't need restructuring to support it: `ConcurrencyLimiterPort.slotRequestDecisions()` is already pure decision logic, separate from `LimiterPort.emitResponse()` as its own distinct emission step — the core just needs to be reachable from something other than "received `worker.slot.requested` over the bus."

**Flagged as a real, generalizable principle beyond limiter specifically** — likely applies to any component that later gets this same direct/bus adapter treatment (engine, worker itself). Real open question, not yet resolved: how this bears on the package dependency graph. One concrete wrinkle worth having in mind: a direct in-process adapter needs a live reference to the actual target component instance (e.g. `Limiter`) to call into — today's convention has `packages/adapters` implement ports without depending on `packages/components/*`; a direct adapter connecting two components is a new kind of edge, wired together at the composition root (`packages/runtime`), not something the bus adapter needs since components already share nothing more than a common bus reference. Not designed further here.

### What actually landed

The investigation surfaced findings genuinely bigger than `worker.ts` alone — a candidate port-driven component-interaction model that would eventually supersede parts of `ADR-0005` (components as necessarily self-driven bus subscribers) and `ADR-0006` (worker core owning bus/queue coupling). Rather than design that in place inside this arc, it was synthesized separately with outside help into a durable, top-level (not initiative-nested, since it's bigger than this one) reference: [`docs/component-architecture/`](../../../component-architecture/README.md) — a pattern/vocabulary draft, a limiter port/adapters sketch (`limiter.next.temp.ts`, intentionally gitignored), an independent review of both against the real current code, and a phased Worker V2 implementation guide. That guide's phases seed Changes C2–C6, continued in [`worker-v2-build.md`](./worker-v2-build.md).

Held off, deliberately, per existing project practice: a Proposed-status ADR for this direction — no second reader for it yet (solo project, one initiative at a time); write it the moment that stops being true. See `INITIATIVE.md`'s Not yet scoped for the concrete trigger.

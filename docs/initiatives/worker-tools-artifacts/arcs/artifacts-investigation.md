## Change C7 - Artifacts refactor investigation — API shape, `ArtifactIndex` retirement, infra-vs-component boundary - in progress

`packages/artifacts` has been an open boundary question since before this initiative started (`CLAUDE.md` already flagged infra-vs-application-component as unsettled). This Change is the investigation pass — understand the actual shape, blast radius, and real usage before committing to any redesign, same discipline as Change C1 did for the worker.

### Discussion

**Scope, broadened from the one-line sketch in `INITIATIVE.md`.** The original Change C7 note only said "simplify the store API." Discussion surfaced four separable goals: collapse the API toward one real put/get primitive, retire `ArtifactIndex` (a filesystem-era relic name), decide where the artifacts boundary actually belongs (restructure/reclassify), and accept keeping the current shape if the blast radius turns out too wide to justify a change. Explicitly agreed to tackle these one at a time, starting with a broad architecture review and real blast-radius data, not a redesign proposal.

**Blast-radius findings, verified by direct grep rather than assumed.** `Artifacts` (`packages/artifacts/src/artifacts.ts`) is one class implementing a 14-method `ArtifactsPort` — not zero-I/O, since it calls `ArtifactStorePort`/`ArtifactRepositoryPort` directly, just structured as a domain service over two ports. `ArtifactIndex` is a confirmed, already-documented fossil: `docs/todo.md` already has a naming-debt entry describing it as a pre-CAS/pre-SQL filesystem-index name, with a half-executed plan already on record (`ArtifactsPort.write()` was added specifically so it could eventually absorb the older `put()`/`putJson()`/etc. family — that migration never happened). `FsArtifactIndexStore` is fully dead — zero wiring, zero tests, not merely the "legacy/fallback path" `CLAUDE.md` currently calls it; that line is stale and worth correcting regardless of what else happens here. Real call-site survey across worker, engine (3 effects), 5 app-services, runtime, and `run-flow` found nobody calls the generic `put()`/`get()` overloads — every real caller uses format-specific methods — and only `ArtifactService` plus `PrismaRunQuery`'s UI-decoration path ever touch `ArtifactIndex`'s actual fields.

**A real, load-bearing read/write asymmetry, confirmed against actual code.** Every real write call site wants both the CAS write and the SQL metadata write together — nobody writes an untracked blob on purpose. Almost all real reads (worker resolving refs, all three engine effects) only need content by hash+format and never touch metadata; only `getAuto()` and `ArtifactService`'s metadata-facing endpoints need both ports. Confirmed this split reflects genuinely different real use cases — metadata-focused reads exist mainly for UI/listing, execution-path code just wants content — not an accident.

**A prior, more foundational question got raised before designing artifacts' own split.** The taxonomy rule that `app-services` and `components` communicate only through the bus is exactly why a fused CAS+SQL artifacts service can't live in `app-services`, even though components need it too — but is that rule itself still correct, or just historically true? Rather than design around it as given, decided to research the boundary question first, using an outside high-reasoning model pass — the same synthesis pattern that originally turned Change C1's investigation into `docs/component-architecture/`.

**Result: [`app-services-components-boundary.md`](../../../component-architecture/research/app-services-components-boundary.md).** Found the "bus-only" premise already stale — Worker V2's real `JobExecutionPort`/`JobExecutorPort`/`LocalWorkerJobExecutor` already prove a direct in-process call works with no bus involvement (confirmed: `worker.ts` has zero bus references) — and already incomplete even before that: `SystemService` already calls `EnginePort`/`RouterPort`/`LimiterPort`/`ObservabilityTapPort` directly (confirmed by reading `system.service.ts`). Recommended replacement rule: narrow port contracts, not literal bus-only; process placement (in-process vs. remote) doesn't by itself dictate command-vs-event shape. Surfaced real, related friction worth remembering later, not yet acted on: `run.requested` doing double duty as both command and lifecycle fact, `InMemoryEventBus.publish()`'s fire-and-forget semantics (`queueMicrotask`, async handler failures swallowed — confirmed by reading it directly), replay control being command-shaped, and `RunService`/`SqlRunProjectionSink` both writing the `Run` row with no single clear owner.

**Follow-up question: what governs a thing that fuses 2+ ports and needs to be usable by both app-services and components?** Result: [`capability-modules.md`](../../../component-architecture/research/capability-modules.md), naming the category **capability module** — defined by policy ownership (who decides ordering/success/partial-failure/idempotency across dependencies), not port count, and explicitly distinguished from the existing single-port `Operations` convention rather than treated as its generalization.

**Checked against two other real/hypothetical cases, not just artifacts, so the category wouldn't be overfit.** `startForkedSim()` (`packages/use-cases/run-flow`) was correctly rejected as _not_ a capability module — it's caller-specific orchestration, not a reusable capability. A hypothetical `RunSubmission` port (sketched in the boundary doc) was also correctly rejected — Engine already owns terminal command semantics; a neutral pass-through would just obscure that. `run-flow`'s own package boundary was deliberately treated as non-precedential going in, since it was already known to be unsettled and only ever derived from one example (`runFlow()` itself).

**For artifacts specifically**, the recommendation is to keep `packages/artifacts` as the physical home (no new subfolder/package tier needed) but split the one fused `ArtifactsPort` into a writer port (needs both `ArtifactStorePort` + `ArtifactRepositoryPort`, owns write-order/success/partial-failure policy) and a narrower content-reader port (needs only `ArtifactStorePort`) — matching the empirical read/write asymmetry found earlier almost exactly.

**Verified several of the doc's most load-bearing claims directly against `artifacts.ts`, all confirmed accurate.** The optional `repository` dependency really does make `write()`/`putIndex()` silently succeed with zero metadata written when no repository is supplied. `getAuto()` really does fall back to raw `"bytes"` format when no repository is present (`inferFormat(undefined, undefined)` → `"bytes"`) — a real bug, not yet hit in production since runtime always wires both. `write()`'s idempotency gap is real: it stamps a fresh `time` on every call, so a retry after a partial failure isn't actually idempotent at the metadata layer. `PrismaArtifactRepository` really does use `upsert()` with no transaction spanning the filesystem and SQL writes, so a SQL failure after a successful blob write leaves an orphaned-but-harmless blob with no compensation path today.

**User's reaction.** Agrees with the capability-module framing and the artifacts split; comfortable leaving `packages/artifacts` as the physical package, no dedicated subfolder needed. The repository-optional behavior and `getAuto()`'s bytes-fallback are both agreed relics, not intentional design, worth fixing as part of the new API rather than preserved. The idempotency/no-transaction gap is acknowledged as real but unsurprising — "this was never meant to be that robust," a deliberately low-quality first version, not a design regression. Leaning toward _not_ building a redundant metadata-recovery mechanism preemptively (e.g. a CAS-side sidecar record — which would effectively resurrect the now-dead `FsArtifactIndexStore`'s shape, just repurposed for reconciliation): `store.putBytes`'s content-addressing already makes a full `write()` retry safe after a SQL-only failure, so a typed incomplete-write outcome that preserves the hash is probably enough robustness for where this project actually is. A real reconciler is a legitimate future addition if orphaned metadata turns out to be a recurring problem in practice, not a hypothetical one.

**Explicitly deferred: drafting an ADR for any of this.** Wants to wait until there are actual findings in code to point to, not decide/distill prematurely from research alone — a draft, mutable ADR is possible later, likely broader than just the boundary question given how much else surfaced (`run.requested`'s dual role, `SystemService`'s possible misplacement), but not now.

**`docs/component-architecture/` reorganized** to host this ongoing research cleanly: `model.md` (the original draft interaction model, renamed from `README.md`), `research/` (`review-results.md`, `app-services-components-boundary.md`, `capability-modules.md`), `worker-v2/` (worker's own build plan) — with a new top-level `README.md` added as a plain "what's here" index, distinct from the model itself.

**A migration-plan prompt was drafted and sent to an outside high-reasoning model** (mirroring how the two research docs above were produced), asking for a phased build plan structured like `worker-v2/README.md` — new writer/reader ports built clean alongside the old `Artifacts`/`ArtifactsPort`, a real vertical-slice consumer proven first, old surface removed last. It hit a session usage-window limit before returning a result; the prompt itself is saved (a temp file under `docs/component-architecture/`) to resend once that window resets, not lost.

**Decided not to wait on that reset to keep moving.** The remaining work — concrete port/class shapes for artifacts — is judged to be mechanical application of decisions already made here, not the kind of fresh-perspective question the outside-model passes were reserved for (that reasoning was reserved for the app-services/components boundary and naming the capability-module category, both genuinely unsettled beforehand). Whatever comes back from the pending prompt later can still be checked against whatever gets built directly, the same way a second opinion would be.

**Decided against writing a grand plan up front.** Instead: do the repo-hygiene pass first (mechanical, no design decisions, same treatment already given to `packages/events`, `packages/integrations`, and `packages/components/worker`), then come back to sketch the rough shape of the writer/reader ports, classes, and adapters only once there's a clearer picture — not a full spec before any code exists.

**`v2/` folder, decided with an explicit caveat.** Will start with a `packages/artifacts/v2/` subfolder as the new work's home, same mechanical container Worker V2 used, even though the exact port/class shape isn't fully pictured yet — easier to start with a container and reshape or move things out later than to over-specify structure before writing anything. Explicitly decided _not_ to duplicate the small pure helpers currently in `artifacts.ts` (`hashBytes`, `sortJson`, format inference, `defaultContentType`) into `v2/` — new code gets written from first principles rather than copied from the old shape, and the existing `Artifacts` class is left completely untouched (no tinkering) until the final removal phase, same discipline Worker V2 used toward old `worker.ts`.

### What's landed so far

**Repo-hygiene pass on `packages/artifacts`.** `clean-dist` and `typecheck`/`tsconfig.typecheck.json` already existed from earlier work; only `eslint.config.js`, a real `lint` script, and `clean-node-modules` were actually missing. Added `eslint.config.js` copied from `packages/components/worker`'s (flat config, `@eslint/js` + `typescript-eslint`, `consistent-type-imports`, `no-unused-vars` with a `^_`-prefix ignore pattern — dropped worker's comment explaining that pattern, since there's no evidence yet that artifacts' own tests use it) and added `@eslint/js`/`eslint`/`typescript-eslint` devDependencies; changed `lint` from an `echo lint` stub to real `eslint .`; added `clean-node-modules`. First real lint run surfaced 4 pre-existing `import type` violations in test files (`get-json`, `hash-bytes`, `put-format-extension`, `put-json`) — auto-fixed via `eslint --fix`, no manual changes needed. Verified clean end to end: `clean-dist` + `clean-node-modules` + reinstall, then `build`/`typecheck`/`lint`/`test` (22 tests across 7 files) all pass, and `turbo run build --filter=@lcase/artifacts...` confirms dependents (`@lcase/ports`, `@lcase/types`) still build.

**Planned via a formal plan-mode pass, not sketched ad hoc.** A targeted Explore pass first corrected two assumptions before planning: `ArtifactRepositoryPort.writeArtifact()`'s `format` field is genuinely optional and unvalidated at both the port and the Prisma/DB layer, so the new writer could simply omit it rather than needing a contentType→format shim; and worker's real write call sites are narrower than the general port surface suggests — the primary output is always JSON (hardcoded), and the only real format decision (declared exports) already comes from a MIME-string `declaration.type`, mapping directly onto `save()`'s overloads with no new format-detection logic needed.

**Built**, matching the plan: `LegacyArtifactStorePort`/`LegacyFsArtifactStore` (today's extension-probing behavior, moved verbatim, unchanged) alongside a new `ArtifactStorePort`/`FsArtifactStore` (content-type carried as first-class data via a sidecar file, extensionless content files, no probing). `ArtifactWriterPort` (overloaded `save()` — `JsonValue`+`"application/json"`, `string`+`` `text/${string}` ``, `Uint8Array`+any `contentType` — and `SaveArtifactResult`'s `saved`/`content-only`/`failed` union) and `ArtifactWriter` in `packages/artifacts/src/v2/`, built fresh with no borrowing from `Artifacts`'s existing implementation. Worker's writes (`execution-output-storage.ts`, both call sites in `worker.ts`) migrated onto the new writer; reads deliberately untouched, staying on the legacy `ArtifactsPort` until the read-side Change. Runtime wiring constructs both the legacy `Artifacts` and the new `ArtifactWriter` side by side in `makeRuntimeContext`, reusing the same `PrismaArtifactRepository` instance.

**A real test-authoring question surfaced and was deliberately left open, not resolved.** Tried to carry worker's "genuine fake, no `as unknown as X` cast" convention into `packages/artifacts/tests/helpers/`, but overshot it — the resulting `ArtifactRepositoryPort` fake reimplemented real business logic (multi-field filtering, `ArtifactListItem` shaping, null-vs-undefined update semantics) for five of its seven methods that these tests never even call, and a real bug surfaced inside that unnecessary logic. The deeper question — whether a unit test's fake should be a second real adapter implementation at all, given that it and the real adapter now both need to stay behaviorally consistent for the tests to mean anything — is logged in `docs/todo.md` as genuinely undecided, not acted on further per explicit instruction.

**Fixed a copy-of-the-old-pattern error-handling smell**: `encodeContent`'s failures were originally wrapped in the same generic `UNKNOWN` code + buried-in-`cause` pattern the old `Artifacts` class used throughout. Since the thrown errors already carry precise, specific messages, fixed to surface them directly as `message` under a new, dedicated `ENCODING_FAILED` code — and removed `UNKNOWN` entirely from both `ArtifactContentError` and `ArtifactMetadataError`, since fixing this one spot left it fully dead in both types.

**A real production bug surfaced only by an actual live end-to-end run, not by any automated test.** With the new writer and legacy reader both wired to the same root directory, nothing written by the new writer (extensionless content + sidecar) was discoverable by the legacy reader's extension-probing — silently breaking ordinary multi-step flow chaining (a later step resolving an earlier step's `output`/export). `exports` misleadingly appeared to work at first, purely because a prior run's leftover legacy-format file happened to already exist on disk under that same content hash — not because anything was actually functioning. Fixed by widening `LegacyFsArtifactStore`'s probe to also check the new store's bare path as a fallback (one additional check, legacy's own extensioned files still take priority when both exist), verified by a dedicated regression test and a live re-run of the exact flow that surfaced it.

**A real design tension surfaced mid-implementation, deliberately left unresolved.** Revisited whether content-type belongs in the CAS store at all, versus git's actual model (type lives only on whatever references a blob, never the blob itself) — considered dropping it from `ArtifactStorePort` entirely. Decided against: a narrow reader should be able to _confirm_ a hash's actual content-type against what a caller expects, not just trust context, which a git-style anonymous blob store can't provide. Named directly, and worth remembering for future decisions in this initiative: repeatedly choosing the smallest correct scope for right now, individually reasonable each time, was still working against the stated goal of an actual longer-term redesign — the bigger SQL-schema/git-model question (not every artifact needing a row) remains genuinely deferred by this Change, not resolved or abandoned.

Full repo `build`/`typecheck`/`test`/`lint` green at every checkpoint throughout.

**Not yet done, next up:** the read side (`load()`), deferred to its own Change.

**Sketching `ArtifactWriterPort` surfaced a longer-term line of thinking, written up separately: [`research/artifact-versioning-and-gc.md`](../research/artifact-versioning-and-gc.md).** Settled on `save`/`load` over `put`/`get`/`write` for the new ports, since those words are already each claimed by one specific underlying adapter (`ArtifactStorePort.putBytes`, `ArtifactRepositoryPort.writeArtifact`) and a capability module shouldn't leak either one's vocabulary. `ArtifactContent` collapsed to bytes-only rather than a per-format union — format/content-type is descriptive metadata, not a shape the port branches on — which opened real questions about revision history, artifact grouping, and garbage collection explored in that doc (a git-inspired model: content-addressed blobs already exist; the missing pieces are a lightweight versioning concept for user-created and step-output artifacts, a "tree" concept for what a run/step produced, and reachability-based GC). Direct, load-bearing consequence for this Change: not every artifact needs a SQL `Artifact` row, which means most of the worker's writes during execution don't need `ArtifactWriterPort`'s CAS+SQL fusion at all — only individually-significant artifacts do. That research doc is exploratory and not committed to this initiative's scope, but it's shaping how `save()`'s signature and the writer/reader boundary get drawn so the design doesn't foreclose it later.

## Change C8 - Artifacts read side (`load()`) + legacy migration - merged

### Discussion

**Scope narrowed explicitly, twice.** This Change is the read side (`load()`) only — not a sweep of every remaining legacy consumer. And within the read side, only the worker gets migrated onto it; engine's effects, `ArtifactService`, and the HTTP routes all stay on `Artifacts`/`ArtifactsPort` for now. Full legacy migration is later work, not this Change's job.

**A new reader port, mirroring `ArtifactWriterPort`'s shape but narrower — only `ArtifactStorePort`, no repository dependency.** Confirmed against worker's actual read call sites (`#resolveOneRef`, `worker.ts:322-346`): it never touches metadata, only content — `text/plain`/`text/markdown` via `getText`/`getMarkdown`, everything else via `getJson` + a JSON-path resolve. Matches the capability-modules research's read/write asymmetry finding exactly.

**`load()` needs two calling modes, both real, not one replacing the other.** A caller that already knows the expected type (worker, always) wants confirmation — decode to the exact shape asked for, fail if the stored contentType doesn't actually match (the "confirmed" behavior named as a requirement back in Change C7). A caller that doesn't know the type up front (the real `getAuto()` successor — future workbench/`ArtifactService` consumers, not this Change) wants inference from whatever contentType is actually stored, handed back alongside the decoded value.

**A real naming collision surfaced designing the auto-mode return shape, caught before writing any code.** Forcing the auto case through the same generic `Result<T, E>` used by the confirming overloads means `T` becomes `{ contentType, value }` — nested one level inside `Result`'s own `value`, producing `result.value.value` to reach content and `result.value.contentType` beside it. `value` doesn't hold up as a name across both cases: it works when the content is the entire payload, breaks once the payload needs to travel with a sibling field. Fix: the auto-mode overload gets its own literal success shape (`{ ok: true; contentType: string; value: ... }`, siblings, no nesting) instead of routing through the shared `Result<T, E>` alias; the confirming overloads keep plain `Result<T, ArtifactLoadError>` as-is.

**Combined reader+writer dependency for the worker: nested, not flat.** `{ reader: ArtifactReaderPort; writer: ArtifactWriterPort }` — the two existing capability modules bundled as fields, no new delegating facade class to keep in sync. Chosen over a flat `{ save(), load() }` single interface specifically to keep the reader/writer distinction (different port dependencies, from the capability-modules research) visible rather than blurred behind one object. Combined port named `ArtifactAccessPort` — picked without strong conviction (no better name surfaced), open to revisiting once it's been lived with a while.

**A real compatibility gap surfaced while planning, before any code was written.** Run params and flow defs are still written exclusively through the legacy path (`ArtifactService.put`/`write`, `run-flow`'s `add-flow.ts`/`create-fork-spec.ts`'s `putJson` — confirmed by grep), i.e. `LegacyFsArtifactStore`'s extensioned files, not the new `FsArtifactStore`'s sidecar format. Moving the worker's reads fully onto the new reader as planned would have broken `ref.scope === "params"` resolution (`NOT_FOUND`), since nothing writes params into the new format yet. Resolved by widening `FsArtifactStore.getBytes()` with a legacy-format fallback probe — symmetric to Change C7's own reverse-direction fix on `LegacyFsArtifactStore`, deriving `contentType` from whichever legacy extension matched. Chosen over the alternative of splitting the worker's reads by ref scope (params staying on the legacy `ArtifactsPort`, only steps/exports moving to the new reader), which would have partly undone this Change's own goal of one combined dependency. Small, temporary, precedented duplication — removed once legacy writers eventually migrate onto `ArtifactWriterPort`.

**Where a `load()` failure surfaces, deliberately left as-is, not decided as "correct."** Checked what actually exists today rather than assumed: `packages/artifacts` has zero HTTP/Fastify references and zero bus/`EmitterFactory` references — translation to an HTTP status or an observable event is exclusively ever done by a consumer, never inside the domain package itself. But the existing consumer-side precedent is weaker than it looks — `apps/http-server` routes today pick a flat 400/500 by call site with no `error.code` switch, and some routes (`get-artifact.ts`, `get-run-detail.ts`) don't set a status at all on failure; this is the same general gap already logged in `docs/todo.md` from Change C7, not solved here. For worker specifically: an artifact-read failure already flows through an existing, working path — `#resolveRefs` wraps it into worker's own `INPUT_RESOLUTION_FAILED` code, which reaches `#finishFailedExecution` → `lifecycle.record(makeJobExecutionFailedEvent(...))`, an existing `WorkerLifecycleEvent`. This Change reuses that path unchanged for `load()`'s errors rather than inventing new plumbing. Explicitly not settled, and flagged as genuinely unknown rather than a deferred-but-obvious answer: whether a failed artifact load is actually well-described as a "lifecycle event" at all, versus some other category not yet named. Revisit later, once the broader error-handling/observability convention work happens.

### What actually landed

Built matching the plan closely. `ArtifactReaderPort` (`packages/ports/src/artifacts/artifact-reader.port.ts`) — the two-mode `load()` (auto-inferring vs. confirming, per the discussion above) plus `AutoLoadResult`/`ArtifactLoadError` (`NOT_FOUND`/`TYPE_MISMATCH`/`DECODING_FAILED`) — and `ArtifactAccessPort` (`{ reader, writer }`) as plain compositions. `ArtifactReader` (`packages/artifacts/src/v2/artifact-reader.ts`) built fresh, structurally symmetric to `ArtifactWriter`'s `encodeContent`/`decodeContent` split.

`FsArtifactStore.getBytes()` widened with the agreed legacy-format fallback probe (`getLegacyBytes`, a small local extension→contentType map, tried only after the sidecar-based lookup fails) — verified both directions with dedicated tests (`legacy-fallback-read.test.ts`) and confirmed live (below).

Worker migrated: `WorkerDeps.artifacts`/`writer` collapsed into one `artifacts: ArtifactAccessPort` field; the two output-storage call sites switch to `this.#deps.artifacts.writer`. `execution-output-storage.ts` itself needed no changes — it already took `writer: ArtifactWriterPort` directly. `create-worker.ts` and `runtime.ts` updated the same way, with `runtime.ts` now constructing one shared `FsArtifactStore` instance for both the reader and writer.

**`#resolveOneRef` simplified after the initial migration, not just ported mechanically.** The first pass mirrored the old code's shape verbatim — four near-identical branches (params/steps × text/plain/text/markdown) each calling `reader.load()` with a literal contentType, falling through to a fifth default JSON branch. Once `load()` actually existed, the real duplication became visible: the four branches differed only in _which field_ supplied the contentType (`ref.paramType` vs. `ref.exportType`), not in what they did with it. Collapsed to one contentType lookup (`(ref.scope === "params" ? ref.paramType : ref.exportType) ?? "application/json"`) followed by a single JSON/text split — JSON applies `resolveJsonPath`, text returns the decoded string directly, matching the old code's behavior exactly (verified by the existing suite plus the two new ref-resolution tests, unchanged). This is the simplification the combined port was meant to enable, made concrete rather than left as an aspiration.

**A real, pre-existing test-coverage gap got closed, not just carried forward.** Every existing `worker.test.ts` case used an empty `refs` array, so `#resolveOneRef`'s actual reader calls had never been exercised by any test — the same category of blind spot that let Change C7's real production bug through. Added two new tests (a `params`-scope `text/plain` ref and a `steps`-scope JSON ref, both resolved through a seeded fake reader into the materialized request) closing that gap for the new code, not just migrating the old fakes mechanically.

**Live end-to-end verification, deliberately repeating the same kind of check that caught Change C7's real bug.** Built a two-step httpjson flow against `httpbin.org` (`getUser` reads a `params`-scope ref, exports a value; `echoAgain` reads a `steps`-scope ref off that export) and ran it through a live `apps/http-server`. First attempt failed on an unrelated mistake (wrong export JSON path, not a code defect — httpbin's response shape has no `.body` wrapper). Second run completed successfully end to end: confirmed via the file layout on disk that the param was genuinely written through the legacy path (`.txt` extension) and reached the worker only via `FsArtifactStore`'s new legacy-fallback probe, while the export chained between steps through the ordinary new-writer/new-reader path unchanged from Change C7.

Full repo `build`/`typecheck`/`test`/`lint` green throughout (27/27 build, 26/26 typecheck, 26/26 test tasks, 26/26 lint).

**Explicitly not done, unchanged from the plan:** every other legacy consumer (engine effects, `ArtifactService`, HTTP routes) still uses `Artifacts`/`ArtifactsPort` — later work.

## Change C9 - Migrate remaining legacy consumers onto new artifact ports - merged

### Discussion

**Started as an explicit exploratory phase, not a plan.** Goal: map what it would actually take to move every remaining `Artifacts`/`ArtifactsPort` consumer onto the new ports, and how hard a full swap would be if backward compatibility isn't a constraint (no shim, no parallel-running old API).

**Port shape settled at three, replacing the nested `ArtifactAccessPort` from Change C8.** Discussed and decided in sequence:

- A combined port is wanted alongside the existing `ArtifactReaderPort`/`ArtifactWriterPort`, but deliberately capped at three total — no port-per-consumer sprawl.
- Shape: **flat**, not nested — `interface ArtifactReadWritePort extends ArtifactReaderPort, ArtifactWriterPort {}`, so callers write `artifacts.load(...)`/`artifacts.save(...)` directly rather than `artifacts.reader.load(...)`/`artifacts.writer.save(...)`. Named `ArtifactReadWritePort` (not `ArtifactPort`) for clarity.
- `ArtifactAccessPort` (Change C8's nested `{ reader, writer }`) gets retired, not kept alongside as a second combined shape — the worker migrates onto `ArtifactReadWritePort` too, so there's exactly one combined-port pattern in the codebase, not two.

**Real call-site mapping, not assumption, done before sizing the work.** The legacy `ArtifactsPort` declares 12 methods; only 6 are ever actually called anywhere in the repo (`getJson`, `getAuto`, `write`, `putJson`, `getText`, `getMarkdown`) — `putText`/`putMarkdown`/`putBytes`/`getBytes`/generic `get()` have zero external callers. That shrinks the real migration surface a lot. Full consumer map:

- **Mechanical, read-only, no repo dependency** (→ `ArtifactReaderPort`): engine's 3 effects (`get-flow-def`, `get-fork-spec`, `resolve-branch-value`), `RunService`, `EvalService`, the observability `EvalResultProjectionSink`.
- **Mechanical, read+write** (→ `ArtifactReadWritePort`): `FlowService`, `SimService`, the two `run-flow` use-case files (`add-flow.ts`, `create-fork-spec.ts`), and the worker (migrating off `ArtifactAccessPort`).
- **Zero direct changes**: HTTP routes never call `ArtifactsPort` at all — every artifact route goes through `ArtifactService`. They're only affected transitively if `ArtifactService`'s public return shapes change.
- **The hard one**: `ArtifactService` itself — see below.
- **Dead code found along the way, not migrated**: `ArtifactService.putArtifact()` (no caller anywhere) and `ForkSpecController` in `packages/archive/controller` (exported but never instantiated) — both flagged for deletion rather than porting.
- De-risking note carried over from Change C8: the legacy and new on-disk stores already have mutual fallback probes (`LegacyFsArtifactStore`'s bare-path lookup, `FsArtifactStore.getBytes`'s legacy-extension probe), so migrating readers over is safe mid-rollout regardless of what order consumers move in.

**`ArtifactService`'s real blocker: `ArtifactWriterPort.save()`'s metadata is too narrow for curated writes.** `createArtifact()`'s legacy `artifacts.write()` call carries full `ArtifactWriteMetadata` (`curated`, `paramCurations`, `flowId`, `flowVersionId`), but `ArtifactWriterPort.save()`'s `ArtifactMetadataInput` only ever accepts `{ label?, filename? }` and `ArtifactWriter.save()` hardcodes `{ curated: false, label }` when calling the repository — there was no way to write a curated artifact through the new port at all. Decided fix, extending the existing port rather than adding a new one:

- Widen `ArtifactMetadataInput` to a discriminated union mirroring `ArtifactWriteMetadata`: `{ curated?: false; label?; filename?; flowId?; flowVersionId? } | ({ curated: true; filename? } & ArtifactUpdateMetadata)`. `curated` optional-false in the first branch means every existing caller passing just `{ label }`/`{ filename }` keeps type-checking unchanged.
- `ArtifactWriter.save()` passes the resolved metadata through to `repository.writeArtifact()` instead of hardcoding `curated: false`.
- Also would let `ArtifactService.createArtifact()` return the full `ArtifactIndex` `repository.writeArtifact()` already hands back (currently discarded down to a bare hash by `SaveArtifactResult`) — **but this last piece is now on hold, see below.**

**A side discussion on retiring `ArtifactIndex` surfaced, researched, and deliberately scoped out of this Change.** Investigated whether `ArtifactIndex` is a safely-removable relic; it isn't — it's the literal wire contract for three HTTP endpoints (`PostArtifactRes`, `PatchArtifactRes`, `GetCuratedArtifactsRes`, all `Result<ArtifactIndex, string>`), consumed directly by workbench frontend code, and its `.format` field is tightly coupled to the Prisma `Artifact` model (`PrismaArtifactRepository`'s `toArtifactIndex()` mapping is generated in lockstep with the schema's columns, including a mirrored Prisma `ArtifactFormat` enum). Renaming the TS type alone wouldn't touch the DB; actually changing what's stored (e.g. dropping the `format` column) would be a real migration. One genuinely dead field found along the way: `ArtifactIndex.id?: string` has no DB column and is never read anywhere. Decision: full retirement is its own future discussion once schema/metadata needs are clearer, not folded into this Change — so `SaveArtifactResult`'s "saved" branch does **not** get an `index: ArtifactIndex` field added (would re-cement the exact type slated for retirement).

**One small, real, contained piece pulled out of that side discussion and kept in scope: simplify `isArtifactCompatible` to pure `contentType` equality, dropping its `.format` fallback.** Verified before deciding: the fallback isn't dead — `ArtifactService.createArtifact()`'s pre-persist compatibility check (`contentType` can be genuinely absent on the `ArtifactPutInput` before it's written) and the workbench's `CreateArtifactDialog.tsx` upload path (raw browser `File.type` is unreliable/empty for `.md`/`.txt`) both actually rely on the `format` branch today. Zero tests exist for this function anywhere, so nothing pins the fallback behavior down either way. Resolved shape: `isArtifactCompatible(contentType: string | undefined, type: FlowParamContentType): boolean` — takes a bare string, no `ArtifactIndex` at all. The two real fallback-dependent call sites get fixed at the source instead, by resolving a concrete `contentType` up front via a new small `defaultContentTypeForFormat(format): string` helper (mirrors legacy `Artifacts.defaultContentType()`, placed next to `isArtifactCompatible` in `packages/functional-core/flow-analysis`, already imported by the workbench) rather than leaning on the compat function's own fallback. Side effect: this also removes the four `{ format, contentType } as ArtifactIndex` casts that existed purely to satisfy the old signature (`artifact.service.ts`, `CreateArtifactDialog.tsx` ×2, `use-artifact-authoring-panel.ts`).

### What actually landed

Built matching the plan. `ArtifactReadWritePort` (`packages/ports/src/artifacts/artifact-read-write.port.ts`) — flat, `extends ArtifactReaderPort, ArtifactWriterPort` — and `ArtifactAccessPort` deleted outright rather than kept alongside it. `createArtifactReadWritePort(store, repository)` (`packages/artifacts/src/v2/artifact-read-write.ts`) composes `ArtifactReader`/`ArtifactWriter` internally and binds their methods onto a plain object — `ArtifactReader`/`ArtifactWriter` themselves untouched, still usable standalone.

`ArtifactMetadataInput` (`packages/ports/src/artifacts/artifact-writer.port.ts`) widened to the planned discriminated union; `ArtifactWriter.save()` now passes the resolved `ArtifactWriteMetadata` straight through to `repository.writeArtifact()` instead of hardcoding `curated: false`.

**One real regression caught by tests, fixed beyond the original plan.** Wiring `ArtifactService.createArtifact()` onto `save()` exposed that `ArtifactWriter.save()` never populated the legacy `format` column at all (confirmed: it silently regressed a real `POST /api/artifacts` integration test's response shape) — `ArtifactWriter` now infers `format` from `contentType` via a small local mapping (deliberately not imported from `@lcase/flow-analysis`'s `inferFormatFromContentType`, to avoid a new cross-package dependency for four lines) and writes it on every save, closing the "format quietly going stale" gap Change C8 had flagged as already-latent, not introducing a new one.

`isArtifactCompatible` (`packages/functional-core/flow-analysis/src/artifact-compat.ts`) simplified to plain `contentType` equality, per plan. New `artifact-format.ts` in the same package holds `defaultContentTypeForFormat`/`inferFormatFromContentType` (the second one, translating a resolved `contentType` back to the legacy `format` bucket, wasn't in the original plan text but was needed for `ArtifactService.getArtifact()`'s `AutoGetResult` translation below — same category of helper, same file). Every real call site updated: `RunService`, `ArtifactService` (both spots), and — bigger than scoped, since the signature change forced it — the workbench's `RunInputRow.tsx`, `CreateArtifactDialog.tsx` (both upload-path spots, now genuinely fixed rather than newly regressed), and `use-artifact-authoring-panel.ts`, all four `{format, contentType} as ArtifactIndex` casts gone.

**All planned consumers migrated.** Read-only → `ArtifactReaderPort`: engine's 3 effects (`resolve-branch-value.effect.ts` also picked up the same contentType-lookup-then-single-branch simplification already proven in the worker's `#resolveOneRef`, collapsing its old markdown/text special case), `RunService`, `EvalService`, `EvalResultProjectionSink`. Read+write → `ArtifactReadWritePort`: `FlowService`, `SimService`, `ArtifactService`, the worker (now flat — `#resolveOneRef` and the output-storage call sites dropped the `.reader`/`.writer` indirection from Change C8), and the two `run-flow` use-case helpers (`add-flow.ts`, `create-fork-spec.ts` — both narrowed to plain `ArtifactWriterPort`, since neither ever reads).

**`ArtifactService`, the one genuinely non-mechanical piece, done as designed.** `getArtifact()`: `load(hash)` then `inferFormatFromContentType()` to reconstruct the `AutoGetResult` shape `ArtifactServicePort` still contracts (deliberately unchanged this Change). `createArtifact()`: branches on `input.format` to call the right `save()` overload, then one `artifactRepository.getArtifact(hash)` round-trip on success to get the full `ArtifactIndex` back — no `SaveArtifactResult` widening, as decided. Dead `putArtifact()` deleted from both the class and `ArtifactServicePort` (confirmed zero real callers beyond a stale test comment). `AutoGetResult` relocated from the deleted `artifacts.port.ts` into `services.port.ts` itself, its error branch now `ArtifactLoadError` instead of the old bespoke `GetError` — flagged in `docs/todo.md` (amending the existing `ArtifactIndex` relic entry) as a small preview of the bigger `ArtifactIndex`/error-type rework, not resolved here.

**Legacy stack fully deleted**, confirmed safe via an exhaustive construction-site grep before touching anything: `Artifacts`, `ArtifactsPort`, `LegacyFsArtifactStore`, `LegacyArtifactStorePort` (plus their whole test suites, except `legacy-fallback-read.test.ts`'s fixture setup rewritten to write the fixture file directly rather than via the now-deleted class — the fallback behavior it tests is permanent), the `createArtifacts` wire-function, and the single-entry `artifactRegistry`. Also deleted: the already-orphaned `FsArtifactIndexStore`/`ArtifactIndexStorePort`, and — found only once the build actually broke on it — the dead `ForkSpecController` in `packages/archive/controller`, which the Change C9 discussion had already flagged as a deletion candidate. `ArtifactsConfig` simplified to `{ path: string }`; all 3 apps' `runtime.config.ts` updated to match; `RuntimeContext.artifacts` retyped from `ArtifactsPort` to `ArtifactReadWritePort` (same field name — every narrower consumer gets it via ordinary structural typing, no second `artifactReader` field needed).

**One incidental layering fix, found via the same full-repo build sweep**: `packages/functional-core/json-ref-binder` (a zero-ports package per its own tier) was importing `JsonValue` from `@lcase/ports` — only reachable because `artifacts.port.ts` re-exported it from `@lcase/types`. Fixed by importing directly from `@lcase/types`, incidentally correcting a real (if harmless) tier violation that predated this Change.

**Test-fixture gaps of exactly the kind flagged in the discussion above, caught by the full suite, not missed**: two `apps/http-server` integration tests inserted artifact rows with `format` but no `contentType` (fine under the old fallback, broken under the new contentType-only check) — fixed by adding real `contentType` values, the same fix the discussion already anticipated for production code, just also needed in test fixtures.

## Change C10 - Flatten `packages/artifacts/src/v2` into the package root - merged (PR #359)

### Discussion

The `v2` subfolder existed only to distinguish the new artifact ports from the legacy `Artifacts` class living alongside it at `packages/artifacts/src/artifacts.ts`. Change C9 deleted that legacy class outright, so by the end of Change C9 `v2` was the only real content in the package — a versioning label with nothing left to version against. Decided to drop the folder as a small closing cleanup for this initiative, rather than carry a stale "v2" name forward into whatever consumes this package next.

### What actually landed

`artifact-reader.ts`, `artifact-writer.ts`, `artifact-read-write.ts` moved from `src/v2/` to `src/` directly; `v2/index.ts`'s three re-export lines merged into the package's existing root `index.ts` (which previously just re-exported `./v2/index.js`). Test files moved the same way (`tests/v2/*.test.ts` → `tests/*.test.ts`), with their relative imports (`../../src/v2/...` → `../src/...`, `../helpers/...` → `./helpers/...`) updated to match the new depth. `draft.temp.ts` (an unrelated, never-exported design sketch already at `src/` root) untouched. Full repo `build`/`typecheck`/`test` green throughout (27/27 build, 26/26 typecheck, 26/26 test).

Full repo verification clean throughout: `build`/`typecheck`/`test`/`lint` all green (27/27, 26/26, 26/26, 26/26).

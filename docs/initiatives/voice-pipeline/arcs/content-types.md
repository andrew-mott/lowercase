# Voice Pipeline — Arc A2: Content types (Changes C2–C2)

**Previous:** [The http step](./http-step.md) (Changes C1) · **Next:** [The http job](./http-job.md) (Changes C3)

Part of the [`INITIATIVE.md`](../INITIATIVE.md) Change log, split out to keep that doc scannable. This arc widens the flow definition's content-type fields past the three fixed MIME strings they allow today, and closes the interpolation-legality gap that widening opens.

## Change C2 - Widen content types past three exact values - merged (#394)

`FlowParamContentType`, `Ref.paramType`, `Ref.exportType` and `ExportRef.type` each allow only `application/json`, `text/plain` and `text/markdown` today. This Change widens a param's declared type to any MIME type, adds the classification that widening needs, and stops a binary value from being interpolated somewhere only a string belongs.

### Discussion

- **The four unions are duplicated, not shared — but they don't all widen together.** `FlowParamContentType`, `Ref.paramType`/`Ref.exportType`, and `ExportDeclaration.type`/`ExportRef.type` are each independently written out as the same three-literal union in four different files, with no shared name. Every consumption site (`job-runner.ts`, the branch-value effect, export storage) already forks on exactly one condition — `type === "application/json"` vs. everything else — and exports are always JSON-extracted, so `ExportDeclaration.type`/`Ref.exportType`/`ExportRef.type` can never legally be binary. Only a param's declared type can be. So this Change splits the duplication into two named types instead of one: `ContentType` (widened to `"application/json" | (string & {})` — free-form MIME strings, with `application/json` still available for autocomplete) for `FlowParamDefinition.type`/`Ref.paramType`; `TextSafeContentType` (unchanged, the exact three literals) for `ExportDeclaration.type`/`Ref.exportType`/`ExportRef.type`/`HttpExportDeclaration.type`. Both live in `packages/types`.
- **The same narrow type is also what `apps/workbench`'s artifact-authoring panel needs**, found while grepping for existing `FlowParamContentType` usages: `detect-authored-format.ts` and `artifact-authoring-panels-slice.ts` use it for an exhaustive switch over what a human can type into a textarea, which genuinely can't author binary content either way. They move to `TextSafeContentType`, not `ContentType` — a real, distinct concern that happened to reuse the same name only because the two were identical until now.
- **`TextSafeContentType` is narrower than "text" really means, on purpose, for now.** Under `classifyContentType`'s scheme (below), "text" is any MIME type prefixed `text/`, not just `text/plain`/`text/markdown` — the authoring panel could someday offer `text/csv`, `text/html`, etc. `TextSafeContentType` stays pinned to the exact three literals in this Change, matching what `ExportDeclaration`/the authoring panel actually support today; widening it to "json or `text/*`" is real future work, not done here.
- **A new `FlowProblem` variant, `InvalidBinaryRefPosition`, and `RunService` refuses it.** A binary-classified param may only be referenced as the whole value of an http step's `body.artifact` or a multipart file's `artifact` field — anywhere else the ref would have to become a string, which a binary value can't. `RunService`'s existing ref-problem guard (already refusing `InvalidExportRef`/`InvalidExportRefPath`) is extended to refuse this too, not just have flow-analysis report it: it's reachable today through a working `httpjson`/`mcp`/`branch` step referencing a newly-widened binary param, not gated behind the `http` step's own executor.
- **Every consumption site already forks on exactly one condition: is it JSON.** The worker's ref resolution (`job-runner.ts`), the branch-value effect, and export storage all check `type === "application/json"` and treat everything else identically — load the whole value, no path traversal. `text/plain` and `text/markdown` behave identically everywhere today; nothing distinguishes them. Widening needs no change to that fork — it already treats "not JSON" as one bucket.
- **Interpolation is the real gap.** `{{...}}` substitutes a resolved value into a string position — a JSON field, a multipart string part, plain text. That's safe for `application/json` and any text type, and meaningless for binary bytes. Nothing stops it today because only text-safe types exist. A new analysis-time check — the same shape as `validateExportRefPath`'s existing path-depth guard — refuses a ref classified `binary` wherever it isn't the whole value of an `artifact` position (`body.artifact`, or a multipart `{ artifact }` part).
- **`classifyContentType(mime): "json" | "text" | "binary"`** does the classification: exact match on `application/json`; prefix match on `text/` for text, which follows MIME convention and needs no whitelist to maintain as new text subtypes show up; everything else binary. It lives beside `isArtifactCompatible` in `packages/functional-core/flow-analysis/src/artifact-compat.ts` — pure, zero I/O, the same tier as its sibling `defaultContentTypeForFormat`/`inferFormatFromContentType` in the same package. A real `application/*` text format (`application/xml`, `application/x-yaml`) is left classified `binary` until something actually needs it, the same way `application/json` earned its own exact case. `isArtifactCompatible` itself is unchanged: it's already exact-string equality, which stays correct against a wider legal value set.
- **`body`'s `artifact` kind keeps its name.** Considered renaming it `binary` to separate mechanism from MIME category; rejected, because `artifact` already means "pass this stored Artifact's bytes through verbatim, whatever they are" — including a JSON or text artifact forwarded unmodified — so `binary` would be a narrower, wrong name for what it actually does.
- **`ArtifactFormat`/`ArtifactIndex` are explicitly out of scope.** `format` (`json`/`text`/`markdown`/`bytes`, on the Prisma `Artifact` row and `ArtifactIndex`) is documented legacy duplication with `contentType` (ADR-0002, `docs/todo.md`) that this Change does not retire. `classifyContentType` is computed at runtime from `contentType`, never stored, so nothing here forces a schema decision either way. Retiring `format` for real is left to the larger SQL-architecture rework already planned separately (removing per-artifact SQL rows, writing metadata alongside the blob instead of during the run) — resolving it now would be work that rework throws away.
- **Related, not solved here: the read path.** `GET /artifacts/:hash`'s response shaping already branches on the legacy `format` field's `bytes` case, returning only `byteLength`. Widening content types doesn't fix that route — it stays the separately-tracked "read path" item in the Initiative's Not yet scoped — but it's the natural place to swap that branch's `format` check for one derived from `contentType`/`classifyContentType` once that item is taken up.

**Not in C2:** retiring `ArtifactFormat`/`ArtifactIndex`; whole-step-output refs (`{{steps.X.output}}`); multipart _responses_ (a server bundling several parts back, each its own content type) — not needed by either target flow, and a real but separate extension of the `http` step's protocol support if it's ever needed; the command/terminal Messages; the worker's `http` executor.

### What actually landed

Matches the discussion, with these deltas.

- **`packages/specs`'s Zod schema was still narrow, and that's the real gate.** `FlowParamDefinitionSchema.type` (in `flow.types.ts`) hard-coded `z.enum(["application/json", "text/plain", "text/markdown"])`, independently of the TS type — widening `FlowParamDefinition.type` to `ContentType` didn't change what `FlowSchema.safeParse` actually accepts, since Zod schemas and TS types aren't kept in sync by the compiler. A flow declaring an `audio/wav` param would have been rejected at parse time regardless of everything else in this Change. Found by writing a real `RunService` test against the actual schema, not just unit tests against the flow-analysis functions in isolation — caught before merge only because the test exercised the whole path. Fixed: `type: z.string().min(1)`, with a comment on why nothing more specific is validated. `ExportDeclarationSchema.type` was already correctly left alone (still the closed enum, matching `TextSafeContentType`).
- **`isTextSafeContentType` doesn't live in `packages/types`.** That package is types-only; a real type guard (needed because a plain `===` chain doesn't narrow reliably against the `string & {}` branch — TS's control-flow analysis gives up on it) is logic, not a type. It lives beside `classifyContentType`/`isArtifactCompatible` in `packages/functional-core/flow-analysis/src/artifact-compat.ts` instead, and the two workbench files import it from `@lcase/flow-analysis` (which they already depended on), not `@lcase/types`.
- **Two more workbench consumers of the old narrow type turned up beyond the two found by the initial grep**, because that grep was `.ts`-only and missed `.tsx`: `CreateArtifactDialog.tsx`'s file-picker accept-hint, and `use-artifact-authoring-panel.ts`'s "return to this param" effect. The second was a real gap, not just a type-signature fix — it was passing a param's declared type straight into the text-authoring panel's state with no guard. Both now skip the text-authoring assumptions for a binary-typed target rather than building new binary-upload UI, which stays out of scope.
- **`RunService`'s guard is `#validateRefProblems`,** renamed from `#validateExportRefProblems` since it's no longer only about export refs, and extended to refuse `InvalidBinaryRefPosition` alongside the two problem types it already refused. Its thrown message changed from "Invalid step export reference(s)" to "Invalid step reference(s)" — one existing test asserted the old wording and needed updating.
- **Whole-step-output refs got a concrete answer, not just a deferral,** during discussion for this Change: enforcement belongs on the worker side, checked dynamically against the artifact's real stored `contentType` at ref-resolution time (`ArtifactReaderPort.load(hash)`'s untyped overload already returns `{ contentType, value }` together — no new port capability needed), rather than statically like `validateBinaryRefPosition`, because a step's output has no declared type in the flow definition the way a param does. Recorded in `INITIATIVE.md`'s Not yet scoped, not built here.

## Change C3 - The http job's command and terminal Messages - merged (#395)

`httpjson` already has its own job command/terminal event family. `http` needs the same three events — `submitted`, `completed`, `failed` — before the engine can dispatch it (C5) or the worker can execute it (C4).

### Discussion

- **Hand-rolled, not schema-first — deliberately, and only for now.** The Design principles above call for a schema-first bridge on "a command's schema," but `packages/events`'s `eventSchemaRegistry` is entirely hand-rolled Zod across its ~15 existing families with no AJV bridge anywhere in it, and is itself flagged (`CLAUDE.md`) as a known rough edge and an active refactor target that the `json-schema-migration` Initiative (I7) owns — "moves the existing schemas." Building a one-off JSON-Schema/AJV bridge just for `http`'s three events, while every sibling family stays pure Zod beside it, would be inconsistent scaffolding thrown away once I7 actually runs. So C3 hand-rolls `job.http.submitted`/`completed`/`failed` as a file-for-file mirror of the existing `httpjson` family. The Design principles' schema-first bullet is amended accordingly: proven and scoped to flow-definition shapes (C1), not extended to the Message/event layer by this Initiative.
- **Nothing new to schema for terminal data.** `JobCompletedData`/`JobFailedData` are already capability-agnostic — `httpjson`'s own terminal schemas already point `data` at them unmodified, not at anything httpjson-specific. `http`'s terminals reuse them exactly the same way; no new terminal data type exists.
- **The one new data shape is the submitted command's, and it's inherited, not invented.** `JobHttpSubmittedData` mirrors `JobHttpJsonSubmittedData`'s exact shape: `Omit<StepHttp, "type" | "on" | "exports"> & JobSubmittedData & { exportRefs? }`. `StepHttp` is already schema-first at its source (C1's generated type), so this wrapper inherits that rather than skipping it.
- **Command verb: `submitted`, not `execute`.** Matches `httpjson`'s existing past-tense precedent (`job.httpjson.submitted`) rather than running two tenses across capability families for the same conceptual event. `execute` is where an eventual real command/event split would land — worth naming now so it isn't mistaken for a decision already made, but only once Messages are genuinely migrated to a system that distinguishes them (the `kind` envelope attribute the Design principles already flag as deferred), not before.
- **Terminal types: `job.http.completed`/`job.http.failed`, additive only — no shared generic type string.** Considered a fully capability-generic `job.completed`/`job.failed` shared by both `httpjson` and `http`, since the data is already generic either way. Rejected for now: it would mean migrating `httpjson`'s own already-working `job.httpjson.completed`/`failed` too (touching `engine.ts`'s `handleJobTerminal` signature, `job.catalog.ts`'s `JobTerminalType` union, the subscription), for a naming-purity win only. Minimal disturbance wins here for the same reason as the schema-first call above: real unification is refactor work, and doing it incidentally here would blur what's actually been migrated from what's still the old pattern.
- **The wiring surface is genuinely small.** `JobEventMap` (`packages/types/src/events/job/map.ts`) is `JobHttpJsonEventMap & JobMcpEventMap` — adding `& JobHttpEventMap` is the one manual union edit needed at the type level; `EventType`, `JobSubmittedType`, `JobCompletedType`, `JobFailedType` all derive automatically via template-literal `Extract` over the merged union's keys, not separately maintained lists. `CapMap` (`packages/types/src/flow/map.ts`) gets one new entry, `http: StepHttp`.
- **`job.catalog.ts`'s topic unions stay untouched — that's not this Change.** They were originally scoped into C3, but tracing it further: a `MessageBinding`'s handler type is derived directly from its subscription's topic `types` (`MessageHandler<SelectedTypes<Topics>>`), so widening `jobCommandTopic`/`jobTerminalTopic` would force real production call sites to typecheck against the wider union — `apps/http-server/src/profiles/api-host/bind-subscriptions.ts` binds `engine.handleJobTerminal` (typed to exactly the two `httpjson` terminal types today) to `engineJobTerminalSubscription`, and `apps/worker-host/src/profile/bind-subscriptions.ts` binds `worker.handleHttpJsonSubmitted` (typed to exactly `HttpJsonSubmission`) to `workerJobCommandSubscription`. There's nothing real to do yet with a delivered `job.http.submitted` — no executor exists until C4 — so widening now would mean a stub/guard with no behavior behind it, which is exactly the dispatch/execution work already scoped to C4/C5. Whichever of those first needs the shared topics to actually carry `http` traffic widens them then.
- **`packages/events`'s own `RefSchema` was missed by C2, found while touching this file for the new family.** `packages/events/src/schemas/job/job.data.schema.ts`'s `RefSchema` hand-writes `paramType`/`exportType` as the closed three-literal enum — a fourth independent copy of the pre-C2 union, in a package C2's audit never reached. This is exactly where `Ref.paramType` (now `ContentType`, widened) flows through at job-dispatch time once `makeStepRefs` populates it, so a widened value legal since C2 (`audio/wav`, or even a plain `text/csv`) would still fail this schema. Fixed the same way as C2's `packages/specs` finding: `paramType: z.string().min(1).optional()`. `exportType` and `ExportRefSchema.type` stay the closed enum, matching `TextSafeContentType` — only a param's declared type was ever meant to widen.
- **`CapIdSchema` (same file) gets `"http"` added to its `z.enum([...])`**, matching `CapMap`'s new entry — otherwise a `Ref`/job payload naming the `http` capability would fail this schema even though the type-level `CapId` already allows it.

**Not in C3:** message-topology catalog wiring (`job.catalog.ts`'s topic/subscription type unions) and both host apps' `bind-subscriptions.ts` — deferred to C4; the worker's `http` executor (C4); engine planning/dispatch that actually publishes `job.http.submitted` or subscribes expecting its terminals (C5); any events-layer schema-first migration (left to I7); unifying `httpjson`'s own terminal type strings with anything shared with `http`.

### What actually landed

Matches the discussion, including both corrections found during planning (the catalog-wiring scope cut and the `RefSchema` fix).

- **`packages/types`**: `job/http/{data,map,index}.ts` add `JobHttpData`, `JobHttpSubmittedData` (mirroring `JobHttpJsonSubmittedData`'s shape over `StepHttp` instead of `StepHttpJson`) and `JobHttpEventMap` (`submitted`/`completed`/`failed` only). `JobEventMap` becomes a three-way intersection; `JobEventType`/`JobSubmittedType`/`JobCompletedType`/`JobFailedType` picked the new literals up automatically through the existing template-literal `Extract`s, no separate edit needed. `CapMap` gained `http: StepHttp`.
- **`packages/events`**: new `schemas/job/http/http.event.schema.ts` and `registries/job/http.{types,schema}.map.ts`, wired into `event-schema.registry.ts`/`event-types.ts`/`category.registry.ts`/`otel-attributes.ts`/`entityTypes` — each of those is a `satisfies`/`Exclude<...>` exhaustiveness check, so a missed wiring edit failed the build immediately rather than silently compiling. The `JobHttpDataSchema.body` union (`json`/`artifact`/`multipart`) is hand-written Zod, not reused from `packages/specs`'s AJV-backed `validateHttpStep` — that validator covers a whole step (needs `type: "http"`, and no `exports`/`on`), not the narrower job-data projection, and `httpjson`'s own job data schema doesn't reuse its step-level validation either, so this keeps the same precedent rather than introducing a new one.
- **The one Zod-inference snag**: `z.object({ json: z.unknown() })` infers `json` as optional (Zod treats any field whose schema accepts `undefined` as an optional key, and `unknown` does), which didn't satisfy `HttpBodyJson`'s required `json: unknown`. Fixed by using `ShallowJsonValueSchema` (already imported for `httpjson`'s own body) instead of `z.unknown()` directly — narrower than `unknown` but still assignable to it, and its members don't include `undefined`, so the key stays required.
- **The `RefSchema.paramType`/`CapIdSchema` fixes and the scope correction (catalog wiring deferred to C4) both held as planned** — no further deltas. `pnpm format && lint && typecheck && -r test` all pass clean across the repo, including `apps/http-server`/`apps/worker-host`/`packages/components/engine`/`packages/components/worker`, confirming the scope cut actually achieved what it was for: zero production call sites needed to change.

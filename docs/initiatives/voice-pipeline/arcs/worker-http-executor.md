# Voice Pipeline — Arc A4: The worker's http executor (Changes C4–C6)

**Previous:** [The http job](./http-job.md) (Changes C3)

Part of the [`INITIATIVE.md`](../INITIATIVE.md) Change log, split out to keep that doc scannable. This arc builds the worker's execution logic for `http` — by widening `httpjson`'s existing executor rather than building a second one beside it. That unification is scoped to exactly one layer: the flow step types (`httpjson`, `http`) and the event families (`job.httpjson.*`, `job.http.*`) both stay separate, exactly as Change C3 decided. Only the worker's request-building/response-handling implementation is shared.

**Not in this arc:** retiring `httpjson` as a step type, or unifying its events with `http`'s — a separate, undecided question at a different layer than this arc touches. Engine planning/dispatch for `http`, including flipping `RunService`'s `STEP_TYPES_WITHOUT_EXECUTOR` gate — that's C7, not yet scoped in detail. Any events-layer schema-first/AJV migration — left to `json-schema-migration` (I7).

## Change C4 - A shared executor for http and httpjson - merged (#396)

### Discussion

- **The core decision: one executor, not two.** `httpjson`'s body is a bare `JsonValue`; `StepHttp`'s `HttpBodyJson` is `{ json: JsonValue }` — same wire behavior, just wrapped. `httpjson`'s entire executor today (build JSON body, call `fetch`, parse the response as JSON-or-text) is exactly what `http`'s `json` body case needs to do. Rather than write that logic twice, this Change generalizes the existing executor to handle `StepHttp`'s full body union (`json`/`artifact`/`multipart`), with `httpjson`'s request normalized into the `json` case before it hits the same code. `httpjson`'s existing wire behavior must not regress — this is a refactor of working code, not new code added beside it.
- **Scope is deliberately narrow: execution logic only.** This does not touch the flow step-type layer (no change to `StepHttpJson`/`StepHttp` as parsed/validated shapes) or the event layer (C3's additive, separate `job.httpjson.*`/`job.http.*` families are untouched). Whether `httpjson` ever becomes a preset of `http` at those other layers is still an open, separate question.
- **Build and test the executor in isolation first**, against hand-built resolved-request fixtures rather than real ref resolution — proves out `JSON.stringify` vs. raw-bytes vs. `FormData` dispatch for the three body kinds without needing `JobRunner` or ref-resolution changes yet. The downstream piece (C5) exists to _produce_ the resolved-request shape this Change settles on, not to help define it.
- **`ProtocolResult` starts carrying the response's actual `Content-Type`.** Cheap to capture while already generalizing `readResponseBody` to handle non-JSON, non-text responses (needed for `artifact`/`multipart` request bodies to have any response-parsing story at all). Whether/how storage acts on it is deferred to C6 — this Change only makes the information available.
- **Multipart sending has no precedent anywhere in the codebase** — every existing multipart use is receiving (`@fastify/multipart` server-side, browser `FormData` in the workbench talking to our own API). Node's global `fetch` (already the injected HTTP client, `HttpJsonExecutorDeps.fetch`) accepts a `FormData` body natively — no new dependency needed.
- **No streaming story, and that's fine.** `ArtifactReaderPort.load()` always returns a fully materialized `Uint8Array` — every artifact byte a multipart file part or an `artifact` body would carry is already fully buffered by the time the worker has it, regardless of HTTP client choice. Worth knowing going in rather than designing around a stream that doesn't exist anywhere upstream.

### What actually landed

Matches the discussion, with one correction to how narrow the response side stayed: `readResponseBody` was **not** generalized past JSON-or-text — it's untouched. Only the response's `Content-Type` header is captured, as an additive field alongside the unchanged, still-JSON-or-text `payload`. Confirmed directly during review: a genuinely binary response would still be mis-decoded by `readResponseBody`'s `response.text()` fallback today (UTF-8-decoding arbitrary bytes into a lossy string) — fixing that is squarely C6's job, not started here.

- **`packages/components/worker/src/protocol/http-json/http-json.types.ts`**: `ResolvedHttpJsonRequest.body` changed from a bare `json?: JsonValue` to `body?: ResolvedHttpBody`, a `kind`-tagged union (`json` / `artifact` / `multipart`). New `ResolvedHttpBinary` (`{ contentType, bytes, filename? }`) is shared between a top-level `artifact` body and a multipart file part. `HttpJsonResponse` gained `contentType?: string`.
- **`http-json.executor.ts`**: `invoke()` now builds the fetch body from `request.body.kind` — `JSON.stringify` for `json` (unchanged behavior), the raw bytes (via `Buffer.from`, to satisfy `BodyInit`'s `Uint8Array<ArrayBuffer>` typing) for `artifact`, and a `FormData` (string parts via `formData.append`, binary parts as a `Blob` with `filename`) for `multipart`. The GET/HEAD guard generalized from `request.json !== undefined` to `request.body !== undefined`. The response's `content-type` header is captured into `HttpJsonResponse.contentType` and threaded through to `ProtocolResult.contentType` on both the success and failure paths — additive only, so `job-runner.ts`/`execution-output-storage.ts` (which type `payload` as `JsonValue` and never reference `contentType`) needed no changes, confirmed by a clean full-repo typecheck.
- **`materialize-http-json-request.ts`**: the one real production caller, updated to wrap its output as `{ kind: "json", value: bound.body }` — `httpjson`'s existing behavior is unchanged, just produced through the wider type.
- **A Node/TypeScript typing snag**: `Uint8Array<ArrayBufferLike>` (what a `Uint8Array` read back from storage is typed as) isn't structurally assignable to `BlobPart`/`BodyInit`, which pin `Uint8Array<ArrayBuffer>` — TS's generic-TypedArray change surfaced this. Fixed by wrapping with `Buffer.from(...)` at both the `artifact`-body and multipart-file-part call sites, since Node's `Buffer` typing is pinned to a real `ArrayBuffer`.
- **Tests**: `http-json-executor.test.ts` grew from 11 to 17 cases — existing ones updated for the wrapped body shape and the new `contentType` field on exact-match assertions (`toMatchObject`-based tests were unaffected); new cases cover an artifact body sending raw bytes, a multipart body producing a real `FormData` (asserted via `formData.get()`, including the file part's `type`/`name`/bytes), the GET-rejects-any-body guard exercised across all three kinds (`it.each`), and a non-JSON response's `Content-Type` being captured. `materialize-http-json-request.test.ts` needed one assertion update for the wrapped shape.
- `pnpm format && lint && typecheck && -r test` all pass clean across the full repo (exit 0), confirming the additive-only design held: no package outside `packages/components/worker` needed a change.

## Change C5 - Worker and JobRunner wiring for two submissions, one executor - in progress

### Discussion

- **"Two normalizers, one executor," not "pick among executors."** Because C4 already generalized the executor itself, `WorkerDeps.protocol`/`JobRunnerDeps.protocol` can stay a single `ProtocolExecutor` — no registry or union of executors needed. `httpjson` and `http` submissions each get normalized into the resolved-request shape C4 settled on.
- **A step's content type for an `artifact`/multipart body comes from `ref.paramType`, already in hand — no separate ref-resolution change needed.** Traced this while scoping: `JobRunner.#resolveOneRef` already calls the _typed_ `ArtifactReaderPort.load(hash, contentType)` overload for a binary-classified param, which validates the declared type against what's actually stored (`TYPE_MISMATCH` on any mismatch) before returning bytes — so `ref.paramType` is already guaranteed to equal the artifact's real content type by the time resolution succeeds. The new `materialize-http-request.ts` this Change adds already receives the full `refs: Ref[]` array untouched, same as `materialize-http-json-request.ts` does today, so it can just read `ref.paramType` for whichever ref backs an `artifact`/multipart-file position. `bindStepRefs` (`@lcase/json-ref-binder`, functional-core, zero I/O) only ever carries plain values through its `resolved: Record<string, unknown>` map, so this also avoids giving that pure package a content-type-aware shape. Exports are locked to JSON/text/markdown today (`TextSafeContentType`), so this only applies to params — if an export's declared type ever widens the way C2 widened `paramType`, the same mechanism would extend to `exportType`, but nothing needs that yet.
- **Terminal-type selection stays capability-aware.** `job.http.completed/failed` vs. `job.httpjson.completed/failed` still needs picking based on which capability the submission came from — these stay separate per C3, since unification stops at the execution layer.
- **Catalog and `bind-subscriptions.ts` widening lands here, now that there's real behavior to attach it to.** `job.catalog.ts`'s `JobCommandType`/`JobTerminalType` unions widen to admit `job.http.submitted`/`completed`/`failed`. On the worker side this is a real code change, not just a type widen: `worker.ts`'s inbound handler needs to become dispatch-capable across two submission shapes, since they normalize differently even though they now share an executor. On the engine side (`apps/http-server`'s `bind-subscriptions.ts` binding `engine.handleJobTerminal`) it's a type-signature-only widen, since `handleJobFinished` underneath is already capability-agnostic (dispatches only on `.endsWith(".completed"/".failed")`).
- **Still not C7.** This Change makes the worker able to receive and execute a `job.http.submitted` message and publish its terminal — it does not make the engine send one, or flip `RunService`'s `STEP_TYPES_WITHOUT_EXECUTOR` gate. An end-to-end run still can't exercise this until C7.

### What actually landed

Matches the discussion, with a few deltas found while building or during full verification.

- **`job.contracts.ts`**: `ProtocolRequest` became a real discriminated union (`kind: "httpjson" | "http"`, each branch with its own `body` type), and `HttpJsonWork` was renamed to `Work` — its only capability-specific part was always `protocol`, and that field now carries its own tag.
- **New `materialize-http-request.ts`**, alongside the existing `materialize-http-json-request.ts` in the still-unrenamed `protocol/http-json/` directory: resolves `StepHttp`'s `json`/`artifact`/`multipart` body union, looking up each `artifact`/multipart-file ref's content type via `ref.paramType` (found already-guaranteed-correct, so no ref-resolution change was needed, matching this Change's own discussion above). It also sets `Content-Type` from that content type for the `artifact` case, and deliberately leaves it unset for `multipart` so `fetch` can set its own boundary-bearing header — a concrete detail beyond what the discussion spelled out, needed for the Design principle ("Content-Type taken from the artifact's own metadata") to actually reach the wire. Considered extracting the ~20 lines duplicated verbatim between the two materializers (the GET/HEAD-body guard, URL validation, Accept default) into a shared helper; held off deliberately, since `httpjson` may be retired as a step type later and a shared abstraction built now could become dead weight to unwind.
- **New `http-submitted-message.ts`** (`HttpSubmission`, `toHttpWork`), mirroring `submitted-message.ts`. `JobIdentity` needed no change — it's already a structural pick of the four envelope fields every `AnyEvent` carries, so an `HttpSubmission` already satisfies it.
- **`job-runner.ts`**: `run()`/`#prepareProtocolRun` now take `Work` and dispatch to whichever materializer matches `work.protocol.kind`.
- **`worker.ts`**: `handleHttpJsonSubmitted` renamed to `handleJobSubmitted`, now dispatch-capable across both submission shapes (`submission.type === "job.httpjson.submitted"` picks the normalizer). Three call sites needed the rename: `apps/worker-host/src/profile/bind-subscriptions.ts`, and — found while tracing every binder, not just the one the discussion named — `packages/process-hosting/profile-local-system`'s own `local-system.profile.ts` and its test helper `http-job-graph.ts`, since the embedded single-process host binds Worker separately from `apps/worker-host`.
- **`terminal-message.ts`**: `JobTerminalType` widened to four literals; `buildJobTerminal` picks `job.http.*` vs `job.httpjson.*` by narrowing on `submitted.type`, exactly as the discussion called for.
- **`job.catalog.ts`**: `JobCommandType`/`JobTerminalType` and both topics' `types` arrays widened. This broke a test outside the arc's anticipated scope: `resolve-host-plan.test.ts` (a different file from `job.catalog.test.ts`) hardcoded the terminal topic's exact `types` array — caught only by the full-repo `pnpm -r test` pass, not by the worker package's own suite.
- **`engine.ts`**: `handleJobTerminal`'s parameter union widened — confirmed a pure type-signature change, `handleJobFinished` needed no edits.
- Two stray doc comments left over from this session's Change renumbering (in `http-json.types.ts` and `protocol-executor.types.ts`, both said "Change C7" for what is now C6) were fixed in passing.
- Worker package test count grew from 100 to 120 (new `materialize-http-request.test.ts` and `http-submitted-message.test.ts`, plus added cases in `worker.test.ts`/`job-runner.test.ts`/`terminal-message.test.ts` covering dispatch and terminal selection across both submission shapes). `pnpm format && lint && typecheck && -r test` all pass clean across the full repo.

## Change C6 - Output storage stores a response as what it says it is - not started

### Discussion

- **The gap:** `storeExecutionOutputs`/`tryStoreOutput` unconditionally call `writer.save(payload, "application/json")` today, regardless of what the origin server actually sent — even a plain-text response gets tagged `application/json`. The Design principle "a response is stored as what it says it is" is specifically about `http`, but this code is shared with `httpjson`.
- **Open scope question, to settle when this Change is planned:** fix it generally so both capabilities store a response under its real reported `Content-Type`, or scope the fix to `http` only and leave `httpjson`'s existing (mistagged) behavior untouched — mirroring the minimal-disturbance precedent C3 set for the event layer. Not decided yet.
- **The port already supports this.** `ArtifactWriterPort.save`'s three-way overload (JSON / `text/*` / raw bytes with any content type string) needs no change — the gap is entirely in the caller, which as of C4 has the response's real content type available on `ProtocolResult` and simply isn't using it yet.
- **Doesn't depend on C5.** `storeExecutionOutputs` is already live code on the `httpjson` path today, and `ProtocolResult.contentType` already exists as of C4 — this Change could be built and merged before C5's wiring lands.

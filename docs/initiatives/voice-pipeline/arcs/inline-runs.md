# Voice Pipeline — Arc A8: Inline runs (Change C13)

**Previous:** [Results out](./results-out.md) (Changes C10–C12)

Part of the [`INITIATIVE.md`](../INITIATIVE.md) Change log, split out to keep that doc scannable. This arc lets an application that knows nothing about the workflow engine send a run's inputs and the flow it wants in one request, and get the result back on the same connection.

**Not in this arc:** progress reporting beyond a heartbeat, streaming artifact bytes, and moving result retrieval off artifacts onto a system-agnostic endpoint. That last one is wanted eventually; going through artifacts is good enough for now.

## Change C13 - Inline run request that holds for the result - merged (#405)

### Discussion

The caller today uploads each input as an artifact, starts the run with the hashes as params, waits on its own, then reads the outputs (C11) and bytes (C12). The callers this arc serves want one request carrying the audio and the flow, and one response carrying the result.

- **The request is one `multipart/form-data` POST.** One JSON part named `run` describes the run (`flowId`, `flowVersionId`, `flowDefHash` for now), and every other part is an input. A part becomes an artifact bound to the param named by the part, with the part's declared `Content-Type` as the artifact's type, which is what an upload already does. The multipart plugin and its per-file size cap are already registered for every route.
- **The response is an SSE stream, and it carries a small vocabulary of our own.** It is not the event taxonomy, which callers should never learn. The messages are:
  - `accepted`, first, carrying the run id, so a caller has a handle even if the connection drops.
  - Heartbeat comments while the run works, so idle timeouts do not cut the connection. The existing `/events` route already does this every 20 seconds.
  - One terminal message, `completed` with the outputs manifest (the shape C11 returns) or `failed` with the error, after which the stream closes.
- **Heartbeat only. Progress is deferred.** A later `progress` message, such as step counts, can be added without breaking callers because the vocabulary is ours. What progress means is not decided here.
- **Every part carries its own `Content-Type`, and a part without one is meant to be rejected with a 400.** That turned out not to be enforceable: see "What actually landed". The part's type is checked against the param's declared type exactly as a curated artifact is (`isArtifactCompatible`, wildcards included), and a mismatch is a 400 before any run exists. JSON parts are sent as the raw JSON text and parsed by the server, text is decoded as UTF-8, and anything else is stored as bytes. This is the mapping `POST /api/artifacts` already applies, so it should be shared rather than copied. Binary data belongs in a part with a `filename`, since plain fields are read as UTF-8 strings under a small size limit.
- **What the caller does not learn.** The request and the stream name no event, topic, step, or store. The only engine-shaped things a caller sees are the hashes and content types in the outputs manifest, and the artifact content route it fetches bytes from. That is the one deliberate leak: it is contained at the edge, and a later system-agnostic result endpoint can replace it without changing the request or the message names.
- **Reading the stream.** `EventSource` only issues GET, so a caller reads this POST's response with `fetch`.
- **Errors before the run exists are real statuses with a JSON body**, as C12 does: a malformed request, an unknown flow, a param whose artifact type does not match. The stream only begins once the run is accepted, and from then on a failed run is the `failed` message.
- **A dropped connection does not cancel the run.** The run id was already sent, so the caller can fetch the outputs route once the run finishes. The terminal message is derived from the run's state, not only from a live event, which is what makes any re-attachment safe.
- **C13 also ships `GET /runs/:id/stream`, and the POST is a wrapper around the same code.** The shared piece takes a run id, writes `accepted`, sends heartbeats, waits for the run to finish, writes the terminal message and closes. The POST calls it after creating the run, and the GET calls it after checking the run exists (404 otherwise). A GET for a run that finished long ago reads SQL, sees a terminal status and answers `completed` immediately, which is the same path a very fast run takes. This is what stops a dropped connection being a dead end. Any run id can be streamed; auth is deferred project-wide.
- **`run` is a reserved part name.** A flow that declares a param called `run` cannot be started through this route. That is accepted: it is one name, and the alternative of prefixing every input's part name makes every client worse for a rare clash.
- **`completed` carries the same shape as the outputs manifest, and nothing comes between `accepted` and the terminal message.** Small text and JSON outputs are inline up to the limit the outputs route already applies, and everything else is fetched by hash.
- **The wait has a server-side cap, and hitting it sends a `timeout` message and closes the stream.** It is not a connection limit. The workbench's `/events` stream stays open forever because it is an open-ended feed that nothing waits on. This stream has an ending and a blocked caller, and a run can hang (the engine has no deadline) or its terminal write can fail to land, so without a cap the server would hold that waiter and connection indefinitely. A timeout does not cancel the run, and the caller can reattach through the GET. The cap is a configurable server setting with a generous default; the number is chosen when the code is planned.
- **Where artifact creation sits.** Settled: the route orchestrates it. It writes each part through the artifact service, builds the param map from the resulting hashes, and calls the run service's `requestRun`, which already validates each hash and its content type against the flow's params. `RunService` stays read-only for artifacts and no new service is added. That puts orchestration in a route, which is not where it ideally lives, and is accepted for now.
- **Inline inputs must not be curated, and the existing write path cannot yet promise that.** `curated` means a person deliberately made or curated an artifact (ADR-0003), and it drives the workbench's "browse user-made artifacts" view, so one-off inputs an application sends should not be marked. `ArtifactService.createArtifact` always writes `curated: true`, so it needs a non-curated variant. The larger problem, confirmed against the real repository on SQLite and Postgres: `ArtifactWriter` turns any non-curated write into `curated: false` explicitly, and the Prisma repository's upsert then writes that value on update as well as create. Sending bytes identical to an already curated artifact (an application resending a sample the user curated) would silently un-curate it and overwrite its time (and its filename, when the new write names one). The repository's own comment and ADR-0003 both say a re-put of identical content leaves curation alone, which only holds if the metadata is omitted, and the writer never omits it. The same applies to a worker re-storing an output that matches a curated artifact. The check curated an artifact, then called `writeArtifact` with exactly the metadata the writer builds, `{ curated: false }`: `curated` went from true to false. C13 does not fix this: it writes inline inputs non-curated and accepts the hazard, which is not causing a problem today. The fix is tracked in `docs/todo.md`, with two options (leave `curated` unset in the writer, or check whether the hash exists before writing).
- **How the server notices a run finishing.** Traced, and the shape of the problem is this:
  - The API host runs the Engine and Observability in the same process (the embedded host does too), so `run.completed` and `run.failed` always pass through that process's tap. Only the Worker is out of process, and its terminal reaches the engine over the carrier. So an in-process wait can see every run end, and no cross-process signal is needed today.
  - The event is not the right thing to wait on. `SqlRunProjectionSink.handle` returns immediately and flushes to SQL in the background, so the tap moving on says nothing about whether the projection has been written. `getRunOutputs` reads the projection and refuses a run that is not terminal there. A waiter that answered on the raw event could ask for outputs and be told the run has not finished.
  - The sink already stores a terminal status last, after every step, so once SQL says terminal, the outputs are readable. What is missing is a way to learn that the terminal write landed without polling SQL.
  - **Settled: the sink reports that it finished the terminal write through a small in-process notifier**, an interface in `packages/ports` that the sink calls and the waiter registers with. A waiter registers first and then reads the run's current status, so a run that finished a moment earlier is not missed, and otherwise waits for the notification. It needs a timeout regardless: the sink retries a failing flush but nothing guarantees it ever succeeds.
  - **Considered and not chosen.** An event on the event bus, because the bus is the legacy path, and a new event would need a schema, an `EventMap` entry and more emitter boilerplate, with a sink publishing back into the tap that feeds it. A new Message family, which is the principled home and works across processes, but costs a catalog, a topic, a subscription and a publisher inside a sink, in a Change that is already large.
  - **Known to be temporary.** Observability sharing a process with the API is expected to go away, and this notifier goes with it. The interface is shaped like a Message so the later move to a Message family is mechanical. That is a decision for when the processes split, not now.
- **Connection limits.** Settled as a documentation point, not a design one. The server sets no timeouts of its own: Fastify 5.7.2 defaults to no connection or request timeout, and its 72-second keep-alive applies only between requests. Not tested by holding a real connection open. The rest is on the client and anything in between: idle timeouts are typically 60 to 100 seconds, so the 20-second heartbeat clears them, the response headers are sent immediately (as `/events` does) so a client's headers timeout never fires, and a buffering proxy can hold back heartbeats (nginx needs `proxy_buffering off`), which belongs in deployment notes. A dropped connection is expected of a caller on a phone or a flaky link, and the re-attach route is the answer to it.

### Open

- **How the flow is named.** Three identifiers today (`flowId`, `flowVersionId`, `flowDefHash`). C13 takes the existing three inside the `run` part; naming by name and version instead was considered as a Change here (was C14) but not scheduled — the real blocker turned out to be flow versioning, not the naming route. See "Naming a flow by name and version" in `INITIATIVE.md`.

### What actually landed

Matches the discussion, with the deviations below.

- **The request.** `POST /api/runs` dispatches on a multipart body, and the JSON request is unchanged, moved into its own function. The route body only dispatches. The work is in `routes/runs/inline/`: `read-inline-run-parts` (reads the parts, separates `run`, rejects a missing or duplicate part), `parse-inline-run` (validates the `run` JSON), `store-inline-inputs` (stores each input, returns the param map, separates a bad part from a storage failure), `inline-part` (chooses how a part is stored from its content type alone) and `start-inline-run` (sequences them and maps each failure to a status before any stream begins).
- **The stream.** `stream-run` writes `accepted`, a heartbeat every 20 seconds, and one of `completed` (`{ ok: true, outputs }`, the outputs route's shape), `failed` (`{ ok: false, error }`) or `timeout` (`{ runId }`). Headers are flushed immediately. `GET /api/runs/:runId/stream` uses the same function, 404s an unknown run, and answers a finished run's `completed` straight away.
- **Finish detection.** `RunService.waitForRun` registers a waiter, reads the run's status, and only then waits for the notifier or the timeout, so a run that settles between the two is not missed. `SqlRunProjectionSink` reports through `RunSettledPublisherPort` after its terminal write, and an in-memory notifier in `packages/adapters` implements both sides. Both profiles create one and give the publisher to observability and the waiter to `RunService`. The wait timeout defaults to 10 minutes and the route takes it as an option; it is not a server setting yet.
- **Inputs.** `ArtifactService.storeInputArtifact` stores a part without curating it. `createArtifact` and it share a private save.
- **Deviation: a part with no `Content-Type` is treated as `text/plain`, not rejected.** The multipart parser fills in `text/plain` when a part sends none and does not expose the raw headers, so an unlabeled part cannot be told from a labeled text one. Rejecting it would mean bypassing the plugin every other multipart route uses. The param type check still catches unlabeled audio sent to an audio param, which is the case that mattered.
- **Deviation: any error `requestRun` throws is a 400.** Its errors cannot be told apart, and the ones a caller can cause (an undeclared param, a wrong type, a missing artifact) are the common ones.
- **Checked live** against the distributed deployment (API and worker in separate containers): a multipart request with a text param streamed `accepted` then `completed`, the output's hash matched the run's stored output and its bytes came back through the content route, the input was stored non-curated, a re-attach returned `completed` at once, and the 400 and 404 cases behaved as designed.
- **Found live, and fixed here: a denied run never finished.** A run started without a param the flow declares is refused by the engine with `run.denied`, which nothing recorded, so the run stayed `requested` forever and its stream could only end in `timeout`. The JSON request had the same hang. `SqlRunProjectionSink` now stores a denied run as `failed`, which also settles the wait immediately, and this holds for all five reasons the engine denies a run. The reason text is still not stored, so a caller sees only "Run failed"; that gap is in `docs/todo.md`.
- **Deployment note.** A proxy that buffers responses can hold back the heartbeats and the messages. Behind nginx, `proxy_buffering off` is needed for these routes.
- **Deliberately not done.** Cancelling the wait when the client disconnects (the waiter is dropped when the run settles or the timeout fires), a wait timeout as a server setting, progress messages, and fixing the un-curate hazard.

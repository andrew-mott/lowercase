# Voice Pipeline — Arc A7: Results out (Changes C10–C12)

**Previous:** [Binary uploads](./binary-uploads.md) (Changes C8–C9)

Part of the [`INITIATIVE.md`](../INITIATIVE.md) Change log, split out to keep that doc scannable. This arc lets a caller get a flow's result back: the flow says what its result is, a route returns a finished run's outputs, and binary results can be read as raw bytes.

**Not in this arc:** starting a run from inline data and waiting for it (A8), and using a whole step output as another step's input (C16).

## Change C10 - Flow outputs

### Discussion

Looked at the flow definition, ref analysis and the run projection to see what a flow output can be.

- **`outputs` is an untyped stub.** `FlowDefinition.outputs` is `Record<string, unknown>` in both the type and the schema. Nothing reads it and no example or doc flow uses it, so it can be defined without migrating anything.
- **The hashes a result needs are already recorded.** A run's step projection stores each step's `outputHash` and `exportHashes`. A flow's result can be worked out when it is read, from the flow definition plus those hashes, so the engine, the events and the worker do not change. The route that does the lookup is C11.
- **Both ref forms already parse.** `steps.X.output` and `steps.X.exports.NAME` go through the existing ref parser and binder. Using a whole output as a _step's_ input is C16 because it needs the worker to check a content type it cannot know statically. Declaring one as a flow output involves no worker, and the stored artifact already carries its content type, so C10 supports both forms.
- **Settled: an output is an object holding a `payload`.** `{ "payload": "{{steps.tts.output}}" }`. The field is `payload`, not `ref`, so that a later output can be a JSON structure with references inside it, built from several step results. Params and exports are objects already, and it leaves room for a `description` or an asserted type.
- **Settled: C10 accepts only a whole-value reference as the payload.** The schema leaves `payload` open, and analysis reports a problem for anything other than a single `{{...}}` that is the entire value. Composition is deferred, but the shape does not have to change for it. A binary result can only ever be the whole-value form anyway, since bytes cannot be embedded in JSON.
- **Settled: no declared type.** The result's content type is read from the stored artifact when it is fetched, which is what makes an audio result work without the flow saying so. An asserted type (`audio/*`, reusing the wildcard matcher) is planned for later, not part of C10; the object shape already leaves room for it.
- **Settled: a missing output is reported, not silently dropped.** A branch can skip the step an output points at. The result says the output has no value and why, rather than returning nothing for it, so a caller can tell a skipped output from a mistake. The flow does not mark outputs optional. Not `null` (a later payload may be a JSON structure, and `null` is a legitimate JSON value) and not an absent field (indistinguishable from a typo in the name, and it carries no reason). Each declared output gets a tagged result in the repo's `{ ok, ... }` style: `{ ok: true, value: { hash } }` or `{ ok: false, error: { reason } }`, with `reason` being `"not-produced"` or `"step-failed"`. C10 computes this; C11 turns the hash into content type and bytes and decides the exact response shape.
- **What the projection can tell us.** The run projection only handles `step.started`, `step.completed`/`step.failed` and `step.reused`, with step statuses `started`, `success` and `failure`. A step that never started has no record, so "skipped by a branch" and "not reached yet" look the same. Settled: use the run's status to separate them instead of adding a skipped state to the engine. On a completed run an output with no value can only be a skipped branch (`not-produced`); a step with a failure status is `step-failed`. On a run still in progress, C11 refuses to return results. An explicit skipped step state would be a separate engine change and is left as a possible later refinement.
- **Validation has a gap to fill.** The current ref checks assume the ref sits inside a step: `validateRefTargetStep` compares against the referring step's `stepId` for reachability. An output has no referring step. What has to hold instead: the step exists, an export is declared on it, and a whole `output` comes from a step that produces one (`http` or `httpjson`, not `branch`, `parallel` or `join`).

### What actually landed

Matches the discussion, with one addition found while building: `RunService` refuses a run only for a whitelist of problem types, so the two new output problems had to be added to it. Without that, a flow with a bad output was accepted at request time and failed later in the engine, after its run row existed.

- **Types and schema.** `FlowOutputDefinition` (`{ payload: string }`) replaces the untyped stub, and `FlowSchema` validates each output with a strict schema, so a bare string, a missing or non-string payload, and unknown keys are all rejected. The result types are `FlowOutputSuccess` (`{ hash }`), `FlowOutputError` (`{ reason }`) and `FlowOutputResult`, a `Result` of the two.
- **Validation.** `parseOutputPayload` accepts only a single whole-value reference of the form `{{steps.X.output}}` or `{{steps.X.exports.NAME}}`. Surrounding text, two references, `params` or `input` scope, a `| json` transform and any trailing path or index are all rejected. `validateFlowOutputs` then checks the step exists, the export is declared on it, and a whole `output` comes from a step that produces one, using a new `stepHasOutput` beside `stepExports`. There is no reachability check, so an output may point at a step a branch can skip. The two problems are `InvalidFlowOutputPayload`, which carries the payload as written in a field named `payloadDefinition`, and `InvalidFlowOutputTarget` with a reason of `unknown-step`, `undeclared-export` or `no-output`. `analyzeRefs` runs the check, so it applies at run request and in the engine's plan, and `formatProblem` describes both.
- **Result computation.** `resolveFlowOutputs(flow, steps)` is a pure function over the run's recorded steps. Every declared output gets an entry: a failed step gives `step-failed`, a recorded hash gives success, and anything else, including a step with no record, gives `not-produced`. It does not look at the run's status, which C11 does by refusing a run still in progress.
- **Tests.** A new small file each for the schema, payload parsing, output validation, problem formatting, result computation, and the `RunService` refusal.
- **Deliberately not done.** The route that returns results (C11), reading bytes (C12), asserted output types, composite payloads, payloads in `params` or `input` scope, and an explicit skipped-step state in the engine.

# Worker/Tool Extensibility Model — Research Toward a Future ADR

## Purpose

This is pre-ADR research, not a decision record. Referenced from `docs/initiatives/architecture-boundaries/INITIATIVE.md`, not duplicated there. Related to [`package-tier-taxonomy.md`](./package-tier-taxonomy.md) — `packages/tools` was deliberately left unclassified there, pending this doc.

Full discussion trail, including every rejected alternative and the order things were pressure-tested in, lives in [`../arcs/worker-tool-extensibility.md`](../arcs/worker-tool-extensibility.md). This doc distills the settled conclusion and the open threads; it doesn't re-derive the reasoning.

## The core conclusion: there is no tool registry — the worker's protocol surface is the extension mechanism

The starting intuition, held for a long time, was that tools are the extension point and something has to register them: a tool declares a capability, a registry tracks what's available, a step's `tool` field selects an implementation. Every version of that idea — declaring a new named capability with its own contract, or a tool declaring which existing step type's job-event envelope it can consume — was pressure-tested against real justifications (auth/secrets, resource locality, discoverability) and none held up:

- **Secrets/credentials** aren't a registration justification. A step can already carry auth headers to a credentialed endpoint via direct invocation. The real fix for secrets safety (see "Open threads" below) is resolving a `secrets` ref scope at the worker level before dispatch — orthogonal to whether anything is registered.
- **Resource locality** (a tool that needs specific hardware, e.g. GPU-bound local inference) doesn't require a colocated-worker or registered-tool mechanism either. The tool deploys on the hardware; the worker, wherever it runs, reaches out to it over the network. Compute placement is solved by where the _service_ lives, not by the worker knowing about it in advance.

What's left: **the worker owns all infrastructure coupling — the bus, the queue, CAS, ref resolution, lifecycle — and nothing it calls out to needs any of that.** A protocol the worker speaks (`httpjson`, `mcp`) is not a pluggable, third-party-authored thing; it's built into the worker. Whatever's on the other end of a call is just the outside world — an existing HTTP API, an MCP server, written by someone who has never heard of this project.

This matches, rather than changes, how `httpjson`/`mcp` already work today: the worker interprets a step's resolved args and constructs an ordinary protocol call itself (an HTTP request built from `method`/`url`/`headers`/`body`, or an MCP tool invocation); the target never receives "a job event" or anything shaped by this project's internals. The envelope-shape/registration ideas explored earlier in the discussion were never quite accurate descriptions of how the existing tools behave.

**Consequence:** third-party extension of this system = standing up a service that speaks a protocol the worker already supports. No registration step, no code shipped into or loaded by this repo, no plugin system. Extending the _set of protocols_ the worker supports is this project's own work (or a much heavier, separate path — see "running your own worker instance" below); using an existing protocol requires nothing beyond writing a step against it.

A second, heavier path remains real but needs no new design: running your own worker instance, scoped to your own tool(s), colocated with your hardware if needed. This falls out of the existing per-tool-id job queue shape rather than requiring a new mechanism — though it isn't available today as-is, since `InMemoryQueue` is in-process only; it would need a distributed queue adapter first (`swappable-infrastructure` territory).

## Terminology: "tool" is likely dissolving as a concept

"Tool" was conflating two different things — a protocol the worker speaks, and whatever's on the other end of a call — and once those are pulled apart there's nothing left for "tool" to denote on its own. Genuinely open, not resolved: whether "tool" gets retired as vocabulary, gets repurposed for something else (the convenience-step-type layer is the closest remaining candidate), or just quietly stops being load-bearing while staying around informally. Worth deciding before this shape gets written into an ADR, not after.

## Convenience step types are a first-party concern, not a third-party extension mechanism

Some workflow engines ship opinionated step types for specific well-known APIs (a "create a Google Doc" step, an OpenAI step). Those are real and worth having eventually, but they're not a third-party extension path — they're the project's own accumulating library of shortcuts layered on top of the protocols the worker already speaks, added the same way any feature is. This is consistent with flow-definition step types already being closed to third parties, not a new exception to that rule.

**Real cost, worth remembering when deciding whether to build one**: a convenience step buys known-shape richness by having the worker hardcode a specific external API's contract — and that contract can drift as the external API evolves, silently, unless it's actively tracked and the worker is updated to match. A generic protocol step degrades gracefully when the target's shape changes (a missing field fails cleanly); a hardcoded convenience step degrades by going stale until someone notices.

## General principle: the system governs its own behavior toward the outside world, never the outside world's behavior toward it

Retry, timeout, backoff — all of this is the system's own posture toward whatever it calls, never something assumed of or required from the other side. This generalizes past liveness specifically: a plain worker-side timeout (no completion within N seconds → treat as failed) is the settled v1 mechanism for detecting a hung external call, not because heartbeating wouldn't be nicer, but because nothing in this system is entitled to assume a call target will proactively report its own health. A real heartbeat/liveness convention remains a named, legitimate design consideration for later — not foreclosed by this shape, just not required by it.

## What "the worker supports a protocol" actually requires: a response-interpretability floor, not just wire connectivity

`httpjson` is scoped to JSON specifically, confirmed as a deliberate choice, not an incidental limitation: it's the minimum floor of structure the worker needs to turn a response into step outputs, a success/failure signal, and a storable CAS artifact at all. A fully generic, unscoped HTTP transport would lose that floor entirely — arbitrary bytes, unknown content-type, nothing to reliably interpret.

This generalizes into a sharper test than "can the worker send and receive bytes over this protocol": **every protocol the worker supports needs its own version of this interpretability floor**, and protocols differ in how expensive that floor is to establish. MCP carries its own discovery/negotiation (a server can be asked what it offers and what shape it expects); raw HTTP carries none of that — the shape has to come from somewhere else, either the flow author's own knowledge of the target API or a first-party convenience step baking that knowledge in. Worker-side protocol support may eventually need to include using a protocol's own negotiation when one exists, rather than one uniform call-and-interpret shape applied identically to every protocol.

## Open threads, explicitly not resolved

- **How far to open up `httpjson` beyond JSON-only.** Real, named future direction — genuinely undecided how flexible the response shape should become, what (if anything) validates it, and how storage adapts if the floor described above gets pushed further out.
- **The secrets-safety boundary** (`docs/todo.md`) — now substantially settled, not just unblocked:
  - **Two distinct leak surfaces, not one.** (1) Our own resolved step inputs leaking into events/replay — solved by resolving a `secrets` ref scope at the worker level, using the real value only to build the outbound call, and emitting a redacted/placeholder version onto the bus; deterministic and complete, since the worker already privately holds the resolved value to build its own request regardless. (`env`/`input`, the two other still-unimplemented ref scopes in `parse-references.ts`, are unrelated aspirational stubs from earlier thinking about this same problem, not real precedent to build on.) (2) Arbitrary third-party response content leaking into CAS — confirmed as _current, real_ behavior, not hypothetical: `packages/tools/src/httpjson/httpjson.tool.ts` stores the entire response (headers, body, status) as a step's raw output unconditionally, regardless of `exports`. Not solvable by detection (no ref points at "the secret" in someone else's response; heuristic secret-scanning is a different, much larger, not-worth-building-now problem). Solved instead by narrowing capture: **response headers are not stored by default at all** — no whitelist, no blacklist (both rejected: blacklist fails open against arbitrary/bespoke header vocabulary; whitelist-as-default has the same failure mode one step removed). This extends the same discipline `exports` already applies to the response body to headers too. A step-definition-level opt-in to keep specific headers on the raw output (distinct from a full `exports` declaration) is a named, deliberately-deferred future extension, left to evolve from real observed need rather than designed now.
  - **Storage mechanism decided:** an encrypted DB column with an externally-held key (a plain environment variable is a legitimate v1 key source, not a shortcut), not the OS keychain — even though keychain would fit `apps/desktop` well via Electron's `safeStorage`, it has no real story for a headless standalone server, and a mechanism that works uniformly across both deployment targets was preferred over per-target adapters. Natural implementation shape once built: a `SecretsPort` behind the same ports/adapters convention already used everywhere else in this codebase.
  - **Multi-worker credential distribution** — a real future scaling question, not a live concern today. Named shapes for later: a centralized secrets service each worker queries on demand, every worker holding all credentials (simplest, worst blast radius), or secrets partitioned by which capabilities a given worker runs.
  - **Explicitly out of scope for this research pass, named as its own dedicated future push:** actually building the `SecretsPort`/adapter, the `secrets` ref scope's resolution, and the header-capture change. This doc settles the shape; it doesn't implement it.
  - **Longer-term UX idea, deferred:** OAuth flows for connecting directly to third-party services (OpenAI, Google, etc.) inside the app, instead of pasting a raw API key. A real v2+ direction on top of the storage mechanism above, not designed here.
- **Data transforms** — floated as possibly not a worker-dispatched capability at all, possibly an engine-side extension point that never round-trips through a worker. Independently converges with `docs/todo.md`'s existing "compose" note and the `resolve-branch-value.effect.ts` precedent ("not every CAS-touching operation is a worker capability") — two separate lines of reasoning landing in the same place, worth taking seriously, but genuinely unresolved and deliberately kept as its own discussion.
- **Concurrency/rate-limiting** for tools with real capacity limits (a local LLM that can only handle one request at a time). Ties to `packages/limiter` (already known incomplete elsewhere in this codebase). Tentative shape if pursued: limits configured by endpoint/transport pattern rather than by a registered tool identity, since no such identity exists under this model.
- **stdio/terminal transport support** — wanted, not designed. Unclear how a transport-agnostic worker model extends to local/subprocess tools.
- **Streaming** — a founding-vision goal, motivated by a real earlier project (a local STT → LLM → TTS pipeline over Redis/MinIO) where streaming would have materially cut latency. Explicitly longer-term, not addressed in this pass.
- **Worker-level liveness** — whether the engine can tell if the worker itself is hung, distinct from tool-level liveness. Named as a real, currently-missing layer; not explored.
- **A tool/service-author SDK** — originally imagined as fairly substantial (event-parsing helpers, lifecycle conventions), its scope narrowed considerably once it became clear a target service needs zero awareness of this project to act as a valid protocol endpoint. What's left is optional convenience (a heartbeat/status convention if liveness tracking is ever wanted, maybe response-shape helpers) — not load-bearing, not designed.

# Package-Tier Taxonomy — Research Toward a Future ADR

## Purpose

This is pre-ADR research, not a decision record. It carries forward and reorganizes a taxonomy that was already worked out across an earlier, long discussion (prompted by designing Artifacts mode's write path, prior to this initiative existing) and has lived as a single growing entry in `docs/todo.md`. This doc becomes the live home for that thread going forward; `docs/todo.md`'s own entry should eventually shrink to a pointer here rather than carry the full text in two places.

Referenced from `docs/initiatives/architecture-boundaries/INITIATIVE.md`, not duplicated there.

## The problem

The goal is clear enough package boundaries that new code — AI-authored or not — has an obvious answer for "which package does this go in." This predates AI-assisted work on the repo (getting boundaries right already mattered), but matters more now specifically because inconsistent/undocumented boundaries make it harder for AI-authored code to land in the right place without guessing.

The taxonomy replaces an earlier `use-cases` → `workflows`/`domains` reorg idea (folded forward from a since-deleted `ARCHITECTURE-NEXT.md`) — those names never actually sat right and are superseded, not just renamed.

## Tiers, current state

**Already correct, no gap:**

- **`packages/runtime`** (wires services + everything else — separately known to need its own consolidation, see the `runtime-storage-consolidation` initiative) and **`apps/*`** (thin callers of the bundled services, decoupled/swappable — a CLI and an HTTP server can share the same service set).

### `apps/*` naming — one real gap found, plus a forward-looking convention

**`apps/web-app` → `apps/workbench`.** The one inconsistency in an otherwise-clean naming set: `cli`, `desktop`, `http-server` all name what they are without repeating "app" — `web-app` is the outlier, redundant against its own parent directory (`apps/web-app`). "Workbench" isn't invented for this doc — it's already the real, live product name throughout the actual source (`pages/Workbench.tsx`, a whole `components/workbench/` directory, `dock-context.ts`, `dock-persistence.ts`), the same "recover, don't invent" move already made for `components`. Deliberately bare, not `web-workbench`: per the dual-deployment-target setup, the same UI is reused inside the Electron shell for `apps/desktop` (zero extra tabs) — a "web-" qualifier would only be true for one of its two real targets.

**Forward-looking convention, not yet needed**: if a `components`-tier piece is ever extracted into its own standalone deployable app (e.g. `engine`), it belongs in `apps/<component-name>` — plain, matching the sibling pattern, no "-service" suffix. `apps/engine` and `packages/components/engine` sharing a base name isn't a collision (different parent directories, different npm package names); it's the predictable, repeatable shape — a thin composition root in `apps/` wrapping the real logic that stays in `packages/components/`.

### `packages/ports` — what "Port" actually means here

**Not strictly hexagonal, and that's fine — it's Dependency Inversion Principle applied more broadly.** The defining property of a port was never "this must actually get swapped for different infrastructure someday" — it's narrower and more mechanical than that: **a consumer depends only on the interface; only the composition root (`packages/runtime`) ever imports both the interface and its concrete implementation together.** Classic hexagonal swappability is just one payoff of that structural fact — the one the pattern happens to be named after. Two other real payoffs of the exact same property, deliberately used in this codebase:

- **Build-graph decoupling.** Turbo's build cache is per-package. If `services` depends only on `WorkerPort`, a change inside `packages/worker`'s internals doesn't invalidate `services`'s build cache — only `worker` itself and `runtime` (which imports both) need to rebuild. This doesn't shrink the _total_ build — `runtime` still rebuilds on any change, since it's the one place everything gets wired together — it shrinks which packages _between_ the interface and `runtime` are forced to rebuild for a given change.
- **Test seams.** A consumer typed against `WorkerPort` can be handed any object shaped like one in a test, without touching the real implementation.

Neither of these requires a second real implementation to ever exist. So: an interface earns the `Port` suffix by being genuinely depended-on-instead-of-the-concretion — whether or not it's ever swapped — not by some stricter hexagonal-infrastructure test.

**The actual litmus test for a live port**: is it used as a type annotation somewhere real, outside `packages/ports` itself (a dependency field, a function parameter, a factory's return type) — whether satisfied via a literal `implements` or structurally (an object literal/factory return typed to match)? Checked empirically across the repo: ports like `WorkerPort`, `EnginePort`, `ServicesPort`, `LimiterPort` show up constantly as dependency-field types in `packages/services`/`packages/runtime` — exactly the "consumer depends on the shape, not the concretion" pattern. By contrast, several `*Port` interfaces (`ControllerPort`, `ClientApiPort`, `StreamPort`, `StepRunnerPort`, `EngineTelemetryPort`, `FlowParserPort`, `RunEmitterPort`, the `Rm*` family, the `*EmitterPort` family) show zero usage anywhere outside their own definition — not dead in principle, just genuinely unreferenced leftovers from earlier design iterations (several line up with already-known-dead packages: `controller`, `scheduler`). Real, but a maintainability/cleanup matter, not a taxonomy question — tracked as a to-do, not part of this decision.

**Supporting types that ride along with ports (e.g. `ToolDeps` in `tools/tool-context.ts`, a dependency bag built from `ConsumerStreamPort`/`ProducerStreamPort`/`EmitterFactoryPort`) legitimately live in `packages/ports` too**, for the same structural reason `LimiterDeps` couldn't live in `types` — a type composed of port references can't live below `ports` in the graph. They're not ports themselves (nothing implements them; they're not meant to be), and shouldn't carry the `Port` suffix or `.port.ts` naming, but splitting them into a separate package isn't warranted either — anyone who needs `ToolDeps` already needs `packages/ports` anyway (same coupling logic as the `types` tier's fourth test), so centralizing costs nothing and a dedicated "interfaces" package would just fragment one coherent home for "things implemented by a class" without buying anything.

### `packages/types` — placement rule

**Purpose, stated precisely:** `packages/types` exists so a consumer can get a shape without also importing the package or library that produces it — e.g. an event payload's type without needing to import `zod`. It's a pure vocabulary layer, not a catch-all for "anything shared." The general invariant: a type used within one package stays local to it; a type genuinely shared across packages moves here — but "shared across packages" turns out to need real tests, not just a headcount of importers, since a package can legitimately export its own type without that type belonging in `types`.

Verified empirically against the full cross-package `@lcase/*` import graph (776 import sites) — no violations found. **Caveat found later, while checking `run-history`**: that initial scan didn't exclude `dist/` output, and at least one package (`run-history`) has stale compiled `.d.ts` files for source that's since been deleted — so the raw 776 count is inflated by build artifacts, not all real current source. Doesn't change the conclusion: every specific example actually cited below (`LimiterDeps`, `RuntimeConfig`, `Services`, `PrismaClient`, `StepArgs`) was independently verified by reading real `src/` files directly, not by trusting the raw count. The invariant holds in practice, not just in intent. What surfaced instead were the real edge cases below, resolved into four tests, applied in order:

1. **Cycle test (mechanical, disqualifying).** `types` sits at the bottom of the dependency graph — `ports` depends on `types`, never the reverse (`CLAUDE.md`'s layering). If a type's own definition needs to import something that would invert that (a port interface, a class from anywhere above `types`), it categorically cannot live in `types`. Examples: `LimiterDeps` (references `EventBusPort`/`EmitterFactoryPort` from `ports`), `RuntimeConfig`, `Services` (both reference concrete service/adapter classes).
2. **Boundary test (mechanical, disqualifying).** No cycle risk, but the type would leak an implementation-specific concern into a layer meant to stay implementation-agnostic. `PrismaClient` (from `packages/db-prisma`, imported by `adapters`) is the case: `db-prisma` doesn't depend on `types`, so nothing would cycle — but `CLAUDE.md` already states `types` is "intentionally Prisma-free," because the whole point of the ports/adapters split is a swappable storage backend (see the `swappable-infrastructure` initiative), and letting a Prisma-generated type into the shared vocabulary layer would tie every consumer of `types` — including the frontend — to one specific storage implementation. Different reason from the cycle test, same verdict.
3. **Ownership test (judgment, only reached if 1 and 2 don't disqualify it).** Is this package's whole reason to exist defining this exact shape? If so, it stays even though it could mechanically move. `StepArgs` in `packages/specs`: `specs` only depends on `types`, so nothing forces `StepArgs` to stay there — but `specs`'s entire job is being the authoritative source for flow-definition shape, so moving `StepArgs` out would split the schema library from the type it's the schema for.
4. **Coupling test (judgment, also only reached if 1 and 2 don't disqualify it).** Does any real consumer need the type without already needing the rest of the package for something else? If every actual use already depends on the package anyway, centralizing is pure ceremony — leave it. If a consumer needs the type but has no other reason to depend on the package, that's the actual signal to move it out. Checked against `LimiterDeps` directly: every file in `packages/runtime` that imports `LimiterDeps` (`registries/limiter.registry.ts`, `wire-functions/create-limiter.ts`) sits in a package that elsewhere (`registries/limiter.registry.ts` itself, `runtime.ts`) also imports the real `Limiter`/`ConcurrencyLimiter` class from `@lcase/limiter` — nobody gets the type "for free." Confirms it should stay put.

Tests 3 and 4 aren't redundant with each other — a type can pass ownership and fail coupling, or the reverse; both get checked once 1 and 2 are cleared.

### `packages/specs` — scope, and whether it should split

**History, for context.** `specs` predates this repo's later types/schema split. It started as a schema-first design (Zod schema, type inferred via `z.infer`) — an evolution of an even earlier standalone experiment (a different, prior repo) around a types/JSON-definition package. It migrated partway to a types-first design (hand-written types, Zod manually kept in conformance via `satisfies z.ZodType<X>`) but never got the physical package split that `packages/events` later did: pure event _types_ live in `packages/types`, while `packages/events` holds the Zod schemas/emitter helpers that implement them — confirmed as a real, working win (`web-app` pulls 62 type imports from `packages/types` and **zero** imports from `packages/events` — it never needs the schema package at all). `specs` still bundles both types and schemas together in one package.

**Whether to apply the same split here: checked empirically, not assumed.** Across all 10 cross-package import sites of `@lcase/specs` in the repo, only **one** — `packages/engine/src/resolve.ts`'s `import type { StepArgs }` — is a pure type-only import. Every other consumer (`observability`, `events` ×2, `engine`'s second import, `services` ×3, `web-app`, `cli`) imports a real schema or the `parseFlow` function — genuine runtime need, not an accident of packaging. Notably, `web-app` itself needs `parseFlow` for live flow-draft validation, so unlike the `events` case, splitting wouldn't reduce the frontend's own zod exposure at all — it already has a real runtime dependency on the parser.

**Decision: don't split `specs` as part of this initiative.** The justification that clearly earned the split for `events` barely applies here (9 of 10 consumers need the runtime value, not just the shape). There's also a timing reason beyond the thin justification: `json-schema-migration` (initiative 3, right after this one) is specifically about moving `specs`'/`events`' schemas off Zod onto JSON Schema/AJV — which can generate types _from_ the schema, a different relationship than today's "Zod manually conforms to hand-written types." Splitting the package now risks doing structural work that initiative would reshape anyway, not just re-implement.

**Confirmed dead code, safe to delete outright:** `engine.types.ts` (`StatusSchema`, `RunStepContextSchema`, `RunContextSchema`, `Status`) and `result.types.ts` (`TestResultSchema`, `TestResult`) — every export from both files checked out to zero real usage anywhere in the repo (a couple of near-hits were false positives: an unrelated same-named `RunContextSchema` defined independently in `packages/events`, and `Status` matches were just JSX label text/comments, not imports). `result.types.ts` is additionally unreachable via the package's own public API — never re-exported from `index.ts`. Not a taxonomy question, just cleanup — small, but worth doing since it's fully confirmed, not speculative.

**Durable convention surfaced along the way, worth keeping**: a Zod schema written with a trailing `satisfies z.ZodType<X>` is the modern, types-first pattern this package is converging on; one written the old schema-first way (`z.infer<typeof Schema>`, no `satisfies`) is legacy. This lined up exactly with which files turned out to be live vs. dead — every current schema file in `specs` uses `satisfies`; both dead files use neither. Useful as a fast "is this file current" signal for `specs` specifically, and relevant again once the real `json-schema-migration` work starts.

### `functional core` — definition, membership test, and organization

**Name settled: "functional core"**, from the well-known "functional core, imperative shell" pattern (Gary Bernhardt) — not a DDD term, and deliberately not adopted as a wholesale methodology, just borrowed for the one concept it names precisely: a pure, side-effect-free layer wrapped by an imperative shell (`services`/Operations) that handles orchestration and I/O. Chosen over `use-cases`/`workflows` (both explicitly rejected, never sat right) and over bare `core` (too generic, would risk becoming a catch-all the way `types` deliberately isn't). `packages/flow-analysis` and `packages/json-ref-binder` are the working precedent, just not yet formally recognized as "the tier."

**Membership test: zero ports, zero I/O.** Safe for services, components, and the frontend to import directly, precisely because nothing about it can vary by environment or need mocking. This is a hard, binary test, not a judgment call — and it's exactly why the "Operations" tier exists as a separate thing: something that needs even one port to do its job is not functional core, no matter how small or pure-feeling its own logic is otherwise. Operations was invented specifically to catch pieces that could otherwise masquerade as functional core without qualifying. **Real finding, not just a naming gap:** today's `packages/use-cases/*` (`run-flow`, `run-history`) does not actually qualify as functional core either — per `CLAUDE.md`, it depends on ports (`runFlow()` emits via the event bus), so it's orchestration wearing a use-case-shaped name. Its actual contents likely belong in `services`, not here.

**Naming convention for individual pieces inside it: noun-headed, not verb-object.** `flow-analysis` and `json-ref-binder` both read cleanly because they're headed by an agent-noun (`analysis`, `binder`) describing _what the subsystem is_, with the domain word as a modifier in front of it — `<domain-word>-<agent-noun>`. Contrast with `run-flow`/`run-history` (a different, non-functional-core tier, but the same shape of mistake): a bare verb-object phrase with no noun head, genuinely ambiguous between "the action of running a flow" and "the flow of a run." This generalizes past this one tier, but it's the sharpest test available here since both good and bad examples already exist side by side in this codebase.

**Grouping/granularity convention: one package per cohesive sub-problem, not one per function and not a single mega-bundle.** `flow-analysis` bundles eight files because they're all one sub-problem (structural analysis of a flow definition); `json-ref-binder` is separate because ref-binding is a genuinely distinct sub-problem, even though related. Matches an already-flagged future case in `docs/todo.md`: the ref-hash-resolution logic duplicated across the engine/worker/UI is slated to become its _own_ new functional-core package, not folded into `json-ref-binder` — because it's a distinct sub-problem, not because of a function-count threshold.

**Physical organization: a real subfolder, `packages/functional-core/*`** — not just a mental category, though it started as one. Confirmed mechanically cheap, not just organizationally nice: `pnpm-workspace.yaml` already lists `packages/use-cases/*` alongside `packages/*`, so adding `packages/functional-core/*` is the same already-proven pattern. Every cross-package import in the repo goes through `@lcase/<name>` (confirmed against the full 776-site import scan run earlier for the `types` tier) — never a relative path crossing package boundaries — so moving a package's directory requires no import-statement changes anywhere, and the npm package name (`@lcase/flow-analysis`) stays exactly as-is; directory location and package name are fully independent. The actual move is `git mv packages/<name> packages/functional-core/<name>` plus the one workspace-glob line, per package. Not a mandate to subfolder every tier — selective, for tiers (like this one, and likely "component pieces" later once it's named) that actually have multiple related members and benefit from the grouping.

### `application services` (formerly "services") and Operations

**Name change: `packages/services` → "application services", package `@lcase/app-services` for short.** Driven by the same collision risk that shaped `components`' definition: "services" alone reads ambiguously in a codebase whose whole architecture is modeled on event-driven, potentially-standalone pieces — a reader could reasonably expect "services" to mean _those_, not the in-process application façade that never touches them. `components` itself keeps its name unchanged (see above) precisely because it's deliberately deployment-agnostic and doesn't want to claim "distributed" or "microservices" or any other topology commitment it hasn't earned yet — but the word "services" still evokes that world generally, so the rename happens on this side instead. Class names (`RunService`, `FlowService`, ...) and their `XxxServicePort` interfaces are unaffected — only the package/npm name changes. Checked the actual footprint before treating this as free: only 3 `package.json` dependency declarations (`apps/http-server`, `packages/runtime`, `packages/services` itself) and 9 source/test files import `@lcase/services` directly; everything else reaches it indirectly through `packages/runtime`'s bundled `ServicesPort`. Small, bounded rename, not a sprawling one.

**A middle tier, name settled: "Operations."** Small, focused units that need exactly one port to do one piece of work, but aren't meant to be part of the application-facing surface (not bundled into `runtime`, not called directly by an app). Deliberately a different word from `packages/engine/src/effects/`'s "Effects" — that term already carries specific, load-bearing meaning in this codebase (the reducer/planner/effect trio) and reusing it here would blur it, not generalize it. "Operations" was chosen partly because it's an established hexagonal/DDD term, matching a general preference to lean on existing conventions where they fit.

**The "exactly one port" restriction, justified from first principles, not just asserted.** Two independent reasons, not one:

1. **Orchestration boundary.** Needing multiple ports at once means deciding the relationship/sequence between independent external capabilities — and that decision-making _is_ what orchestration means. One port can't cross that line structurally; there's nothing to sequence against.
2. **Reuse-cost scaling.** Every additional required port is one more thing a future caller must already have wired before it can reuse the logic — directly undermining the reason Operations exist at all (portable building blocks). One port is the minimum cost above `functional core`'s zero, keeping the reuse/test surface as small as possible while still allowing real (non-pure) work.

**Who wires an Operation's dependencies — confirmed via two independent, unrelated examples in the codebase, not just reasoned abstractly.** `packages/runtime` is the one true wiring root for everything, including Services' own dependencies — a Service isn't an independent wiring authority, it's relaying a slice of what `runtime` already gave it. An Operation is never wired separately by `runtime`; whoever calls it (a service, `engine`, `worker`) must already hold whatever port it needs, and just threads that dependency through. Confirmed twice: `RunService`'s constructor already takes `EmitterFactoryPort` as one of its own injected deps and passes it straight through when calling `runFlow()`; independently, `packages/engine/src/registries/effect.registry.ts`'s `wireEffectHandlers(deps)` does the identical thing for the engine's own effect functions (`emitFlowAnalyzedFx`, `getFlowDefFx`, etc.), closing over `EffectHandlerDeps` once and handing it to each Operation-shaped function it wraps. Two unrelated pieces of code converging on the same pattern without coordinating is stronger evidence than either alone. A caller entirely outside the `runtime`-wired tree (e.g. a future standalone-app component with its own composition root) would need to supply the port itself from wherever its own composition happens — which is exactly what makes Operations portable rather than a gap to fill later.

**The "who's the caller" test, confirmed against real code, then corrected for a precision gap it surfaced.** Original phrasing — surface-facing (apps/`runtime` call it directly) is a Service; internal-building-block (only ever called from inside a service/engine/worker) is an Operation — used "lives under `apps/`" as a proxy for the real test, and that proxy holds only by coincidence: every app _today_ (`http-server`, `cli`) happens to be request/response shaped. **Corrected test: does it orchestrate one bounded, external, request/response-shaped interaction** (an HTTP request, a CLI invocation — something with a discrete start and end triggered by an outside actor)? That's what "application services" actually means in DDD/Clean Architecture terms — not "used by anything that happens to live in `apps/`." Surfaced by asking whether a future `apps/engine` (a `components`-tier piece extracted into its own deployable, per the `apps/*` convention above) would need `application services` — it wouldn't, even with its own minimal HTTP wrapper for something like a health/control endpoint, because internally it's still long-lived and event-driven, not request/response shaped. Being "an app" was never the actual test; a component being extractable into one doesn't change what it needs internally. **The monolith's `components` are semi-deliberately designed to be peeled away and moved out-of-process, if the runtime/system ever supports it — but "peelable" describes the event-bus boundary already in place, not a reason to add a new dependency on `application services` now.** If a peeled-away component ever needed its own small request/response surface, that would be its own local, separately-scoped service-shaped code — not a reason to reach into today's `packages/app-services`, which stays scoped to this monolith's specific use cases (Run, Flow, Sim, Eval...), not a universal layer every future app must plug into. Checked directly:

- `runFlow()` (`packages/use-cases/run-flow`) — needs exactly one port (`EmitterFactoryPort`), called from exactly one place in the entire repo (inside `RunService`), never by an app. Textbook Operation.
- `EvalService` — called directly by `apps/http-server/src/routes/evals/*.ts`. Genuinely application-facing. Clean Service.
- **Correction to an earlier guess in this doc**: `run-history` was grouped with `run-flow` and assumed to "likely fold into services." Checked directly — its live exports (`updateRunIndex`, `initRunIndex`, `hasRunId`) have **zero port imports anywhere**; they're pure functions folding events into an in-memory index. That's `functional core`, not Services or Operations at all. The guess was right for `run-flow`, wrong for `run-history` — the two were never one uniform thing.
- **`create-fork-spec.ts`'s `startForkedSim()`** needs two ports at once (`EmitterFactoryPort` + `ArtifactsPort`) — a live example of the "one port" rule correctly flagging real orchestration (using artifacts data, then emitting based on it) that should decompose into single-port pieces rather than being accepted as one Operation. `run-flow` as a whole package mixes three different shapes under one roof (a pure function, a clean one-port Operation, and this two-port orchestration function) — not a pattern to treat as precedent, just an artifact of predating this taxonomy.

**Open, deliberately not decided: class-based Services vs. a functional/closures-based equivalent.** Not a live plan to change anything — captured because real trade-offs surfaced while discussing it, worth having on record:

- **Not a difference**: testability. Both approaches take `deps` as a parameter (constructor vs. factory argument); mocking is identical either way.
- **Real difference 1 — `this`-binding safety.** A closure has `deps` baked in lexically; a method can be handed around as a bare reference (passed to a callback, registered as an event handler) and still work. A class method needs `.bind()` or an arrow class field to be equally safe. Not biting today (every call site is `obj.method()` inline), more likely to matter in `components`-adjacent, event-driven code than in `services` as currently used.
- **Real difference 2 — genuine runtime encapsulation.** TS `private` is compile-time only (`(obj as any).field` still reaches it); a variable local to a factory function that's never returned is truly inaccessible, no cast can reach it.
- **Two different functional shapes, not one** — a distinction worth keeping precise: an _inline factory_ (`createEvalService(deps) => ({ method: ... })`, methods defined directly) has the same size/growth characteristics as a class, no repetition tax. A _registry-of-external-functions_ factory (the shape `wireEffectHandlers` actually is — methods defined as independent functions elsewhere, wired together in one place) pays a per-line wrapper cost in exchange for real composability: each piece independently testable/reusable, and growing the surface is additive (new function, one new line) rather than an ever-growing class/factory body. `wireEffectHandlers` was flagged as repetitive, but that repetition is specific to the registry shape, not an inherent cost of "functional" in general.

### `components` — definition, membership test, and organization

**Name settled: "components"** — not invented for this doc, recovered from the project's own founding vision. An early README (commit `84637dc`) already used this exact word for this exact idea: "every component, from queues to workers, communicates through events, allowing generic components with swappable infrastructure... modular and extensible, supporting everything from lightweight in-memory execution to distributed setups." That original text lumps queues in as a component too — the one real correction from the taxonomy work already done in this doc: `InMemoryQueue` was already confirmed as a clean single-port adapter with no own lifecycle or bus-subscription, so it doesn't qualify under the sharper definition below. Not a contradiction of the founding vision, just the "correcting, not just executing" this initiative exists to do.

**Membership test: three properties**, distilled from months of the underlying distributed-systems/event-driven architecture drawings this whole taxonomy traces back to:

1. **Long-lived, own lifecycle** — a persistent thing, not a one-shot call.
2. **Self-driven by subscribing to the bus** — it decides its own next action by consuming events itself, rather than being invoked synchronously by something else calling a method on it. This is the sharpest line against Operations: an Operation is _called_; a component _listens_.
3. **Not infrastructure** — it embodies real logic about how the system's event flow should behave, not a swappable technology choice sitting behind a port.

**Composability is a consequence of property 2, not a fourth thing to check.** If a component only ever touches its neighbors through `EventBusPort`/queue/whatever port, it structurally doesn't matter whether that port is in-process or over-the-wire — the same reason the `swappable-infrastructure` initiative can even entertain Redis Streams later without touching component internals. A component that reached into another component's internals directly would break this; nothing currently does.

**Name kept as "components," deliberately, even after `services` got renamed to disambiguate against exactly this tier's distributed-systems flavor.** Considered and rejected: renaming `components` to "services" (matching real SOA/microservices vocabulary, arguably more precise than "component" for a long-lived, message-driven, potentially-independently-deployable unit) paired with `application services` for the other tier. Rejected specifically because the architecture is deliberately deployment-agnostic — property 2 already establishes that composability is a consequence, not a commitment, and "services"/"microservices"/"distributed services" all bake in a topology claim (independently deployed, over a network) that isn't true today and may never be true for every component. "Components" makes no such claim either way, which is exactly why it's the more accurate word for something whose deployment shape is intentionally left open. More precise framing surfaced along the way: the system today is **event-driven, structured as a modular monolith** — a real, standard term for one process today with the internal seams of a distributed system, so it stays splittable later without a rewrite. That description, not "microservices," is the accurate one for the present.

**Sub-distinction: critical-path vs. tap.** `engine`, `worker`, `limiter`, and `NodeRouter` are all _in the critical path_ — their event consumption is what makes the next thing in a run happen. `ObservabilityTap` passes all three membership properties (long-lived, self-subscribes to the bus, real fan-out logic) but sits _outside_ the critical path — it taps the same event stream without anything downstream depending on it to advance a run; its output is projections/sinks, not further events that drive execution. Both are legitimately components; this is a real, recognizable variant within the tier, not a sign observability fails the test.

**Data plane vs. control plane — an acknowledged, deliberate gap, not an oversight.** The membership test above governs a component's _data plane_: the actual event flow doing real work. What's currently code-driven rather than event-driven is the _control plane_ — which `ObservabilityTap` sinks are active, starting/stopping a component, any "configure/manage this component" concern. This isn't specific to observability's sinks; it's the same shape of thing as every component's `start()`/`stop()` handles. Consciously deferred early on specifically to avoid inventing that layer before it was needed — not an accidental inconsistency. The named aspiration, not committed or scheduled: an event-driven control plane too (sink registration, start/stop, eventually maybe scaling/routing, all as commands over the bus) — but the membership test itself doesn't need a caveat for this; it's correctly scoped to data-plane behavior, and the control-plane gap is a separate "where I want to go," recorded honestly rather than glossed over.

**Resolves the `packages/artifacts` split** (see "Ambiguous packages" below) without changing that existing finding: it fails the component test on property 3 both ways — the hashing/canonicalization rules are real logic but have zero I/O and no lifecycle (`functional core`, not a component), and `FsArtifactStore` is a single-port translator with no own lifecycle or bus-subscription (infrastructure/adapter, not a component). Neither half was ever a component.

**`packages/tools` is deliberately out of scope here** — its own contract is unsettled; see [`worker-tool-extensibility.md`](./worker-tool-extensibility.md) rather than duplicating that thread in this tier's definition.

**Physical organization: `packages/components/*`**, same mechanical justification as `functional-core` — `pnpm-workspace.yaml` already proves the nested-glob pattern via `packages/use-cases/*`, every cross-package import goes through `@lcase/<name>` (never a relative path), so the move is `git mv packages/<name> packages/components/<name>` plus one workspace-glob line, with npm package names unchanged.

**Confirmed principle, not just assumed:** services can import the pure tier directly, no DI/port needed — a pure function has exactly one correct implementation, so wrapping it in an interface is ceremony with nothing to abstract. (Note: this is _not_ the same claim as "a port only earns its keep when there's a real implementation to swap" — see the `packages/ports` section below, which found that build-graph decoupling and test seams alone justify a port even with a single implementation. The distinction here is different: pure functions have no meaningful _concept_ of a swappable implementation at all, which is why DI doesn't apply to them regardless of payoff.)

### `packages/adapters` — definition, what it may and may not import, and why it stays one package

**Name and origin.** "Adapter" is genuinely generic — the Gang-of-Four Adapter pattern (1994): convert one interface into another a client expects. Older than, and independent of, DDD. Ports-and-Adapters/Hexagonal Architecture (Cockburn, 2005) borrowed the word for a specific _role_: the concrete thing that fills a port at the boundary. Often paired with DDD, not DDD vocabulary itself.

**Membership test: the inverse of `components`.** Implements exactly one port, has no own lifecycle, and doesn't self-subscribe to the bus — it's _called_ synchronously by whoever holds the port, never self-driven. Where `components` required "not infrastructure," adapters _are_ the infrastructure.

**"Infrastructure" is descriptive language here, not an independent test — confirmed by an existing case that would otherwise be excluded.** `InMemoryQueue` does no real I/O at all (no disk, no network — just an in-memory structure), yet it's cleanly an adapter, already correctly classified as such earlier in this doc. So the actual test isn't "does it touch a real external system" — it's the structural one above (port, no lifecycle, not self-driven). Whether the concrete mechanism happens to be SQL, filesystem, or plain in-memory doesn't change whether something _is_ an adapter, only what you'd colloquially call it.

**The "shouldn't do more than infrastructure mechanics" line, made precise by a real, already-flagged violation.** `FsArtifactStore`'s extension-probing (`getBytes` brute-force-trying 4 known extensions in a fixed order) isn't infrastructure mechanics — it's a decision about what a closed `format` enum should mean, dressed up as a filesystem detail. Already flagged for removal in the `artifacts` split (see "Ambiguous packages" below) — moving content-type resolution to a SQL metadata lookup instead of probing. Sharp version of the test: **adapter logic should be entirely about the mechanics of talking to the external system — how to open a file, run a query, call an API — never about what the data means or what to decide.** Anything actually deciding something belongs in `functional core` (if pure) or gets injected via a port from something that does decide.

**What adapters may import:**

- `types`/`ports` — trivially, this is their whole job.
- **`functional core` — allowed, same principle already established for services** ("a pure function has exactly one correct implementation, so wrapping it in an interface is ceremony with nothing to abstract" — never actually scoped to services specifically). Not hypothetical: once `packages/artifacts` splits (hashing/canonicalization → `functional core`), `FsArtifactStore` will _need_ to import that logic to compute hashes before writing bytes. Checked: nothing in `packages/adapters` imports `flow-analysis`/`json-ref-binder` today, so this is new guidance, not a correction.

**What adapters may not import:**

- **Other concrete adapters, directly.** Checked all adapter subdirectories (`run-repository`, `artifact-store`, `queue`, `router`, ...) for cross-references — zero found, already clean, worth keeping that way. If two adapters ever needed to collaborate, the correct path is through a _port_ (injected via constructor, wired by `packages/runtime`), never a direct import of the other's concrete class — importing another adapter directly would couple two independently-swappable technology choices to each other for no reason, exactly what the port abstraction exists to prevent.
- **Operations — no current example, and the direction looks backwards.** Operations consume a port as their one dependency; adapters _are_ the concrete filler for a port. An adapter depending on an Operation would be infrastructure reaching up into a business-logic-shaped layer. Flagged as "no current need, direction looks wrong," not a confirmed hard rule — nothing's tested it either way.

**Physical organization: stays one package, deliberately not subfoldered like `functional core`/`components` — the opposite call, for a real reason, not less rigor.** Those two tiers benefit from splitting because they have broad, independent consumption (services, `engine`, the frontend all reach into `functional core` directly) — separate packages give real turbo build-cache decoupling, since a change to one doesn't force unrelated consumers to rebuild. Adapters have no such pressure: confirmed empirically, only `packages/runtime` imports a concrete adapter in real application code (`apps/http-server`'s references are all in `tests/`, constructing real adapters directly for integration tests — a separate, legitimate pattern, not application wiring). `runtime`, being the composition root, already rebuilds on any change anywhere in the graph regardless of adapter packaging granularity — there's no consumer to protect from an unrelated adapter's churn. The existing per-adapter subdirectories inside `packages/adapters/src` (`run-repository/`, `artifact-store/`, `router/`, ...) already do the real organizational job; a package split here would add ceremony with nothing to decouple.

## Ambiguous packages, sorted so far (checked against actual code, not guessed)

- **`NodeRouter`** (`packages/adapters/src/router/node.router.ts`) — currently filed as an adapter (`implements RouterPort`), but confirmed against the `components` tier's test (see above): own `start()`/`stop()`, self-subscribes to the bus, and depends on three things at once (`EventBusPort`, `QueuePort`, `EmitterFactory`) to do real multi-step work — the same critical-path, bus-reactive, own-lifecycle shape as `engine`/`worker`/`limiter`, not a thin single-port translator like `PrismaArtifactRepository`. Implementing a port doesn't disqualify it from being a component — `engine`/`worker` also depend on plenty of ports while staying components. Belongs in `packages/components/`, not `adapters`.
- **`packages/observability`** (`ObservabilityTap` + sinks) — confirmed as a component, specifically the tap/side-observer variant (see `components` tier above): self-subscribes to the bus, real internal fan-out logic to sinks, but sits outside the critical path rather than in it like `NodeRouter`. Its sink-registration mechanism is also the concrete case that surfaced the tier's data-plane/control-plane distinction — sinks are wired in code today, not over events, a deliberate scope cut rather than an oversight.
- **Queues** (`InMemoryQueue`) — genuinely fine as-is, a clean single-port adapter, no ambiguity. (The project's original README language did lump queues in as "components" too — see the `components` tier above for why that's since been corrected.)
- **`packages/artifacts`** — confirmed to split across two tiers, neither of which is `components` (see the `components` tier's resolution above): its actual job (hashing-algorithm rules, canonical JSON sorting for deterministic hashes) is pure logic, no I/O — `functional core`, not `components` or `adapters`. Needs to get more generic (move away from named methods, support arbitrary content types). Two distinct, real problems inside it, not one:
  1. `ArtifactIndex`/`ArtifactIndexInput` are filesystem-era relic names.
  2. It carries two fields doing the same job — `contentType` and `format` — a duplication that crept in as the package grew, not a deliberate design.
  - **Concrete reason the `format`/`contentType` merge is a real refactor, not a rename:** `FsArtifactStore`'s on-disk extension (`.json`/`.txt`/`.md`/`.bin`, keyed off `format`) is load-bearing for reads today, not cosmetic — `getBytes(hash)` takes no format/contentType argument at all; it brute-force-probes the four known extensions in a fixed order and returns the first that exists. That only works because `format` is a closed four-value enum. Moving to open-ended MIME `contentType` breaks the probe — reads would need to be told the content type explicitly (most naturally: look up `contentType` from the SQL metadata row by hash before reading bytes), or `FsArtifactStore` would need to drop on-disk extensions entirely and store extensionless by hash, leaving `contentType` purely as SQL metadata. That second option is also what S3/MinIO already do — extension-free object storage with `Content-Type` as opaque metadata, unrelated to how the object is addressed — so it would make `FsArtifactStore` structurally closer to a future S3-backed adapter, not just avoid the probing problem.
  - Directly relevant to the `worker-tools-artifacts` initiative, which owns where `packages/artifacts` actually ends up living.
- **`packages/replay` — corrected from "explicitly parked": genuinely live, not barely-used.** Small (2 source files), but real: `ReplayEngine` gets constructed inside `makeRuntimeContext()`, which `createServices()` (the path `apps/http-server`/`apps/cli` actually use) calls to build its context; `ReplayService` wraps it, and `apps/http-server/src/routes/runs/events/events.ts` calls `app.services.replay.getAllEvents(runId)` — a real, working route. `ReplayEngine implements ReplayEnginePort` (already confirmed as a live port with exactly one implementer) — no own lifecycle, not self-driven — so it's cleanly an **adapter**, just one sitting in its own small package rather than physically inside `packages/adapters`.
- **`packages/tools`** — different category from "components," used/bound to the worker, but can't be meaningfully categorized yet since even its own contract is still unsettled. See [`worker-tool-extensibility.md`](./worker-tool-extensibility.md) — this is the other half of what this initiative needs to settle, and the two questions are related, not independent (where tools live affects whether they need a tier of their own).
- **`packages/scheduler`** — confirmed dead, zero consumers anywhere outside itself. Already known-deprecated per `CLAUDE.md`; empirically re-confirmed while sweeping the remaining unclassified packages. Safe for outright removal, not archival — git preserves history fully, nothing is actually lost.
- **`packages/ui`** — confirmed dead. Once drove `apps/desktop`'s Electron UI, didn't work out long-term; the current shared UI lives fully inside `apps/web-app`. Three raw grep hits, but only two are real: `apps/desktop/vite.config.ts` and `apps/desktop/src/main.tsx` (both inside `apps/desktop`, already tracked as mostly dead); the third, `apps/web-app/note.temp.ts`, is a literal scratch note file whose content is a pasted tsconfig comment, not real code. Transitively dead through an already-dead consumer.
- **`packages/db-prisma`** — doesn't cleanly fit any of the eight tiers, and forcing it into one would be dishonest rather than useful. Not `types` (deliberately Prisma-free by design), not `ports`, not `functional core` (`PrismaClient` does real I/O, not pure), not itself an adapter (it doesn't implement a port — the real adapters, `PrismaArtifactRepository` etc., live in `packages/adapters` and depend on `db-prisma`, rather than `db-prisma` being one). Better described precisely than boxed: a project-owned, codegen-based dependency that real adapters build on, structurally beneath even `types` in the graph, since `types` deliberately excludes it. Nothing else in the taxonomy needs to reference it directly.
- **`packages/events`** — genuinely straddles two tiers, and stays bundled as one package for the same cohesion reason `specs` does. Its Zod schemas are zero-port/zero-I/O, mechanically passing the `functional core` test. But `EmitterFactory` — the concrete class implementing `EmitterFactoryPort`, used everywhere as `ef.newRunEmitterNewTrace(...)` etc. — has no own lifecycle and isn't self-driven, cleanly passing the **adapter** test too, despite living outside `packages/adapters`. Splitting it apart would break real cohesion: `EmitterFactory`'s per-domain emitter construction needs the exact per-domain schemas it validates against. Same legitimate exception already made for `specs`, not an oversight like `NodeRouter`'s misfiling was.
- Dead/unused packages exist and can be removed — see `scheduler`/`ui` above, plus the ports/`specs`/`run-history` dead code already found earlier in this doc; all tracked in `INITIATIVE.md`'s Change C4.

## Scope: migration vs. new-code-only guidance

**Resolved — this initiative is a deliberate exception to organic adoption, not in tension with it.** "Guide new code first, no mass-migration" is the right default for ordinary day-to-day work: outside a dedicated architecture pass, you can't just go move everything, and doing so piecemeal alongside unrelated feature work would be its own kind of chaos. But `architecture-boundaries` _is_ that dedicated pass — a deliberate, higher-level reorganization effort, not incidental code-touching done in passing. Within its scope, real package movement (per the initiative summary's "expect real movement, not just relabeling") is the point, not something to avoid. The two principles just apply at different times: organic/incremental is the standing policy for everyday work; this initiative is a scheduled, intentional exception to it, not a rewrite of the policy itself.

## Open questions, explicitly not yet resolved

- Whether/when the `components` tier's control-plane gap (sink registration, `start()`/`stop()`) actually gets built as event-driven — named as the aspiration, not scheduled or committed.

## Post-ADR-0005 finding: `events`' "adapter" half no longer describes the package, supersession deliberately deferred

`ADR-0005` described `packages/events` as straddling `functional core` (its Zod schemas) and **adapter** (`EmitterFactory`, which implements `EmitterFactoryPort` — a real port, satisfying the adapter test as written at the time). That was a reasonable read of the code that existed when the ADR was written.

The `events-refactor` initiative's Change C1/Change C2 then added a genuinely different shape alongside it: `emit()`/`buildEvent()`/`publishEvent()` (`packages/events/src/core/`) implement no port — they take `EventBusPort` as a parameter and are called from many places that already hold it (confirmed directly in Change C2: `Engine` already held `this.bus` for topic subscription; wiring it into `EffectHandlerDeps` for effect handlers to call `emit()` with required zero `runtime.ts` changes). That's not the adapter shape (implements-a-port); it's the `Operations` shape (consumes-a-port-as-its-one-dependency, caller-wires-it) — the ADR's own speculative tier, on its own terms: "**Status: speculative... If this tier doesn't hold up once real code is built against it, the fix is a follow-up ADR superseding this section specifically**." This is that real code.

**Deliberately not acted on yet — explicit user call, not an oversight.** ADR-0005 is `Accepted`, and superseding it should be its own dedicated research pass (matching how the original taxonomy got real discussion before being written down), done once the `Operations` shape has been proven out across more than this one refactor — not amended reactively off a single Change. Recorded here now so the finding isn't lost before that happens, not as a draft of the eventual supersession.

Two more threads worth carrying into that future pass, not resolved now:

- **`Operations`, capitalized, was never meant to be a permanent proper-noun tier name** — it stuck through the ADR specifically because there was no real implementation to check it against yet ("a best-current-guess, not a proven tier"). Once proven out, expect it (like every other tier name — `functional core`, `services`, `adapters`) to end up lowercase, not capitalized as if it were a formally branded pattern.
- **The schema-authoring question isn't `events`-specific.** `events`' Zod schema/registry layer and `specs` (the flow-definition schema+parser) are structurally the same kind of thing: a runtime-validator package deliberately kept unsplit from its types today, for the same two reasons in both cases — most consumers need the runtime Zod value, not just the shape, and `json-schema-migration` will likely restructure schema-vs-type entirely, so splitting either one now risks doing it twice. Whether that ends up as a shared `schemas`-shaped tier (parallel to, not nested inside, `functional core` — declarative/data-shaped rather than computational, the same distinction that already keeps `types` separate from `functional core`) is `json-schema-migration`'s question to resolve for both packages at once, not a call to make for `events` alone.

## Change C3 - Renames + dead-code cleanup - merged (PR #343)

### Discussion

**Renames:**

- **`XxxServicePort` interface names stay unaffected by the package rename, long-term, not just for this Change's scope.** Every port in `packages/ports/src` is named for its role (`RouterPort`, `ArtifactRepositoryPort`, `EngineTelemetryPort`, ...), never for the tier/package that hosts or implements it — none carry a `Component-`/`Adapter-` prefix today. `app-` in `app-services` is a package-boundary disambiguator (there's no sibling "domain services" tier it's contrasting against), i.e. location information, and location already lives in the package path, not the interface name. Renaming to `SomethingAppServicePort` later would be the only tier-prefixed port name in the codebase and would break that consistency.
- **By the same logic, the class implementations don't pick up the prefix either**: `ArtifactService` stays `ArtifactService` (not `ArtifactAppService`), same for `RunService`, `SimService`, etc. — file names too (`artifact.service.ts`, not `artifact.app-service.ts`). Tier lives in the package/directory (`packages/app-services/src/artifact.service.ts`), never duplicated into the class or file name.

**Combining with dead-code cleanup**: originally scoped as a separate Change C4, since renaming and dead-code deletion are two different kinds of risk. Folded into this Change once Change C4's real scope was actually verified (below) and turned out to be the same class of light, low-risk organizational work as the renames — both fully mechanical, both already fully investigated before any code changed. Nothing downstream had a fixed Change number riding on Change C4 staying separate, so this is a plain renumber (old Change C5 → 4, old Change C6 → 5), not a "skip." Accepted tradeoff: independent revertability (a bad rename entangled with a dead-code deletion in the same commit) in exchange for less ceremony — acceptable here since this is dev-only reorganization, not user-facing, and both halves are independently low-risk.

**Dead-code cleanup, scope as inherited from `INITIATIVE.md`'s "Next up"**: the confirmed-dead `*Port` interfaces (`ControllerPort`, `ClientApiPort`, `StreamPort`, `StepRunnerPort`, `EngineTelemetryPort`, `FlowParserPort`, `RunEmitterPort`, the `Rm*` family, the `*EmitterPort` family), `specs`'s `engine.types.ts`/`result.types.ts`, `WsService`, `list-completed-steps.ts` in `run-history`, and two whole dead packages (`packages/scheduler`, `packages/ui`) — plus `packages/engine`'s dead `@lcase/adapters` dependency, found during Change C2's execution.

**Re-verified empirically before planning, per Change C1's own stated litmus test ("used as a type annotation somewhere real, outside `packages/ports` itself — a dependency field, a function parameter, a factory's return type"). Every item held up except one, which was a real, significant miss:**

- **Confirmed genuinely dead, zero usage outside their own definition file, nothing extends them under a different name**: `StepRunnerPort`, `EngineTelemetryPort`, `FlowParserPort` (its one other hit is a commented-out line in `engine.port.ts`, not real usage — its sibling types `FlowQueuedParsed`/`FlowSubmittedParsed` are also unused outside this dead cluster). All three whole files are self-contained deletions.
- **Third major correction: `ControllerPort` and `StreamPort` are not dead either — drop both from scope.** The original single-symbol grep missed a real blind spot: `\bControllerPort\b` doesn't match `ClientControllerPort` (no word boundary between "Client" and "ControllerPort"), same for `\bStreamPort\b` and `ConsumerStreamPort`/`ProducerStreamPort`. Checking `extends`/`implements` explicitly surfaced real, live derived interfaces: `ClientControllerPort extends ControllerPort` is used in `packages/ui/src/context/ControllerContext.tsx` and `apps/desktop/electron/electron.controller.ts`; `ServerControllerPort extends ControllerPort` is used in `packages/controller/src/{workflow,sim}.controller.ts`. `ConsumerStreamPort`/`ProducerStreamPort extends StreamPort` are genuinely core infrastructure — used across `packages/tools`, `packages/adapters/src/stream/*`, `packages/ports/src/{stream-registry,tools/tool-context}.ts`. Both `controller.port.ts` (also holds the actively-used `RuntimeStatus` type) and `stream.port.ts` stay untouched, in full.
- **`ClientApiPort`: also not dead, for a related reason — its only usage (`packages/ui/src/context/ClientApiContext.tsx`) lives in `packages/ui`, which this same investigation already pulled from the deletion list** (see below). Kept, not deleted.
- **The `Rm*` family (`RmToolConcurrencyPort`, `RmHandlerRegistryPort`, `RmToolHandlerPort`) plus `SchedulerPort` itself (`packages/ports/src/scheduler/scheduler.ts`, the port `packages/scheduler/src/scheduler.ts`'s `Scheduler` class implements) — all four confirmed dead, and not individually: the entire `packages/ports/src/scheduler/` subfolder is dead as a unit**, a direct consequence of `packages/scheduler` itself being deleted (below). Not even part of `@lcase/ports`' public surface — `packages/ports/src/index.ts` never re-exports this subfolder at all, only `packages/scheduler` reached into it. Whole-folder deletion, not file-by-file.
- **Major correction: the `*EmitterPort` family is not dead — drop it from this Change's scope entirely.** Checked all 12 (`Base`/`Step`/`System`/`Replay`/`Job`/`Engine`/`Flow`/`Run`/`Worker`/`Tool`/`Scheduler`/`Limiter`EmitterPort): every single one is referenced as a method return type inside `EmitterFactoryPort` (`packages/ports/src/events/emitter-factory.port.ts`), and several (`BaseEmitterPort`, `StepEmitterPort`, `SystemEmitterPort`, `JobEmitterPort`, `EngineEmitterPort`, `FlowEmitterPort`) also have real concrete implementations in `packages/events/src/emitters/*.emitter.ts` (`class BaseEmitter implements BaseEmitterPort`, etc.). `EmitterFactoryPort` itself is one of the most heavily-consumed ports in the repo — real usage confirmed across `packages/app-services`, `packages/components/{engine,worker,limiter}`, `packages/replay`, `packages/use-cases/run-flow`, `packages/ports/src/tools/tool-context.ts`. This satisfies Change C1's own litmus test exactly (a factory's return type) — the original research's claim looks like a direct oversight, not a judgment call to revisit. `RunEmitterPort` specifically is also exercised at the call site: `run-flow.ts`'s `ef.newRunEmitter(...)`.
- **`specs`'s `engine.types.ts`/`result.types.ts`**: confirmed dead — every exported schema (`StatusSchema`, `RunStepContextSchema`, `RunContextSchema`, `TestResultSchema`) has zero real usage anywhere else (one apparent hit, `RunContextSchema` in `packages/events/src/schemas/run.event.schema.ts`, is a same-named but independently-defined schema, not an import — pure name collision). `result.types.ts` isn't even re-exported from `packages/specs/src/index.ts`, so it's unreachable via the package's own public API on top of being unused.
- **`WsService`**: confirmed — wired into `packages/runtime` (`runtime.ts`, `app-services/src/{types,ws.service}.ts`) but zero real call sites (`wsService.` never appears anywhere in `apps/http-server`). Checked the other wiring path too, since it's the one `apps/desktop` — which this Change is otherwise careful to keep working — actually uses: `WorkflowRuntime`'s constructor (`packages/runtime/src/workflow.runtime.ts`) receives `wsService` in its `services` parameter but never reads it. Genuinely unused on both paths, not just the one already known to be unreachable.
- **`list-completed-steps.ts`**: confirmed — reachable only from its own test file; not even re-exported from `run-history`'s own `index.ts`.
- **`packages/scheduler`**: confirmed — zero `package.json` dependency declarations anywhere, zero source imports outside its own directory.
- **`packages/ui`: not dead, drop it from this Change's scope entirely.** The original research's "only reference outside an already-dead `apps/desktop` is a scratch note file, not real code" doesn't hold up: `apps/desktop/src/main.tsx` — the app's actual Vite/React entry point — does `import { App, ControllerProvider } from "@lcase/ui"`, wired via a Vite alias in `apps/desktop/vite.config.ts` straight to `packages/ui/src` (not a normal `package.json` dependency, which is likely why the original dependency-declaration search missed it). `packages/ui` is `apps/desktop`'s actual UI shell, not a stray reference.
- **`packages/engine`'s `@lcase/adapters` dependency**: confirmed — declared in `package.json`, zero imports anywhere in `src/`.
- **`apps/observe-web`, added to this Change's scope (not in the original list)**: genuinely obsolete per `CLAUDE.md`'s own existing note ("obsolete... slated for removal"), and confirmed isolated — zero consumers, nothing imports from it, no `build`/`typecheck`/`test` script, only outside mention is `pnpm-lock.yaml` (clears itself on next install). Unlike `controller`/`ui`/`desktop`, nobody wants this kept as reference — plain deletion, not archival.

**Net scope change from this verification pass**: the `*EmitterPort` family, `ControllerPort`/`StreamPort` (whole files), and `ClientApiPort` all come out of the original dead-code list entirely — real code, not touched. `packages/ui` also comes out, but as an _archive_, not a no-op (see below). `packages/scheduler` is the only outright whole-package deletion carried over from the original list; `apps/observe-web` is added as a second. Everything else in the original list (the three isolated dead ports, `specs`'s two files, `WsService`, `list-completed-steps.ts`, `packages/engine`'s dead dependency) is confirmed exactly as planned.

**`packages/controller` and `packages/ui`: kept, but reorganized into `packages/archive/` — a new, explicit "kept intentionally, not actively maintained" location, distinct from just leaving them mixed into the live tier folders.** Both are genuinely used (`controller` by `apps/desktop/electron/bootstrap.ts`; `ui` by `apps/desktop/src/main.tsx`, confirmed above), but only within `apps/desktop`, which is itself paused/mostly-dead and has no `typecheck`/`lint`/`test` script — the user wants `apps/desktop` kept standing as reference scaffolding for a future real Electron rebuild, not actively maintained code. Decided: rather than leave these two indistinguishable from live tier packages, or delete them and lose the reference value, move both into a new `packages/archive/` folder (glob added to `pnpm-workspace.yaml`, mirroring the existing tier-folder pattern). Deliberately minimal-blast-radius: `controller` is a normal `workspace:*` dependency, so its move is the same zero-import-change mechanical pattern as Change C2 (only the physical path + workspace glob change, `apps/desktop`'s own source untouched). `ui` has one real exception: `apps/desktop/vite.config.ts`'s alias (`"@lcase/ui": path.resolve(__dirname, "../../packages/ui/src")`) is a literal relative filesystem path, not a package import, so it needs a one-line update to match the new depth — the only change inside `apps/desktop` this Change makes, and only because the alternative is a silently-broken alias. `apps/observe-web` is a plain deletion, not part of this archive — nobody wants it kept.

**Decided: go ahead and remove the confirmed-dead port interfaces now, in this pass, rather than deferring to a hypothetical future `packages/ports` refactor.** Raised as an open question (this initiative is more about removing dead packages/bigger structural things than a fine-grained ports cleanup), but no reason found to wait — these are all real deletions with zero consumers, confirmed above, and leaving them in place only means re-discovering and re-verifying them later.

### What actually landed

**Renames:**

- **Both renames landed via `git mv`**: `packages/services` → `packages/app-services` (`package.json` name `@lcase/services` → `@lcase/app-services`), `apps/web-app` → `apps/workbench` (`package.json` name `@lcase/web-app` → `@lcase/workbench`).
- **`@lcase/services`'s real footprint, verified rather than assumed from Change C1's research**: only **2** dependency declarations, not the 3 originally recorded — `packages/runtime/package.json` and `apps/http-server/package.json`. The original "3" count was off (likely double-counting `packages/services/package.json`'s own `name` field as a consumer declaration). 9 import sites updated: `packages/runtime/src/{create-services,runtime,workflow.runtime}.ts`, `packages/controller/src/sim.controller.ts` (a commented-out import, updated anyway for parity), and 5 `apps/http-server/tests/*-routes.test.ts` files.
- **Found and deliberately left alone**: `packages/controller/package.json` imports `@lcase/services` (now `@lcase/app-services`) directly in `sim.controller.ts` but never declares it as a dependency at all — a pre-existing gap on an already mostly-dead package, not caused by this rename. `pnpm build`/`typecheck`/`test` all pass regardless, confirming it's a latent oddity rather than a real break; not fixed, since fixing it would mean investing in code this initiative has already flagged as heading for removal.
- **`apps/web-app` had zero external workspace consumers** (nothing declared it as a dependency) and its internal source already used "Workbench" throughout, per `ui-workspace` Changes C47/48 — this rename was purely the outer package/folder name catching up to naming already live inside it.
- **Doc sweep, beyond the footprint originally scoped, done because a rename leaving stale paths/instructions behind isn't actually finished**: root `README.md`, `CLAUDE.md`, `apps/workbench/README.md`, `apps/http-server/README.md`, `docs/api-reference.md`, `docs/api-usage-audit.md`, `docs/todo.md`.

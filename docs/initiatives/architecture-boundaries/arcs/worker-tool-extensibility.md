## Change C4 - Worker/tool extensibility research - merged (PR #344)

### Discussion

- **Starting point is deliberately zoomed out, not the in-process-vs-out-of-process question the placeholder research doc opens with.** That question and the secrets-boundary question (`docs/todo.md`) may end up colliding with or resolving out of whatever's decided here, but starting there risks answering a mechanism question before the concept it's a mechanism _for_ is settled.
- **The actual starting question: what is a tool, philosophically, as distinct from a worker — and how is this project meant to be extended by other people?** The long-held, evolving intuition has been that tools are _the_ extension point, but that's never been pinned down into a concrete shape: what does a third party actually write, hand over, or run to add a capability, and is that shape even achievable given how tools and the worker currently relate to each other.
- **Tool = a location-agnostic capability that registers with a worker; in-process binding (today's only real implementation) is one special case, not the definition.** Worker's job is purely orchestration — dispatch to whatever actually does the work — which raises its own small, separate question (not yet resolved, not blocking): does "worker" stay the right name if its job is calling out rather than doing. Explicitly rejected: making the _worker itself_ the extension point (would force a third party to stand up a worker just to extend the system) and building a plugin system (code loaded into this repo's process) — extension should not require writing code that runs inside `packages/components/worker`.
- **A candidate reframing, floated and only partly confirmed:** `httpjson`/`mcp` may not be "capabilities" in the same sense a domain-specific one (`stt`) would be — they're closer to **transports**, the worker's small fixed set of built-in ways to reach out-of-process work. A "capability" would then be a thin declarative layer on top (name + contract + which transport carries it), registered rather than coded.
- **Real prior design, from an earlier, since-cut attempt at this exact problem — surfaces a sharper, different resolution than the transport/capability split above.** Motivating constraint, still true today: flow-definition step _types_ are closed (not extensible) per `CLAUDE.md`. The old idea: a tool doesn't get its own step type or its own schema — it declares which existing step type's **job event envelope shape** it can consume (e.g. "I accept an httpjson-shaped envelope" or "an mcp-shaped envelope"). A `tool: "x"` field on the step selects it; a registry (an early "resource manager" concept) decided routability — could this step's declared tool actually be reached. Registration was two-sided: tools registered the envelope shapes they support, workers registered which tools/capabilities they cover. Cut before it was finished — real motivating idea, not a settled design to resurrect wholesale.
  - **Consequence worth naming, not yet confirmed as acceptable:** under this shape, a capability doesn't get a typed, domain-specific contract inside the flow definition — an `stt` tool is still invoked via a plain httpjson step, its actual expected body/headers shape communicated out-of-band (docs), not enforced by the flow schema. That's consistent with "no plugin system" (a third party ships no code, just something that speaks one of the existing envelope shapes, registered under a name) — but it does mean "capability" is a routing label, not a contract, unless something else is layered on top later.
- **Grounding case, from a real earlier project**: a hardcoded local STT → LLM → TTS pipeline over a LAN, each stage its own process, Redis + MinIO for coordination/storage. Motivates the shape but was never generalized past that one hardcoded pipeline.
- **A separate, genuinely hard, unresolved problem surfaced alongside this: liveness/health of a synchronous, single-concurrency external tool** (e.g. a local LLM call that can't interleave a heartbeat response while busy). Floated as possibly separable rather than blocking: push liveness detection to the _caller_ (worker-side timeout policy — "no completion within N seconds means treat as hung") rather than requiring every synchronous tool to implement heartbeating/threading itself. **Settled enough to move past for now**: a plain worker-side timeout is fine as the v1 mechanism, no demonstrated case where it wasn't enough — but a real heartbeat/liveness signal still feels needed conceptually and should stay a named design consideration for later, not something the current shape should foreclose.
- **Sharp pushback, genuinely useful: if a tool just talks httpjson to a fixed endpoint, why register it at all instead of inlining the URL directly in the step?** Resolved as: registration isn't inherently better than direct invocation — it's a mechanism you reach for to get specific properties, not an architectural default. A static, single-environment, no-secrets call has no need for a registry; a plain httpjson step pointed straight at the endpoint is simpler and fine. Registration starts earning its cost when you need: environment-independent addressing (same flow definition, different registered endpoint per deployment), credential/secrets indirection (keeps auth out of the flow definition entirely — directly relevant to the secrets-in-flow-defs problem already flagged in `docs/todo.md`), multi-instance/failover routing, discoverability, or liveness/health tracked over time. Reframes "should this tool register" from a blanket rule to a per-case check against that property list.
- **Step types are closed to third parties, not closed forever.** The project itself can keep adding first-class step types over time beyond httpjson/mcp — floated candidates: an opinionated OpenAI convenience type (fills in specifics a generic transport wouldn't), a terminal-execution type, a data-transform type (fit still genuinely uncertain — may connect to the "compose" idea already flagged in `docs/todo.md` as possibly not a worker capability at all, closer to `resolve-branch-value.effect.ts`'s "not every CAS-touching operation is a worker capability" precedent; not resolved here). httpjson/mcp being "just transports" describes today's only two, not a permanent ceiling on what a step type can be.
- **A real confusion, named and resolved: transport and envelope-shape are the same axis, not two.** A tool doesn't need a separate "which transport do I use" field alongside "which step-type envelope do I declare support for" — the envelope-shape choice already answers the transport question. Carrying both invites drift (a tool claiming transport X while its declared envelope implies Y).
- **The existing generic `args` field already on these steps** (a free-form handle for tool-specific payload data) is the concrete mechanism this whole envelope-shape approach already leans on — not something new that would need to be added.
- **Correction: credential indirection isn't actually a registration justification.** httpjson can already carry auth headers to a credentialed endpoint via direct invocation, no registry involved. The real fix for the secrets-in-flow-defs problem (`docs/todo.md`) is resolving a `secrets` ref scope at the worker level before dispatch — a ref-resolution concern, orthogonal to whether a tool is registered. Narrows the earlier property list down; what's left standing and sharp is resource locality.
- **Resource locality (the real motivating case, from the LAN STT/LLM/TTS pipeline) resolves without a new mechanism.** GPU-bound tools don't require a colocated-worker extension path — the tool (an HTTP/MCP service) deploys on the hardware; the existing worker, wherever it runs, reaches out to it over the network. Compute placement is solved by where the _tool_ lives, not by moving the worker.
- **Landed principle: the worker owns all infrastructure coupling (bus, queue, CAS, ref resolution, lifecycle); a tool owns none of it — one transport in, one shaped result out.** This is _why_ "worker as the extension point" feels wrong, made precise rather than just intuited: a third party extending via a bundled worker would need real bus/queue/CAS access, comparable weight to the plugin system already rejected, just moved one layer out. Keeping tools infrastructure-free is what keeps this a light extension model.
- **A second, heavier extension path is still real but doesn't need new design: running your own worker instance, scoped to your own tool(s), colocated with your hardware.** Already latent in the existing per-tool-id job queue shape — not a mechanism to invent. Caveat: `InMemoryQueue` is in-process-only today, so a second worker process can't actually share a queue with the main one yet; this path only becomes real once a distributed queue adapter exists (`swappable-infrastructure` territory), not blocking this discussion.
- **The "smaller sidecar helper" idea, floated at the end, maps onto the SDK-package concept already named in the placeholder research doc/`docs/todo.md`** — a thin optional helper (payload parsing, response shaping, maybe a lifecycle convention) for a tool author to use, deliberately without bus/queue/CAS access. Not yet confirmed how much surface it should have; open.
- **Worker-level liveness — "is the worker itself hung, from the engine's perspective" — flagged as a related, currently-missing layer, not the same as tool-level liveness.** Not explored further yet, just named as a real gap.
- **Tentative core conclusion, arrived at by pressure-testing every registration justification raised so far and finding none compelling: no tool registry.** The worker being transport-agnostic — supporting as many transports as it reasonably can (http/json today, `mcp`, eventually stdio/terminal, eventually streaming) — _is_ the extension mechanism. A third party extends the system purely by standing up a service that speaks one of the worker's supported transports; there's no registration step and no code that ships into this repo. This is a genuine shift from every earlier version of the idea in this doc (envelope-shape registration, capability-as-routing-label) — those all assumed some registry had to exist; this arrives at not needing one at all.
- **Reframes what "convenience step types" (an opinionated Google-Docs-style or OpenAI-style step, as many nice workflow engines have) actually are: a first-party-only concern, not a third-party extension mechanism.** Consistent with step types already being closed to third parties — these are just the project's own accumulating library of opinionated shortcuts layered on top of the underlying transports, added the same way any feature is, not something needing an extensibility design of its own.
- **Reframes what the wanted SDK is for, correspondingly: not for registering a tool or authoring a step type — for the _tool/service author_.** A standalone helper package making it easy to stand up a service that correctly speaks one of the worker's transports (payload parsing, lifecycle/heartbeat/status conventions) without hand-rolling conformance. Confirmed by the user as the right shape.
- **Concurrency/rate-limiting for tools with real capacity limits (a local LLM that can only handle one request at a time) raised as a real, separate, unsolved problem — explicitly flagged by the user as possibly its own discussion, not resolved here.** Ties to `packages/limiter` (already known incomplete elsewhere). Tentative shape floated, consistent with no-registry: limits configured by endpoint/URL/transport pattern rather than keyed to a registered tool name, since there is no registered tool identity to key off of.
- **Two real future transport-shaped needs named, not explored further yet:** stdio/terminal support (wanted, unclear how a transport-agnostic worker model extends to local/subprocess tools), and streaming (a founding-vision goal, motivated by the original STT/LLM/TTS latency problem — explicitly deferred by the user as longer-term, not for this discussion).
- **Confirmed as the likely settled shape — simple and, in the user's words, "maybe the most powerful" version of this.** The main thing given up (life-cycle/heartbeat awareness, knowing a tool "exists") is judged genuinely not needed, not a reluctant compromise. Falls out naturally: without a registry, per-endpoint concurrency/rate/timeout limits just become configuration keyed by transport + endpoint (matches the concurrency question raised last turn), which is `packages/limiter`'s territory, not a new mechanism.
- **Important clarifying correction to how `httpjson` (and the `mcp` binding, built the same way) actually work today, surfaced only once described concretely: the external endpoint never receives "the job event envelope" at all.** The worker interprets the step's resolved args (method/url/headers/body) itself and constructs a plain outbound HTTP request from them; the target service just receives an ordinary HTTP request and replies like any HTTP API would — no awareness of this project's event shapes required. This retroactively confirms the whole envelope-shape-registration idea explored earlier in this doc was never quite accurate for `httpjson`'s real behavior, and reinforces the no-registry conclusion further: an arbitrary, already-existing HTTP API already qualifies as a valid tool today, zero helper library required.
- **Correspondingly narrows the SDK's scope, not yet settled:** with the external service needing to understand nothing about this project's internals, the SDK's candidate value shrinks to optional convenience — a heartbeat/status convention if liveness tracking is ever wanted (judged not currently needed), and possibly response-shape conventions for richer interop. Not confirmed as load-bearing; genuinely smaller than it looked a few turns ago.
- **Fundamental reshaping, not just a scoping decision: "tools" as a distinct vocabulary may dissolve entirely.** What's been called a tool (`httpjson`, `mcp`) isn't a first-class pluggable/registered entity — it's the internal name for a protocol the worker knows how to speak. The worker has protocols/transports; whatever it calls out to is just the outside world, uncontrolled, not a "tool" in any special systemic sense. Genuinely open whether "tool" survives as vocabulary at all, or whether "protocol"/"transport" fully replaces it — named, not resolved.
- **A general principle crystallized, generalizing the earlier worker-side-timeout conclusion beyond just liveness: the system never governs the outside world's behavior, only its own.** Retry, timeout, backoff — all the system's own responsibility toward whatever it calls; never assumed or required of the endpoint on the other side. Reframes the earlier "a plain timeout is enough" conclusion as one instance of this broader posture, not a special case scoped only to liveness.
- **Data transforms floated again, tentatively as an engine-side extension point rather than a worker-dispatched capability at all — possibly never round-tripping through a worker.** Independently converges with the same idea already flagged in this arc via `docs/todo.md`'s "compose" note and the `resolve-branch-value.effect.ts` precedent ("not every CAS-touching operation is a worker capability") — two separate lines of reasoning landing in the same place, a real signal even though genuinely unresolved. Explicitly deferred again by the user as its own discussion.
- **Revisited once more, at the close of this Change's discussion, and partially walked back**: putting data transforms in the engine doesn't sit right either, on reflection — the engine's job is orchestrating a flow definition's execution, resolving what it must to do that, not performing data transformation as a first-class concern. Doesn't overturn the earlier "maybe not a worker capability" instinct, just removes "so it must be the engine" as the default fallback. Genuinely unresolved where data transforms actually belong; deliberately not pursued further in this Change.
- **A real, unresolved tension: the more generic a protocol is, the less the worker actually knows how to interpret what comes back.** `httpjson` is scoped to JSON specifically — not an arbitrary restriction, but the minimum floor of structure the worker needs to turn a response into step outputs/success-or-failure/CAS artifacts at all. Plain, unscoped HTTP loses that floor entirely (arbitrary bytes, unknown content-type); JSON's own internal shape is still unknown per-call but is at least schema-validatable if a flow author supplies one. Suggests a sharper test for what it means for the worker to "support a protocol": not just wire-level send/receive, but having _some_ convention for interpreting the response — every protocol the worker adds needs its own version of this floor.
- **Confirmed directly: the JSON-only scoping of `httpjson` was exactly this — a deliberate move to standardize the shape of what comes back** (and, less certainly, what's sent), not an incidental limitation. Validates the "interpretability floor" framing above as the actual original intent, not just a plausible reconstruction.
- **A real cost of first-party convenience step types (Google-API-style), surfaced but not previously named: they buy known-shape richness by having the worker/engine hardcode specific knowledge of an external API's contract — and that knowledge rots as the external API evolves, silently, unless the vendor's own docs/notifications are tracked and the worker is updated to match.** Same "the system doesn't govern the outside world" posture from earlier, showing up here as an ongoing maintenance cost rather than a runtime robustness question.
- **A real, explicitly-not-to-be-designed-now future direction: move toward a more generic HTTP protocol/step type than today's JSON-only `httpjson`.** Genuinely open how flexible, what gets restricted on either side of the call, how results get stored — "a big world out there." Named as a real destination, deliberately left open rather than scoped.
- **New axis surfaced: protocols differ in how self-describing they are, and that difference matters for what "the worker supports this protocol" even has to mean.** MCP carries its own discovery/negotiation (a server can be asked what it offers and what shape it expects); raw HTTP carries none — the shape has to come from somewhere else (a flow author's own knowledge, or a first-party convenience step baking that knowledge in). Floated, not resolved: worker-side protocol support may need to include using a protocol's own negotiation when one exists, not just a uniform call-and-interpret step for every protocol alike. Carries forward into whatever the generic-HTTP direction above ends up looking like.

### Discussion — secrets thread (opened once the core worker/tool shape settled)

- **Grounding check before opening this thread: the existing `env`/`input` ref scopes (`packages/functional-core/flow-analysis/src/parse-references.ts`) are not good precedent.** Both are parseable syntax with zero real resolution behind them (`value-refs.ts`'s own doc comment: "does not yet support inputs or other resolutions") — aspirational stubs from earlier thinking about this exact problem, not a partially-built secrets mechanism to extend. Environment variables were never confirmed as secrets-equivalent either ("I generally treat them like they are, but unsure"). A `secrets` scope (or whatever it ends up named) is new, not a repurposing — `env`/`input`'s fate is separate and not decided here.
- **Two structurally different leak surfaces identified, not one problem:**
  1. **Secrets leaking into events/replay** — our own resolved step inputs. Deterministic and fully solvable: a `secrets:` ref points at exactly one known value, so redacting it wherever it was interpolated (real value used only worker-side to build the outbound call, placeholder emitted onto the bus) is complete, not just best-effort. Confirmed as the settled direction for this half.
  2. **Secrets leaking into CAS via arbitrary third-party response content** — a different, harder category. Confirmed as a _current, real_ behavior, not hypothetical: `packages/tools/src/httpjson/httpjson.tool.ts` captures the entire response object (headers, body, status) as the step's raw output unconditionally, regardless of what's actually declared in `exports`. There's no ref pointing at "the secret" in a third-party response the way there is for our own inputs, so detection would require heuristic secret-scanning (entropy checks, known token-format regexes — the same imperfect class of technique tools like `gitleaks`/`truffleHog` use) — not something to design or build now. Proposed direction instead: narrow _what gets captured as output in the first place_ — response headers aren't stored wholesale by default, mirroring how `exports` already requires explicit declaration for named response fields — rather than attempting after-the-fact detection. Not yet confirmed.
- **Multi-worker credential distribution named as a real future scaling question, explicitly not a live concern today.** Three broad shapes for later: a centralized secrets service each worker queries on demand, every worker holding all credentials (simplest, worst blast radius), or secrets partitioned by which capabilities a given worker actually runs (mirrors the earlier per-tool-id job-queue scoping idea, applied to credentials instead of jobs). Not designed further.
- **Confirmed: default to capturing zero response headers on a step's raw output — no whitelist, no blacklist.** Blacklist rejected outright, not just deprioritized — it fails open against arbitrary third-party header vocabulary (a bespoke API could always introduce a sensitive custom header no fixed list anticipated), the same structural failure mode as blocklist-based malware/WAF rules. Whitelist rejected as the _default_ for the same reason, one step removed — floated only as a possible additive convenience later (e.g. `content-type`/`date`, proven safe and consistently useful through real use), never as the initial posture. "Zero by default" isn't a new restriction — it extends the same discipline `exports` already applies to the response body (nothing durable without explicit declaration) to headers too, closing a gap rather than adding a new rule.
- **Real value acknowledged and deliberately deferred, not designed now: headers can matter for debugging a run without re-running it.** Floated direction for later, not committed: a step-definition-level field to explicitly keep specific header fields on the raw output even without a full `exports` declaration — distinct from `exports` (which goes through the schema/CAS-artifact path). Left to evolve organically once real, repeated need shows which headers are actually safe and worth keeping by default, rather than guessing now.
- **Secret storage direction confirmed: an encrypted DB column with an externally-held key, not the OS keychain — even for a desktop target.** OS keychain was explained (the OS owns key management and access control, tied to the logged-in session; natural fit for `apps/desktop` via Electron's `safeStorage`, no real story for a headless standalone server) and explicitly passed over in favor of a mechanism that works the same way regardless of deployment target. A v1 key source as simple as an environment variable is a legitimate, common starting shape (the same pattern as e.g. Rails' `secret_key_base` or a plain `ENCRYPTION_KEY` env var), not an inferior shortcut — upgradable later to a real KMS without changing the encrypted-column shape itself. Natural implementation pattern once built: a `SecretsPort` behind the same ports/adapters convention every other storage-backed capability in this codebase already follows — not a new architectural decision, just consistency.
- **Explicitly named as its own dedicated future push, not something this research pass designs or builds.** Consistent with how this initiative treats other real-but-deferred work (see "Open threads" in the research doc).
- **Longer-term UX idea floated and explicitly deferred: OAuth flows for connecting directly to third-party services (OpenAI, Google, etc.) inside the app, rather than a flow author pasting a raw API key.** Named as a real v2+ direction on top of the storage mechanism above, not designed.

### What actually landed

- **[`research/worker-tool-extensibility.md`](../research/worker-tool-extensibility.md)** — rewritten from a placeholder into the settled research. Core conclusion: there is no tool registry; the worker's protocol surface is the extension mechanism, and third-party extension means standing up a service that speaks a protocol the worker already supports, nothing more. Also landed: "tool" identified as likely-dissolving vocabulary (the naming question itself left open); convenience step types confirmed as first-party-only, never a third-party mechanism; a general principle that the system governs its own behavior toward the outside world and never assumes the reverse; a response-interpretability-floor test for what "the worker supports a protocol" actually has to mean; and the secrets-safety boundary substantially settled — the events-leak half solved (worker-side `secrets` ref resolution, redacted bus events), the CAS-leak half solved by capturing zero response headers by default rather than attempting detection, and a storage direction chosen (encrypted DB column, externally-held key, no OS keychain) — with the actual `SecretsPort`/adapter implementation explicitly named as its own separate future push, not built here.
- **Real corrections and reversals found along the way, not a plan executed straight through**: the original envelope-shape-registration idea (a tool declares which step type's job event it accepts) was replaced entirely once it turned out `httpjson`/`mcp` don't forward the job event to the target at all — the worker builds an ordinary protocol call from resolved args, and the target never sees anything shaped by this project's internals. Credential indirection was floated as a registration justification, then retracted once direct `httpjson` invocation was shown to already support arbitrary auth headers with no registry involved. Resource locality (the actual motivating case, from a real earlier LAN STT/LLM/TTS pipeline) resolves without any new mechanism — the tool deploys near the hardware, the worker just reaches out to it. Data transforms' home was floated as engine-side, then walked back at the very end of this discussion once weighed against what the engine's job actually is (orchestration, not data transformation) — left genuinely unresolved, deliberately not pursued further here.
- **Open threads carried forward, not resolved in this Change** (full list in the research doc's "Open threads"): how far to open `httpjson` beyond JSON-only, data transforms' actual home, concurrency/rate-limiting per endpoint (ties to `packages/limiter`), stdio/terminal transport support, streaming (a founding-vision goal), worker-level liveness, the now-narrowly-scoped tool/service-author SDK, multi-worker credential distribution, and OAuth-based credential UX.

## Change C2 - Physical package moves - merged (PR #342)

### Discussion

- **The clean moves are fully mechanical, already verified**: `packages/flow-analysis`, `packages/json-ref-binder` → `packages/functional-core/*`; `packages/engine`, `packages/worker`, `packages/limiter`, `packages/observability` → `packages/components/*`. Zero import-statement changes anywhere — every cross-package import already goes through `@lcase/<name>`, never a relative path — and npm package names stay as-is. One new `pnpm-workspace.yaml` glob line per subfolder, mirroring the existing `packages/use-cases/*` pattern.
- **`NodeRouter` isn't a `git mv` — it's a new package.** It's just two files (`node.router.ts`, `index.ts`) living inside `packages/adapters/src/router/` today, not a standalone package, so extracting it means scaffolding a real new package from scratch. Settled: name `@lcase/router`, home `packages/components/router`. Re-verified rather than assumed that its only construction site is `packages/runtime/src/runtime.ts:116` (inside `makeRuntimeContext()`) — and confirmed, correcting an earlier read, that `create-services.ts` (the `apps/http-server`/`apps/cli` path) isn't a separate consumer that misses `NodeRouter`: it calls `makeRuntimeContext()` itself, so both wiring paths already funnel through the same construction site. Also found while grepping: `@lcase/events` is used in `packages/adapters/src` _only_ by `node.router.ts` — once the router moves out, that dependency becomes dead weight in `packages/adapters/package.json` too.
- **What `NodeRouter` actually does, mechanically**: subscribes to `job.*.submitted`, unconditionally requeues as `job.<capid>.queued` onto the `QueuePort`. No real routing logic (no capability-based rules, no conditionals) — it exists mainly so the engine's step-dispatch is observable on the bus before/while it's queued, not because it makes decisions. Discussed and set aside as future, not this Change's scope: whether `NodeRouter` survives as its own component long-term, or whether the engine could push into queues directly (worker still needs queue infra regardless; the only reason not to have the engine do this itself today is losing that observability step). A separate idea — evolving it into a durable-queue admission/concurrency-control point for run requests — was raised and set aside as overlapping with `packages/limiter`'s existing job, not a `NodeRouter` concern.
- **General package-granularity rule worked out during this arc, not just applied to `NodeRouter`**: a components-tier package boundary isn't a bloat-avoidance decision, it's the tier's own membership test (independently meaningful on the bus, real port, candidate to run standalone — already established in Change C1) restated at the packaging level. Bundling components together would contradict that test, not just be a missed optimization, so "don't split until it hurts" (the right rule for further-splitting something like `adapters`, where no such claim exists) doesn't apply to whether components get their own packages in the first place. Grounded empirically: `worker`/`limiter`/`observability` have zero consumers outside `runtime` today, `engine` has one real consumer plus a dead `@lcase/adapters` dependency (folded into Change C3, after the Change C3/4 merge) — confirming there's no _build-cache_ reason to split, while confirming there's no tree-shaking safety net to fall back on either (`tsc` has no dead-code elimination; only `apps/desktop`, via Vite/Rollup, bundles at all — `apps/http-server`/`apps/cli`, the shape any future standalone `apps/engine`/`apps/worker` would likely follow, don't and likely never will). Net: package boundaries are the only real lever for "engine extracts without dragging Prisma/MCP-SDK/siblings along," permanently, for that deployment shape — which is why splitting components now is correct even with today's single-consumer reality.
- **Bus wildcard-routing rules, tangential but worth a paper trail**: `InMemoryEventBus` does publish-side pattern expansion (`generatePatterns()`) plus exact-match subscribe — the inverse of how a real broker (NATS subjects, RabbitMQ topic exchanges, Redis `PSUBSCRIBE`) typically does it, and those rules live only in that one adapter, not on `EventBusPort`. Not part of this Change's scope; captured in `docs/todo.md` for whenever a second bus adapter is actually built.

### What actually landed

- **Six clean `git mv`s, zero import-statement changes**: `packages/flow-analysis`, `packages/json-ref-binder` → `packages/functional-core/*`; `packages/engine`, `packages/worker`, `packages/limiter`, `packages/observability` → `packages/components/*`. `pnpm-workspace.yaml` gained two new globs, mirroring the existing `packages/use-cases/*` pattern.
- **`@lcase/router` scaffolded as a real new package** at `packages/components/router` — `package.json`, `tsconfig.json`, `NodeRouter`'s two files (`node.router.ts`, `index.ts`) moved in via `git mv`. `packages/adapters/package.json` lost its `./router` export and its now-unused `@lcase/events` dependency (confirmed nothing else in `adapters/src` used it). `packages/runtime/src/runtime.ts`'s one construction site updated to import `@lcase/router`; `packages/runtime/package.json` gained the new dependency.
- **Two real gotchas found during execution, neither anticipated by the plan**:
  1. Every moved package's `tsconfig.json` had a broken `extends` path — going one directory deeper meant `"../../tsconfig.base.json"` needed to become `"../../../tsconfig.base.json"`. Fixed across all 6 moved packages plus the new `router` package. Not an import-statement change, so the original "zero import changes anywhere" claim didn't cover it — a real example of the kind of thing only actual execution surfaces.
  2. `@lcase/router` turned out to be the first package in the repo with a real `vitest` script (not one of the 9 packages already stubbed `"echo test"`) that hits zero test files — `NodeRouter` never had tests, but bundled inside `adapters` this never tripped vitest's "no test files found" exit-nonzero behavior. Fixed with a `vitest.config.ts` + `passWithNoTests: true`, matching infra, not new production code.
- **Full verification, whole-workspace fan-out**: `pnpm build`, `pnpm typecheck`, `pnpm test`, `pnpm lint` all green (27/27, 26/26, 26/26, 27/27 tasks respectively) after the fixes above.
- **Follow-on findings from re-checking the plan against the taxonomy**, folded into `INITIATIVE.md`'s "Not yet scoped" and `docs/todo.md` rather than executed here (out of this Change's scope):
  - `packages/use-cases/run-flow` mixes a pure function, a clean one-port Operation, and a two-port orchestration function (`startForkedSim()`) that itself needs to split before it's Operation-shaped — confirming why `use-cases/*` correctly wasn't part of this Change's clean-move list.
  - `packages/replay`'s tier turned out less settled than Change C1's research concluded: `ReplayEngine` actively republishes events to the bus and needs three ports at once, the same shape that classified `NodeRouter` as a component rather than an adapter — genuinely open, not a simple fold-into-`adapters` call. `JsonlEventLog` (the real filesystem/JSONL storage implementation) is unaffected either way, already correctly filed in `packages/adapters`.
  - A separate, bigger idea surfaced alongside that: event storage's on-disk shape may want to mature alongside any future CAS backend swap (MinIO/S3), tying into the already-planned `swappable-infra proof` initiative — captured in `docs/todo.md`, not this initiative.
  - The bus's wildcard-routing rules (`InMemoryEventBus`'s publish-side `generatePatterns()`) are private to that one adapter, not part of `EventBusPort`'s contract — relevant only once a second bus adapter is actually built; captured in `docs/todo.md`.

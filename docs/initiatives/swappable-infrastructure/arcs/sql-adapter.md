# Prove Swappable Infrastructure Initiative — Arc: SQL Adapter (Changes C15–C18)

**Previous:** [`work-tracking-migration.md`](./work-tracking-migration.md) (Change C6) · **Next:** [`remote-worker.md`](./remote-worker.md) (Changes C19–C24) · **Related:** [`queue-adapter.md`](./queue-adapter.md) (Changes C4–C5, C7–C9, C11–C14), [`package-tooling.md`](./package-tooling.md) (Change C10)

Part of the [`INITIATIVE.md`](../INITIATIVE.md) Change log, split out to keep that doc scannable. Adds Postgres via Prisma **alongside** SQLite, and wires the choice into `packages/runtime`'s config selection.

**SQLite is not being replaced.** It is the lightweight install option for this application and stays a supported profile branch indefinitely — the point of this arc is that `sql` becomes a real config axis with two live backends, the same as `artifacts` (`filesystem`/`s3`) and `messaging` (`in-process`/`redis-streams`). An earlier revision described Postgres as replacing SQLite, which was never the intent — "swappable" here means selected by configuration when a process is composed, with every implementation retained. Migration histories do still collapse, but for an unrelated reason (no users, no data to preserve, schema in flux) rather than because one backend is going away.

Background research: [`research/prisma-sql-backend-strategy.md`](../research/prisma-sql-backend-strategy.md) (what two providers costs under Prisma) and [`research/prisma-provider-type-seam-spike.md`](../research/prisma-provider-type-seam-spike.md) (a measured compile probe settling how narrow the shared type seam has to be).

## Arc shape

Originally scaffolded as two Changes — "Postgres adapter" then "profile branch" — which turned out to bundle four different kinds of work behind one number. Sized before planning: as a single Change it lands around 5,000–6,000 modified lines, combining a destructive migration reset, a semantic rewrite of three transactional writes, mechanical schema/generation plumbing, and a restructuring of roughly 3,700 lines of tests. Those four have different risk profiles and want different kinds of review, so they are split.

The cut deliberately puts the only semantically risky piece **first and alone**, before any Postgres exists, so it is reviewed on its own terms rather than found inside a much larger diff:

| Change | What it is                                         | Postgres involved? | Risk                                         |
| ------ | -------------------------------------------------- | ------------------ | -------------------------------------------- |
| C15    | Retire `$transaction` in favour of nested writes   | No                 | Semantic — the real one                      |
| C16    | Two provider schema roots, clients, narrowed seams | Generated only     | Mechanical, plus destructive migration reset |
| C17    | Shared contract suites against both real databases | Yes, running       | Test coverage fidelity                       |
| C18    | Profile selects the SQL backend by config          | Yes, running       | Composition                                  |

C16 lands **inert**: both clients generate and every repository accepts either, but nothing constructs a Postgres client. Change C12 set that precedent in this initiative — infrastructure landing ahead of the flip that uses it.

## Change C15 - Retire `$transaction` in favour of nested writes - merged (PR #374)

### Discussion

- **Wanted independently of Postgres, which is why it goes first.** The preference is to express these writes in explicit Prisma API terms rather than reach for a transaction wrapper, and `PrismaArtifactRepository.writeArtifact` already does exactly that — a parent-plus-relation write as a single `upsert()` with the relation as a nested `deleteMany`/`createMany`, deliberately instead of `$transaction`, with the reasoning written down at the call site. This Change finishes a conversion the codebase started.
- **Three call sites, all structurally identical to that one.** `run` with `runParam` (58 lines), `run-step-projection` with `runStepExport` (53 lines), and the artifact repository's own second method with `artifactParamCuration` (16 lines). Roughly 200 lines rewritten in total.
- **Atomicity is preserved, not traded away.** Prisma wraps a nested write in its own implicit transaction, which is its documented default for atomically writing a parent plus related rows. This is not a durability relaxation.
- **The existing SQLite tests are the verification, unchanged.** Nothing about the test setup moves in this Change, so a green suite means the behaviour is identical. That is only true because this lands before the test restructuring, not after — another reason for the ordering.
- **It also happens to remove the one type-level blocker to Postgres.** `$transaction`'s callback overload hands back a full client, which drags the whole-client provider incompatibility into any seam that includes it; the spike confirmed removing it makes all three affected repositories accept a Postgres client. That is a consequence rather than the motivation, and this Change stands on its own if the Postgres work were dropped entirely.

### What actually landed

All three `$transaction` call sites are gone, replaced by nested writes on the parent; the only remaining mentions in `packages/adapters` are comments explaining what the code does instead. The repository seams shrank as a result: `PrismaRunRepositoryDb` is now `Pick<PrismaClient, "run">` alone, and the artifact and run-step-projection seams dropped their `$transaction` member.

- **The `deleteMany`/`createMany` relation scoping holds, and is now tested rather than assumed.** A nested `deleteMany: {}` clears only the parent's rows; the rows given to a nested `createMany` omit the foreign key entirely because the parent supplies it. That was the one failure mode here that would have been silent and catastrophic — an unscoped delete would have wiped every run's params — so it has a dedicated test asserting that replacing one run's params leaves another run's intact.
- **Composite-key relations work in a nested write, checked rather than assumed.** `RunStepExport` relates to `RunStepProjection` through `[runId, stepId]` rather than a single key, and this was flagged before implementation as the likeliest thing to reject. Prisma fills both halves from the parent with no help.
- **`upsertStepProjection` lost a read as well as a transaction.** It used to write exports and then re-read them inside the same transaction to build its return value. `include: { exports: true }` on the upsert returns them directly, so one round trip replaces three. `toRunStepProjectionRecord` keeps its two-argument shape, and `runStepExport` stays in that repository's seam because `getStepProjection` and `listStepProjections` still read it directly.
- **The `undefined` versus `{}` distinction is preserved and was previously undocumented.** Absent params or exports mean "leave them alone"; an empty object means "clear them". The old code drew that line by guarding `deleteMany` on `!== undefined` rather than on row count, which was easy to lose in translation — it is now explicit at both call sites and covered by tests.
- **The riskiest conversion turned out to be the one nothing tested.** `createRun`'s params-writing branch had no coverage anywhere: its own suite never mentioned params, and `prisma-run-query` and `run-sql-routes` both seed `runParam` rows directly through Prisma, exercising only the read path. Two live callers write params — `RunService.requestRun` and `SqlRunProjectionSink`. Five cases were added covering create, wholesale replacement, clearing, omission, and cross-run isolation. Adapter tests 103 to 108.
- **Verified end to end, not just by unit test.** A two-step `httpjson` flow taking a `userId` param ran through `apps/http-server` to `run.completed`, with the param written and read back through `GET /api/runs/:id` and the first step's export chaining into the second — exercising both the `run.params` and `runStepProjection.exports` nested writes against a real database. Workspace `build` 25/25, `typecheck`/`test`/`lint` 24/24.

## Change C16 - Two provider schema roots, generated clients, narrowed seams (inert) - merged (PR #375)

### Discussion

- **The behavior is portable; the types are not.** `schema.prisma` has no SQLite-specific workarounds (real `enum` blocks, no `@db.*` native-type pins, no JSON-as-string hacks), a repo-wide grep finds zero `$queryRaw`/`$executeRaw` outside the generated client, and changing only `datasource.provider` plus the generator output produced a working Postgres client from the current ten-model schema. What does not carry across is TypeScript: a Prisma driver adapter selects how a generated client reaches a database, but it does not change the provider that client was generated for. The initial scaffold's assumption — that this is one client with a swapped driver adapter — is wrong.
- **Two providers means two of nearly everything, and that is Prisma's design rather than a workaround.** A schema has one datasource with one literal `provider`, and multi-file schemas merge into that same single logical schema rather than providing overlays or imports. Supporting both therefore requires two schema roots, two generated clients with different output directories, two driver adapters, and two migration histories. Prisma keeps none of it in sync; one authoritative model source rendered into both targets by a repository-owned derivation step is project tooling, not a Prisma feature.
- **Both migration histories collapse freely, and will keep collapsing until the schema is stable.** This is a standing policy rather than a one-time step for this Change: there is no user base and no data anywhere that has to survive, both schemas are in active flux, and the whole schema is expected to need a refactor. So SQLite's five-migration history collapses to a single init alongside Postgres's fresh one, and either may be collapsed again whenever the models move enough to make the history noise. The end condition is stability plus real users — at that point history starts being kept for real and this bullet stops applying. Note this supersedes the earlier framing (collapse because Postgres replaces SQLite), which rested on a premise that was never true, and also overrides the research document's "do not discard the SQLite migration history" caution, which assumed data worth preserving.
- **Cross-provider parity is checked before generation, not after.** The derivation step is what guarantees both targets carry the same models; `migrate diff --exit-code` then verifies each provider's own history against its own schema. `migrate diff` cannot compare across providers at all — Prisma requires both inputs to use the same connector — so there is no command that answers "do these two schemas describe the same models," and the repository-owned step has to be the thing that guarantees it.
- **The models themselves stay inside the SQLite/Postgres common subset, deliberately.** Today they already are: only `String`, `Int`, `Float`, `Boolean`, `DateTime` and three enums, with no `@db.*` native-type pins, scalar lists, `Json`, or `Unsupported`. Holding that line is what keeps the derivation step a copy rather than a rendering with per-provider overlays, and a shared model carrying a Postgres-only feature (`@db.Uuid`, `String[]`, `jsonb`, `@@schema`, GIN indexes, full-text search) would fail SQLite validation outright. Divergent _migration SQL_ is expected and fine — identical models produce `CREATE TYPE` on Postgres and `TEXT` on SQLite for the same enum — since that is Prisma's job and needs no overlay. The likeliest first pressure on this is `EvalResult.payload`, JSON stored as a string today, which Postgres would want as `jsonb` to query into; that pressure and the `groupBy` tripwire below are the same pressure and would probably arrive together.
- **The generated `PrismaClient` type must not be used as the shared database seam, and today it effectively is.** All seven repositories narrow with a model-level `Pick` (`Pick<PrismaClient, "flow" | "flowVersion">` and siblings), and the compile probe shows even that rejects the Postgres client — the picked delegate still carries its entire generic API, including a `groupBy` signature nothing calls whose namespaces differ per provider.
- **Settled by spike: a method-level `Pick` is sufficient, and this Change is schema and generation work rather than a seam-design problem.** See [`research/prisma-provider-type-seam-spike.md`](../research/prisma-provider-type-seam-spike.md). Typing the seam against the **SQLite** client makes the Postgres client satisfy it unchanged, because Postgres's generated input types are a strict superset (`mode?: QueryMode` and field-reference list inputs that SQLite lacks) and method parameters are contravariant. Fifteen of seventeen delegate methods pass across all ten models, and narrowing the seven existing aliases in place is non-breaking. With Change C15 already landed, all seven repositories accept either client. No capability types, forwarding functions, or casts are needed.
- **The ceiling this accepts, and the tripwire for revisiting it.** Shared repository code is limited to the SQLite-compatible subset of the Prisma API — no `aggregate`, no `groupBy`, no `mode: "insensitive"` — enforced by the compiler, which is a stronger guarantee than a single provider-agnostic query-builder type would give (that moves the same ceiling from compile time to runtime). `groupBy` and `aggregate` are ordinary SQL rather than exotic features, so their absence is a real long-term constraint: the moment eval or observability work wants aggregate statistics over runs, this reopens on its own merits. The ports boundary keeps that reversible — every repository already implements a port, so a later query-layer migration never reaches `app-services` or any component.
- **The derivation is a header substitution, and the derived schema is a build artifact rather than a source file.** The authored file stays a complete, valid schema (`prisma/sqlite/schema.prisma`) so that editor tooling and `prisma validate` keep working on it; the script replaces its thirteen-line generator/datasource header to produce `prisma/postgres/schema.prisma` and copies the models verbatim. A headerless models fragment was the alternative and is worse: Prisma requires a datasource block to validate, so the file every schema change is actually written in would be the one file with no tooling. The asymmetry of treating SQLite as the source is honest rather than incidental — it is the default install. The derived file is gitignored, alongside the generated clients, which is what removes the need for a drift check: a committed derived schema would need CI to verify it, whereas one rebuilt before every consumer cannot drift. It also costs nothing in review, since it is byte-identical to the authored schema below the header, so reading the authored diff already reads both.
- **Generation already runs on every build, so the derivation joins that chain rather than adding a new gate.** `packages/db-prisma`'s `build` and `typecheck` both run `prisma generate` first and the generated client is untracked, so CI regenerates from the schema on every run and no generated artifact can be stale. The derivation becomes its own script that both `generate` and the migrate scripts depend on — every Prisma command needs it to have run, not just generation. One quiet benefit of keeping the derived schema untracked: Turborepo hashes a package's non-ignored files and the build task declares no custom `inputs`, so the cache key comes from the authored schema, which is the real source. Committing the derived file would let a hand edit to it produce a cache hit that ignores the change.
- **`@lcase/db-prisma` gains a subpath per provider rather than splitting into two packages.** A subpath is a real import-path difference, which is the property that matters; splitting is available later if a runtime that uses one provider ends up carrying the other's client. The package root currently re-exports the single generated client's types wholesale, and that flat shape is what has to change. The narrow side also wants re-exporting under a provider-neutral name, so repositories do not read as SQLite-flavoured even though the type is exactly that.
- **The seam narrowing introduces no shared type.** The seams stay seven local aliases, each still typed against the SQLite client, which is the contract precisely because it is the narrower of the two. Only the granularity changes, from a model-level `Pick` to a method-level one: `Pick<PrismaClient, "run">` becomes `{ run: Pick<PrismaClient["run"], "findUnique" | "findMany" | "update" | "upsert"> }`. No repository body changes, which the spike verified by typechecking the package with these in place.
- **A compile-time assertion is what makes portability enforced rather than asserted.** Since nothing in this Change constructs a Postgres client, nothing would notice if the Postgres client stopped satisfying a seam — the first `groupBy` added to a repository months from now would break it silently. So `packages/adapters` needs a type-only import of the Postgres client asserting all seven seams, failing `typecheck` rather than a test run. Without it this Change proves portability in a document instead of in the build.
- **Nothing constructs a Postgres client in this Change, and it turned out to be authorable with no Postgres at all.** The runtime keeps using the SQLite singleton exactly as it does today, and `prisma generate` is offline, so both clients build with no database anywhere. Migrations looked like the exception, since `migrate dev` provisions a shadow database on the same server — but `migrate diff --from-empty --to-schema` renders the same initial DDL with no connection, which is how the Postgres init migration was actually written. Postgres still joins `docker-compose.yml` next to minio and redis, because the check that _would_ need it does: `migrate diff --from-migrations` refuses without `shadowDatabaseUrl` on every provider except SQLite, so nothing here verifies the Postgres history against its own schema. That check, and the first real application of that migration, belong to C17. What this Change proves is that both clients build and both satisfy every repository seam.

### What actually landed

Both clients generate from one authored model source, all seven repository seams accept either, and a compile-time assertion enforces that rather than a document asserting it. `packages/db-prisma` gained `./sqlite` and `./postgres` subpaths; its root now exports a single type.

- **The whole Change turned out to be authorable offline, which the discussion above had wrong.** `migrate diff --from-empty --to-schema` renders the initial DDL with no connection, so the Postgres init migration was written without a Postgres running at all. It has since been applied to the compose container and creates all ten tables, so the offline-authored SQL is real rather than merely plausible. What still needs a server is `migrate diff --from-migrations`, which refuses without `shadowDatabaseUrl` on every provider but SQLite, so nothing yet checks the Postgres history against its own schema; that check belongs to C17. The SQLite equivalent runs offline and reports no difference.
- **The compose service host port is 5434, and that is a considered choice rather than an arbitrary one.** A machine with native Postgres installs can hold both of the obvious ports: an EnterpriseDB 15 and 16 side by side listen on 5432 and 5433, which is exactly what the machine this was built on had. Docker reports that collision as `ports are not available … bind: address already in use`, which reads as a Docker fault and sent the first diagnosis down the wrong path entirely. The port is `${POSTGRES_HOST_PORT:-5434}` so a third clash needs no edit to a tracked file. Worth recording because adding any service to the compose file makes a bare `docker compose up` fail for everyone whose machine already claims that port, whether or not they use the new service.
- **The derived schema is a build artifact, and that removed a check rather than adding one.** `scripts/build-schemas.mjs` splits the authored SQLite schema on a `// ---- shared models ----` sentinel and re-emits everything below it under a Postgres header. Because the output is gitignored and rebuilt before every Prisma command, it cannot drift, so no CI comparison is needed. Keeping it untracked also keeps Turborepo's cache key honest: the hash comes from the authored schema, where a committed copy could be hand-edited into a cache hit that ignores the edit.
- **The seams stayed local and gained no shared abstraction.** Seven aliases moved from a model-level `Pick` to a method-level one, spelling out the six methods actually used across all ten models (`create`, `findFirst`, `findMany`, `findUnique`, `update`, `upsert`). No repository body changed. They are typed against `SqlClient`, which is concretely the SQLite client under a provider-neutral name — the narrower client is the contract, and that asymmetry is the mechanism, not an accident of naming.
- **The parity assertion was verified by breaking it on purpose.** `packages/adapters/tests/prisma-provider-parity.ts` asserts `PostgresClient extends Seam` for all seven. Adding `groupBy` to one seam fails `pnpm typecheck` with an error naming both the seam and `run.groupBy`; without that check the same edit would have stayed green until something finally constructed a Postgres client. It is not a `.test.ts`, so vitest skips it, and `tsconfig.json` includes only `src`, so it never reaches `dist` — it exists purely to fail a typecheck.
- **The migration collapse was a genuine collapse, not a rename.** Five SQLite migrations became one init covering all ten models, and Postgres got its own single init from the same models, both under `prisma/<provider>/migrations`. The two histories share a timestamp deliberately: they are the same baseline. Identical models produce visibly different SQL, `CREATE TYPE` on Postgres against `TEXT` on SQLite for the same enum, which is Prisma's job rather than something needing an overlay.
- **Test churn was two mechanical edits, held back on purpose.** Twelve suites repointed at `prisma/sqlite/migrations`, and twelve switched their client import to `@lcase/db-prisma/sqlite`, which is the honest path for a test that builds a SQLite file. The duplicated migration-applying helpers were left alone rather than folded together, since C17 replaces them with a shared harness and touching them twice would be wasted work.
- **Verification.** Workspace `build` 25/25 and `typecheck` 24/24, all package suites green including the 108 adapter tests, integration suites green, prettier clean. A from-scratch rebuild with `src/generated` and the derived schema deleted regenerates both clients and emits all three subpath entry points.

## Change C17 - Shared repository contract suites against real SQLite and Postgres - merged (PR #376)

### Discussion

- **The twelve existing SQL tests are SQLite-shaped in a way that will not survive.** Every Prisma adapter test and five `apps/http-server` route tests construct `PrismaBetterSqlite3` directly against a temp file and hand-apply migration SQL by splitting the file on `;`. That works only because SQLite migrations here are flat `CREATE TABLE`s with enums erased to `TEXT`; Postgres emits `CREATE TYPE ... AS ENUM` and the naive split stops being safe.
- **The duplication is the opportunity, not just the problem.** All twelve files carry the same 28-line `applySqlFile`/`applyMigrations` pair byte-for-byte — 336 duplicated lines that collapse into one harness. So the headline figure (3,691 lines across those files) badly overstates the churn: assertions largely move unchanged, and the total is as likely to shrink as grow.
- **This is where the repo-wide test-style question gets its first worked example.** A shared database harness has to be built here regardless, which makes it the cheapest available moment to establish the pattern against a real case rather than write a convention in the abstract. See the corresponding `docs/todo.md` entry; that broader review stays out of this arc.
- **Behavior assertions become provider-agnostic; setup and teardown stay provider-specific.** Database semantics are the thing this Change actually tests and the thing types cannot prove — transaction semantics, constraint and cascade behavior, collation and case sensitivity, timestamp precision, ordering of unordered queries, and error mapping.
- **Running under integration is a filename convention plus an environment gate, and the selection mechanism had to change to make it one.** Distinguishing by filename rather than folder was chosen deliberately, so the selection survives directories being rearranged. But the `test` glob (`tests/**/*.test.[jt]s`) also matches `*.integration.test.ts`, and `test:integration` was only a path-substring filter over the same set, so every integration file belonged to both tasks. The existing suites survived that by accident rather than design: Turborepo's strict environment mode strips the undeclared variables under `test`, so they loaded and skipped. The SQLite suites have no gate and would have run twice in full. So each package gains a second vitest config, and the default one excludes what the integration one selects. `test:integration` also sets `cache: false`; caching it is acceptable once the suites provision and reset their own state, with the one exposure being that Turborepo cannot hash container state, so a cached pass replays even if the server was later stopped or recreated on a different image.
- **The harness becomes `packages/test-support`, and one import rule keeps it from spreading.** It supplies infrastructure and never domain objects: per-provider provisioning returning a live client plus reset and dispose, migration application, the environment gate so twelve files stop reading `process.env` directly, and a provider-matrix helper so one contract body runs twice without each suite hand-rolling the loop. That rule fixes its dependencies at `@lcase/db-prisma` plus the two Prisma driver adapters — not `@lcase/adapters`, not ports, not services — because the consumer constructs its own repositories against the returned client. A subpath of `@lcase/adapters` was the alternative and was rejected: the helpers would then ship inside a package the runtime depends on. The dev-dependency edge is real, since Turborepo traverses `devDependencies` for `^build`, but it adds one small package at a depth both consumers already reach through db-prisma. Domain fixtures stay where they are, in `packages/adapters/tests/fixtures`.
- **Migrations get applied by `prisma migrate deploy`, once per provider in a vitest global setup.** The hand-rolled `;`-splitter goes away rather than getting smarter, and truncation becomes the per-test reset, so the cost is one subprocess per provider per run instead of a file read and dozens of raw statements per test. It also populates `_prisma_migrations`, so the database matches what the application would really see. `prisma db push` is the faster alternative and the wrong one: deriving the schema straight from the models means a broken migration passes the suite.
- **Isolation is a Postgres database per vitest worker, cloned from a migrated template.** Vitest runs test files in parallel, so suites sharing one database and truncating between tests would clobber each other intermittently. Global setup migrates a template once and each worker issues `CREATE DATABASE ... TEMPLATE`, which copies rather than re-migrating; isolation then comes from the database name in the connection URL, which every driver understands. A schema per worker was the first proposal and is cheaper to create, but it depends on the search path reaching the connection — and `?schema=` was a Prisma query-engine feature, while Prisma 7 hands the connection string to the driver rather than parsing it. Choosing the database means that question never has to be answered. A spike settled this before any harness code was written, because the alternative was designing against an unverified driver behaviour.
- **`@prisma/adapter-pg` arrives in this Change, not C18.** The earlier plan deferred it to whenever something first constructed a Postgres client, on the assumption that would be the runtime. The contract suites construct one, so it lands here. Only `@prisma/adapter-better-sqlite3` is in the tree today.
- **The Postgres migration history finally gets checked against its own schema.** C16 left that gap open on purpose: `migrate diff --from-migrations` refuses without a `shadowDatabaseUrl` on every provider but SQLite, and there was no Postgres running. There is one here, so the check becomes possible for the first time.
- **The route tests keep the harness, stay SQLite-only, and their real fate belongs to C18.** Three different things are fused in those five files: repository behavior against a real database, which is what the contract suites are for; route behavior given a service, which needs no database at all and would be clearer against a fake `ServicesPort`; and that composition wires the right concrete things, which is a genuine gap nothing covers. The tell is that `apps/http-server` depends on `@lcase/runtime` for its code and carries `@lcase/adapters` only as a devDependency, purely so those tests can hand-compose six repositories that `createLocalSystem()` already constructs for real — a parallel composition that can drift from the actual one with nothing to catch it. The reason not to fix it here is a blocker rather than scope discipline: `local-system.profile.ts` imports the module-global `prisma` by deep relative path into `dist`, built at import time from `DATABASE_URL`, so it cannot be pointed at a test database without setting an environment variable before module load. C18 removes that singleton, which is what makes a real composition test possible.
- **Postgres joins the CI integration job here**, alongside the existing MinIO and Redis services; it already joined `docker-compose.yml` in C16. Change C14's finding applies directly: any new environment variable must be added to `turbo.json`'s `test:integration` `env` array, or Turborepo strips it and the suite skips silently in CI while passing locally.
- **Availability is probed, and the connection URL defaults in code rather than in an env file.** The first shape gated the Postgres half on `POSTGRES_TEST_URL` being set, which reproduced the exact failure C14 recorded: forget the variable on a machine where the container is running, and the suites skip while reporting success. So the URL defaults to the compose service the same way `prisma.postgres.config.ts` does, the variable becomes a pure override for a different host or port, and global setup decides availability by actually reaching the server. A skip now means there is no server. This also settles where local defaults live, which was otherwise heading toward either a second tracked env file — two files, unclear precedence, unclear where a developer puts their own edits — or a script that copies defaults on first run, whose copy then never refreshes and silently shadows later changes. A default in code has one home, needs no copying, and cannot go stale.
- **The compose container is the local database too, not just CI's.** A developer machine may already run native Postgres servers — the one this was built on runs two — and pointing the suites at whichever of those happens to exist would make the tests depend on a version, a superuser, and a database nobody declared. The container is declared, disposable, and identical to what CI runs, so the only cost of preferring it is remembering that its host port is not 5432.

### What actually landed

All seven repository suites run their existing assertions against both real databases, and 129 tests pass with no assertion changed. That last part is the actual finding: the repositories behave identically on SQLite and Postgres, so the parity C16 proved in the type system holds in behaviour too.

- **Not one assertion needed a provider conditional.** The plan expected the opposite and said so — ordering of unordered queries, case sensitivity, and timestamp precision genuinely differ between the two, and a suite failing on Postgres was anticipated as likely to be asserting SQLite incidentals. None did. The repositories already order explicitly and compare exactly, so the suites moved across untouched.
- **`Omit` cannot express the portable-client type, and the reason generalises C16's spike.** Narrowing to "everything except `aggregate` and `groupBy`" states the real rule and does not compile. A generated delegate also carries a `types.operations` metadata property describing every argument shape, and those sit in covariant positions that recurse into provider-specific `WhereInput` types, so contravariance does not rescue them. `Omit` keeps that property; picking method names drops it. This is why C16's seams work and is worth knowing before anyone tries to write a tidier version of either.
- **The type is the assertion, so there is no separate assertion.** `createPostgresTestDb` assigns a Postgres client to a type written against the SQLite one, with no cast. It either compiles or the harness does not build. The `Omit` attempt above was the negative control for it, failing loudly on exactly that line before the `Pick` version passed.
- **The database-per-worker mechanism was proven before anything was designed around it.** A throwaway script confirmed the `lcase` user can create a database from a template, that a clone carries both the schema and `_prisma_migrations`, and that truncating one worker's database is invisible to another's. The search-path question the schema-per-worker alternative rested on never had to be answered.
- **`migrate diff` needs a shadow database that already exists**, unlike `migrate dev`, which creates one. `prisma db execute` provisions it, and that creation doubles as the reachability probe and is allowed to fail when it already exists, so the check is re-runnable — the second run simply finds it there. `scripts/check-migrations.mjs` covers both providers, skips Postgres when no server is reachable, and was verified by adding a model to the schema and confirming it fails naming both.
- **The default is the standard port, and `POSTGRES_HOST_PORT` is the one knob that moves everything.** The first revision inverted this: 5434 was committed as the default because the development machine runs native Postgres on 5432 and 5433, so one contributor's port conflict became everyone's default. CI then published 5432 instead, and since `prisma.postgres.config.ts` falls back to the compose port and never reads `POSTGRES_TEST_URL`, the migration check fell through to a port with nothing on it and reported the result as drift. The fix was to make the default conventional and derive every client-side URL from the same variable Compose already substitutes, so setting it once in `.env` moves the binding, the Prisma configs, the suites, and the drift check together. Previously the port lived in two independent variables that had to be kept in agreement by hand, which is exactly how this broke.
- **Two smaller faults surfaced while doing that, both the same shape.** `check-migrations.mjs` read the port variable without loading `.env`, so it stayed on the default while everything else followed the override — caught immediately, because on this machine the default port is a foreign server that rejected the credentials. And the harness treated _any_ setup failure as "no server", so those same rejected credentials reported as unreachable and silently skipped all 61 Postgres tests while the run reported success. That is Change C14's failure mode a third time. Skipping is now limited to connection-level errors, which Prisma separates cleanly: `ECONNREFUSED` for nothing listening, `P2010` wrapping the driver's own error for a server that answered and refused. The general shape is worth remembering — a default that happens to match the development machine hides a missing value until something runs somewhere else.
- **Locating `@lcase/db-prisma` from inside a test is not possible the obvious way.** `import.meta.resolve` is absent in vitest's module runner, so global setup shells out through pnpm's workspace filter instead, which finds the package from anywhere and sets its directory as the working directory. That is also what the relative `--config` path needs.
- **The cost is smaller than budgeted.** The adapter integration suites take 5.2s against SQLite alone and 8.3s against both, rather than the doubling the plan braced for. The twelve suites lost 362 lines net while gaining a second provider, and `packages/test-support` is 427 lines including its comments.
- **Global setup comes in two entry points, one per provider need.** The default migrates both templates; `sql-global-setup/sqlite` migrates only SQLite. `apps/http-server` takes the second, because its suites never construct a Postgres client and the default would otherwise pay a `CREATE DATABASE` and a `migrate deploy` subprocess on every run for a template nothing reads. That waste was real and measured before the split, not anticipated.
- **`packages/test-support` has real ESLint rather than the `echo lint` stub** most packages still carry, taken as the moment to do it since the package is new.
- **Verification.** Workspace `build` 26/26, `typecheck` 25/25, `lint` 25/25, unit `test` 24/24, integration green across all three packages, both migration histories reported clean, prettier clean. Pointing `POSTGRES_TEST_URL` at a dead port reports the server as unreachable, names the command that starts it, and leaves the Postgres halves reported as skipped rather than silently absent.

## Change C18 - Extend the `local-system` profile with the `postgres` SQL branch - merged (PR #377)

### Discussion

- **Less mechanical than the original scaffold assumed, because there is no config selection on this axis yet to extend.** `SqlConfig` is threaded through `LocalSystemConfig` and both app configs, but nothing reads it: `packages/db-prisma/src/client.ts` exports a module-global `prisma` constructed at import time from `DATABASE_URL`, and both the profile and its observability builder import it by deep relative path into `dist` rather than through the package export. So the first half of this Change is removing that singleton in favor of provider-specific client construction, and only then does Change C3's `buildArtifactStore` pattern apply.
- **Provider selection is per process, decided at composition, and is not hot-swappable.** One selected client instance is shared by every repository including observability's, which means `buildObservability()` receives repositories rather than importing the global itself. Connect, health check, and disconnect join the managed runtime lifecycle. Changing the configured backend does not move data between them.
- **The shared narrowed client type stops being test-only, and promoting it costs no adapter change.** Because one client instance feeds all seven repositories, composition needs a single type satisfying all seven seams at once — a value rather than a parameter, which is the thing C16 correctly declined to build when nothing yet held one. C17 built it anyway for the harness (`TestSqlClient`), so it moves to `@lcase/db-prisma` beside `SqlClient` and the harness imports it instead of owning it. The two are different roles and both survive: a seam states what one repository _requires_, spelling out only the methods it calls, while the promoted type states what composition _provides_. Both are derived from the SQLite client, so their members are identical rather than merely compatible. The only addition over the harness version is `$connect`, which a managed lifecycle needs and a test never did.
- **Verified by compile probe before planning, not assumed.** A throwaway file in `packages/adapters` asserted the promoted type against all seven seams and both concrete clients against the promoted type. Nine assertions, all passing, with no adapter edited. Adding `aggregate` to the portable method set was the negative control and failed on the Postgres assertion, so the probe was live rather than vacuously green.
- **Whether the seams re-base onto the promoted type is a real trade, left open until planning.** They currently `Pick` from the full SQLite client, so a repository reaching for `groupBy` compiles and is caught afterwards by `tests/prisma-provider-parity.ts`. Picking from the portable type instead fails at the seam itself, which is earlier and names the right file. The cost is that the seven parity assertions then collapse into one, since a subset of an already-portable type is portable by construction — one blunt error in place of seven precise ones.
- **The route tests are explicitly out of scope, superseding C17's forward reference to this Change.** C17 recorded that their fate belonged here, on the grounds that removing the singleton is what unblocks a real composition test. Removing it still does, and this Change still does it. Taking the unblocked work as well would fuse a composition change with a test-level redesign that has its own shape and its own trigger: those five files fuse repository behavior, route behavior, and composition into one level, and separating them belongs to the repo-wide test review in `docs/todo.md` or to genuine end-to-end coverage for `apps/*`. So `apps/http-server` keeps hand-composing its six repositories, and the drift that allows stays recorded rather than fixed.
- **The absolute SQLite path in `.env.example` goes away here, because this is the code that computes it.** Nobody actually has to set `DATABASE_URL` today: both `client.ts` and `prisma.sqlite.config.ts` already resolve the same repo-root default from their own module location, so the CLI and the runtime agree from any working directory. What the example file teaches is the opposite, and a relative override is currently ambiguous, meaning the schema directory to the CLI and the working directory to better-sqlite3. The rule worth adopting is that a relative `file:` URL resolves against the directory of the `.env` it came from, which yields today's value while dropping the fixed walk-up from a module path, and stays correct once an app supplies the URL through config instead. A deployed app never reads `.env.example`, so its own private database is a matter of passing a different value, not of path format. Also worth clearing up in passing: `packages/db-prisma/.env` is a Prisma scaffold leftover that nothing reads, since both configs point dotenv explicitly at the repo root file.
- **`apps/http-server` and `apps/cli` still pick it up for free** once the branch exists, the same way they did for the CAS and messaging axes.
- **This is the Change that makes the arc count as a swappability proof.** Following the precedent set by Change C3 for MinIO and Change C14 for Redis, that means pointing an app config at Postgres, running a real flow end to end, confirming the data landed, and reverting the config afterward — a local edit rather than a permanent env-var branch.
- **It is also the last Change in this arc, and it is expected to land whole.** The four pieces above (retire the singleton, promote the type, the relative SQLite path, the end-to-end proof) are one coherent piece of composition work, and none of them is semantically risky the way C15 was. If that holds, the initiative's three adapter axes are all real and the Remote Worker Arc becomes the next work, beginning at C19 — the thing this initiative says it exists for.

### What actually landed

`sql` is a real config axis. A two-step flow with a param and a chained export ran end to end against Postgres through `apps/http-server`, writing `Run`, `RunParam`, `RunStepProjection` and `RunStepExport` rows and reading back through `GET /api/runs/:id`, then the same flow ran against SQLite from the same code path. The module-global client is gone.

- **`$connect()` does not reach the server, which made the first version of this Change report a healthy start against a database that was not there.** Measured, not assumed: pointed at a dead port, `$connect()` resolved cleanly and `runtime.start()` returned `ok`. Under a driver adapter the pool connects on demand, so the connect call proves nothing. The start hook now issues one `SELECT 1`, which turns an unreachable database into a failed start naming `sql` as the resource, and rollback takes care of the rest. This is Change C14's failure shape a fourth time, and the first one caught by looking rather than by a later symptom.
- **The default URLs had the same asymmetry, and it would have bitten during this Change's own proof.** Only the SQLite default loaded the repo-root `.env`; the Postgres one read `POSTGRES_HOST_PORT` straight from `process.env`, which no app populates. On a machine that overrides that port the server would have silently reached for 5432 and found a foreign server. Both defaults now live in `@lcase/db-prisma` (`defaultSqliteUrl`, `defaultPostgresUrl`) and both load the same file, and the two Prisma CLI configs call the same functions rather than reimplementing them — which removed the third copy of the port derivation as a side effect.
- **The repo root is found by walking up for `pnpm-workspace.yaml` rather than by counting `..` segments.** The old fixed depth was correct from `dist/` and would have been silently wrong from `src/`, which matters because `prisma.sqlite.config.ts` imports this module directly and the Prisma CLI loads that config before anything is built.
- **`url` is optional on both branches, and that is what kept both app configs untouched.** Neither `apps/http-server` nor `apps/cli` needed an edit to compile or to run, which was the check on the decision: an app names a database only when it wants a different one. Switching the server to Postgres for the proof was a one-word edit.
- **SQL starts first and stops last.** The projection sinks write through this client, so disconnecting before they stop would drop their final writes. `assembleEmbeddedSystem` gained a required `sql` field rather than an optional one, so every call site fails to compile instead of quietly assembling a system without it.
- **`buildObservability()` stopped constructing its own repositories.** It was the one place that quietly reached for a different client than the services used; it now receives the three it writes through. That is also what forced the profile to construct `PrismaRunStepProjectionRepository`, which had existed only inside that function.
- **Promoting the client type cost no adapter change, as the pre-planning probe predicted.** `PortableSqlClient` moved into `@lcase/db-prisma`; `packages/test-support` keeps the name `TestSqlClient` as an alias so none of the seven contract suites moved. The assignment in `buildSqlClient` is the parity check for both providers, the same way the test harness's is, so there is still no separate assertion to keep in sync.
- **Verification.** Workspace `build` 26/26, `typecheck` 25/25, `lint` 25/25, unit `test` 24/24 including one new suite, integration green across all three packages, both migration histories clean, prettier clean. The lifecycle was checked directly for both providers: healthy start, healthy report, clean stop with no errors, and a failed start with an accurate reason against a dead port. The SQLite branch was confirmed to write to the repo-root database while running with the working directory set to the app, which is the property the path rule exists to preserve.

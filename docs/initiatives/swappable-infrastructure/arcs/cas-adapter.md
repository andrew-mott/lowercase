# Prove Swappable Infrastructure Initiative — Arc: CAS Adapter (Changes C1–C3)

**Next:** [`queue-adapter.md`](./queue-adapter.md) (Changes C4–C5, C7–C9, C11–C14)

Part of the [`INITIATIVE.md`](../INITIATIVE.md) Change log, split out to keep that doc scannable. Builds a real S3-compatible CAS adapter (backed by MinIO for local/dev), replacing `FsArtifactStore`, and wires it into `packages/runtime`'s config selection.

## Change C1 - S3-compatible CAS adapter (MinIO-backed) + local/CI scaffolding - merged (PR #360)

Picked as this initiative's starting adapter — `ArtifactStorePort`'s surface (`getBytes`/`putBytes`, content-addressed) is the narrowest of the three candidate ports and already hardened by the `worker-tools-artifacts` refactor, making it the lowest-risk way to prove the pattern before tackling the queue or SQL.

### Discussion

- **Built against the standard S3 API, not MinIO-specific.** Using `@aws-sdk/client-s3` means the adapter talks the actual S3 HTTP API; MinIO differs only in client configuration (a custom `endpoint`, `forcePathStyle: true`, MinIO access/secret keys instead of AWS IAM creds), not in the calls themselves (`PutObject`/`GetObject`, maybe `HeadObject`). Since the store is already content-addressed (sha256 owned client-side), it has no reason to depend on provider-specific quirks like S3 ETag semantics, which is one of the few places real AWS S3 and MinIO diverge at the edges. Named `S3ArtifactStore`, not `MinioArtifactStore`, accordingly — the same adapter should work unmodified against real AWS S3, Cloudflare R2, Backblaze B2, Garage, or SeaweedFS later, just by changing endpoint/credentials.
- **MinIO chosen over Garage/SeaweedFS** (both real, more-permissively-licensed S3-compatible alternatives) — MinIO is the most standard, best-documented self-hosted option, and since the adapter isn't MinIO-specific, switching later would mean almost no code changes anyway.
- **Scope deliberately includes local/CI scaffolding in this same Change, not a separate infra-only Change beforehand.** An infra-only Change (a compose file + a CI services block, no adapter code) has nothing real to validate itself against; a real integration test that actually puts/gets a blob against a live MinIO container proves both pieces together. This Change is where the "how do integration tests find a real backend, locally vs. in CI" pattern gets established — a `docker-compose.yml` service, env-var-gated integration tests, a GitHub Actions `services:` block (native support — MinIO/Redis/Postgres are all common as GH Actions service containers, not a big ask) — for the later adapters (Redis, Postgres) to reuse rather than reinvent.
- **Secrets**: plain gitignored env vars for MinIO credentials. Real secret management stays deferred, matching the same call already made when `worker-tools-artifacts` punted secrets to a future initiative.
- **Object keys are flat (`hash`), not sharded by prefix.** `FsArtifactStore` shards (`hash.slice(0,2)/hash.slice(2,4)/hash.slice(4)`) because filesystems need it; S3/MinIO don't have the same directory-fanout problem. Only add sharding back if it actually causes a problem for some backend down the line — not preemptively.
- **`S3ArtifactStore` takes an injected `S3Client` + bucket name, not config it builds internally.** All MinIO-specific setup (`endpoint`, `forcePathStyle: true`, MinIO credentials vs. AWS IAM) stays in whatever constructs the client (`packages/runtime`, or a test), keeping the adapter itself backend-agnostic per the S3-not-MinIO-specific decision above, and making it trivial to point at a real MinIO container in integration tests or a mocked client in unit tests.
- **Content-type is native object metadata** (`PutObjectCommand`/`GetObjectCommand`'s `ContentType`), not a `.meta.json` sidecar like the FS adapter needs — a genuine simplification, not just parity.
- **Buffer in, buffer out, matching the port's existing contract** — no streaming. `PutObjectCommand`'s `Body` takes a `Uint8Array` directly; reads use the SDK's built-in `res.Body.transformToByteArray()` rather than manual stream consumption. Revisit only if artifact size ever makes whole-buffer I/O a real problem — that would be a port-level change, not an S3-adapter-only one.
- **A pre-write existence check (`HeadObjectCommand` before `PutObjectCommand`) is optional, not required for correctness.** Content-addressing already guarantees same hash → same bytes, so a blind overwrite is always a no-op; the only reason to check first is to skip a redundant network write. (`FsArtifactStore` already does this check today, for the same optimization reason — nothing to retrofit there.)
- **`ArtifactStorePort.getBytes()` is being widened as part of this Change, not deferred.** Today it returns `T | null`, collapsing "not found" and "read failed for some other reason" into the same `null` — `FsArtifactStore` fail-closes on everything (missing file, missing sidecar, permission error, corrupt JSON) into that one `null`. Since this Change introduces the port's second real implementation, now is the right time to distinguish them rather than revisit both adapters again shortly after. `ArtifactReader.load()` (`packages/artifacts/src/artifact-reader.ts`) is the port's only production consumer, and `ArtifactLoadError` already has an unused `cause?: string` slot ready for this — a new `code` (e.g. `"STORE_ERROR"`) added to its existing union, populated from the store's read failure, is the natural landing spot. One real behavioral call this forces: content present with a missing/corrupt sidecar is today treated as "not found" — under the widened result that's arguably a store error instead, and needs deciding deliberately rather than preserved by accident. `FsArtifactStore` needs its catch blocks (both the primary sidecar read and the legacy-extension fallback loop) rewritten to distinguish `ENOENT` from other thrown errors instead of blanket-catching.
- **New shared error shape adopted for this widening: `DomainError<Code>`.** Surveyed the codebase for existing error-shape conventions and found two already-mature but divergent ones — `ArtifactLoadError`-style (`{code (closed union), message, cause?: string}`) and the worker's `JobExecutionError`-style (`{code (closed union), message, retryable: boolean}`). Rather than add a third shape, consolidating on a shared base:
  ```ts
  export type DomainError<Code extends string> = {
    code: Code;
    message: string;
    cause?: string;
  };
  ```
  `cause` stays a `string` (not `unknown`/`Error`) deliberately — several of these error shapes eventually thread toward HTTP response types, and a string serializes cleanly with no boundary-conversion step. `retryable` isn't part of the shared base (most domain errors have no retry semantics); the worker's type becomes `DomainError<JobExecutionErrorCode> & { retryable: boolean }` on top of it instead of a fully separate shape. Lives in `packages/types` since both `packages/ports` and `packages/components/worker` need it. This does **not** touch the much larger, separate inconsistency of bare-string `Result<X, string>` used across most of `packages/app-services`/`packages/ports`/the HTTP API types — that's real debt but a much bigger migration, deliberately out of scope here. No dedicated ADR for this — the type is meant to document itself at the use site.
- **Contract tests, established here for reuse by later adapters.** No port in this codebase currently has more than one real implementation, so there's no existing shared/parameterized port-contract-test pattern to follow — every adapter test today imports its one concrete class directly. This is the first port getting a second real implementation, so it's a natural place to introduce `runArtifactStoreContractTests(factory: () => ArtifactStorePort)`, parameterized over `FsArtifactStore`, `S3ArtifactStore`, and the existing `createFakeArtifactStorePort()` test fake — reusing the real assertions already in `put-bytes.test.ts`/`get-bytes.test.ts` plus new cases for the widened 3-way `getBytes` result. The Redis and Postgres adapters (Changes C4 and C15 under the current numbering) should reuse this pattern rather than hand-writing disconnected test files again.

### What actually landed

Matches the design above on every structural point — flat keys, injected `S3Client`+bucket, native content-type, buffer in/out, no pre-write check, `DomainError<Code>` — with a few things sharpened or added along the way:

- **`getBytes()` ended up fully `Result`-wrapped, not `T | null` plus a bolted-on code.** `ArtifactStorePort.getBytes()` now returns `Promise<Result<ArtifactStoreGetSuccess, ArtifactStoreGetError>>` (both types finalized as `Get`-prefixed, matching the port's own `getBytes`/`putBytes` vocabulary, not the `Read`-prefixed names floated mid-design) — `null` is gone from the port entirely, not left alongside a widened error union. `ArtifactLoadError` was consolidated onto `DomainError<Code>` too, picking up `STORE_ERROR` in its union so `ArtifactReader.load()` forwards `stored.error` straight through with no mapping step.
- **`FsArtifactStore.getBytes()` rewritten as planned**, splitting the old single `Promise.all` catch into sequential content-then-meta reads so `ENOENT` (→ legacy fallback) is distinguishable from a real error (→ `STORE_ERROR`) — including the missing-sidecar case, which now correctly surfaces as `STORE_ERROR` instead of silently `NOT_FOUND`.
- **Contract suite deliberately does _not_ include the fake**, reversing what's sketched above — a later discussion (see `docs/todo.md`'s "should a unit test's fake be a real reimplementation" entry) concluded that running a fake through the _full_ contract would force it to grow real logic to pass, defeating the point of keeping it thin. Suite covers `FsArtifactStore` and `S3ArtifactStore` only.
- **Added beyond the original plan: `s3-artifact-store.test.ts`**, a always-running, mocked-`S3Client` unit test (via `aws-sdk-client-mock`) covering the `STORE_ERROR`/`cause` mapping the contract suite can't easily trigger against real MinIO without deliberately breaking the connection.
- **MinIO image: `bitnamilegacy/minio`, not `bitnami/minio`.** Discovered mid-build — Bitnami moved its free-tier images to a separate `bitnamilegacy` namespace in 2025; the plain `bitnami/minio:latest` tag no longer resolves. Still the right image choice otherwise (runs correctly from env vars alone, no command override needed — what the official `minio/minio` image would require and GitHub Actions' `services:` block has no field to supply).
- **Local dev tooling, not originally scoped**: root `pnpm test:integration` (`docker compose up -d --wait` + fixed local MinIO creds, then `turbo run test:integration`), scoped to just the infra-gated test file via a `.contract.integration.test.ts` filename convention (composing two independent axes — "uses the shared contract suite" and "needs real infra" — so `test:integration` targets only the second without re-running the rest of a package's unit suite). Needed one non-obvious fix: Turborepo 2.x strips undeclared env vars from tasks by default, so the `S3_TEST_*` vars had to be explicitly listed under the task's own `env` in `turbo.json`, or the integration test silently skipped even with MinIO running.
- **Verified against live MinIO, not just typechecked** — full contract suite (round-trip, `NOT_FOUND`, idempotency) run against a real `docker compose`-started container, both from a cold start (image pull + healthcheck wait) and already-running, confirming `docker compose up -d --wait` is a correct no-op either way.

## Change C2 - Shared assembly layer + leaf config types in `packages/runtime` - merged (PR #361)

Originally scoped as one Change ("wire CAS adapter into `packages/runtime` config"). Split into this Change plus Change C3 once the runtime-composition research (below) made clear the real work is building the assembler/profile system generally, with CAS just being the first, and so far only, port with a real choice behind it. This Change is the foundational half: the shared, adapter-agnostic assembly machinery and config vocabulary, no concrete profile yet.

### Discussion

- **Commissioned deep research before designing further, rather than iterate on the existing registry.** Today's `placement × transport × store` lookup table (`packages/runtime/src/registries/`, `factories/registry.factory.ts`) is mostly decorative — every cell of the bus and queue registries collapses to the same in-memory implementation regardless of which axis values are selected, only the limiter has a genuine single real cell, and CAS has no axis at all (`makeRuntimeContext()` just does `new FsArtifactStore(config.artifacts.path)` directly). SQL sits fully outside the pattern too — both composition roots import a singleton `prisma` client straight from `../../db-prisma/dist/client.js`. Rather than patch that, asked for a full survey of the design space instead. Full output: [`research/runtime-composition-strategies.md`](../research/runtime-composition-strategies.md). The prompt separated fixed constraints (infra must be swappable per-port; some components will eventually run out-of-process; placement and transport are not the same axis — a component can stay embedded while still talking to something like Redis Streams) from genuinely open questions (one runtime vs. many, containerization, connection lifecycle, static-vs-dynamic config granularity), and asked the research to preserve two things already working in this codebase: the inbound/outbound-port split used for real components (Worker V2's `ports/inbound`/`ports/outbound`), and the fact that infra gets swapped locally for two different reasons — durability (S3/Postgres over fs/SQLite, no other process involved) versus an extensibility/observability seam (Redis Streams, so an external consumer can attach to what the engine is doing even while everything stays in one process).

- **Result: three genuinely different approaches surveyed, Approach 2 chosen.** Approach 1 is a universal config-driven runtime importing every provider and selecting among them at startup — close to today's actual shape (one `makeRuntimeContext()`, one config, nominal per-port selection). Approach 2 is explicit per-process-role deployment profiles, each a thin composition module importing only the adapters that role needs, built over one shared, technology-independent assembler. Approach 3 is runtime-loaded provider plugins, installed and versioned independently of the host runtime. Approach 2 won: it gives real separated dependency graphs per deployable — the concrete near-term need, since an eventual isolated worker process shouldn't pull in Fastify, HTTP routes, or unrelated adapters just because it shares a runtime package with `apps/http-server`. Approach 3 solves for arbitrary/third-party-installed providers, which isn't a real requirement yet ("more architecture than the near-term remote worker needs," per the research's own verdict).

- **Key structural correction from the research: no universal three-axis model.** Instead of one `placement × transport × store` table applied uniformly to every port, config splits into three separate concerns: which components a process hosts, how a process reaches another component's inbound port (a _binding_ — `direct` requires both ends to be co-located in the same process, `redis-streams` or any network-capable binding doesn't), and which backend satisfies a passive infrastructure port. CAS and SQL are purely infrastructure under this split — their "remote" case is just the backend's own protocol (S3's HTTP API, Postgres's wire protocol), not a separate application-level remote interface to build ourselves. Only real behavioral components (worker, engine, limiter) get the inbound/outbound-port treatment at all.

- **Binding validity is per-relationship, not one global local/remote toggle.** `direct` is legal only between two components hosted in the same process; a network-capable binding works either way (including embedded-but-still-real-transport, e.g. proving Redis Streams while everything stays in one process). This has to be checked once per binding, not once per profile — moving the worker out of process means every binding it participates in needs to stop being `direct`, not just the one most obviously affected (job execution). A profile's config can legitimately expose a binding as a real, load-time-resolved choice (not baked in at authorship time) — e.g. `bindings.jobExecution: {kind:"direct"} | {kind:"redis-streams", ...}`, resolved when the profile parses its raw config at process start, restart-to-switch. That costs both variants' dependencies living in whatever package constructs the profile (no `pnpm deploy` narrowing for that axis — see Change C3), but is exactly what "config-driven" is supposed to mean here; no special build-time mechanism needed.

- **Several pieces of the research's model don't match where the worker already actually is, post-Worker-V2-rebuild — recorded here so the assembly layer's types don't design around a stale picture:**
  - **Limiter.** The research sketches a `resourceAdmission` binding assuming the worker still talks to the shared, bus-mediated `ConcurrencyLimiter`. It doesn't, as of the Worker V2 rebuild — confirmed empirically, zero references to the `limiter` package anywhere in `packages/components/worker/src`. The worker has its own outbound port instead (`ResourcePermitPort`, `createLocalResourcePermit`), a per-resource-key semaphore, concurrency-only. `PermitRequest` already carries a `rateCost` field, but nothing reads it yet — a real default rate limiter (not just a concurrency cap) is a known, not-yet-built gap.
  - **Router (`NodeRouter`).** Slated for removal, not a component whose placement/binding needs designing around. Its job (translating engine-emitted events into a job queue) was already mostly obsoleted when tools-as-a-registry was torn down, and will be fully obsoleted once Redis Streams replaces both the bus and the queue. Today's local/monolith path already bypasses it entirely.
  - **In-memory event bus / in-memory queue adapters.** Transitional, not a permanent "local transport variant" worth a lasting config axis. They exist today only because observability still gets everything by subscribing to the bus. Once observability (and anything else still riding it) has its own direct in-process sink — the same leap the worker's job-execution path already made — these adapters stop having a job to do. Until then they're load-bearing, not dead weight to prune early.
  - **Lifecycle facts.** Not one undifferentiated bucket — this initiative already commits to four categories (commands / lifecycle events / telemetry / metrics) as separate streams with independent consumer groups. See `queue-adapter.md`'s Change C4 discussion for the resolved shape (topology vs. publication routes vs. subscriptions as separate config concerns) — that's queue-specific detail this Change's leaf config types don't need to anticipate beyond leaving room for it.

- **Follow-up research resolved the config-type shape and how completeness gets enforced — this is what this Change actually builds.** Full output: [`research/runtime-composition-follow-up.md`](../research/runtime-composition-follow-up.md).
  - **No universal `DeploymentConfig` type.** Each profile owns its own independent config shape, built from shared leaf types (`ArtifactStoreConfig`, `SqlConfig`, etc.) — not a broad type narrowed via `Partial`/`Pick`, which would keep every profile coupled to one central schema and let through exactly the invalid states the profile split exists to prevent (`hosts.worker = true` with no worker dependencies, a direct binding in a process with no worker, desktop config accepting server-only adapters). Three distinct representations exist in a pipeline, not one: raw external config → profile-specific parsed config → resolved providers/bindings → typed assembly input → managed runtime.
  - **Completeness is enforced by the shared assembler's own narrow, required input types at each call site**, not by one raw config type — e.g. a `WorkerDependencies` type listing every port the worker actually needs; when the worker gains a required port, every profile calling `assembleWorkerHost()` fails to typecheck until it supplies it. That means the assembler is several role-specific entry points (`assembleEmbeddedSystem`, `assembleEngineHost`, `assembleWorkerHost`, `assembleObservabilityHost`, ...) sharing startup/health/shutdown machinery, not one universal `assembleSystem()` taking a `hosts: {worker: boolean}`-style flag. This Change builds `assembleEmbeddedSystem` specifically, since that's the one Change C3 needs.

- **Still true from before this research, and reaffirmed rather than superseded:** this is where the actual config-selection mechanism gets designed, not just a second hardcoded option. `CLAUDE.md` already flags `packages/runtime` as having two separate, incomplete wiring paths (`createServices()`/`createRuntime()`), with a unified config-driven creation system as the stated but unbuilt direction. Expected to be the heaviest work in this initiative — Change C14 (queue/messaging binding) and Change C16 (SQL) should be comparatively mechanical repeats of whatever shape Changes C2–C3 establish; if either needs real new design too, that's a sign this didn't actually generalize. (The queue/messaging axis turned out to need more than a mechanical repeat after all — see `queue-adapter.md`'s Changes C5, C7–C9, and C11–C14 for why: not this bullet's prediction failing, since the extra work is dispatch/lifecycle plumbing that Change C3's CAS pattern was never going to cover, not the config-selection step itself turning out hard.)

### What actually landed

Matches the design above on every structural point — `ManagedResource<T>`/`Provider<C,T>` with optional lifecycle hooks, `startAll`/`stopAll` with reverse-order rollback, `createManagedRuntime`, `assembleEmbeddedSystem`, and the `ArtifactStoreConfig` leaf type — with one real finding sharpened along the way and two unrelated fixes bundled into the same commit by choice (less ceremony over a perfectly focused diff):

- **A real TypeScript gap, confirmed empirically, not assumed.** `createManagedRuntime`'s three methods (`start`/`stop`/`health`) originally relied on the enclosing function's `: ManagedRuntime` return-type annotation to typecheck their own `return {...}` literals. Confirmed by direct compiler test that this doesn't work: without an explicit return-type annotation on the method itself, TypeScript infers that method's return type from its body, then checks it against the interface via ordinary structural assignability — which tolerates extra properties. An excess field on the `{ok: false, ...}` "already running" branch, for example, would have compiled clean. Fixed by annotating each method's return type directly (`async start(): Promise<StartOutcome>`, etc.) — confirmed this actually catches it. Worth treating as the standing pattern for any future object literal in this codebase implementing a multi-method interface: annotate the methods themselves, not just the enclosing factory function.
- **Bundled, genuinely unrelated to this Change's design: a `docker-compose.yml` project-name fix** — `name: lowercase` added, so containers are `lowercase-minio-1` rather than inheriting the `platform` folder name.
- **Also bundled, but really a Change C1 bugfix rather than new-to-this-Change work: CI silently wasn't testing what it appeared to, since Change C1.** The `services.minio` block, health-check wait, and job-level `S3_TEST_*` env vars were all real, but the actual test step ran `pnpm turbo run test`, not `test:integration` — and since the `test` task declares no `env` array in `turbo.json`, those job-level vars never reached the vitest process, so `s3-artifact-store.contract.integration.test.ts` has been skipping silently in CI since it was introduced. Found while checking whether the root `verify` script should run integration tests too (it didn't either, same root cause). Fixed by adding a dedicated `pnpm turbo run test:integration` step to `ci.yaml` (calling the turbo task directly, not the root `pnpm test:integration` script — that script's own `docker compose up` would conflict with CI's already-running `services:`-managed MinIO on the same port) and adding `test:integration` to the root `verify` script. Verified directly: forced a non-cached `turbo run test:integration` run with the env vars set and got `3 passed`, not skipped.
- Full-repo build/typecheck/test all pass with zero changes to `createServices()`/`createRuntime()`/`workflow.runtime.ts` or any existing consumer — confirmed via `pnpm -w turbo run build/typecheck/test`, including `apps/http-server`'s full route suite (23 tests) passing unchanged.

## Change C3 - Shared `local-system` profile (real CAS choice) + retrofit `http-server`/`cli` - merged (PR #362)

### Discussion

- **A worker-only profile is real, not hypothetical, but it isn't a mode of `apps/http-server`, and isn't part of this profile.** It's exactly the research's own "Remote worker" profile — hosts the worker only, Redis ingress instead of a direct call. Since `apps/http-server`'s entire reason to exist is serving HTTP routes into `app-services`, a worker-only profile with none of that would be a new, separate app package (`apps/worker-host`, not yet built, not in this initiative's scope), not `http-server` running in a different mode.

- **The `local-system` profile lives inside `packages/runtime`, not as a new separate package — confirmed by checking who actually consumes it today, not assumed.** `apps/cli/src/bootstrap.ts` already calls `createServices()` from `@lcase/runtime` — the identical entry point `apps/http-server` uses. That's the "second real consumer" the promotion rule asks for, already true today, not hypothetical. But reuse and package-boundary are different needs: since both apps already depend on `@lcase/runtime`, a shared module inside it (`packages/runtime/src/profiles/local-system/`) satisfies the reuse need immediately, with no new workspace package required. A genuinely separate workspace package is specifically for `pnpm deploy` closure isolation, which is a different, deferred question (see below) — "shared" doesn't imply "its own package" by itself.
  - `apps/desktop` was initially left out of this retrofit as a second consumer, on the grounds that it's mostly old and not actively developed — reframed mid-discussion once it became clear folding it in is what actually lets the old composition code get deleted in this Change, rather than surviving indefinitely as a desktop-only dependency. See below for what that folding-in involves.

- **`pnpm deploy` only prunes at the package.json level, not by actual code usage** — confirmed directly against pnpm's docs, not assumed. `packages/runtime/package.json` today depends on `@lcase/worker`, `@lcase/engine`, `@lcase/adapters`, `@lcase/router`, `@lcase/observability`, `@lcase/app-services`, `@lcase/replay`, `@lcase/limiter`, `@lcase/artifacts`, and `@lcase/db-prisma` together, in one `dependencies` block — confirmed by reading the file, not assumed. So this Change does not achieve real per-deployable dependency narrowing regardless of where the profile module lives; every app already pulls in this entire closure through `@lcase/runtime`. That needs both a deployable-per-profile _and_ this shared package's dependency shape actually split apart, which is a separate, later packaging decision — gated on measuring the real Electron artifact (per Change C1's own established precedent for this kind of question), not attempted here.

- **Electron packaging has a real wrinkle beyond just size, worth knowing before that later measurement happens.** Electron Builder includes production `node_modules` in the packaged app by default — ordinary file-inclusion patterns don't reliably keep dependencies out the way they might for a server deploy. Separately, native (compiled-binary) dependencies need deliberate packaging — they may need rebuilding against Electron's own Node/V8 ABI or explicit unpacking, or they simply won't load. `@lcase/db-prisma` ships exactly this kind of dependency (Prisma's platform-specific native query-engine binary), so this isn't hypothetical for this repo if `apps/desktop` work ever resumes for real.

- **Narrower "all local" / "all remote" profiles are possible but deliberately not built now.** Same principle as the S3-vs-fs pre-write-check decision in Change C1: don't build a leaner profile until measurement shows the flexible one actually costs something for a target that matters. Nothing forces that measurement yet — there's no packaged Electron artifact to check.

- **Scope for this Change: one profile, one real per-instance choice (CAS), everything else single-valued for now.** `LocalSystemConfig`'s `artifacts` field is a real `ArtifactStoreConfig` union (`filesystem` | `s3`) parsed at boot; `sql` and `messaging` fields exist in the type but currently only have one legal value each (SQLite, direct job execution) — not because the type can't express more, but because nothing else has a second real backend yet. Change C14 and Change C16 add real branches to this same profile's config, they don't rebuild it.

- **This profile is a clean rewrite of composition, not a retrofit of `createServices()`/`createRuntime()` — a deliberate choice, not just a side effect of the redesign.** `packages/app-services` (`RunService`, `FlowService`, `ArtifactService`, `SimService`, `ReplayService`, `EvalService`) stays untouched; the new profile constructs those same classes against newly-assembled instances rather than reusing any of the old wiring functions, factories, or registries. `SystemService`/`SystemServicePort` is the one deliberate exception (see below) — everything else in `app-services` is out of scope here.

- **Desktop folds into this Change after all, reversing the earlier call above — which is also what finally lets the two composition-root entry points actually merge into one**, rather than staying separate indefinitely as originally expected. Goal is explicitly archival, not functional — `apps/desktop` is never built, tested, or run right now, and this Change doesn't change that:
  - `apps/desktop/electron/runtime-config.ts` (today's old three-axis `RuntimeConfig`) is deleted; `bootstrap.ts` stops calling `createRuntime()`.
  - `WorkflowController` (`packages/archive/controller`) is coupled to `WorkflowRuntime`'s exact shape (`.flow`/`.replay`/`.sim` plus `startRuntime()`/`stopRuntime()`/`attachSink()`) via a type import from `@lcase/runtime` — confirmed by reading the file, not assumed. That import is replaced with a local interface defined inside `packages/archive/controller` itself, decoupling the archive from the live runtime package entirely. Not new precedent — it's applying the existing one, since the rest of `packages/archive` is already meant to be self-contained reference scaffolding rather than a live dependent.
  - `apps/desktop/electron/bootstrap.ts` builds a small inert literal object satisfying that local interface instead of a real runtime — `startRuntime`/`stopRuntime`/`attachSink` as harmless stand-ins, with a comment marking it a preserved-shape placeholder. No CI covers `apps/desktop` (confirmed — no typecheck/build/test script), so this is verified by the type-checker going quiet, not by running anything.
  - This is what actually clears the way to delete `createServices()`, `createRuntime()`, `makeRuntimeContext()`, `WorkflowRuntime`, the old `RuntimeConfig` type, and the old `placement × transport × store` registries (`registries/`, `factories/registry.factory.ts`) in this same Change, instead of them surviving as a desktop-only dependency.

- **`SystemService`/`SystemServicePort` deleted from `ServicesPort` — the one deliberate exception to leaving `app-services` untouched.** Investigated rather than assumed: `startSystem()`/`stopSystem()`/`attachSink()`/`detachSink()` were never a service anything calls at runtime — every real caller is bootstrapping code. `http-server`'s `build-server.ts` calls `startSystem()` once on boot and `stopSystem()` in its `onClose` hook; `cli` calls `startSystem()` once per command (`run.cmd.ts`, etc.), but `stopSystem()` turned out to be dead code there — `main.ts`'s SIGINT/SIGTERM/exit handlers guard it behind an `isRunning` flag that's declared `false` and never set `true` anywhere, so CLI has never actually stopped the system gracefully; it just lets the process die. No HTTP route and no workbench UI calls any of these four methods. `SystemService`'s implementation was also a third copy of the exact same hardcoded `router → sinks → tap → engine → limiter` sequencing Change C2's `ManagedRuntime` already replaces — worth removing on that basis alone, even setting the "is this really a service" question aside.
  - **Lifecycle control** (`startSystem`/`stopSystem`) moves to the composition root: `build-server.ts` and `cli`'s `bootstrap.ts` get the `ManagedRuntime` back directly from the profile, alongside the services, and call `.start()`/`.stop()` themselves — no service indirection, since those two call sites already are the composition root.
  - **Sink attach/detach** (`attachSink`/`detachSink`) — pure passthrough to `ObservabilityTapPort` today, used only by `http-server`'s `/events` SSE route to attach a per-connection sink for live streaming. Exposed directly via the tap instead of through `services.system` for now. Where sink control should actually live long-term (a proper service of its own) is a real, separate question, deliberately not answered in this Change.

- **Workbench's `/system` page (a theme toggle only, confirmed by reading it) is named for a feature that was never built, not one being removed here.** The intent behind the name: surfacing things like "engine running"/"engine stopped" in the UI, and possibly control over remote pieces later — related to the earlier-floated, already-deferred "supervisor" idea. `ManagedRuntime.health()` (Change C2) already aggregates per-resource `HealthStatus` across bus/router/sinks/tap/engine/limiter, so the foundation for this exists structurally even though nothing surfaces it anywhere yet. Not part of this Change — noted so this angle isn't accidentally designed away later.

- **Port-typing refinement for `EmbeddedSystemAssemblyInput`** (using `RouterPort`/`EnginePort`/etc. instead of `ManagedResource<unknown>` where a clean, already-live port exists) is in scope to attempt in this Change — deferred from Change C2 specifically because this is where it would first matter. Keep only where it earns its keep; `unknown` stays wherever a real port would need forcing or awkward casting.

### What actually landed

Matches the design above on every structural point — `createLocalSystem()` in `packages/runtime/src/profiles/local-system/`, config-driven between `filesystem` and `s3` CAS, `SystemService`/`SystemServicePort` fully removed with lifecycle moved to the composition root and sink attach/detach exposed directly via `tap`, the desktop archival stub, and every old composition-root file (`create-services.ts`, `runtime.ts`, `workflow.runtime.ts`, the three-axis registries/factories) deleted — with several things found only once this got exercised end-to-end, not just built/typechecked:

- **The port-typing refinement (§8) worked cleanly, no forcing needed** — `EventBusPort`, `RouterPort`, `EnginePort`, `LimiterPort`, `ObservabilityTapPort`, `EventSink` all already existed and matched the six resources exactly. One real, small finding along the way: `InMemoryEventBus.close()` returns `Promise<unknown>`, not `Promise<void>`, so its `ManagedResource` stop hook needed an explicit `async (b) => { await b.close(); }` block rather than a bare `(b) => b.close()` passthrough — confirmed by `tsc`, not assumed. Also needed adding `@aws-sdk/client-s3` as a direct dependency of `packages/runtime` itself (previously only a transitive dependency via `@lcase/adapters`), since `buildArtifactStore` constructs the `S3Client` directly now rather than leaving that to the adapter.
- **A real, user-facing bug found only by actually running the S3 branch, not by typechecking or the existing mocked/integration tests**: `S3ArtifactStoreConfig.forcePathStyle` is optional with no default, and the app's own `runtime.config.ts` didn't set it. Without it, the AWS SDK defaults to virtual-hosted-style addressing against the custom `endpoint`, which MinIO doesn't resolve correctly — surfacing as `NoSuchBucket`/`InvalidBucketName`-class errors even against a real, existing bucket. Root-caused with a direct repro script (same client config, with and without `forcePathStyle`) rather than assumed from documentation. Fixed by setting it explicitly in the app's config; left as an open, undecided question whether `buildArtifactStore` should default `forcePathStyle: true` whenever a custom `endpoint` is present, since virtual-hosted-style essentially never works against a self-hosted backend anyway — not changed in this Change.
- **Nothing provisions a bucket for manual/app-level use** — confirmed by reading `docker-compose.yml` (no `MINIO_DEFAULT_BUCKETS`) and the Change C1 integration test (creates its own bucket in its own `beforeAll`, the only place a bucket gets created today). A real gap for anyone manually exercising this profile's `s3` branch locally, worked around here with a one-off `CreateBucketCommand` script rather than fixed structurally — not this Change's problem to solve, but worth knowing before hitting the same "bucket not valid" confusion again.
- **The desktop stub was verified by direct manual `tsc --noEmit`, not by any automated task** — confirmed `apps/desktop` genuinely has no typecheck/build/test script (matching `CLAUDE.md`), so this is the one piece of this Change CI will never check. The stub and `packages/archive/controller`'s decoupled `WorkflowRuntimeHandle` interface both compile clean; the one remaining error in that run (`packages/archive/ui/src/components/observability/ObsPanel.tsx`, an unused-import lint error) was confirmed via `git log` to be pre-existing rot from 2026-08-24, untouched by this Change.
- **Two additional tests added in a follow-up pass, after initial implementation and manual verification were already reported complete**: `packages/runtime/tests/profiles/local-system/{build-artifact-store,local-system.profile}.test.ts` — the first asserts `buildArtifactStore` returns the right concrete class per `kind` (no need to mock `S3Client` itself; that's already covered at the adapter layer by `packages/adapters`' own tests), the second asserts `createLocalSystem()` constructs without throwing and returns every expected `ServicesPort` key plus `runtime`/`tap`. Writing the second one surfaced a real, pre-existing (not new) fact: `JsonlEventLog`'s constructor eagerly does a non-recursive `mkdirSync` for the replay directory — harmless in a real app run since `lcase-db/` already exists by then, but it means `createLocalSystem()` isn't actually side-effect-free at construction, and the test needed a `beforeAll` to pre-create that parent directory. Not fixed here — it's `packages/adapters` code, unrelated to this Change's own scope.
- **Verified against a real, manually-run instance, not just the automated suite**: `pnpm -w turbo run build typecheck test` all green (79/79 tasks, including `http-server`'s full pre-existing 23-route suite, unaffected), plus a live `http-server`/`cli` run — `/api/flows` served real DB-backed data, `/events` SSE attached cleanly via the new `tap` decoration, `cli add` stored a flow in CAS and shut down cleanly (`[limiter.stopped]` logged, confirming the old dead-`stopSystem()` bug is genuinely fixed, not just rearranged). The user then independently exercised the actual point of this Change end-to-end — authored a new flow, ran it, and confirmed via a direct bucket listing that outputs landed in real S3-compatible storage: 4 objects, flat content-hash keys, correct native `application/json` content-type, no `.meta.json` sidecar — matching `S3ArtifactStore`'s design exactly.
- **Several longer-term design questions surfaced during that manual verification, deliberately not solved here — logged to `docs/todo.md` instead**: workbench error-surfacing polish (technical error detail vs. a toast/consolidated log page); `buildObservability()`'s hardcoded sink wiring, to loosen up once observability gets its own architectural focus; switching a live CAS/SQL backend without migration leaving stale, silently-broken references (reachability vs. migration as separate problems, migration motivated by avoiding infra lock-in); the event log's per-run JSONL file being a filesystem-only relic that should eventually flow through CAS instead, addressed by a caller-supplied id rather than content hash; and a leaning toward AJV/JSON Schema over zod for the still-open validation-strategy question, now with a third concrete consumer (a future runtime-read config file, replacing today's compile-time-only TS literal).

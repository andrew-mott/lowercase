# Sims mode — design narrative

Full design history for Sims mode: reuse decisions, the state-machine corrections, and every placement decision made along the way. Extracted from `docs/initiatives/ui-workspace/INITIATIVE.md` to keep that doc scannable; summarized there with a link back here.

**Reuse target correction, settled in discussion**: this does _not_ reuse the old `RunnerSimSelector`/`Sims.tsx`/`CreateSim.tsx`/`ViewSim.tsx`/`SimsFlowView` components (as this doc previously assumed) — those are old-UI pieces bound for their own redesign, and today's step-reuse selection there is genuinely blind (toggles a step by ID/color on the static flow-def graph, with zero visibility into the parent run's actual output/exports). Instead, this reuses the _new_ flow-version-workspace pieces Run History just built: `FlowVersionRunHistoryList`, `useRunEventsWithStatus`, `FlowGraph`+`stepRunInfo`, `StepResultsTab` — the same "reuse is not the goal" distinction applies app-wide, delineating old components not worth carrying forward vs. new workspace pieces actively being built and reused hard.

**Backend needs no schema changes for the minimal version**: `Sim` already has a required, indexed `flowVersionId` FK (`schema.prisma`) — the 1:1 sim-to-flow-version association already exists. `ForkSpec` (`packages/types/src/engine/fork-spec.type.ts`) is already exactly `{parentRunId, reuse: string[]}` — the minimal "reuse steps from one parent run" capability the current system actually supports. The only backend gap is `listSimsByFlowVersionId`, essentially a copy of `listRunsByFlowVersionId`'s shape (port/service/route/adapter/tests). (Separately, whether fork-spec/sim data should eventually move from a CAS artifact to queryable SQL rows is a real, still-open question — deliberately deferred, not blocking this work; see `docs/todo.md`.)

**Left pane: page-state-driven content swap, not tabs.** A bare "Runs" tab would raise a real state-machine question (disabled? hidden? until when?) precisely because Runs isn't a co-equal destination — it only matters while creating a new sim. Model it as page state instead, extending the same pattern `flowVersionRunHistorySlice` already established.

**Corrected during Change C2 planning: 2 modes, not 3 — picking a run is never a one-way gate.** Originally sketched as a linear `browsing → picking-run → authoring` flow where picking a run locked you into authoring for it. Rejected: authoring needs to support freely switching between runs _while_ authoring — comparing what different runs produced — with in-progress reused-step selections and the currently-inspected step (both Change C3) surviving the switch. So:

- **browsing** → left pane shows the sim list (filtered by flowVersionId), with a "New" button
- **authoring** → left pane becomes the run list (`FlowVersionRunHistoryList`, reused as-is) and _stays_ there for the whole time you're authoring — not swapped away once a run's picked. `selectedRunId` is just a freely-updatable field within this mode, not a transition trigger; re-picking a different run updates the main content live. Main content becomes the graph+details view for marking/inspecting reused steps (Change C3); Save or Cancel returns to browsing.

**Interaction: node click means only "inspect," never double duty.** Marking a step reused needs a separate, explicit control — a toggle inside the details panel once a step is inspected, rather than overloading click. Built with shadcn `Switch` (not `Toggle` as originally planned — functionally the same idea, `Switch` just reads clearer for a plain on/off, and is what actually got installed). Right-click (`onNodeContextMenu`) is a clean, cheap option to add later if wanted — React Flow already exposes it as a genuinely distinct prop from `onNodeClick`, requiring only one small additive (non-breaking) prop on `FlowGraph` — but not needed for a first version, especially since this interaction is expected to get revisited once a visual flow editor exists (see `docs/todo.md`'s note on that longer-held, unscheduled goal) and nodes potentially become custom/richer.

**Authoring always shows all 3 panels, even before a run's picked — corrected during Change C3a review.** Originally the "no run selected yet" state showed a 2-panel idle-prompt layout instead of the real graph/details panels. Changed: the graph/details panels already handle empty data gracefully (no `stepRunInfo` just means unstyled nodes, `StepResultsTab` already handles `stepId === null` with its own prompt) — so there's no real reason to special-case that state with a different layout. `FlowVersionSims.tsx` now always renders 3 panels once `mode === "authoring"`, with a small "Select a run below" hint shown above the run list until one's picked.

**Where Cancel (and Save) live — moved out of the details panel, up into the left panel, above the run list.** First attempt put Cancel in the details panel's header; reconsidered because it read as context-less — not obvious _what_ you were cancelling. Left panel now shows a persistent "New Sim" header + Cancel button above the run list for the entire authoring session, regardless of whether a run's picked yet. **Sim Settings (name + description) should land here too, not as a details-panel tab as originally sketched** — same reasoning: a lone Save button in a details-panel tab would have the identical "naked, no context" problem Cancel had. Putting name/description + Save/Cancel together in the left panel, under a "New Sim:" heading, keeps a constant visual anchor for the whole authoring session ("you are creating a sim," not just "here's a random toggle"), and the buttons read as acting on something specific instead of floating alone. Built in Change C3b.

**Change C3b validation/error UI is deliberately minimal — real toast/notification system is future work.** Save requires a non-empty name, a selected run, and at least one reused step (a sim with an empty `reuse` array does nothing — enforced client-side only, `post.ts` doesn't reject it server-side, and it's not yet decided whether that validation belongs at the API layer too). Errors from a failed save render as plain inline text next to the Save/Cancel row — no toast library exists anywhere in `apps/web-app` yet. A shadcn `Tooltip` was installed while exploring a richer treatment for the reused-step hint but held off on — the plan is to revisit inline validation/error rendering once there's a unified toast/notification pattern, rather than build one-off treatments per form. Tracked in `docs/todo.md`.

**Corrected during Change C4 planning: browsing _is_ viewing — not a third mode.** First pass at Change C4 proposed a `"viewing"` mode mirroring how `"authoring"` swaps the left pane to the run list. Rejected: there's no separate viewing mode, because browsing already _is_ viewing. Exactly like authoring keeps the run list visible and lets you freely re-pick `selectedRunId` (a field, not a mode transition), browsing keeps the sim list visible and lets you freely re-pick a new `selectedSimId` field — same pattern, still only 2 modes (`"browsing" | "authoring"`). The middle/right panels stopped branching on `isAuthoring` entirely as a result — they always render now, fed by `inspectingRunId`/`inspectingReusedStepIds` (authoring's own state, or a viewed sim's `parentRunId`/`reuse` fetched via `useGetSimQuery`). Browsing also auto-selects the most recent sim instead of showing nothing, which is what makes Save land you back viewing your just-created sim automatically (`resetToBrowsing` nulls `selectedSimId`, and the list's auto-select effect picks the new latest one up immediately).

Change order:

1. **Backend**: `listSimsByFlowVersionId` — small, precedented, no design risk. Merged (#265).
2. **Scaffold**: the page + left-pane state machine above, sim list ↔ run list swap wired to real data. Merged (#266).
   3a. **Real graph/details wiring**: `FlowGraph`+`useRunEventsWithStatus`+`StepResultsTab` reused for inspection, the reused-step toggle (persisting across run switches, per the state-machine correction above), always-3-panels layout, Cancel anchored in the left panel. Merged (#267).
   3b. **Sim Settings + Save**: name/description inputs anchored in the left panel per the placement decision above, `POST /api/sims`, `sims-api.ts` cache tags so the browsing list picks up new saves. Split out from the original single Change C3 during planning — genuinely separable from 3a, and 3a alone was already a full unit of work. Merged (#268).
3. **View existing sim**: browsing-is-viewing per the correction above, plus a Settings tab (first, default-selected, hidden while authoring) showing the viewed sim's full name/description and raw parent run id. Merged (#269).

## Change C25 - Run Input Params — run-opened panels are read-only, always a rerun - merged (PR #308)

Settled design, through a real discussion pass (ground truth verified directly in code first, not assumed).

### Discussion

- **Runs are read-only, not editable.** A run-opened Flow Graph panel's Run Input tab shows that run's actual resolved params as static display (no `Select`, just the resolved artifact's label per param) — never editable. The toolbar's Run button on a run-opened panel is always a rerun of that exact run, never a fresh param selection.
- **Seeding.** `use-flow-graph-panel.ts` never calls `useGetRunParamsQuery` today — a run-opened panel's Run Input tab starts with whatever `selectedParamHashes` the panel happens to already have (usually empty), unrelated to the actual run. Fix: seed `selectedParamHashes` once on mount from `useGetRunParamsQuery({runId})`, mirroring the existing `parentRunId`-seeding effect's gating.
- **Rerun, free.** `handleRun` already sends `selectedParamHashes` straight through as the run request's `params` — since seeding populates that same (now immutable, for the run case) state, the toolbar's existing Run button _is_ the rerun mechanism with zero new submit-side plumbing. Resolves the open question `docs/todo.md`'s entry had flagged.
- No picker, no curation logic, no artifact-list scoping touched in this Change at all — those only matter for the editable cases, which is all of Change C26.

### What actually landed

Exactly as designed, with one addition planning missed. `openedAs.type === "run"` (fixed at panel-open time, `explorer-panels.ts`) is now threaded down as a new `runOpened` prop through `ExplorerTabContent.tsx` → `Content.tsx` → `useFlowGraphPanel` — the same discriminated union Change C19 added purely for tab icon/color turned out to generalize cleanly to this, since it already captured "how this panel was opened" as a fixed fact rather than something derived from later-mutable state (`runId` alone can't distinguish a truly run-opened panel from a plain panel that just ran itself). `use-flow-graph-panel.ts` gained `useGetRunParamsQuery(runOpened && runId ? { runId } : skipToken)` and a one-shot seeding effect into a new `paramsSeeded` reducer that replaces `selectedParamHashes` wholesale rather than per-name like `paramHashSet`.

One thing planning got wrong: the existing sim-seeding effect gates on `runId === null`, but a run-opened panel's `runId` is _already_ non-null at mount — so the new effect gates on a local `useRef(false)` one-shot flag instead. `FlowVersionRunParamRow.tsx` gained a `readOnly` prop that swaps its `Select` for a static label (keeping the existing Preview/Show-usages buttons) — old-mode's caller never passes it, so no fork was needed for this Change specifically. `RunToolbar`'s button reads "Rerun" via a new `isRerun` prop. Verified: typecheck/lint/202 vitest tests (including new `paramsSeeded` coverage) all pass, plus manual browser testing.

## Change C26 - Run Input Params — curated picker for sim-opened and plain panels - merged (PR #309)

Sims and a plain (no run/sim) panel both keep an editable Run Input tab, unlike Change C25's run case — this Change is the picker improvements that only matter where editing still happens.

### Discussion

- **Sim seeding is not new mechanism, just a wider gate on Change C25's, blocking the same way.** By the time seeding would fire, a sim-opened panel's `runId` (Redux) already equals `parentRunId` — the existing sim effect sets that before this runs. Widening Change C25's seeding query/effect gate from `runOpened && runId` to `(runOpened || simId) && runId` makes it fire for sims too, reusing the same `paramsSeeded` reducer and one-shot ref, with the same `paramsLoading`/`paramsError` blocking treatment as Change C25's read-only case. `readOnly={runOpened}` stays separate and untouched, so sims still end up editable once seeding completes. A plain panel has no run to seed from at all — starts empty, as today.
- **Restore-to-original, deferred.** Once a seeded sim param is edited, a way to restore it back to the parent run's original value would be genuinely useful — explicitly deferred, not in this Change.
- **Artifact list scoping — a second, separate query, not a replacement.** `use-flow-graph-panel.ts`'s existing `useListArtifactsQuery()` (unscoped) must stay exactly as-is, since `FlowVersionRunParamRow.tsx` uses that same list for _lookup_ as well as candidates. Instead, add a _second_ query scoped to `{flowVersionId: versionId, curated: "true"}`, exposed separately (`curatedArtifacts`) and used only to build the editable picker's candidate list.
- **Curation filtering — additive prop, no fork.** New `curatedOnly?: boolean` plus a new `curatedArtifacts` prop, filtering _that_ list by `paramCurations` for this exact `(versionId, paramName)` pair. The existing "selected artifact unavailable or incompatible" warning must keep checking existence/compatibility against the full (unscoped) `artifacts` list, not the curated one — otherwise a sim's freshly-seeded-but-uncurated param would falsely trigger that warning the moment seeding completes.
- **Create-from-picker shortcut, kept out of the shared component entirely — not optional.** `useDockviewApi()` throws if called outside `DockviewApiContext.Provider`, and old-mode's page has no such provider anywhere in its tree — a hook call executes unconditionally regardless of props, so the create-shortcut can never live inside `FlowVersionRunParamRow.tsx`, even prop-gated. Instead, the row gains a generic `extra?: React.ReactNode` slot; `ParamsTab.tsx` (dockview-only) supplies the actual "+ new artifact" button through it.
  - **Temporary, tied to old-mode's continued existence — not a pattern to keep.** Once old-mode's pages are retired, `extra` should be deleted and the create-button implemented directly.
  - **Auto-select on success needs to work for both of `CreateArtifactDialog`'s paths, including the one that hands off to a separate panel.** Mechanism: a new optional `returnTo?: { panelId: string; paramName: string }` field on the `artifact-authoring` variant of `OpenPanelRequest`. `use-artifact-authoring-panel.ts`'s `handleSave`, on success, dispatches `paramHashSet({ panelId: returnTo.panelId, name: returnTo.paramName, hash })` in addition to its existing "open the new artifact's viewer panel" behavior.
  - **Two accepted edge cases, not solved further** — both are the singleton-per-version authoring panel (Change C24's deliberate design) not holding up perfectly under this new reuse: two flow-graph panels for the same version both using the create-shortcut before either saves silently overwrites the first's `returnTo`; and an in-progress plain-"+"-started draft retroactively gains a `returnTo` if a create-shortcut is triggered elsewhere for the same version. Both match the panel's existing "singleton, last-request-wins" nature elsewhere.

### What actually landed

Exactly as designed for the core mechanism, plus two real follow-up rounds found from actually using it — a content-type mismatch that could fail a save outright, and an unrelated resize bug surfaced along the way.

`use-flow-graph-panel.ts` gained `shouldSeedParams = runOpened || Boolean(simId)` and a second `curatedArtifacts` query; `FlowVersionRunParamRow.tsx` gained `versionId`/`curatedArtifacts`/`curatedOnly`/`extra` props (no fork); `ParamsTab.tsx` renders one shared `CreateArtifactDialog` instance per tab; `explorer-panels.ts`'s `artifact-authoring` variant gained `returnTo`.

One real three-way rendering decision, refined through discussion before implementing: a selected param value can be curated-and-listed, real-but-not-curated (the common sim-seeding case), or genuinely broken/incompatible — collapsing the first two into one "unavailable" warning would have falsely flagged every freshly-seeded sim param. The fix keeps the existing scary copy only for the truly-broken case, and shows the real label (annotated "(not curated)") for the middle one.

**Follow-up round 1 — content type could mismatch the target param, causing the whole save to fail server-side.** Root cause turned out to be more general than the create-shortcut itself: neither the author path's content-type change nor the upload path's file-picker change ever pruned `curatedParamNames` of now-incompatible entries — a pre-existing gap, just newly easy to hit. Fixed in three parts: the author path now derives `contentType` from the target param's declared type when arriving via `returnTo` and locks the field; the upload path narrows the file picker's `accept` attribute and rejects a picked file that doesn't actually match; and both paths' `handleSave` now filter `curatedParamNames` down to whatever's currently compatible only at the save boundary, preserving a checked box across a content-type change and back.

**Follow-up round 2 — an unrelated resize bug in the artifact _viewing_ panel (Change C23).** Wide artifact content could push the metadata rail off-screen — `ResizablePanel`'s inner content div gets `maxWidth: "100%"` but never `minWidth: 0`, the exact mechanism already fixed once for Change C24's authoring panel. Fixed with `min-w-0` on both layout branches.

**Deferred refactor, named here rather than `docs/todo.md` since it's tied directly to this work and easy to lose track of otherwise: `useFlowGraphPanel`'s return value and `Content.tsx`'s consumption of it.** As of Change C25, the hook returns 36 properties, all destructured flat in `Content.tsx` and then hand-picked back apart into smaller groups per child — not disorganized, just flattened at the export boundary in a way that fights against passing richer objects through as-is. The likely shape: keep the genuinely cross-cutting values flat at the top, and bucket the rest into sub-objects mirroring each child's actual `Props` type. This grew further in Change C26 (`curatedArtifacts`, `shouldSeedParams`) exactly as anticipated when this was first deferred — still not done, still worth doing.

Verified: typecheck/lint/202 vitest tests, plus manual browser testing of both rounds.

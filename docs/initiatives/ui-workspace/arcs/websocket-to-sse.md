## Change C40 - Replace the WebSocket live-events transport with SSE - merged (PR #323)

### Discussion

**Real history behind today's WebSocket code, not guessed.** The original WS client (`apps/web-app/src/redux/middleware/ws.ts`) was never built as real session/connection management — it was minimal scaffolding for a different, already-solved problem: how to batch very fast incoming events into Redux state without causing render thrashing (the rAF-scheduled `buffer`/`scheduleFlush` mechanism, dispatching a single `eventsBatch` action into a plain `events-slice.ts` reducer rather than one dispatch per event). Once that batching worked well enough, the WS transport itself was left alone — the known session-management gap (a single global socket keyed by the literal string `"client"` in `apps/http-server/src/routes/ws-route.ts`'s `sockets` Map, so a second browser tab silently steals live-run monitoring from the first) has been a known, accepted rough edge the whole time, not a surprise found late.

**Run-kickoff was tried over the socket first, and deliberately moved to REST — real precedent, not to be re-litigated by this Change.** Earlier design work explored driving a run's _start_ over the same live connection; that caused real problems (mixing "start a thing" with "stay connected to hear about things"), so `POST /runs` was built as its own REST endpoint instead, with the live channel narrowed to pure observation. That split is treated as settled going into this Change, not something to reopen — REST for actions, one channel for observation.

**Confirmed by reading the code, not assumed: the client genuinely never sends anything meaningful today.** `wsSend` exists in the middleware but has zero callers anywhere in the app (`grep` came back empty). This matches the project's existing trust boundary elsewhere (see memory `user_result_envelope_philosophy` and `project_security_deferred`): the server is the sole author of real domain events; the frontend was never trusted to construct them. If a "send something over the channel" want ever comes back (e.g. run-kickoff eventually riding the same connection), it'd still go through a REST-shaped request the server turns into a real event, not a client-authored event forwarded onto the bus — full-duplex WS was never actually buying anything here.

**Server-side event flow, traced exactly**: `WsService` (`packages/services/src/ws.service.ts`) subscribes once to `bus.subscribe("*", ...)` and forwards any event carrying a `runid` to whichever socket is registered for that run in its own `monitoredRuns` map, auto-unsubscribing on `run.completed`/`run.failed`. `monitorRun()` is only ever called from inside the `POST /runs` handler at request time — there's no route today that can attach a socket to a run already in flight. That gap (watching a run you didn't personally start) is orthogonal to the WS-vs-SSE choice; it isn't solved by either transport as things stand, just named here so it doesn't look forgotten.

**Why SSE over shoring up WS, given the above:**

- `EventSource` reconnects automatically per spec (~3s default, browser-implementation-defined, overridable by the server sending a `retry: <ms>` line) — this alone replaces a real chunk of client-side work WS would otherwise need hand-built (today's WS middleware has zero reconnect logic at all; a dropped connection stays dead until page reload).
- The one thing WS uniquely offers — true bidirectional messaging — isn't used and isn't wanted (see the `wsSend` finding above), so there's no real cost to giving it up.
- SSE's connection-per-request shape sidesteps the session-identity problem entirely rather than requiring it to be fixed — see the design below.

**Settled design for this Change, not final production hardening, but a real shape:**

- **One general `GET /events` stream, broadcasting the full, unfiltered bus firehose** — not scoped per-run. The client already receives and filters this way today (`events-slice.ts` holds a global bucket of up to 5000 events, `runEventIds` derived per run, filtered client-side by whatever's asking) — that consumption shape carries over completely unchanged; only the connection-establishing code in the middleware changes (`new WebSocket(url)` → `new EventSource(url)`, same buffer/rAF-flush/`eventsBatch` dispatch). Per-run scoped streams (`GET /runs/:runId/events`) would be a real, cleaner option later — genuinely useful once filtering/auth/authz matters (see below) — but deliberately not solved now.
- **No new bus subscription per connection, and no new persistent object either — reuse the existing `ObservabilityTap`, already started once at boot (`ctx.tap`).** Checked, not assumed: `ObservabilityTap.start()` subscribes once to the `"observability"` topic and fans out to a registered `#sinks` Map via `attachSink`/`detachSink` — and this is already a live, established pattern, not theoretical: `SqlRunProjectionSink` and `EvalResultProjectionSink` are both already registered this exact way at boot. What a connection needs is not a new Tap or a new bus subscription — it's a small, per-connection `EventSink` (`{ id, start(), stop(), handle(event) }`, the existing port shape in `packages/ports/src/observability/observability-sink.port.ts`) whose `handle()` writes to that connection's own `reply.raw`. `attachSink()` on connect, `detachSink()` on the request's own `close` (Fastify/Node's `request.raw.on("close", ...)`, the same hook `@fastify/websocket` already relies on for socket-close detection today). Connection lifetime and sink-registration lifetime are the same thing, so there's nothing left over to track — this eliminates the `sockets` Map / literal-`"client"` bug class by construction, not by patching it. `POST /runs` stays entirely decoupled from the event stream; it doesn't need to know or care whether anyone's listening, which directly avoids re-creating the same run-kickoff/connection coupling that caused real problems the first time it was tried.
- **`SystemService.attachSink()` (`packages/services/src/system.service.ts:78`) is already real, callable code today** — delegates straight to `tap.attachSink()`, matching this codebase's existing convention that route handlers only ever touch `app.services.*`, never raw ports directly. One real gap found while checking: `SystemService` exposes `attachSink` but not `detachSink` — needs a one-line addition mirroring the existing method, otherwise a closed connection's sink leaks (keeps getting `handle()` calls into a dead response) rather than being cleaned up. Agreed as in-scope for this Change, not deferred.
- **`ObservabilityTap.start()`'s fan-out loop gets a real fix as part of this Change, not just a new consumer bolted onto it as-is.** Read directly: `for (const sink of this.#sinks.values()) { sink.handle(event); }` — not awaited, no per-sink try/catch. Today's two sinks (`SqlRunProjectionSink`, `EvalResultProjectionSink`) are fixed and trusted, so this has never mattered; a browser-facing `EventSink` per open tab is a much less trustworthy, much more dynamic population (a connection can drop mid-write, `reply.raw.write()` can throw) — one sink's failure shouldn't skip delivery to every sink registered after it in iteration order, and an unawaited rejected promise from `handle()` becomes an unhandled rejection Node will complain about (or crash on, depending on version/config). Fix: await each `sink.handle(event)` individually, each wrapped in its own try/catch (or `.catch()`), so failures are isolated and logged rather than propagating. Small, directly motivated by what this Change adds, not a separate follow-up.
- **`"observability"` isn't a narrower stream than `"*"` — checked `InMemoryEventBus.getTopics()` directly.** Every `publish()` call fans out to both `"observability"` (what the Tap subscribes to) and `"*"` (what `WsService` subscribes to today) automatically, with one real difference: an event published with `{ internal: true }` still hits `"*"` but skips `"observability"`. So reusing the Tap doesn't reproduce WS's exact current firehose — it gives everything _except_ whatever's already flagged internal-only, which (confirmed with the user, that flag was added for unrelated replay/logging reasons) works out to be the more correct default for something facing the browser, not a loss.
- **A server-side heartbeat (a periodic SSE comment line, e.g. `: ping\n\n`) is needed** to keep a long-idle connection alive through intermediaries (reverse proxies, load balancers) that might otherwise silently kill it — not spec-mandated, but standard practice, and directly relevant here since a stream might sit open for the full duration of a long-running run.
- **`Last-Event-ID` is available for later, not required for v1.** If SSE `id:` fields are sent per event, `EventSource` automatically remembers the last one seen and resends it as a `Last-Event-ID` header on reconnect — a real mechanism for resuming/replaying missed events across a drop, matching the "mature this feature later" story below, but not something this Change needs to use.
- **Each per-connection `EventSink` needs a real, unique `id`** — `ObservabilityTap`'s `#sinks` is a `Map` keyed by `sink.id`; the existing sinks all use a fixed literal (`"sql-run-projection-sink"`, etc.) since there's only ever one of each. A per-connection sink needs something like a UUID generated per connection, or two tabs would collide and silently overwrite each other's registration in the Map — the same bug class this Change exists to eliminate, one level down.
- **`start()`/`stop()` are the sink's own responsibility to implement correctly, and the caller's responsibility to call — confirmed against real usage, not assumed.** `ObservabilityTap.attachSink()` only registers a sink in its Map; it never calls `start()`. `workflow.runtime.ts` calls `sink.start()` explicitly on each sink before attaching. Our SSE sink needs a real `stop()` that cleanly ends the write stream — the existing `WebSocketServerSink` (see below) leaves `stop()` as a literal `throw new Error("Method not implemented.")`, a real gap, not a pattern to copy.

**Confirmed scope boundary against a second, pre-existing live-broadcast mechanism, found while checking the above — `WebSocketServerSink` (`packages/observability/src/sinks/web-socket.server.sink.ts`) is out of scope for this Change, left untouched.** It's a real `EventSink` too (same idiom this Change's design reuses, good confirmation the approach is idiomatic) — but it runs its own dedicated `WebSocketServer` on a port, used only via the config-driven `"websocket-sink"` entry in `RuntimeConfig.sinks`, wired through `createObservability()` in `packages/runtime/src/runtime.ts`. Checked both apps' actual configs directly: neither `apps/http-server/src/runtime.config.ts` nor `apps/desktop/electron/runtime-config.ts` includes `"websocket-sink"` in their `sinks` array — it isn't live in either app today. It shares WS's single-connection limitation (`this.socket = socket`, last connection wins) but that's the desktop app's own old, currently-unmaintained code (see memory `feedback_dont_touch_dying_code_proactively`) — not this Change's to fix or clean up.

**What "replace the WS transport" concretely means for `apps/http-server`, now fully scoped — confirmed nothing here is config-driven, so there's nothing to remove from `RuntimeConfig` itself.** The http-server's live-events mechanism was never expressed through `RuntimeConfig.sinks` at all; it's a separate, hand-rolled path sitting alongside the config-driven sink system. Removed as part of this Change: `WsService`'s construction inside `createServices()` (`packages/runtime/src/create-services.ts`) and its inclusion in `ServicesPort` — confirmed safe for `apps/cli`, which shares `createServices()` but never touches `services.ws` anywhere (`grep` came back empty); `app.services.ws.start()` (`apps/http-server/src/build-server.ts:29`); `app.services.ws.monitorRun()` and the `sockets` Map check (`apps/http-server/src/routes/runs/request.ts`); the `ws-route.ts` Fastify plugin and its module-level `sockets` Map; and client-side, `ws.ts`'s middleware, `ws-bootstrap.ts`, `WebSocketPanel.tsx`, and `wsSend` (confirmed dead, zero callers, earlier in this arc's discussion).

**Named for later, explicitly not this Change — real future application ideas, deliberately not solved now:**

- Per-run scoped streams instead of one firehose (see above).
- Server-side filtering of the broadcast (e.g. by auth/authz once that layer exists — see memory `project_security_deferred`: "of course, it would need to if this ever became more than just a local personal dev server").
- Sending client-originated events over the channel (e.g. run-kickoff itself eventually riding the live connection) — the REST/observation split stays as-is; not being revisited by this Change.
- A toast (Sonner) notification if the connection drops — floated in discussion, explicitly not designed or scoped.
- A route to attach to a run already in flight, not just one this client itself started (the `monitorRun()` gap noted above) — real, but orthogonal to this Change's transport swap.

One real practical caveat carried into this design, not a blocker: browsers cap concurrent connections per origin at 6 under plain HTTP/1.1 (this app's local dev Fastify server), and each open browser _tab_ running this app counts one connection against that — not a concern at the scale this is actually used at, worth knowing if it ever isn't.

**Scaling, discussed but explicitly not a concern at this app's actual scale.** `ObservabilityTap`'s fan-out loop is O(N) per event, N being however many `EventSink`s are attached (open browser tabs) — a real, deliberate tradeoff against today's WS design, which does an O(1) `Map.get(runId)` lookup instead, filtering server-side before deciding who gets an event at all. Broadcasting to everyone and filtering client-side gives that up in exchange for eliminating the session/identity problem — worth naming as a real cost, not free, though negligible at single-digit concurrent tabs. The bigger ceiling isn't this loop at all: `InMemoryEventBus` is Node's built-in `EventEmitter`, in-process and in-memory only — no cross-process fan-out exists today, so if this system ever ran as more than one process, an event published on one instance would never reach a client connected to another. That's a materially bigger question than this Change (real distributed pub/sub — Redis, NATS, etc. — sitting between instances), and it's identical regardless of WS vs. SSE, so not something this Change creates or needs to solve. It's also not blocked by anything this Change does: the bus is already accessed only through `EventBusPort`, and everything proposed here (the Tap, `EventSink`, `SystemService`) is written against that port, not against `InMemoryEventBus` concretely — the ports/adapters split this codebase already commits to (see `CLAUDE.md`'s layering, and the longer-held idea of a fully swappable, configurable runtime with components broken into their own applications) is exactly what would let that adapter be swapped later without touching any of this.

### What actually landed

Core shape matches the design above exactly: a new `GET /events` route (`apps/http-server/src/routes/events-route.ts`) constructs a small per-connection `EventSink` with a `crypto.randomUUID()` id, `attachSink()`/`detachSink()`'d on the existing `ObservabilityTap` via `app.services.system`, cleaned up on the request's own `close` event alongside a 20-second heartbeat. `SystemService.detachSink()` added, mirroring `attachSink()`. `ObservabilityTap.start()`'s fan-out loop now awaits each `sink.handle(event)` individually inside its own try/catch. All old WS plumbing removed from the http-server path: `ws-route.ts` deleted, the `sockets`/`monitorRun` coupling stripped out of `runs/request.ts` (run-kickoff is now fully decoupled from the event stream, as designed), `@fastify/websocket` unregistered and removed from `package.json`. Client side: `middleware/ws.ts` replaced by `middleware/sse.ts` (`EventSource` instead of `WebSocket`, same buffer/rAF-flush/`eventsBatch` mechanism, `wsSend`/`wsStatus` dropped entirely since nothing consumed them), `ws-bootstrap.ts` → `sse-bootstrap.ts`, `WebSocketPanel.tsx` and `ws-slice.ts` deleted (confirmed the panel was `state.ws`'s only consumer), `System.tsx` left with just `<ThemeToggle />`.

**One real correction made during implementation, not caught until typecheck actually failed.** The initial pass deleted `packages/services/src/ws.service.ts` entirely, assuming it was http-server-only — wrong: `packages/runtime/src/runtime.ts`'s `createRuntime()` (the _desktop_ app's separate composition root) also constructs its own `WsService` and passes it into `WorkflowRuntime`, and `packages/services/src/types.ts`'s `Services` type depends on it too. That's exactly the old, unmaintained desktop path already agreed to leave alone. Corrected by restoring `ws.service.ts` and the `WsServicePort` interface, scoping the actual removal precisely to what's http-server-specific: the `ws` field on `ServicesPort` and `WsService`'s construction inside `create-services.ts`. `WorkflowRuntime`/desktop never touches `ServicesPort` at all, so this leaves it completely untouched, as intended.

**Two real bugs found only through live testing, neither caught by typecheck/lint/vitest:**

- **SSE headers never reached the client until the first write.** `reply.raw.writeHead(200, {...})` alone doesn't flush anything to the socket in Node — headers are buffered until the first body `write()`/`end()` call, which for this route could be up to the full 20-second heartbeat interval away. A `curl --max-time 3` request came back with zero bytes, not even headers, which looked like a hang rather than what it actually was. Fixed with an explicit `reply.raw.flushHeaders()` immediately after `writeHead()`.
- **`reply.hijack()` silently dropped CORS headers.** `@fastify/cors` sets `Access-Control-Allow-Origin` via `reply.header()` in an `onRequest` hook, which runs before the route handler — but `reply.hijack()` tells Fastify to skip its own send pipeline entirely (that's the whole point of hijacking), so whatever `@fastify/cors` had already set on `reply` was never actually written to the raw response once headers were written by hand. Invisible to `curl` (which doesn't enforce CORS at all) but blocked the connection outright in a real browser. Fixed by reading `reply.getHeader("access-control-allow-origin")` before hijacking and re-adding it explicitly into the manual `writeHead()` call.

**Verified**: `pnpm typecheck`, `pnpm lint`, and `pnpm vitest run` clean across every touched package (`apps/http-server`, `apps/web-app`, `packages/ports`, `packages/services`, `packages/observability`, `packages/runtime`). The real acceptance test from the plan — two concurrent SSE connections (via `curl`) plus a triggered run — received byte-for-byte identical event streams end to end (`run.requested` through `run.completed`), the exact scenario the old `"client"`-keyed `Map` could never pass. Separately confirmed live in the browser against a real run: no CORS errors, live events rendering correctly.

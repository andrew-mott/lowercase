## Change C16 - EventGraph, spawned from the Flow Graph panel itself - merged (PR #299)

Unlike every panel/tab so far, this one isn't opened by the tree — it's opened by _another panel's own content_, a genuine first for this arc. Adds a button to the Flow Graph panel's toolbar that opens (or focuses) an `EventGraph` panel, showing events live as they arrive, for any run state — not yet started, currently running, or already completed.

### Discussion

**Revised mid-build, after a first pass exposed real identity problems.** The first design gave every Flow Graph panel its own EventGraph, identified by `sourcePanelId` and reading that source's `runId` reactively. Building and testing it surfaced a run of genuine, compounding usability problems, all rooted in the same cause: panel ids were being asked to double as both a stable dedup key _and_ a stand-in for "what I'm currently looking at," and those two only agree when a panel's content never changes after creation — true for a specific run/sim's panel, false for a plain version panel or any panel that gets rerun-in-place. Concretely: closing a panel and reopening the same (plain) id later left its EventGraph frozen on stale data with no way to tell "source closed" apart from "source reopened but blank"; rerunning from inside an already-open run panel made its EventGraph silently start showing a different run than the tab's own title implied; and a rerun's EventGraph didn't line up with the one you'd get by separately opening that new run's own dedicated panel, even though both would show identical data.

**The redesign: EventGraph is a singleton that follows dockview focus, not a per-panel thing.** Only one EventGraph panel can ever be open at once — a fixed id, not derived from any source panel. Clicking "Events" on any Flow Graph panel creates it if none exists, or just focuses the existing one otherwise (unchanged: still goes through the same `OpenPanelRequest`/`explorerPanelId`/`openOrFocusPanel`/`ExplorerTabContent` machinery every other panel kind uses). Once open, it live-tracks whichever Flow Graph panel is currently the dockview-active one, subscribing to `DockviewApi`'s active-panel-change event: while the active panel is a Flow Graph panel, the EventGraph reactively mirrors that panel's live `runId` straight out of Redux — switch focus between two open Flow Graph panels and it updates immediately, no separate "attach" step. The moment the active panel _isn't_ a Flow Graph panel (the tree, the EventGraph's own panel, anything else, or nothing) — including the case where the panel it was tracking just closed, since dockview reassigns active focus as a direct consequence of that close, which fires the same event — it takes one last snapshot of what it was just showing (the runId, plus enough to redisplay identity even if that panel is now gone) and freezes there, inert, until focus lands on a Flow Graph panel again. No latch, no per-panel Redux slice, no "is this the same one" question anywhere in this design.

**The real, accepted cost**: no side-by-side comparison of two runs' events at once, unlike Flow Graph panels themselves (which exist specifically to support that, per Change C14). Decided this is fine — EventGraph is a secondary, drill-in debugging aid, not the primary comparison surface. A manual freeze/pin toggle (stop following focus on demand, to regain comparability for as long as you want it) is a named, plausible future addition, not built now.

**Display needs more than a runId.** Since there's no longer a tab-per-target, the tab title can't do the "which one is this" job it did in the first design — the panel's own content needs a small header (version, and sim name or run date/time when relevant) shown next to the graph, reusing the exact lookup logic already built for the discarded per-panel tab-label (sim-detection via a run's own `simId`, date formatting) rather than reinventing it. That header freezes together with the graph's content, from the same snapshot, so the two can never disagree about what's currently being shown.

**No persistence needed.** Nothing here survives a close or a page reload by design — reopening the EventGraph (fresh mount, fresh close, or after a reload) just starts from whatever's currently dockview-active right then, or a true empty state if nothing is. This also means the `event-graph-panels-slice`/`explorer-persistence.ts`/`store.ts` wiring built for the first design gets removed, not kept alongside the new approach.

**Named so it isn't lost, not scoped yet**: `EventGraph` will eventually need its own internal rail/side-panel, mirroring the Flow Graph panel's own pattern, starting with an Event Details tab (today's old-page equivalent) — that's real, separate work once the panel itself exists, not part of standing it up.

### What actually landed

The singleton/focus-following design above landed as described, plus two real fixes found past the design during build and review:

- **Bootstrap case showed an empty placeholder instead of the source panel's data.** Creating the EventGraph panel makes dockview's own `activePanel` become the new panel itself before it can read "who was focused a moment ago" any other way, so its first render saw only itself and started blank. First attempted fix (`addPanel({inactive: true})`, so creation wouldn't steal focus) caused a worse regression — a lone inactive panel in a brand-new dockview group never becomes that group's selected tab, so it rendered as dockview's own "no tabs open" watermark instead. Landed fix: a one-shot `initialTrackedPanelId` on the `event-graph` `OpenPanelRequest`, set to the clicking panel's own id and consumed once via a `useState` lazy initializer on first mount only.
- **Simplified while reviewing line-by-line after the above landed**: the tracking effect originally reset to "not tracking" (freezing the display) on _any_ focus that wasn't a Flow Graph panel, with a special-cased no-op carve-out for focusing the EventGraph's own panel. Tracing through an edge case showed the carve-out didn't actually help there, since tracking had already been cleared by an unrelated detour. Simplified to one rule instead of two: tracking is sticky, only ever updated when a Flow Graph panel becomes active, left untouched by focusing anything else at all. The tracked panel actually closing is still handled correctly, by a separate, pre-existing `dockviewApi.getPanel(...)` existence check.

Also extracted mid-review: the focus-tracking mechanism (dockview subscription, live-vs-frozen snapshot) moved out of `event-graph-panel/Content.tsx` into its own `use-tracked-flow-graph-panel.ts` hook, returning just `{runId, versionId}`.

Not addressed here, flagged for a possible later pass: the header's sim-specific display may want more tweaking once there's real usage to react to.

## Change C17 - Event Details side panel for the Event Graph - merged (PR #300)

Gives the EventGraph panel its own internal rail/side-panel, the piece Change C16 named but didn't build — starting with exactly one tab, Event Details, matching the old run/run-history mode's `EventDetails.tsx` before dockview existed.

### Discussion

- `EventDetails.tsx` (`components/EventDetails.tsx`) is reused as-is, not rebuilt — it already takes the actual event object (not just an id), an optional ordinal `index`, and an optional `onOpenInMainPanel` callback, and already renders the full field breakdown plus the raw `data` payload via `CodeEditor`. `onOpenInMainPanel` gets the same no-op treatment `StepResultsTab`'s new-UI wrapper already settled on — there's no dockview equivalent of the old single "main panel" concept, and building one is real, separate scope, not a prerequisite for this tab existing.
- Structure mirrors the Flow Graph panel's own `Rail.tsx`/`SidePanel.tsx` split, even though there's only one tab today — a new `event-graph-panel/Rail.tsx` + `SidePanel.tsx`, same icon-button-toggles-open, X-inside-closes interaction model, so a second tab later slots in the same way the Flow Graph panel's seven did.
- The selected event object is resolved in `Content.tsx` from the already-available `events` array + `selectedEventId`, then passed down fully-formed.

**State, worked through carefully since it touches ADR-0004's persistence pattern for the first time on a panel that also has a _derived_ value in the mix:**

- `selectedEventId` and whether the side panel is open both become plain, directly-set Redux state in a new keyed slice (`Record<panelId, ...>`, matching `flow-graph-panels-slice`'s own shape) — deliberately kept keyed even though there's only one real key ever right now, rather than going flat. Two reasons: (1) a flat slice has no way to distinguish "this mount is dockview restoring the panel that was actually open at save time" from "this mount is an ordinary reopen later, unrelated to what was last shown" — the keyed shape's per-id cleanup-on-close makes that distinction safe for free; (2) a real future direction (a pinned, per-run EventGraph, promoted out of the singleton) would need genuine multiple keys — building the keyed shape now means that later change only adds real keys, not a state-shape migration. The key itself is `event-graph-singleton`, sourced from the same id `explorerPanelId()` already computes in `explorer-panels.ts`.
- Since this is the second slice with this exact keyed-by-panelId shape, the `panelRemoved`-style cleanup reducer/action gets pulled into shared logic both slices call, rather than copy-pasting a second near-identical implementation. `pages/Explorer.tsx`'s listener dispatches it for both slices on every panel removal, keyed by that panel's own id.
- The tracked-panel _snapshot_ (`{runId, versionId}`, see Change C16) is different, because it's computed, not directly set. `dispatch()` during render isn't safe the way a component's own `setState` during render is, so the render-time-derive trick Change C16 landed on can't just be swapped for a conditional dispatch in place. Landed shape instead: Redux is read from **exactly once**, at mount, to seed local state's starting value — from then on, for that mount's whole life, only local state is ever read or derived from, and a plain effect one-way-mirrors local state into Redux purely so the _next_ mount has something to seed from.
- Revised from Change C16's own note that `trackedPanelId` "stays local-only, never persisted": that held for same-session remounts but not across a real reload, where there's no live focus history left to re-derive from except whatever got mirrored out beforehand. `initialTrackedPanelId` (the one-shot params hint) only reflects whichever flow-graph panel most recently had its "Events" button clicked, since `openOrFocusPanel`'s dedup path keeps overwriting it live, all session, even though the already-mounted singleton never re-reads it — a different, weaker signal than "which flow-graph panel is actually being tracked right now." So `trackedPanelId` itself now also persists in this slice, mirrored the same way `snapshot` is; on mount, `reduxTrackedPanelId ?? initialTrackedPanelId ?? null` — Redux wins when present, the params hint only still matters for true cold start. Degrades safely if the persisted id points to a panel that's since closed, with no extra guard needed.

**Explicitly not this Change:**

- A generic "open this in its own panel" capability — `EventDetails`' existing "open in main tab" button has nothing to route to yet, since there's no dockview panel kind for arbitrary/non-artifact content.

### What actually landed

The persistence design above landed as planned: `event-graph-panels-slice.ts`, keyed by the constant `EVENT_GRAPH_SINGLETON_ID`, holding `trackedPanelId`, `snapshot`, `selectedEventId`, `sidePanelTab`. `panelRemoved` became a shared action (`panel-lifecycle-actions.ts`), consumed by both this slice and `flow-graph-panels-slice.ts` via `extraReducers` — `pages/Explorer.tsx`'s `onDidRemovePanel` listener dispatches it once, and each slice responds independently.

Two real bugs found only through manual testing, not anticipated in the plan:

- `EventGraph`'s own root (`EChartsReact`) doesn't shrink to fit a flex sibling the way `FlowGraph`'s `ReactFlow` does — without `min-width: 0` somewhere in the chain, the chart's measured content size was winning over its actual flex allocation, crowding the Rail almost fully out of view. Fixed with `min-w-0`/`min-h-0`/`overflow-hidden` on `EventGraph`'s own root plus `min-w-0` on its wrapping flex/`ResizablePanel` slots in `event-graph-panel/Content.tsx`.
- Clicking an event didn't open the side panel if it wasn't already open — only the selection updated. Fixed by having event selection unconditionally switch to the Event Details tab, matching how clicking a node in the Flow Graph panel already unconditionally switches its own side panel tab. Both fixes are also correct if the side panel closed itself instead of not opening — same shared `sidePanelTabSet` dispatch, either direction.

`EventDetails.tsx`'s field list went through two layouts before landing: a CSS Grid fixed the original flex version's inconsistent-per-row label width, but was superseded by a simpler stacked label-above-value layout — side panels are horizontally tight and vertically cheap (they scroll), so optimizing for wrap-width beat optimizing for column alignment.

`explorer-persistence.ts`'s two near-identical dockview-gated reads (`flowGraphPanels`, `eventGraphPanels`) were pulled into one `readGatedPanelState<T>()` helper once the second copy made the duplication concrete.

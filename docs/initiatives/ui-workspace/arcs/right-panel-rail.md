# UI Workspace Initiative — Arc: Right panel icon rail (Changes C9–C13)

**Previous:** [Explorer foundation](./explorer-foundation.md) (Changes C1–C8) · **Next:** [Runs and Sims in the tree](./runs-and-sims-in-the-tree.md) (Changes C14, C15, 18)

Part of the [`INITIATIVE.md`](../INITIATIVE.md) Change log, split out to keep that doc scannable. This covers migrating the old page-based right-panel content (Params, Sim, Problems, Parameters, Step Details, Step Results) onto a single Postman-style icon rail inside the Flow Graph panel — one continuous arc, landing one tab at a time. Change C14 onward continues in [`runs-and-sims-in-the-tree.md`](./runs-and-sims-in-the-tree.md).

## Change C9 - Right Panel Icon Rail (Params/Sim migrated first) - merged (PR #292)

Supersedes this slot's original "Extend the tree with nested sub-lists" idea — displaced, not just renamed, for a reason worth keeping: exposing Runs as a tree node is very likely just a UI for setting `runId` on the Flow Graph panel that already exists, not a new panel/tab kind that needs tree scaffolding first. This is also the point where this arc stops being framed as "the Explorer spike" and starts being the actual migration of the old page-based Edit/View and Run/Run History modes into the new dockview panel model — the Flow Graph panel already generalizes across what used to be four separate pages; what's left is resolving its right-hand panel's tab structure so it can absorb the rest of what those pages did.

### Discussion

Replace `ExplorerRunRightPanel`'s current horizontal `Tabs` with a Postman-style vertical icon rail — fixed-width, always visible, icon buttons with hover tooltips (not text labels), deliberately distinct from dockview's own draggable tabs. Layout, left to right: **Graph → drag handle → Rail (fixed width) → Content pane** (only rendered when a tab is active, appearing to the rail's right — this is why opening content visually "pushes the rail left": the `[Rail+Content]` block widens and Graph absorbs the difference). The rail itself is a plain fixed-width flex child, not a `react-resizable-panels` `Panel` — only the content pane is resizable, via one handle sitting at the rail's left edge. Closing is explicit only (the existing "x" button in the content header) — no drag-past-a-threshold auto-collapse, even though `react-resizable-panels` (already in use here) supports that natively via `collapsible`/`collapsedSize`; not adopted now, worth revisiting only if explicit-only is felt as a real missing convenience in practice.

**Scope of this Change specifically**: build the rail shell and migrate the two tabs that already exist today (Params, Sim) into it, unchanged in content/logic — proves the shell and interaction pattern in isolation before loading in tabs that still need their own design pass.

**Explicitly not this Change, named so it isn't lost:**

- A Step Details / resolved-value tab folding in View/Edit's step inspection — ties to the still-unscoped "full-step resolved preview" idea in the initiative doc's Not yet scoped section.
- Event Details + Step Results tabs folding in Run/Run History's post-run inspection. Likely implication once designed: Run History probably doesn't need its own panel/tab kind at all, just another way to set `runId` on this same Flow Graph panel (pick from a list instead of submitting fresh) — `useRunEventsWithStatus` was already built event-array-agnostic for exactly this reuse.
- Actually wiring up the Sim tab (still a no-op placeholder today).
- Any of Edit mode's real editability, or draft/publish semantics — separate, larger, backend-touching work, deliberately sequenced after migration.

### What actually landed

The design above shipped essentially as planned — `ExplorerRunRail.tsx` (new) is the fixed-width icon rail, `ExplorerRunRightPanel.tsx` was renamed to `ExplorerRunRightPanelContent.tsx` and stripped of its `Tabs` header (plain conditional rendering instead, since `Tabs.Content`'s Presence context no longer wraps it), and `ExplorerFlowGraphContent.tsx` gained the two-branch (rail-only vs. `ResizablePanelGroup`) structure. Two real bugs found via manual testing after the initial build, both fixed:

- **Active-tab indication**: originally tried swapping the rail button's `variant` between `outline` and `ghost`, which caused a visible "flash" on the just-deactivated tab — `Button`'s base classes include `transition-all`, and `outline` carries a border + `shadow-xs` that `ghost` doesn't, so switching variants animated that border/shadow away, which read as a distinct bright flash. Fixed by decoupling the active indicator from `variant` entirely — `variant` stays fixed at `"ghost"`, and active state is just a conditional `bg-accent text-accent-foreground` className (the same tint `ghost`'s own hover state already uses) layered on top. Only one property changes now, so there's nothing uneven left for `transition-all` to animate.
- **Tooltip close stutter**: switching between rail tabs while a tooltip was visible caused a janky, inconsistent close animation. Root cause: Radix Tooltip's animated exit relies on detecting a CSS `animationend` event, which is unreliable at very short/zero durations across browsers — and separately, Floating UI's live repositioning can fight with a still-running CSS transform animation when the trigger changes quickly. Fixed by mirroring each tooltip's open state locally and only rendering `TooltipContent` while actually open, so closing unmounts it outright in the same render instead of going through Radix's animated-exit path at all. The hover-in fade is untouched; only the close side changed.

**Found, not fixed here — logged in `docs/todo.md` instead**: the Params tab has a real, felt render delay (confirmed via React DevTools profiling, not just suspected) driven by `ExplorerFlowGraphContent.tsx`'s `useListArtifactsQuery()` pulling every artifact in the project unscoped (336 in this dev DB) into each param row's compatible-artifacts filter and `Select` dropdown. Ruled out `SelectContent`'s `position` prop as a fix (tried `popper`, made the dropdown's own open animation worse via the same Floating-UI-vs-animation class of issue as the tooltip bug above, and didn't reduce the item count rendered either way). Confirmed the real lever by temporarily slicing the artifact list to 5 items, which dropped the worst render commit from ~50ms to ~2-3ms. Real fix is the already-known Artifacts-mode wiring gap (a curated/scoped artifact set instead of the global list) — out of scope for this Change since it changes picker behavior, not just performance.

## Change C10 - Problems + Parameters migrated to the rail - merged (PR #293)

Supersedes the old loose "Change C10+ - other content types" placeholder with a concrete next three. Both `FlowProblemsList` (flow-analysis problems, from View/Edit's `FlowVersionDetailsPanel`) and `FlowParameters` (the flow's declared param schema — names + content types; a different concept from the rail's existing run-input picker, even though both get called "Params" colloquially) become new rail tabs. Neither depends on step selection or a run existing — both are purely `flowDef`/`flowAnalysis`-driven, reusing existing standalone components as-is. Lowest-risk of the three, no new interaction wiring needed.

### What actually landed

As planned — `ProblemsTab.tsx`/`ParametersTab.tsx` (new, under `flow-graph-panel/side-panel/`) are thin wrappers around `FlowProblemsList`/`FlowParameters`, no data transformation needed since `Content.tsx` already had `flowAnalysis.flowAnalysis.problems` and `flowDef.params` computed. The rail now has four tabs (Parameters, Run Input, Sim, Problems), with a small count badge on the Problems icon, visible even when the panel is closed — mirroring the old page's Problems-tab-trigger badge treatment. One real naming change made while building this, acting on the Parameters-vs-run-values confusion discussed earlier in this arc: the former "Params" tab/rail-item (the run-input value picker) is now labeled and keyed **"Run Input"** (`SidePanelTab`'s `"params"` value renamed to `"runinput"`, `RunToolbar`'s button label updated to match), disambiguating it from the new Parameters tab (the read-only schema view) — both used to colloquially share the word "Params." Visual polish (icon choices, spacing, badge styling) deliberately left rough for now — Step Details (Change C11) and Settings (Change C12) will add more to this same rail/side panel, so it's not worth tuning the visual details until the fuller tab set actually lands.

## Change C11 - Step Details migrated to the rail - merged (PR #294)

The one piece needing real new engineering: `FlowGraph`'s existing but currently-unused `onNodeClickHandler` prop gets wired up for the first time (clicking a step node sets a "selected step" state on the panel), then `StepDetails` renders as a new rail tab driven by that selection. Worth its own Change since a future Event Details/Step Results migration will need the same click-to-select capability — getting it right here pays off twice, not a one-off.

### What actually landed

As planned — a new `selectedStepId` field + `stepSelected` reducer on `FlowGraphPanelState` (persists across rail-tab switches, same as every other panel-scoped field), a new `StepDetailsTab.tsx` under `flow-graph-panel/side-panel/`, and a `handleNodeClick` in `Content.tsx` wired into `FlowGraph`'s `onNodeClickHandler`. The auto-switch-to-Step-Details behavior is gated on `runId`: no run active → switch tabs; a run present → just update the selection, no tab switch, deliberately leaving the `else` branch unbuilt until Event Details/Step Results exist to switch to instead (confirmed working correctly for both cases in manual testing). `StepDetails`' required `onOpenInMainPanel` prop is stubbed as a no-op — "open in main panel" has no equivalent in the new dockview UI yet, logged in `docs/todo.md` rather than improvised here.

**Found along the way, not caused by this Change**: testing the run-active branch surfaced a real, previously-hard-to-reproduce bug — a run showing partial event hydration (REST backfill fills in what already happened, but no further live events ever arrive) when the WebSocket connection ends up attached to a different app instance/session than the one being watched. Root cause is the already-known WebSocket session-robustness gap in `docs/todo.md`, not something new; the concrete repro is now logged there alongside it.

## Change C12 - Settings migrated to the rail, removed from the tree - merged (PR #295)

A decided direction, not a stretch idea — just gated on this Change's own scope (reworking tree click behavior, not only adding a tab), which is why it's sequenced last. Flow/Version Settings currently open as their own standalone tab (a big tab hosting one small form) — a shape that predates the rail, from back when there was no other way to surface settings at all and the tree's own click-vs-open semantics were still being felt out. Once this lands, clicking a Settings tree item will be removed and not its own tab in dockview; Settings becomes a rail tab on the Flow Graph panel instead, the same as Problems/Parameters/Step Details.

### What actually landed

Scope narrowed to Version Settings only, confirmed with the user before planning — Flow-level Settings (scoped to the whole flow, not one version) has no natural per-version-panel home, so it stays exactly where it was, untouched. New `SettingsTab.tsx` under `flow-graph-panel/side-panel/` reuses `Content.tsx`'s already-fetched version data (no new query), showing the same fields the old standalone panel did (id, sequence, hash, created, label, description) via the existing `IdentityField`/`InputField` components, plus one field the old panel never showed at all: "Start Step" (`flowDef.start`), added after initial browser testing once it was noticed as missing. The Version-level "Settings" tree leaf and the `"version-settings"` panel kind were removed entirely (`explorer-panels.ts`, `ExplorerTabContent.tsx`, and the tree row chain), with `ExplorerVersionSettingsContent.tsx` deleted as fully superseded — TypeScript's exhaustiveness check on `ExplorerTabContent`'s switch caught every place that removal needed to propagate to.

## Change C13 - Step Results migrated to the rail - merged (PR #296)

The last piece of Run/Run History's own content: `StepResultsTab.tsx` (Output & Exports, Field Resolution, References sub-tabs) becomes a new rail tab, driven by the same `selectedStepId` Change C11 already added. This is exactly the seam Change C11's `runId`-gate in `handleNodeClick` was left open for — no run active → Step Details (already built); run active → this tab instead, showing the step's outcome rather than its static definition.

### What actually landed

As planned — a new `StepResultsTab.tsx` under `flow-graph-panel/side-panel/` wraps the existing, already-generic `components/flow-version/StepResultsTab.tsx` (Output & Exports / Field Resolution / References), threading `refs` (`flowAnalysis.flowAnalysis.refs`, confirmed real and already computed in `Content.tsx` — no new analysis needed), `paramHashes`, and `stepRunInfo` (all already flowing through `Content.tsx` for other purposes) down into it. `onOpenInMainPanel` is stubbed as a no-op, same as `StepDetailsTab`'s existing precedent (broadened that `docs/todo.md` note rather than adding a new one). Change C11's `runId`-gate in `handleNodeClick` is now complete: no run active → Step Details, run active → Step Results; both rail icons stay independently clickable by hand regardless of run state, confirmed by the user. One refinement made after initial browser testing: manually opening Step Results with no run at all was showing the full tabbed sub-panel UI with an awkward per-step "hasn't run in this run yet" message, which assumes a run exists. Added a `runId` prop through the new wrapper so that case now shows just the selected step's name (if any) plus a distinct "No run has been started yet." message, with the sub-tabs hidden entirely until a run exists.

This covers the **right panel** of the old Run page (and, for step-level content, View/Edit) — not everything those pages did. Two real pieces are still unmigrated, on purpose: **Event Details** (the old right panel's other tab, alongside Step Results) has no home yet — it belongs on a future `EventGraph` tab/rail, not here, since it's driven by selecting a node on the _event_ graph, not the step graph. **Run History's run list** (browsing/picking among past runs for a version) is a separate browsing surface entirely, not a right-panel tab at all. Both continue in [`runs-and-sims-in-the-tree.md`](./runs-and-sims-in-the-tree.md) — this Change only closes out the step-selection-driven right-panel content that lives on the Flow Graph panel itself.

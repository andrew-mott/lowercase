## Change C1 - Explorer Mini Spike - merged (PR #284)

The explorer tree, root level only. Flows expanding into Versions, real data. Clicking a row currently only highlights it (no tab host exists yet to open into) — that part of the original step description is now step 1's job. First because: open question was purely "does the tree navigation model feel right," answerable without a tab host to open things into.

### Discussion

Also folded in here, originally numbered "step 0" before it landed as part of this Change: **Coexistence boundary — decided, needed no work.** New stuff lives inside the existing `AppShell`, reachable as another "spike"-style menu item alongside the current one — not a fully separate root, specifically so old and new are easy to compare side by side while both exist. Nothing in today's routes, `FlowVersionWorkspace`, or any existing mode needed to change for this. Turned out to just be a nav-entry repoint, not its own unit of work.

### What actually landed

Summarized, the important "why" and "what" bits for history — see the original Change for full details:

- `Collapsible`, not `Accordion`, for expand/collapse — each row's state needs to be independent of its siblings, which matters more once step 4 adds a third tree level.
- **Where artifacts live in the tree, resolved**: version-scoped artifacts under their Version node, flow-shared ones (the "Share" toggle) one level up under the Flow node instead of duplicated per-version, and no global-artifacts root in this tree at all — Flows are the tree's actual root; a flat/global browse, if ever built, is a separate surface. Closes the open question in [`artifacts-mode.md`](../artifacts-mode.md) about how cross-version sharing shows up once more UI layers exist. Param-level curation stays out of the tree — deliberately not addressed.
- **Loading latency at scale (relevant once step 4 adds nodes), not solved yet**: lazy-per-node fetching (matching VS Code's own explorer) is still the right shape, but should eventually pair with prefetching one level ahead of what's rendered (RTK Query's `usePrefetch`) rather than eager full-tree preload — exact shape left open until it's actually needed.

## Change C2 - Tab/Panel Skeleton - merged (PR #285)

The smallest possible tab/panel skeleton — open/close/switch between tabs, no drag/split/reorder, state assuming one instance per content type.

### Discussion

- **Tab registry**: a discriminated union on `kind` (`TabEntry = { id, kind, label, ...kind-specific params }`), one Redux slice holding `tabs: TabEntry[]` + `activeTabId`. Entries carry only identifying params, never fetched content — the slice is a routing table, not a cache.
- **One tab per `kind` for now** — opening a tab for a `kind` that already exists overwrites/updates that entry instead of creating a duplicate (matches the singleton-per-content-type scope-narrowing already decided above). `id` stays a separate field from `kind` even though it can trivially equal it today, so relaxing "one per kind" later (multi-instance) is a reducer-logic change, not a storage migration.
- **One action per user intent, not a setter chain** — `openOrFocusTab` creates-or-updates the entry _and_ sets `activeTabId` in a single reducer case (Immer lets one case touch multiple fields); a plain reducer can't dispatch further actions itself regardless, so there was never really a "should a setter also dispatch" question.
- **Rendering**: a dispatch-on-`kind` switch maps a `TabEntry` to its real content component, passing the entry's params as props — the same dispatch-on-a-key idea the router already uses for `<mode>`, just relocated into Redux specifically so switching tabs doesn't cause a real unmount/remount. RTK Query calls live only inside the leaf content components, never the dispatcher.
- **Close/switch — Chrome's behavior, as a starting point, not necessarily final**: closing a non-active tab never touches `activeTabId`. Closing the active tab activates whichever tab is now at that same index (the one that "shifted into" the closed slot), or the new last tab if there wasn't one to its right. Zero tabs open → `activeTabId` is `null`, content area shows a plain placeholder message (unstyled for now).
- **Layout reuses `components/ui/resizable.tsx`** (`ResizablePanelGroup`/`ResizablePanel`/`ResizableHandle` — already installed, already used by nearly every existing `FlowVersion*` mode page) — the Change C1 tree in one resizable panel, a tab strip + content area in the other, both on `/explorer`. No right panel this Change.
- **Right panel explicitly deferred, re-confirmed after real discussion, not just left ambiguous.** Real complexity worth remembering precisely for whenever it's built: today's right panel reacts to one axis (clicks inside whatever page a mode mounted). Once tabs exist there will be two axes — which tab is active, plus whatever's clicked inside that tab's own content — and the panel needs to react to both, not just the one it handles today.
- **First real test uses a placeholder content `kind`, not a real content type** — proves open/close/switch works before Change C3 wires in real content. The trigger is Change C1's existing tree-row click (today it only sets `selectedRowId` for highlighting); this Change extends that same click to also dispatch `openOrFocusTab`, so the tree stops being purely cosmetic.
- **Still explicitly deferred, unchanged from before this discussion**: adopting a docking/tab library (`dockview`/`flexlayout-react`/`rc-dock`); tab-list persistence across a real page reload (a nicety for later, not blocking); movable tabs / multiple instances of the same content kind (the long-term want described in the initiative doc's Design principles section, still not this Change).

### What actually landed

Flow rows in the tree now always toggle expand/collapse on click and never open a tab — resolved a real tension (a click can't simultaneously mean "browse" and "open" without ambiguity) the same way VS Code resolves it for directories. Since that leaves no way to view/edit a Flow's own metadata, a fixed **Settings** row was added as the first child under an expanded Flow — a literal tree leaf, not a new interaction mechanism, reusing the exact same "leaf opens a tab" behavior everything else already had. This container-never-opens/leaf-always-opens split is now the tree's general rule going into Change C3, not just a Flow-specific fix. The now-unreachable `placeholder-flow` tab kind was removed as a result.

## Change C3 - Content In Tab - merged (PR #286)

Land the first real content type in a tab — the flow graph (`FlowGraph.tsx` already exists), proving arbitrary existing React content can live in the new tab host cleanly, using something already built rather than something new. Scope grew from "just the flow graph" to four real leaves, since the container/leaf split Change C2 landed on needed a second real test to confirm it generalizes, not just work once.

### Discussion

- **Version becomes a container**, same rule as Flow: click always toggles expand/collapse, never opens a tab. Confirms the container-never-opens/leaf-always-opens split from Change C2 is the tree's general rule, not a Flow-specific fix.
- **Four real leaves, not one** — Flow Settings (already exists as a placeholder since Change C2, now wired to real data), and three new leaves under Version: **Settings** (first child, fixed position — matches the existing Flow-level pattern), **JSON Definition**, and **Flow Graph**.
- **Both Settings leaves are read-only, and deliberately reuse the existing `Fields` components** (`InputField`/`IdentityField` etc., already built read-only-first for Artifacts mode) rather than inventing a new display pattern — even though there isn't much data to show yet (Flow: name/description; Version: versionLabel/sequence/description/createdAt). Consistency of pattern matters more here than the amount of content.
- **Flow Settings and Version Settings both use data already in memory** — `FlowRecord`/`FlowVersionRecord` are already fetched and held by `ExplorerTree`/`ExplorerFlowRow`/`ExplorerVersionRow` today (that's what renders the tree rows' own labels) — no new query needed for either.
- **JSON Definition and Flow Graph both need the actual flow definition fetched** — `getFlowVersionDef`/`useGetFlowVersionDefQuery` already exists (`GET /flows/versions/:versionId`) and is unused by the Explorer arc so far. Whether both leaves share one query call/cache entry or fetch independently is an implementation detail, not a design one — RTK Query's own cache should just handle this for free either way.
- **Everything stays view-only** — no edit fields, no save button, on any of the four leaves. Matches the standing "you don't ever edit yet, only view" constraint; editing is still blocked on the undesigned draft/published/authoring flow, not this Change's problem.
- **Genuinely still open, implementation-level rather than design-level** — exact new tab `kind` names/params replacing `placeholder-version` (now dead, same as `placeholder-flow` before it); which components live where; whether Flow Graph and JSON Definition end up sharing a fetch. Left for Plan Mode, not resolved here.

### What actually landed

- **The "whether Flow Graph and JSON Definition share a fetch" question resolved itself for free**: `getFlowVersionDef(versionId)` returns `{ version, definition }` in one call, so all three Version-scoped leaves (Settings, Flow Graph, JSON Definition) just need `{ versionId }` and independently call the same query — RTK Query's cache means it's one real request either way, exactly as anticipated, no extra design needed.
- **Error handling landed as designed**: each of the four new leaves fires a dismiss-required toast (`duration: Infinity`) once on error, plus a persistent in-tab "couldn't load" state with a `refetch()`-wired retry button — the toast alone would vanish before you necessarily noticed it, so neither replaces the other. This is the first real (non-test) use of Sonner anywhere in this app.
- **A real, `console`-confirmed bug found and fixed, unrelated to the design above**: a branch step routing two different cases (one named, one the mandatory default) to the _same_ target step produced two edges with colliding ids (`startStepId-endStepId` alone ignores which case an edge represents) — React actually threw a duplicate-key warning. Fixed by disambiguating with `caseValue`/`isDefault`; `gate` (`"always"`/`"onSuccess"`/`"onFailure"`) was never the right field for this, despite reading like it might be.
- **A second, much larger real bug, and a genuinely hard-won lesson**: `FlowGraph`'s `fitView` broke once the same singleton tab got reused for a _different_ version's graph in place — a scenario only this tab model introduces, since the old route-driven pages always get a fresh mount per flow via navigation. Several rounds of fixing this went _the wrong direction_ — replacing the plain declarative `fitView` prop with imperative hooks (`useNodesInitialized`, `useReactFlow`, `useUpdateNodeInternals`, a `ResizeObserver`) — each one individually "correct" per React Flow's own docs, none of them actually fixed it, and it turned out this class of imperative approach has _never_ worked reliably in this app, in any context, confirmed directly against the older, working `FlowEditPanel.tsx` (which uses the plain declarative prop and a **fixed pixel height** container, not a percentage one). The actual fix was narrower than all of that: keep the declarative `fitView` prop exactly as it already worked elsewhere, and force a real, fresh remount per version via a `key={versionId}` at the point the singleton tab's content is dispatched — matching the same "fresh mount" condition the old pages already get for free. Worth remembering precisely: don't reach for React Flow's imperative hook API in this app again without a strong reason: it has a real, established track record of not working here.
- **Explicitly parked, not solved, tracked in `docs/todo.md`**: one specific graph shape (a branch step with two edges sharing a target, the same shape from the id-collision bug above) breaks `fitView`'s _manual_ re-fit specifically — clicking the Controls button does nothing for that graph after panning/zooming, with zero console signal either way. Initial fit still works for it; every other graph shape (including other branch graphs without a shared target) is unaffected for both initial and manual fit. Also parked: the same two edges are visually perfectly overlaid (identical source/target), so their labels sit on top of each other — a layout/rendering question, and possibly a schema question (should a case be allowed to duplicate the default's target at all), for whenever multi-edge-between-same-nodes gets real visual treatment.

## Change C4 - Run Toolbar + Right Panel - merged (PR #287)

Make the Flow Graph tab capable of triggering a run, not just viewing one — the first Explorer Change that isn't purely view-only. A right panel exists for the first time, scoped to this one tab; a small toolbar surfaces Run plus what's needed to configure it (params, sim). This is also the intended test of whether the tree+tab model generalizes to something interactive, not just another passive browsing surface — which is why this jumped ahead of extending the tree with more sub-lists (bumped to Change C5).

### Discussion

- **Right panel, scoped to the Flow Graph tab only for now.** Not a general Explorer-wide feature yet — exists specifically to answer two things: whether it's the right home for run configuration, and, later, whether it can merge with whatever a "view/inspect a flow" panel eventually needs. That merge question is explicitly not resolved by this Change — it's meant to surface more concretely once there's a real Run tab to look at, not answered on paper first.
- **A small toolbar, Postman/Photoshop-style: floating over the graph canvas via z-index, anchored bottom-center, not a separate fixed strip outside it.** Buttons, left to right: **Sim, Params (if the flow has any), Run**. Least-committal/optional on the left, the actual trigger anchored on the right.
- **Which run a tab is watching is local component state, not part of the tab entry.** Today's `flow-graph` tab (`explorer-tabs-slice.ts`) only carries `{ id, kind, label, versionId }` — no run id. The active run for the status overlay lives in local state on the graph tab's content component, not Redux, and needs no explicit reset logic: Change C3's `key={tab.versionId}` remount (added to fix stale-graph bleed between versions) already tears down and recreates that state for free whenever the singleton tab gets reused for a different version.
- **Run is disabled while a run is already in flight for this tab.** Not previously discussed; the simplest consistent rule — re-enabled on the active run's completion or failure, same instinct as most run/debug buttons elsewhere (e.g. VS Code disabling Run while already debugging) rather than allowing concurrent submissions from the same tab.
- **Toolbar existence condition**: renders whenever the Flow Graph tab is open and active — since it's a singleton-per-kind tab (not per-version, see Change C3's `key={versionId}` remount fix), that's exactly whenever `ExplorerFlowGraphContent` is mounted. No other gate needed.
- **Per-button existence, not just per-button state**: Run always shows (every flow is runnable, with or without params). Sim always shows (optional for any flow, not gated by the flow's own content). Params only shows if the loaded flow definition declares ≥1 param — if none, its slot stays a reserved, visually-empty placeholder rather than letting the bar collapse, so Run's position never shifts depending on which flow you're looking at.
- **Sim and Params get their own colored indicator state** (exact palette/number of states still open — at minimum needs to distinguish "nothing to set" from "required and unset"); Run is disabled via normal form-gating if required params aren't set. Neither Sim nor Params ever fires a run themselves — clicking either only opens the right panel to that concern's form.
- **Run ends up a genuine, single-meaning "Run" button, not "Run…"** — took a few wrong turns to arrive at (see rejected alternatives below) before landing on: since Params/Sim get their own persistent, always-visible toolbar presence, informed consent ("did the user know optional params existed before running") comes from that indicator always being visible, not from forcing a reveal step before every run. That removes the need for Run to double as "open config first" — it can just fire.
- **Live run status overlain on the same graph, reusing existing capability**: `FlowGraph` already accepts `stepRunInfo` (built for `FlowVersionRunGraphPanel`, unused by the view-only leaf Change C3 landed) — wiring a run's event subscription through `useStepRunInfo` into the same graph the tab already renders is this Change's only "watch it run" surface. No separate live-view component.
- **Explicitly deferred, not this Change**:
  - **Sim selection is a no-op this pass.** The button/indicator exists and shows correctly, but there's no real picker behind it yet — sim configuration is called out as a separately complex problem (today's version is "pick a premade sim from a list," but sims are meant to be much more powerful/configurable long-term, possibly needing their own construction surface) and deliberately not wired up to avoid blocking on it.
  - **Step-level run diagnostics** (event details, step results — the `EventGraph`/`StepResultsTab`/`EventDetails` equivalents `FlowVersionRunDetailsPanel` already has) are not built this pass. That's genuinely separate, larger new surface (live event subscription plus rendering it), and answers a question ("does Run's panel and a future Inspect panel want to be unified") this Change hasn't earned the right to answer yet.
  - **Params-as-graph-nodes** (a single general "Params" node in the graph itself, clickable to fill out the same form) was seriously considered and is a good later enhancement — not the same problem as the already-deferred general custom/interactive-node editor work, since it'd be one fixed-purpose node scoped to run-context only, but not needed for the toolbar+panel version to work. A further layer on top of that (click a param, highlight which steps it feeds) is noted as an even later nice-to-have.
  - **Folding react-flow's native `<Controls />` (zoom/fit-view/lock) into this new toolbar's visual style** is a long-term intent, not this pass — native `Controls` stays as-is for now; the two toolbars coexisting visually is an accepted, temporary inconsistency.
  - **Opening the event graph in a second panel/tab to watch side-by-side during a live run** — named because it was the most useful thing about the very first live/historical run viewers built for this app — but gated behind a flexible multi-pane layout that doesn't exist yet. Logged for whenever that capability is real.
- **Rejected alternatives, worth keeping for the "why"**:
  - **A params form floated directly on the canvas** (not just small controls) — rejected once the actual content was sized up: param rows + artifact pickers + a sim picker is real form content, not a couple of buttons, and floating overlays are for small persistent controls, not full forms. This is what actually motivated the right panel's existence.
  - **A drawer/popover that always reveals config before ever firing** (the GitHub Actions `workflow_dispatch` pattern) — considered specifically to solve "optional params silently skipped," then superseded once the toolbar's own persistent indicator was found to solve the same problem more cheaply, without forcing an extra click on every run.
  - **One button that means "open config" the first time and "fire" once configured** — rejected as the same button meaning different things depending on hidden state, which was identified as the actual root ambiguity to avoid, not just a wording problem.
- **Right panel's own internal tab switching is local component state, not the main Explorer tab registry** (`explorer-tabs-slice.ts`) — same split `FlowVersionRunDetailsPanel` already has today with its own local `activeDetailsTab`. The right panel reacting to run-vs-params-vs-(eventually)-inspect is a smaller, contextual switch, not a tree-spawnable, singleton-per-kind entity like the main tabs are.
- **Genuinely still open**: exact toolbar/panel visual sizing and the indicator color states; where inside the right panel the actual "fire" button sits relative to the params form (only settled that it's visually tied to the form, distinct from the toolbar's Run); whether/how this right panel eventually merges with a non-run "inspect a flow" panel.

### What actually landed

- **Everything in the design bullets above landed as planned** — toolbar order/existence rules, the reserved empty Params slot, Run as a single unambiguous trigger, live status overlay via the already-existing `stepRunInfo`/`useRunEventsWithStatus` plumbing, sim as a genuine no-op, the right panel's local (non-Redux) tab state mirroring `FlowVersionRunDetailsPanel`. No real surprises in the build itself.
- **A real, empirically-confirmed problem found only from using it, not from the design discussion**: Explorer's tab content fully unmounts — not just visually hides — both when switching to a different Explorer tab (Radix's `Tabs.Content`, no `forceMount` set anywhere in this codebase) and when navigating away from `/explorer` to a different route entirely and back (plain `react-router-dom` unmount/remount). Confirmed directly: mid-edit params and an in-progress run's tracking both reset on either event. The "flagged, not settled" state-ownership note called out during planning wasn't hypothetical caution — it's a live, reproducible gap.
- **This directly shaped the next Change, rather than being patched here.** Rather than hand-rolling `forceMount` or lifting state into a new Redux slice for this one spike, the decision was to adopt a real docking library next — chosen after comparing `dockview`, `flexlayout-react`, and `rc-dock`, and confirming VS Code's own split/grid layout (`src/vs/base/browser/ui/{splitview,grid}` in `microsoft/vscode`) is bespoke, in-house, and not a published reusable package — `dockview`'s own docs state it's explicitly modeled on that same VS Code code. Worth remembering precisely: `dockview`'s **default** rendering mode (`onlyWhenVisible`) does the same DOM-removal-on-hide as Radix's default — adopting it isn't automatically free persistence. Its opt-in `always` mode is described in its own docs as keeping "the panel instance" alive independent of visibility (not just DOM/scroll state), which would be a materially better guarantee than Radix's `forceMount` if confirmed for the React wrapper specifically — that needs a small empirical test, not just doc-reading, before relying on it. Also relevant: `dockview` appears to support per-panel programmatic drag-and-drop locking, the leading candidate for letting an "inspector"-feeling fixed right panel live inside a general docking system rather than needing a fully bespoke component sitting outside it.
- **Small, non-breaking change made along the way**: `FlowVersionRunParamRow`'s `onOpenInMainPanel` prop (and the Preview/Show-usages buttons it drives) made optional, so the row could be reused in Explorer without dragging the old workspace's "main panel" concept along with it. Existing caller (`FlowVersionRunParamsPanel`) unaffected.

## Change C5 - Dockview Added and Implemented - merged (PR #288)

Adopt a real docking library, replacing the hand-rolled tab registry. Motivated directly by Change C4's tab-unmount finding — rather than patching that in place, `explorer-tabs-slice.ts` + Radix `Tabs` get replaced by `dockview` as the single source of truth for tab/panel state, giving drag-and-drop and dynamic panel arrangement as a byproduct rather than something to build by hand later.

### Discussion

- **Package correction, worth remembering precisely**: the plain `dockview` package is framework-agnostic core only — no React bindings. The actual React integration is a separate package, `dockview-react` (depends on `dockview`/`dockview-core` transitively). Confirmed installs cleanly against this app's React 19, no peer-dependency conflicts, clean `tsc -b`.
- **Empirically confirmed via a throwaway spike** (`/dockview-spike`, built, tested, and fully removed again — nothing shipped): all three renderer modes (`always`, `onlyWhenVisible`/default, and unspecified) preserved a panel's React state identically when switching between tabs/panels within a live `DockviewReact` instance — confirmed `always` isn't required for the core state-preservation goal, since the default already behaves this way for the React wrapper. Confirms the docs' own claim ("the panel instance is only ever destroyed when it is removed from the dock") held up in practice, not just on paper.
- **Also confirmed, and a real remaining limitation, not solved by adopting dockview**: navigating away from `/explorer` to a different route entirely and back still destroys everything — a full `DockviewReact` instance unmount via `react-router-dom`, which no per-panel renderer setting can prevent. Dockview solves the _within-Explorer_ tab-switch persistence problem completely; it does not solve "leaving the page" on its own. Not treated as blocking, per the state-architecture conclusion below.
- **Default panel placement confirmed empirically**: calling `addPanel` with no `position` specified lands the new panel in the currently active group, alongside the active tab — matches the VS-Code-style mental model this project already uses, but wasn't spelled out in dockview's own docs, hence testing it directly rather than trusting either the docs' silence or an assumption.
- **State-architecture conclusion: nothing currently in `ExplorerFlowGraphContent`'s local state needs to move to Redux for this Change.** Reasoning, not just a guess: (a) pure UI drafts (unset param selections, which right-panel tab is open) are fine to lose on the rare, deliberate triggers that would cause it (switching to a different saved workspace later, an app restart) — same tolerance most web apps already have for unsaved drafts; (b) durable-feeling state like `runId` is better handled later by re-deriving "is there a recent/active run for this flow version" from the backend on (re)mount, rather than by persisting harder client-side — the run itself is already durable server-side, so client memory doesn't need to be what makes it survive; (c) the old per-mode pages needed Redux because route navigation was constant and unmounted them on every transition — that trigger condition is structurally rare in a panel/dock model where most operations happen inside panels instead of via navigation, so this isn't purely "defer the cost," it's "the condition that made it necessary before mostly doesn't apply here." Revisit if/when workspace-switching or true multi-instance panels of the same content become real.
- **Multi-instance tabs now allowed as a system capability — a deliberate departure from Change C2's "one tab per kind" singleton rule.** The default click-from-tree path stays deduped, though: a stable, deterministic panel id computed from content identity (e.g. `flow-graph-${versionId}`) means `api.getPanel(id) ?? api.addPanel(...)` naturally finds-and-focuses an existing panel without any special-case "already open?" check. A genuine second instance of the same content would only ever come from a separate, more deliberate action later (drag-to-split, an explicit "open in new" gesture) that mints a fresh id on purpose — never from plain repeated clicking. Precedent: VS Code's own explorer keeps exactly this split even though it fully supports multiple views of the same file.
- **Right panel (built in Change C4) stays exactly as it is — a nested `ResizablePanelGroup`, not yet a dockview panel.** Deliberately kept separate so "does dockview solve tab persistence" and "does dockview's per-panel drag-lock make an inspector-feeling fixed panel work" don't get tested and potentially confounded in the same Change. The locking question (dockview supports programmatic per-panel drag-and-drop locking) is the leading candidate for that follow-up, not solved here.
- **Initial single panel/group is left unlocked** — drag-to-split stays enabled rather than restricted, since testing whether that actually feels right is part of what this adoption is for, not something to suppress by default. Locking is only a real requirement for the right/inspector panel, already out of scope above.
- **A thin, typed wrapper between tree clicks and raw dockview API calls** — decided, not yet designed; left for Plan Mode's own investigation now that the real API surface is known (`api.addPanel`, `onReady` → `api`, a `components` map keyed by name with per-panel `params`, `watermarkComponent` for empty-group state, `onDidDrop`/`onWillDrop` as the hook for external drag-and-drop later).
- **Explicitly not this Change**: layout save/load serialization (a named future "workspace views" feature — dockview makes it easy, but wiring it up now would be scope creep past "adopt the mechanism"); folding the right panel into dockview's own panel model; dragging items from the tree into the dock to create panels (confirmed feasible later via `onDidDrop` + native HTML5 drag on tree rows, not attempted yet); visual theming/CSS tailoring (looked acceptable in the spike's default styling; cosmetic tuning deferred to after the functional swap).

### What actually landed

- **Everything landed as designed, and the core premise held up in the real app, not just the spike**: state now genuinely survives switching between panels — params drafts, JSON editor scroll position, an in-progress run's live overlay, all confirmed by hand after the merge. Two different versions' flow-graphs coexist as separate panels as intended, each with its own independent right panel — an emergent benefit not specifically designed for: since the right panel was already local to each `ExplorerFlowGraphContent` instance (a Change C4 decision made for unrelated reasons), multi-instance panels get independent, side-by-side-comparable inspectors for free.
- **A real theming bug, found and fixed, worth remembering precisely**: applying a theme override via inline `style` on a `<div>` wrapping `<DockviewReact>` (the pattern dockview.dev's own theme-editor tool generates) silently does nothing. The theme's CSS class isn't applied to `DockviewReact`'s own root — dockview applies it internally to a "shell" element it manages itself, which re-declares the same `--dv-*` custom properties via its own class selector (`.dockview-theme-abyss`). CSS custom properties are re-established at whichever element directly sets them, so anything below the shell inherits from _it_, never from a wrapper further up — no override placed above the shell can ever win, regardless of specificity. The actual fix: a real stylesheet rule targeting that same class name (`.dockview-theme-abyss { --dv-...: ...; }`), loaded after dockview's own CSS import — same selector, same specificity, later source order wins.
- **A second small mechanic confirmed by reading dockview-react's actual source, not assumed**: `panel.api.updateParameters()`/`.setTitle()` have no internal diffing at all — the React bridge unconditionally bumps a render counter on every call (deliberately, per the library author's own comment, to defeat React's own setState bailout). This is a re-render, not a remount, so it was never a state-loss risk — but `openOrFocusPanel` guards both calls with a `shallowEqual`/string check anyway, avoiding a pointless re-render when refocusing already-open, unchanged content.
- **Small deviations from the pre-build design, both judgment calls made during implementation**: `ExplorerTabHost.tsx` was deleted outright rather than kept unused (fully superseded, recoverable from git history if ever needed); `explorer-tabs-slice.ts`'s store registration was removed, which as a necessary consequence also required deleting its now-unusable `selectExplorerTabsState` selector (its only consumer was the deleted tab host) — the slice's reducers/actions themselves, and their own test, are untouched and still pass independently.

## Change C6 - Migrate Flow Graph Panel State to Redux - merged (PR #289)

Get the state story right before building more panel content, not after. Move `ExplorerFlowGraphContent`'s local state (`selectedParamHashes`, `runId`, `rightPanelTab`) into a keyed Redux slice — `Record<panelId, PanelState>`, deliberately not a singleton, since multi-instance panels are real as of Change C5 and a singleton-per-"current thing" slice (like the old `flowVersionRunSlice`) would break the moment two flow-graph panels are open at once. Includes Dockview-removal cleanup — session housekeeping for intentionally removed panels, not generic React-unmount cleanup and not related to persistence. The slice itself needs no workspace-awareness at all; that's scoped to Change C7's storage layer, not this Change's shape. Full reasoning trail (why Redux over a dockview-`params` trick or components self-serializing, the identity-vs-runtime-acquired-state distinction that motivated it) in [`state-management.md`](../research/state-management.md) — this Change is the "build it for real, scoped to one panel type" validation step that doc's "Sequencing" section calls for before an ADR gets written.

### Discussion

**Refinement before implementation: panel state cleanup should be tied to Dockview panel removal, not generic React unmount.** A bare component cleanup (`useEffect(() => () => dispatch(removePanelState(panelId)), [])`) would fire both when the user intentionally closes a panel and when the whole Dockview host unmounts because the app navigated away from `/explorer` (or, later, because some shell/workspace boundary changed). Those are different semantic events: closing a panel should delete that panel's keyed state; navigating away should preserve it as part of the current workspace/session; switching to a different workspace should reset the entire live explorer slice and hydrate the target workspace instead of deleting panel entries one by one. So Change C6 should prefer a Dockview-owned close/removal hook, or equivalent controller-level wiring, for per-panel cleanup. The panel component can read/write its keyed RTK state, but should not decide when that saved slot dies. **Confirmed empirically during the build**: Dockview's panel-removal event does not fire during full `<DockviewReact>` teardown — navigating away from `/explorer` and back leaves Redux state untouched, only an intentional tab-close deletes it. No teardown guard needed.

**Further refinement, resolved in discussion before planning: one slice per panel kind, not one combined slice** — keeps tests targeted, actions domain-specific, and code-splitting easier as more panel kinds eventually grow their own state. Since only flow-graph panels have local state to migrate today, Change C6 builds exactly one slice, `flow-graph-panels-slice.ts`. No shared "common explorer panel" slice is being built now — there's no real cross-kind state need yet (persistence-pipeline status like `dirty`/`saving`/`lastSavedAt` was considered and correctly ruled out as belonging here too: it's global/singleton, not keyed by `panelId`, and describes the persistence system itself rather than any panel's behavior — it'd be its own slice, whenever Change C7 needs it). The one thing that is shared is the removal _action_, not state: `panelRemoved` (named to match dockview's own `onDidRemovePanel` event) lives on `flow-graph-panels-slice` for now, dispatched from a single central listener wherever the live `dockviewApi` is held — described that way deliberately rather than as "`Explorer.tsx`'s responsibility," since that page is a temporary spike home, not necessarily the final one. **Panel id should come from `props.api.id`** (the real id dockview assigned via `addPanel({id, ...})`), not recomputed from `explorerPanelId()` a second time inside the component — one source of truth, threaded down as a `panelId` prop.

**Also resolved: the "no new user-visible behavior" framing above undersold this Change.** Redux's store is a singleton that lives above the router — unmounting the dockview host through route navigation destroys dockview's own ephemeral layout, but not the Redux store. Panel ids are already content-derived and deterministic (`${kind}-${contentId}`, true since Change C5, originally for click-dedup, not for this), so reopening the same content after a host unmount resolves to the same id and finds its old Redux entry waiting — `selectedParamHashes`/`runId`/`rightPanelTab` resume automatically, with zero persistence/localStorage work. That's a real, demoable capability from Change C6 alone: same-session state survival after navigate-away-and-back, once the same content is reopened. This does **not** apply to intentional panel removal: `panelRemoved` deletes that panel's keyed slot. What doesn't come back on its own is the tab _arrangement_ — dockview's own layout is genuinely gone, and restoring it (even just for navigate-away-and-back, not only hard reload) is left entirely to Change C7, on purpose, to keep dockview owning 100% of layout/tabs and Redux owning 0% of it.

### What actually landed

- **The design landed as planned, no real deviations.** One slice (`flow-graph-panels-slice.ts`, keyed by `panelId` sourced from `props.api.id`), one `panelRemoved` action dispatched from a central `onDidRemovePanel` listener in `Explorer.tsx`. Confirmed by hand after merge: navigating away from `/explorer` and back, then reopening the same version's flow-graph tab, resumes its exact prior params/run/right-panel-tab state; closing a panel via dockview's own tab-close control correctly clears that panel's entry instead of leaving it orphaned.
- **Four unrelated bugs found and fixed while manually testing this Change, none of them design deviations — just things testing surfaced**:
  - A nested `<button>` inside a `<button>` in `components/artifacts/ArtifactList.tsx` (the standalone `/artifacts` page, unrelated to Explorer) — invalid HTML, and the inner "Copy Hash" button's click was bubbling up and also selecting the row. Fixed by making the row a `<div role="button">` instead and stopping propagation on the inner button.
  - `events-slice.ts`'s `selectRunEventIds` returned a fresh `[]` literal instead of a stable reference whenever there was nothing to return, defeating `createSelector`'s reference-equality memoization in `makeSelectRunEvents` — the exact case reselect's own dev-mode warning ("input selector returned a different result") exists to catch. Fixed with a shared `EMPTY_EVENT_IDS` constant. A further, bigger inefficiency surfaced while tracing this — the whole flat event map changes reference on every event app-wide, so a run's filtered list gets needlessly re-derived on every websocket batch regardless of relevance — deliberately not fixed here (would mean nesting events by run in the state shape); tracked in `docs/todo.md`.
  - A scrollbar-flicker bug reported as "dockview panels thrashing" during a browser resize turned out not to be dockview at all: `react-resizable-panels`'s own `Panel` component defaults its content wrapper to `overflow: auto`, and since `DockviewReact` manages all of its own internal sizing, that outer scrollbar had nothing legitimate to do and could oscillate on/off mid-resize. Fixed with `style={{ overflow: "hidden" }}` on the `ResizablePanel` hosting `<DockviewReact>` in `Explorer.tsx`. (An earlier guess that this was a dockview-internal `.dv-view` overflow rule was wrong and reverted once the real cause was found.)
  - `ExplorerFlowGraphContent`'s `stepIds` was recomputed as a fresh array every render with no `useMemo`, defeating `useStepRunInfo`'s own memoization by reference and rebuilding `FlowGraph`'s nodes/edges from scratch on every unrelated re-render (e.g. just switching the right panel's tab) — visible as a brief flicker on edge labels. Fixed with `useMemo` keyed on `flowDef`.

## Change C7 - Serialize Redux State + Dockview Layout - merged (PR #290)

The Change that actually fixes "refresh loses all my open tabs." Build the persistence mechanism: a subscriber that serializes the keyed slice from Change C6 alongside dockview's own layout (`dockviewApi.toJSON()`) to `localStorage` on change, plus the rehydration path on load (`fromJSON()` to restore panels, then repopulating the Redux slice from the same storage). Storage keyed with a workspace id from day one, even though only one implicit workspace exists yet — same "design the seam before the feature needs it" move already made for multi-instance panel ids before multi-instance was actually used anywhere. See [`state-management.md`](../research/state-management.md)'s "Workspace-switching implications" section for why the Redux slice itself stays workspace-agnostic while this layer isn't.

### Discussion

**Resolved in discussion before planning: one combined blob, not two independent writes.** Persist `{version, dockview: SerializedDockview, panelState: {flowGraphPanels}}` as a single object under one workspace-scoped storage key, rather than writing dockview's layout and the Redux slice separately — atomic, and matches the "one key = one workspace" framing already settled. The field is named `panelState`, not `redux`, because the persisted format should describe the domain concept rather than the current implementation mechanism. **Only plain reducer slices get persisted, never RTK Query's API-cache slices** (`flowsApi`, `runsApi`, `artifactsApi`, etc.): that cache is explicitly designed to be disposable and re-fetched on mount, is unbounded/growing in a way `flowGraphPanels` isn't, and would raise its own staleness questions if frozen into a persisted blob. A restored panel only needs its own identity (already free, inside dockview's own layout snapshot) to redrive its normal data-fetching hooks on mount — nothing about the underlying flow/version/artifact data itself needs to survive a reload for the UI to work, just to briefly show a loading state on the way back. The persistence subscriber has to select `state.flowGraphPanels` specifically — never serialize `RootState` wholesale, which would also sweep up unrelated slices, `events` (up to 5000 entries) chief among them.

**Also resolved: write triggers, typing, and where the real trust boundary is.** Redux-side writes are inherently low-frequency (discrete user actions — a param pick, a run start, a tab switch) and don't need debouncing; dockview's own `onDidLayoutChange` can fire rapidly during an active drag-resize and likely does, so that side probably wants one. The write side is fully strongly typed — everything going into the persisted object already comes from typed sources (`dockviewApi.toJSON()` → `SerializedDockview`, importable from `dockview-react`; `state.flowGraphPanels` → `FlowGraphPanelsState`, which needs exporting from `flow-graph-panels-slice.ts` now that this is a second real consumer). The read side is a genuine trust boundary typing can't cover — `JSON.parse` returns `any`, and casting that straight to the persisted type is an assertion, not a guarantee, since the actual `localStorage` content could be from an older schema or corrupted. Handled proportionately: a `version` field check plus a try/catch, falling back to fresh/empty state on any mismatch — not a full schema validator, which would be disproportionate for low-stakes local UI convenience state. The accessor functions stay synchronous for now (matching what `localStorage` actually is, and because `configureStore`'s `preloadedState` can't be async anyway — the harder part of a future async/database-backed migration is bootstrap sequencing, not this function's signature), but live in one isolated module so that migration later only touches that module and its direct callers.

**Hydration ordering and failure policy, settled before implementation: pause persistence writes until restore is complete.** Read/parse/version-check the snapshot first, stage it in memory, hydrate `flowGraphPanels` before calling `dockviewApi.fromJSON(snapshot.dockview)` so restored panels mount against their saved keyed state, then enable the persistence writer only after both Redux and dockview restoration have completed. If the top-level snapshot is missing, corrupted, or has the wrong version, discard the whole thing and start fresh.

**Failure policy is symmetric, not all-or-nothing: keep whichever half independently validates, regardless of what happened to the other.** Considered and rejected an asymmetric version of this (discard `flowGraphPanels` too if `fromJSON()` fails, but keep the layout if `flowGraphPanels` is the one that's missing/malformed) — that asymmetry wasn't actually protecting against anything real. The two halves validate through entirely separate code paths (`fromJSON()` vs. populating the Redux slice) and aren't causally entangled: a broken layout doesn't make otherwise-valid panel state unsafe to keep, it just means that state sits unused until the same content gets reopened by hand — which is exactly the harmless, by-design mechanism Change C6 already relies on. So: each half is validated on its own terms and kept or discarded independently — `fromJSON()` failing resets dockview to an empty layout but leaves `flowGraphPanels` alone; `flowGraphPanels` being absent/malformed leaves the (successfully restored) layout alone and starts flow-graph panels from empty state. One rule instead of two, and it doesn't throw away data that's still good just because something unrelated to it broke. If this produces a UX rough edge in practice (e.g. a restored panel whose business state came back but whose neighbors didn't), that's a real thing to revisit once it's actually seen, not something to design around preemptively.

**Revised after actually tracing through it: no longer symmetric, on purpose.** The rough edge named above turned out to be real, found by walking through what "dockview missing, `flowGraphPanels` kept" actually does: with dockview empty, the only way a panel comes back is the user manually clicking a tree row, which creates a genuinely fresh panel — but since panel ids are deterministic, that "fresh" panel would silently inherit old params/run/tab state from `flowGraphPanels`, looking like a new open while secretly not being one. The reverse direction (dockview restores, `flowGraphPanels` doesn't) has no equivalent problem — a restored panel's identity lives entirely in dockview's own `params`, so it just shows up correctly-identified with empty business state, indistinguishable from a panel genuinely opened for the first time. So the rule is now a one-directional dependency, not full independence: `flowGraphPanels` is only ever used if `dockview` also validated successfully; `dockview` restoring is never conditioned on `flowGraphPanels`. This is deliberately not treated as ADR-worthy on its own — it's a UI-behavior detail subject to iteration based on how it actually feels to use, not an architectural decision, and it was made without waiting on more certainty for exactly that reason. Whether this needs to become fully symmetric the other way too (or stay exactly this asymmetric) isn't knowable yet — that depends on living with it, not something to resolve by argument now.

Debounced dockview writes need an explicit final flush. A drag/resize-triggered `onDidLayoutChange` writer can debounce normal writes, but then there is always a small window where the latest layout change has not hit `localStorage` yet. Change C7 should flush any pending write on explorer host unmount and, if practical, on `pagehide`/`beforeunload`, so a refresh immediately after a layout edit does not lose the last change.

Explicitly deferred past this Change: **validating dockview's own `SerializedDockview` shape** — third-party, deeply recursive, and a maintenance burden to hand-validate against a serialization format that isn't necessarily a stable contract across `dockview-core` upgrades. Worth checking empirically first, whenever this is picked up, what `fromJSON()` actually does when handed malformed input (throws? silently drops bad panels? partially applies?) before deciding how much validation is needed on top of that. Also deferred: **signing or encrypting the persisted blob** — no real secret can be kept client-side without a server to hold the key, and this data isn't sensitive enough to warrant it even if one could be. Once this moves to a real server-backed version later, the actual right mitigations are standard boundary hygiene (payload size limits, per-user auth scoping, never interpreting the blob server-side) rather than deep shape validation — consistent with security being deliberately deferred project-wide for now, not specific to this feature.

### What actually landed

- **The design landed as planned — one combined `{version, dockview, panelState}` blob under one workspace-scoped key, an injectable-storage accessor module (`redux/explorer-persistence.ts`), redux-side hydration via `configureStore`'s `preloadedState`, dockview-side hydration via `fromJSON()` gated behind a `hydrationComplete` flag so the write listeners can't attach until after restore has actually run.** Confirmed by hand after implementation, in a fresh tab each time (see below for why that matters): basic refresh restores a panel's exact position, params, run, and right-panel tab; deleting the stored key or setting `version` to a wrong value correctly discards everything and starts fresh, with no crash; independently corrupting just `dockview` or just `panelState` confirmed the failure policy in both directions as originally (symmetrically) built — later revised, see below.
- **Later revision, same Change: `localStorage` alone wasn't enough once real multi-tab testing started.** Split into a two-tier scheme in `redux/explorer-persistence.ts` — tab-local `sessionStorage` is read first (covering both in-app navigation and a real reload with zero cross-tab interference, since it's physically isolated per tab), falling back to the cross-tab-shared `localStorage` "last known good" only for a genuinely new tab. `savePersistedExplorerState` now writes to both on every save; `loadPersistedExplorerState` tries session's envelope first, only reaching for local if session has nothing usable. No changes needed in `store.ts` or `Explorer.tsx` at all — the whole two-tier logic stayed contained inside the one accessor module, confirming that isolation was worth building. Confirmed by hand: in-app navigation no longer loses a tab's own layout to a different tab's edit; reloading a tab restores that tab's own state even when a different tab wrote more recently; a genuinely new tab still seeds from the shared latest as before. Full reasoning trail in [`state-management.md`](../research/state-management.md)'s "Cross-tab and cross-device coordination" section.
- **Further revision, same Change: the failure policy stopped being symmetric.** See the "Revised after actually tracing through it" paragraph above — `flowGraphPanels` now depends on `dockview` having also restored; the reverse independence stays.
- **Initial implementation hit two of this repo's stricter React-Compiler-readiness ESLint rules (`react-hooks/refs`, `react-hooks/set-state-in-effect`)**: the write-snapshot function had to move inside a `useEffect` rather than being assigned directly in the render body; a `hydrationComplete` flag's `setState` call had to be deferred via `queueMicrotask` to avoid being a bare statement in an effect body. **Superseded before merge, not just patched**: `queueMicrotask` was a workaround that satisfied the linter's syntax check without addressing what the rule actually flags (an avoidable extra render). The `hydrationComplete` flag itself turned out to be unnecessary — its only job was enforcing "don't attach the layout-change listener until after `fromJSON()` has run," which is already guaranteed for free by (1) plain synchronous execution order within one effect callback, and (2) React's own per-commit, declaration-order effect execution across separate effects. Final `Explorer.tsx` has no `hydrationComplete` state, no `queueMicrotask`, and one fewer effect than the version that first passed lint — same behavior, simpler code, found by asking "is there a different way to solve that" rather than settling for the first thing that satisfied the linter.
- **A real, non-obvious testing gotcha worth remembering: manually editing `localStorage` in devtools and then refreshing the _same_ tab doesn't test what it looks like it tests.** The `beforeunload`/`pagehide` flush (added specifically so a debounced write in flight isn't lost right before a refresh) fires on _any_ unload of the current document, including a refresh triggered right after a manual edit — and it unconditionally re-writes the app's current in-memory state, racing and overwriting whatever was just hand-edited. Same-tab, this makes manual corruption testing look broken (edits appear to silently "undo" themselves) when the actual persistence/validation logic is working correctly. The fix is procedural, not code: edit `localStorage`, then open the app in a **new tab** rather than refreshing the one you edited — a new tab has no prior instance to flush anything on unload, so it reads storage exactly as left.
- **Real multi-tab bug found via that same testing, and fixed: closing a stale, long-untouched background tab could stomp a different, more-recently-active tab's more current write.** Root cause: the flush-on-unload was unconditional — it always re-persisted whatever was in memory, even if that tab's own state hadn't changed since its last successful write. Fixed with a single-tab-local `isDirtyRef`, set whenever a layout or panel-state change schedules a write and cleared once a write actually happens — the flush now only fires if something is genuinely pending. This does **not** solve cross-tab coordination in general (two tabs each with real pending changes still resolve last-write-wins) — see [`state-management.md`](../research/state-management.md)'s "Cross-tab and cross-device coordination" section for why that larger question stays explicitly parked. This is a narrower, purely local fix for the specific "idle tab closing clobbers active tab" case, not an attempt at the bigger problem.

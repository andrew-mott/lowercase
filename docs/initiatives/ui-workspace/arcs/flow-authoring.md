## Change C38 - Basic flow authoring in the modern dockview UI, from the tree - merged (PR #321)

Today's Explorer/dockview UI has no way to create a flow at all — the only path in is uploading a flow definition file, and only through the old page-based UI. Re-sequenced up from "least important" once that gap became clear (see `INITIATIVE.md`'s `Next up`/`Not yet scoped` sections).

### Discussion

Context already settled in earlier notes, not being re-derived here:

- Full drag/drop visual editing stays explicitly off the table for this Change (see memory `project_visual_flow_editor_vision`) — what's wanted is a deliberately minimal "flow creation" story, modeled directly on the artifact authoring flow's own two paths (Change C24: a "+" entry point opens a dialog with two choices — upload a file, handled entirely inside the dialog; or author in place, which closes the dialog and opens a real dockview panel). This turned out to still include a live JSON-driven graph preview (below) — that part is cheap enough via existing pipeline reuse that it's worth including now, not deferred with the rest of the visual-editor idea.
- Always exactly one flow + one flow version per creation — no real versioning story attempted here. Version creation itself is allowed to be superficial; having _a_ story for it matters more than it being good yet.
- Change C42 (pruning old pages) is gated mostly on this Change landing first — a fair amount of the old page-based UI only still exists because there's no other way to create a flow yet.

**Entry point and the two paths, both funneling into one editable authoring panel.** A `+ New Flow` entry above the tree opens a dialog with two choices, mirroring Change C24's artifact-creation dialog shape:

- **Upload a file** — picked via a plain file input, read client-side via `File.text()` (no server round-trip needed to read it). Dialog closes; the authoring panel opens seeded with that text.
- **Author new** — dialog closes; the authoring panel opens blank.

Both paths land in the _same_ editable authoring panel, unlike Change C24's artifacts precedent where upload stayed a bare parse-and-submit modal with no preview at all — that shape made sense there because artifacts have no structural preview; flow definitions do, via `<FlowGraph>`, so both entry points benefit from the same live validation/preview rather than upload staying a dead end if the file has a fixable problem. Confirmed the uploaded file's name is genuinely irrelevant, not just deferred: `PostFlowReq` (`packages/types/src/api/flows/post-flow.ts`) is `{ body: FlowDefinition }` — no filename field anywhere server-side, nothing to preserve.

**Validation and preview are almost entirely reuse, not new engineering** — confirmed against real code, not assumed:

- `parseFlow` (`@lcase/specs`, pure Zod `safeParse`) plus `useFlowAnalysis` (`src/hooks/use-flow-analysis.ts`) — the _exact same hook_ already powering the real Flow Graph panel's own Problems tab (`use-flow-graph-panel.ts:156`) — run entirely client-side against the draft text on every change, no persisted version needed. `fa.problems` feeds the existing `ProblemsTab`/`FlowProblemsList` components unmodified.
- `<FlowGraph>` takes a plain `flowDef` prop, not a versionId, so the same `useFlowAnalysis` output (`layout`, `outEdges`) renders a live preview with zero `stepRunInfo` (nothing's run yet).
- The old `src/components/AddJsonFlow.tsx` (bare textarea, no problems display, no preview) is the prototype this Change properly replaces — not reused, just noted as a pruning candidate for Change C42's list later. No strict pruning policy decided (batch vs. as-found) — doesn't matter enough to settle now.

**Preview is its own real dockview panel, not embedded** — deliberately, for two reasons: the Flow Graph side already has its own side-panel element (even a reduced, read-only-for-now one, at minimum Problems) rather than fitting cleanly into the authoring panel's own split; and this is explicitly viewed as the first concrete step toward the long-parked visual-editor vision (see memory `project_visual_flow_editor_vision`) — a JSON panel and a flow-graph panel, kept in sync, is the real shape that vision would eventually take, even though only JSON→graph sync is built in this Change (graph→JSON, i.e., editable side-panel fields writing back into the JSON, is a separately-named future direction below).

**Panel identity — both panels are plain singletons**, `contentId() => "singleton"`, same shape as `event-graph`'s in `explorer-panels.ts`. This is a genuinely new case for that file: every existing panel kind keys off something that already has a real, persisted id (`versionId`, `flowId`, `hash`, `runId`) — a not-yet-created draft has none of those. Decided against minting a fresh draft id per click (which would allow multiple simultaneous drafts) specifically because it would force a second, harder question — see below — that a singleton sidesteps entirely: only ever one draft, re-clicking `+ New Flow` while one's open just refocuses it, matching artifact-authoring's "re-clicking refocuses" rule but scoped globally since there's no version to scope by yet. The preview panel is a second singleton (`flow-authoring-preview`), 1:1 with the authoring one under this model — no compound draft-id keying needed.

**A real gap the singleton design surfaced, not solved by singletons alone: the authoring panel and preview panel are separate dockview panel component trees, so they need an actual shared source of truth for the draft — one can't just read the other's local `useState`.** Resolves cleanly by following the established convention rather than inventing anything: a new Redux slice, keyed by panel id exactly like every other panel kind (`event-graph-panels-slice.ts` keys by `EVENT_GRAPH_SINGLETON_ID` despite also being a singleton), holding the draft text.

**Correction, caught during implementation planning, not assumed either time: the draft _does_ survive a reload, and it cost nothing extra.** An earlier pass here claimed reload-survival "would need a heavier persistence model than anything else in this app does today" and deferred it. That was wrong — `artifact-authoring-panels-slice.ts`'s own `content` field (the actual authored text, not just display state) is _already_ one of the four fields `explorer-persistence.ts` persists, via the exact same mechanism every keyed-panel slice would use. The new `flow-authoring-panels-slice.ts` is wired into `explorer-persistence.ts`/`store.ts`/`pages/Explorer.tsx` at the same four touch points `artifactAuthoringPanels` already uses — no new persistence model, no separate lift.

**Named for later, not scoped now: side-panel fields that edit the JSON back (the bidirectional half of the visual-editor seed above).** The real open question, correctly identified before any design was attempted: who's authoritative, and what happens when the JSON stops parsing mid-edit (either invalid JSON, or valid JSON that fails `parseFlow`'s schema). Likely default direction, not committed to: JSON text stays authoritative, holding the last-successfully-parsed object as the actual source of truth; a side-panel field edit patches that last-good object and re-serializes; an edit that doesn't parse simply doesn't commit, leaving the last-good state displayed. Real complications not worked through yet — e.g. whether editing a step's discriminated `type` field needs to restructure the rest of that step's shape. Even if this becomes several Changes, it's the more interesting long-term direction and worth tracking as a first-class idea now that a concrete JSON-first starting point exists.

**Named for later, not scoped now: Monaco inline JSON-Schema validation/autocomplete for the authoring editor.** Explicitly out of this Change — the underlying `packages/specs` → JSON Schema conversion is a cross-cutting concern beyond this initiative (it's about the schema itself, not this UI), so it's tracked as its own item in `docs/todo.md` rather than duplicated here.

### What actually landed

Core shape matches the design above: `+ New Flow` entry above the tree, `CreateFlowDialog` with upload/create-new paths, both landing in the `flow-authoring` editor panel (seeded from the picked file's text on upload), a separate `flow-authoring-preview` panel, both plain singletons, a new `flow-authoring-panels-slice.ts` wired into `explorer-persistence.ts`/`store.ts`/`pages/Explorer.tsx` at the same touch points `artifactAuthoringPanels` already uses (the draft survives a reload). Validation/preview reuse held up as designed: `parseFlow` + `useFlowAnalysis` power everything unmodified, `<FlowGraph>` renders straight from a plain `flowDef`, `ProblemsTab`/`FlowProblemsList` reused as-is.

Two real design changes made after actually using it, not part of the original plan:

- **Preview stopped auto-opening.** Both panels originally opened together from the dialog; live testing showed that's presumptuous — the editor now opens alone, with an explicit "Preview" button that opens the preview panel positioned `{ direction: "right", referencePanel: panelId }`, the same `openOrFocusPanel` mechanism EventGraph already uses for `"below"`.
- **The editor got its own Rail/SidePanel too.** Not in the original design (only the preview had a reduced Rail) — testing showed the editor had no visibility into Problems without opening Preview, and the error banner standing in for it kept resizing the editor based on message length. The editor now has a 2-tab Rail (Problems, Parameters — no Step Details, since there's no graph here to click a node on), and both panels converged on one shared idea for errors: a "last good" snapshot showing the frozen last-valid version's real `analyzeFlow` problems even while current content is broken, plus the live parse error, in one consistent place. That snapshot logic (previously only in the preview panel) was extracted into a shared `useFlowDraftSnapshot` hook (`use-flow-draft-analysis.ts`, alongside a shared `EMPTY_FLOW_DRAFT_SNAPSHOT` stub) once the editor needed the identical behavior, rather than duplicating it a second time.

Two real bugs found and fixed, both empirical, not guessed:

- **The tree didn't show a newly-created flow until reload.** Not a caching failure — the manual `flowsApi.util.updateQueryData("getFlows", ...)` push was appending with `.push()`, while the server orders flows `createdAt desc` (`prisma-flow-repository.ts`). Fixed with `.unshift()` to match.
- **Toggling layout orientation did nothing while the preview was showing a parse error.** The snapshot's frozen `flowAnalysis` bundled graph structure and layout together, so a direction toggle had nowhere to write to while the snapshot couldn't advance. Fixed by decoupling: `computeDagreLayout` is the only direction-dependent step in the whole analysis pipeline, so layout is now recomputed from the frozen snapshot independently, regardless of whether current content parses.

Smaller real additions beyond the original design:

- A shared `GraphViewControls` component (zoom in/out, fit view, layout orientation) extracted out of `RunToolbar.tsx` — used by both the real Flow Graph panel and the new preview panel's own toolbar, which also means the preview no longer shows React Flow's default `<Controls>` (already-existing `FlowGraph.tsx` behavior: it only renders those when no custom `toolbar` prop is given).
- The preview panel no longer bails out to a bare "nothing to preview" message before the first valid keystroke — it renders a real, empty graph canvas + Rail from the start, backed by the shared `EMPTY_FLOW_DRAFT_SNAPSHOT` stub.
- A `problemsBadgeVariant` prop added to `Rail.tsx` (defaulting to the original color, so the real Flow Graph panel is untouched) — the Problems badge turns red when the count includes a save/parse-tier failure, not just `analyzeFlow` problems.

**A real, pre-existing, unrelated bug surfaced while testing**: Monaco's `CodeEditor` wrapper sometimes stops accepting spacebar input entirely, in both this editor and artifact-authoring's. One concrete theory (a debounced-value echo racing Monaco's own value-prop resync) was implemented and tested live — it did not fix the symptom, so that mechanism is ruled out, not just unimplemented; reverted rather than left as unproven complexity in a shared component. Full trace in `docs/todo.md`; not this Change's to fix.

**Explicitly discussed, not built**: whether artifact creation's own upload path should adopt the same upload-into-an-editor pattern this Change used (today it stays a bare parse-and-submit modal, with no content validation at all beyond content-type/format matching). A plausible future improvement, but the artifact and flow authoring panels would stay separate components even if it happened — an artifact's editor needs a metadata sidebar flows don't and has no structural preview to speak of (the content _is_ the preview), while a flow validates against a fixed schema and artifacts don't. Two data points isn't enough to guess the right shared shape from yet.

Verified throughout: `pnpm typecheck`/`pnpm lint`/`pnpm vitest run` (286 tests, including new coverage for `parseDraftFlow`'s three tiers and the two new panel kinds' ids/icons) at every step, plus extensive live manual testing — which is what actually drove most of the changes above.

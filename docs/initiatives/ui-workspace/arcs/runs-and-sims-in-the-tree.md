# UI Workspace Initiative — Arc: Runs and Sims in the tree (Changes C14, C15, 18)

**Previous:** [Right panel icon rail](./right-panel-rail.md) (Changes C9–C13) · **Next:** [Event Graph](./event-graph.md) (Changes C16, C17)

Part of the [`INITIATIVE.md`](../INITIATIVE.md) Change log, split out to keep that doc scannable. Continues from [`right-panel-rail.md`](./right-panel-rail.md). Covers promoting Runs and Sims from candidate ideas into real, lazy-loaded tree categories (each opening its own Flow Graph panel), plus the Simulate authoring flow that builds on the Sims list. Change C16/17 (EventGraph) is a separate, unrelated feature that happens to sit between these numerically — continues in [`event-graph.md`](./event-graph.md).

## Change C14 - Runs list in the tree, each run opens its own Flow Graph panel - merged (PR #297)

Promotes the "Runs as a lazy-loaded, collapsible tree category under a Version" candidate into a real Change. Adds a "Runs" sub-node under each Version in the tree, listing that version's past runs newest-first with a brief date/time label. Clicking a run opens a Flow Graph panel scoped to that specific run, distinct from the version's plain graph panel and from any other run's panel — by design, so multiple runs (or a run alongside the live/editable graph) can sit open side by side for comparison.

### What actually landed

As planned — new `ExplorerVersionRunList.tsx` (named for what it is, a run list scoped to one version, leaving room for a possible future "all runs across a flow" list under a different name) fetches `useListAllRunsQuery({flowVersionId})`, sorted newest-first. `ExplorerVersionRow.tsx` gained its own local `isRunsExpanded` toggle (lazy-fetch only on expand), sibling to the existing "Flow Graph"/"JSON Definition" leaves. Panel identity (`explorer-panels.ts`) now folds an optional `runId` into `contentId()` for the `"flow-graph"` kind — `flow-graph-${versionId}-${runId}` — giving each run its own stable, distinct dockview panel id, while the plain "Flow Graph" leaf (no `runId`) is untouched. A new `runSelected` reducer on `flow-graph-panels-slice.ts` is mechanically identical to `runSubmitted` but named for its different call-site meaning — picking an existing historical run from the tree, not just having submitted a fresh one. `ExplorerTabContent.tsx`/`Content.tsx` needed **no changes at all**: `Content` still only ever reads `runId` out of Redux via `panelId`, exactly as before — the run is carried entirely by which panel id got opened, not by anything threaded through dockview params.

Also fixed along the way, not originally scoped but surfaced immediately in testing: `runs-api.ts` had no RTK Query tag-based invalidation at all (unlike `artifacts-api.ts`/`sims-api.ts`, which already use this pattern) — submitting a run never refreshed the tree's Runs list. Added `tagTypes: ["Runs"]`, `providesTags` on `listAllRuns`, and `invalidatesTags` on `requestRun` (only when the response is `ok:true` — a failed request shouldn't trigger a refetch).

**Explicitly deferred, raised in discussion but genuinely undecided**: whether `EventGraph` fits into this story at all (still not integrated into the new panel anywhere); whether the Run button should change (e.g. to "Rerun") on a run-specific panel; whether a run-specific panel's Run Input tab should show that run's actual chosen params (a `useGetRunParamsQuery({runId})` endpoint already exists returning the exact shape needed — `RunParamManifest = Record<string,string>`, same as `selectedParamHashes` — making this easier than first assumed, but not built); and whether those params should be editable or treated as a stable historical record. All logged in `docs/todo.md` rather than improvised here.

## Change C15 - Sims list in the tree, click opens a sim in its own Flow Graph panel - merged (PR #298)

Promotes "Sims in the tree" from a candidate bullet into a real Change — same per-version, lazy-loaded tree-category shape Change C14 just proved out for runs, applied to `SimRecord` instead.

### Discussion

- Sims list mirrors Change C14's `ExplorerVersionRunList` shape closely — a lazy-expand "Sims" node per version, `useListAllSimsQuery({flowVersionId})`, each row showing the sim's own `name` (no date fallback needed, unlike runs — a `SimRecord` always has one).
- Clicking a sim opens a Flow Graph panel loaded at `spec.parentRunId` (`SimDefinition = {sim, spec: ForkSpec}`, `ForkSpec = {parentRunId, reuse}`, from `useGetSimQuery({simId})`). Not read-only overall — running directly from this panel is allowed and useful, unlike the old Sims page. Only the per-step "reuse" indicator is non-interactive: pass `StepResultsTab`'s existing `isReused` prop (unused since Change C13) without `onToggleReused` — it already disables its own `Switch` when that's undefined, no new "read-only mode" needed. That overlay should stop applying the moment the panel's `runId` moves past `spec.parentRunId` (i.e. once you actually run from it) — also falls out for free, since it's only ever computed while `runId === spec.parentRunId`.
- Panel identity: keyed by `simId`, not `runId` — mechanically the same editable-panel shape the plain graph panel already has (mutable `runId`, just starting non-null here instead of `null`), plus a `simId` for its own identity/title/reuse-overlay. Explicitly provisional, flagged in discussion as possibly needing to diverge later (collisions, or whatever's allowed to be viewed by then) — not settled now.
- The rail's existing `"sim"` tab (currently a stub, "Sim selection isn't wired up yet") becomes this sim's own identity display (name/description/parent run) when sim-scoped, with a plain fallback message otherwise.

**Also needed for this to actually behave like a fork, not just visually resemble one**: `Content.tsx`'s `handleRun` needs to pass `simId` through to `requestRun` — `PostRunsReq` already has `simId?`/`forkSpecHash?` and `run.service.ts` already threads them into `runFlow()`, but nothing in the new UI sends either today, so running from a sim panel as-is wouldn't actually reuse anything.

**Explicitly not this Change, named so it isn't lost:**

- Assigning a sim to run with from the plain/non-sim panel (a dropdown initially; drag-and-drop into a future "run workspace" is the longer-term idea), or previewing an assigned sim before committing to running it.
- Authoring/creating a new sim at all — a right-click-a-run-to-fork-a-sim flow, or any other creation path — separate, unresolved.
- Showing which sim a run used on the Runs _list_ itself (the tree). `RunListItem` (the list endpoint's type) doesn't carry `simId` — needs a small backend read-path addition first. **Correction, found while wiring the Sim tab for arbitrary run panels**: this gap is narrower than first thought — it's list-only. The _detail_ endpoint (`useGetRunDetailQuery`) already returns the full `RunRecord` (nested under `.run`), which already has `simId`/`forkSpecHash` — no backend change needed for any already-open panel to know its own run's sim. A migration lapse on the list specifically (an old version of the runs list had an icon for this), not a new gap, but not part of this Change.
- The long-term "two run ids" question — a sim's own parent run vs. the run it actually produces by running it — and how much swapping between viewing those two is really needed.

### What actually landed

Abbreviated — real substance, several fixes found past the original plan during testing. The Sims tree list, sim-specific panel identity, and reuse indicators landed as designed above. Three real fixes came out of testing, not scope creep:

- **Running a sim didn't actually fork/reuse anything** — `handleRun` was sending `simId` but not `forkSpecHash`, and only the latter drives the engine's reuse planning (`simId` is pure attribution). Traced through `run.service.ts`/`run-flow.ts`/the engine's `flow-def-result.planner.ts`, confirmed via the old `RunnerRunButton.tsx`'s working precedent, fixed by also sending `simDefinition.sim.forkSpecHash` (already in hand, no new fetch).
- **The graph's own "↺ " reused-node marker was never wired up** — `FlowGraph.tsx` already had a `reusedStepIds` prop from the old UI; `Content.tsx` just never passed it. Now does, gated the same way as the Step Results reuse indicator.
- **The "Reuse" switch now merges two sources**, not one: the sim's declared pre-run plan (as designed) _or_, falling back, a step's real `sourceRunId` fact from its own `step.reused` event — so a completed run's actually-reused steps show correctly too, not just a sim's forward-looking plan. Same switch, no new UI.

One more extension beyond the plan: the Sim tab's identity display now shows for _any_ panel whose currently-displayed run has an active sim — not just panels opened directly from a sim — by reading `simId` off `useGetRunDetailQuery`'s existing `RunRecord`, no backend change needed (that gap turned out to be list-endpoint-only, corrected above).

Two things surfaced during testing, deliberately not investigated, logged in `docs/todo.md` instead: a real bug with sims that combine parallel branching/joins and step reuse, and a note that the run detail and run list endpoints could use a joint review (the detail one's a bit old).

## Change C18 - Simulate — author a sim from a run - merged (PR #301)

Renames the Flow Graph panel's toolbar "Sim" button to **Simulate**, and gives it an actual authoring flow — today it only pulls up a mostly-static sidebar. v1 is scoped to exactly what sims already support: a single base run (`parentRunId`) plus a `reuse` list of step ids, no individual output mocking yet.

### Discussion

- **Rename "Sim" to "Simulate."** The button's primary job is trending toward _doing_ something (authoring), with viewing an existing sim's info becoming the secondary case — a noun-named button ("Sim," like "Settings"/"Problems") fits viewing, not authoring. Cheap and reversible either way — one label, no logic change — but worth doing now rather than after the authoring flow exists and the mismatch is more visible. `RunToolbar.tsx`'s existing button/prop just gets relabeled; `onOpenSim` stays the handler name.
- **Precedent found and reused, not reinvented**: the old (pre-dockview) route-based flow — `pages/sims/CreateSim.tsx`, `components/sims/SimsFlowView.tsx`, `SaveSimButton.tsx`, `sims-slice.ts` — confirms the actual save payload: `postSim({ flowId, flowVersionId, parentRunId, reuse: string[], name, description? })`. `SimsFlowView.tsx`'s own separate React Flow renderer is **not** ported — `FlowGraph.tsx` (already used everywhere in the new Explorer) already accepts `reusedStepIds` and already visually marks them, so authoring reuses it directly instead of maintaining two graph renderers.
- **Entry point: the Simulate tab's empty state.** Today it's a static "This panel isn't viewing a sim." When there's a real run loaded and no sim yet, that same spot gets a way to start authoring one from this run instead — same button, same tab, branching by context, rather than a second button.
- **No graph-click mode overload.** Node clicks keep their one existing meaning (select/inspect a step) the whole time, authoring or not — never repurposed to mean "toggle reuse." This was considered and deliberately rejected: overloading a click with a second, invisible-state-dependent meaning is exactly the "accidentally did the wrong thing" problem tool-mode toolbars (cursor vs. pan, considered and explicitly not built here) exist to solve, and this flow doesn't need that machinery.
- **The reuse decision happens on Step Results, via a switch that already exists.** `components/flow-version/StepResultsTab.tsx` already has a `Switch` for "Reuse" (`isReused`/`onToggleReused` props) — currently always disabled in the new dockview UI, per its own comment, because `onToggleReused` is never passed. Wiring that through live while authoring is active means deciding reuse happens exactly where you're already looking to inspect a step, no separate selection surface needed. Its visibility gate (`effectiveIsReused !== undefined`) means every eligible step needs an explicit `true`/`false` passed while authoring, not left `undefined` — otherwise a step nobody's touched yet wouldn't show the switch at all, not just show it unchecked.
- **`parallel`/`join` steps: no switch rendered at all while authoring**, not merely disabled — same exclusion the old flow had, but re-homed here now that clicks aren't what gates it. The engine doesn't support reusing these pure-control-flow steps today; may be revisited later, not this Change's problem.
- **Persistent anchor: a new, separate top-center `Panel`, not the existing bottom-center `RunToolbar`.** `FlowGraph.tsx` already renders its toolbar via `@xyflow/react`'s `<Panel position="bottom-center">` — a library primitive that supports multiple independent panels at different positions at once. A second, small `<Panel position="top-center">`, visible only while authoring, holds a step-count and Save/Cancel — compact, not a full bar. This is the piece that solves "I lose track I'm authoring if I go inspect a different tab": it renders independent of the rail/side-panel, so switching to Problems or Step Details to look around never hides it. Kept as its own new component rather than added to `RunToolbar`, since it's authoring-specific and temporary, not a permanent toolbar member like Sim/Params/Events/Run.
- **Save opens a `Dialog` for name + description, not an always-visible inline form.** `Dialog` already exists as a UI primitive (`components/ui/dialog.tsx`, already used in `FlowVersionArtifacts.tsx`) — Name (required, blocks confirm if empty) and Description (optional) live there, and confirming is the actual `postSim` dispatch. Not really "double save": the toolbar's Save declares intent to finish, the dialog collects the metadata the record actually needs — same shape as a "Save As" dialog. `description` is already a real, optional field on `PostSimsReq` that the old UI never actually surfaced (only ever collected a name) — this isn't restoring something that existed before, it's adding UI for a field that was always available.
- **Run is disabled while authoring is active on this panel**, rather than allowing a rerun (or reopening this same panel at a different run) mid-authoring and having to define what that does to an in-progress draft. Sidesteps the question entirely instead of answering it — authoring has to be finished (saved) or explicitly cancelled before this panel's run can change at all.
- **After saving, the panel itself is unaffected** — its own `runId`/identity doesn't change, Run re-enables, and the Simulate tab just now shows the newly-created sim's info instead of the empty state (the same view every already-existing sim gets). Actually running _with_ the new sim means going to open it from wherever sims are listed (Change C15's sims-in-tree), same as any other sim — not something this panel does for you.
- **State**: the in-progress, not-yet-saved reuse selection is new fields on `flow-graph-panels-slice.ts` — keyed by `panelId`, same as `selectedParamHashes`/`sidePanelTab`/everything else there — rather than a new slice. This means it persists across reload for free, using the exact same already-wired persistence path (`explorer-persistence.ts`'s existing `flowGraphPanels` field) — no new plumbing needed, unlike Change C17's EventGraph work. Deliberate: losing a half-marked authoring session to an accidental reload would be a bad experience for zero cost to avoid, given the mechanism already exists.

**Explicitly not this Change:**

- The dropdown to pick an _existing_ sim from a plain, no-run Flow Graph panel — a separate, smaller, not-yet-designed piece.
- A generalized multi-tool graph toolbar (cursor vs. hand/pan mode, and whatever else) — named while discussing why node clicks shouldn't be overloaded here, but a real, bigger, separate idea that also touches panning, not something to build as a side effect of this feature.
- **Attaching the freshly-authored sim to the current panel/session as a convenience** — e.g. so the run you just authored from now shows as "this run + the sim overlaid," ready to rerun with it attached, without leaving the panel. Genuinely unsure whether this is wanted: it would need to be visually unambiguous that the panel is no longer showing the plain original run, and reruns from that state would mean something different than they do today. Deferred deliberately.
- **Visually distinguishing "this step was reused _by the run you're viewing_" from "this step will be reused _by the sim you're currently authoring_"** — with today's plain-box nodes these look identical (both just the same `↺` marker), and a real, separate bug was found and left alone on purpose: the graph's own reuse markers and the Step Results toggle are keyed off the _narrow_ `simDefinition` (only populated when this panel was opened directly with a `simId`), while the Sim tab already uses the _broader_ `activeSimDefinition` (any run that happens to have incidentally used a sim) — so an incidental run's reuse can show correctly in the Sim tab while the graph itself stays blank for it. Deliberately not fixed here: custom node types are the right place to actually design how run-status/reuse/authoring-draft states get shown on a node — solving it now with plain boxes would likely be thrown away once that lands.
- **Simulate's behavior on a plain, no-run Flow Graph panel** — deliberately left as just "open the tab" (which itself says "Open a run to simulate from it."), not designed further.
- **The side panel needs more specificity across the three viewing contexts** (a sim opened directly, a run that incidentally used one, a plain flow graph) — flagged as real during review, not dug into. Exact shape not known yet.
- **A general "what am I looking at" signal across open panels** — now scoped as its own Change, continues in [`panel-icons-and-nav-rail.md`](./panel-icons-and-nav-rail.md).
- **Editing an existing sim** — named, not designed. The rough idea floated: a sim might be freely editable while it has no runs of its own yet, and more locked down once it's actually been used, mirroring how a flow version becomes more fixed once it's been run. Not something to build until sims themselves feel more settled.

### What actually landed

A string of small refinements made from actually using it, before stopping here for now. The design above landed as planned. On top of it, several rounds of using it surfaced small fixes and behavior changes, roughly in the order they came up:

- Icon swapped to `BotIcon` (from the initial `FlaskConicalIcon`, which stayed matched to the old "Sim" meaning) and the dialog's own visual styling adjusted, both direct polish, no behavior change.
- A real gap found and fixed in `SaveSimDialog.tsx`'s save handler: it only ever branched on `result.data?.ok` being true, so a _logical_ failure (`{ok: false, error}` — a real response the server sent on purpose) was silently swallowed, distinct from a transport-level failure (`postState.error`) which at least showed a generic inline message. Sonner toasts added for both success and failure, the failure one now surfacing the server's actual message for the logical case.
- `SimAuthoringBar.tsx`'s Save disabled until at least one step is marked for reuse (an empty-reuse sim isn't a meaningful save).
- `SimAuthoringBar.tsx`'s text portion reworked into two atomic, `whitespace-nowrap` phrases ("New sim" / "N reused") inside a `flex flex-wrap` row instead of one inline string with a `·` separator — with only two atoms, wrapping can only ever produce one row or two, never a mid-phrase break. The `·` separator was dropped in the process (would've read oddly orphaned on whichever line it landed on when stacked).
- Simulate hidden entirely (no reserved slot, unlike Params) when the panel was opened directly at a sim (`simId` prop set) — nothing to author there, only view, and the rail's own Simulate tab still covers that.
- Simulate's click behavior changed for the has-a-run case: it now starts authoring immediately (dispatches the same action the in-tab button did) in the same click that opens the tab, instead of requiring a second, in-tab click — collapsing two steps into one. Still allowed when the run incidentally already used a sim (chaining, decided earlier to be fine); skipped only when already mid-draft (so it can't reset an in-progress list) or when there's no run loaded at all, which still just opens the tab as before.

**Stopping here for now** — there's more to get right in sims authoring, named above, but this is a reasonable place to pause and let it sit before continuing.

## Change C53 - Activate `apps/web-app`'s real production build - merged (PR #336)

`apps/web-app`'s `build` script is currently `echo build` — production `vite build` was never exercised this whole initiative. Bundled with it, per the user's own call: the dead `baseUrl`/`paths` tsconfig config, and hardcoded `localhost:3000` in 6 files, both found during the same Change C49 review pass.

### Discussion

**Root failure, confirmed by running it: Rollup can't resolve `@lcase/types` at all.** `vite build`'s production path goes through Rollup, which resolves workspace packages via each package's `exports` map, honoring only real runtime conditions (`"import"`/`"require"`/`"default"`) — never `"types"`, which is a TypeScript-only resolver hint. `@lcase/types`'s `exports["."]` has only `"types"`, so Rollup finds nothing to resolve and fails outright. `tsc` and `vite dev` both tolerate this today (`tsc` only ever needs the `"types"` condition; `vite dev`'s resolution is lazier and apparently doesn't hit the same wall) — only the production bundler actually exercises the gap.

**Why `@lcase/types` has no JS to point `"import"` at, traced to the actual cause, not assumed: `packages/types/tsconfig.build.json` sets `"emitDeclarationOnly": true`.** That's a deliberate, explicit flag — every other package's build config omits it and gets normal `tsc` output (`.js` + `.d.ts` side by side). `packages/types` is the only package in the repo built this way.

**Confirmed this is atypical for _this repo_ specifically, not for types-only packages in general — checked `packages/ports` directly, the repo's other pure-types package.** `packages/ports` has no `emitDeclarationOnly` override, so `tsc` emits real `.js` files for every module, and its `exports["."]` already has both `"types"` and `"import": "./dist/index.js"` — already working the standard way. Its emitted `dist/index.js` is a real, if trivial, artifact: a flat chain of `export * from "./foo.js"` re-export statements, one per port file, nothing else — no runtime logic, because there's no runtime logic in the source to emit. `packages/types` would produce the same shape of near-nothing output built the same way, since neither package has any source that isn't a pure `interface`/`type` declaration.

**Answers the general question this Change raised: there is no "runtime-free" `exports` condition that bundlers respect.** `"types"` is consumed only by TypeScript's own module resolver; Node and Rollup/Vite/webpack ignore it completely for actual module resolution and require a real `"import"`/`"require"`/`"default"` target to exist as a resolvable file, even if that file ends up empty or entirely tree-shaken away. The only way to have a truly zero-JS-emitting package stay importable is full, disciplined use of `import type { ... }` at every call site across all consumers (fully erased by the compiler, never reaching the bundler's resolver) — fragile against a single accidental non-`type` import anywhere in the tree, and not something this repo enforces today. So shipping a real (if trivial) build output, matching `packages/ports`'s existing pattern, is the normal fix here, not a compromise.

**Settled fix for `@lcase/types`:** drop `emitDeclarationOnly` from `tsconfig.build.json` so `tsc` emits real `.js` output like every sibling package, add `"import": "./dist/index.js"` to its `exports["."]` map, matching `packages/ports`'s exact shape.

**Once that's fixed, `apps/web-app`'s build is likely just swapping `build`/`build-old` back** — the real `vite build` command (`tsc -b && vite build`) already exists under `build-old`, disabled and renamed at some point rather than missing. **Found the actual Change: #201, immediately after #199's Vite scaffolding.** Not stated in the Change description or commit history, but the user's own recollection, checked against the timing, fits — a root `pnpm build` fans out across the whole turborepo, so having `apps/web-app` do a real `vite build` in that chain would slow down every backend-only iteration for a frontend build that wasn't needed yet. Not a sign of some other blocking problem, just an iteration-speed tradeoff made early and never revisited — safe to swap back.

**Also bundled into this Change, per the user's own call (2026-08-20), rather than split into separate piecemeal follow-ups:**

- `apps/web-app/tsconfig.app.json`'s deprecated `baseUrl`, and the root `tsconfig.json`'s matching `baseUrl`/`paths` block (the latter likely fully vestigial — that file has `"files": []`, no direct compilation of its own) — both confirmed dead during Change C49's review.
- 6 files hardcoding `"http://localhost:3000"` with zero env-var abstraction: `sse-bootstrap.ts` (events endpoint) and all 5 `redux/api/*.ts` files (API base URL). Framed by the user as a build-config concern — Vite's `import.meta.env.VITE_*`, resolved per `.env`/build target — given the app's dual localhost-browser/Electron deployment target genuinely needs the base URL to vary per build. Not attempted or scoped beyond this diagnosis yet.

**A third bundled item, decided 2026-08-22: real ESLint for `packages/types` and `packages/ports`, both currently stubbed `"lint": "echo lint"`.** Motivated directly by the fix above — nothing in either package's `tsconfig.build.json`/`package.json` actually stops runtime code (a stray `function`, `class`, `enum`, top-level `const x = ...`, or a value-importing `import`) from creeping into what's supposed to be a pure-types package; `@lcase/types` only avoided that by accident, not by any enforced rule, which is exactly how it ended up on `emitDeclarationOnly` with no one questioning whether the packages actually stayed empty. **Deliberately lint-only for now, no postbuild dist-content check** — the user's own call: the dist-check idea (asserting emitted `.js` is nothing but `export * from` re-exports) is real and still worth having eventually as the stronger, output-level guarantee, but it's a "later, if I want to really force it" item, not part of this pass. Lint gets most of the way there now with much less setup, given these packages have never had real ESLint configured at all (both currently just stub `"lint": "echo lint"`, no precedent to follow within the packages themselves).

- **Config shape**: a real flat `eslint.config.js` per package, matching `apps/web-app`'s existing style (ESLint 9 flat config, `@eslint/js` + `typescript-eslint`, both already proven in this repo) but scoped down — no React/browser plugins or globals needed, these are plain Node/TS packages.
- **The actual enforcement rules**, both new to this repo: `no-restricted-syntax` banning `FunctionDeclaration`, `ClassDeclaration`, `TSEnumDeclaration`, `VariableDeclaration`, `ExportDefaultDeclaration`, `ArrowFunctionExpression`, and `FunctionExpression` — the constructs that actually emit runtime JS, each with a custom message pointing at why (`interface`/`type`/re-exports only); plus `@typescript-eslint/consistent-type-imports` so any import that's only ever used as a type is forced to `import type`, keeping it erased rather than becoming a real runtime `import` statement.
- **Known gap, accepted rather than solved by this pass**: a bare top-level expression statement calling an imported value (no declaration to catch via the rules above) wouldn't be flagged. Real but obscure — the syntax-ban list catches the realistic accidental cases (someone adding a helper function, a class, a default export), not deliberately adversarial code. The dist-content check, if it's ever added later, is what closes this gap for good by checking the actual output instead of trying to enumerate every syntax shape that could produce one.

**Resolved by the time of build:** the `.env`/`VITE_*` question turned out to be one var (`VITE_SERVER_URL`), not per-target ones — see "What actually landed." `build-old` was swapped back verbatim, not rewritten. Whether any other workspace package needs the same `exports` fix as `@lcase/types`: no other package ever surfaced a similar Rollup resolution failure across the many full clean builds run over the course of this Change — the same mechanism that originally caught `@lcase/types` would have caught any sibling with the same gap.

### What actually landed

**The `@lcase/types` fix, spiked and confirmed clean end to end.** Dropped `emitDeclarationOnly` from `tsconfig.build.json`, added `"import": "./dist/index.js"` to `exports["."]`, matching `packages/ports`'s exact shape. Real build output is exactly as predicted: `dist/index.js` is nothing but a flat chain of `export * from "./x.js"` re-exports, no runtime logic, since the source has none. Ran the actual `tsc -b && vite build` chain (`apps/web-app`'s `build-old` script) cold — succeeded outright, no second failure behind the one that was found. Ran `pnpm typecheck` from the repo root afterward — all 25 packages clean, confirming the fix doesn't regress anything else that consumes `@lcase/types`.

**`build`/`build-old` swapped for real, confirmed safe first.** Found the Change that disabled it: #201, immediately after #199's Vite scaffolding. Not stated in the Change description or commit history, but the user's own recollection — a root-level `pnpm build` fans out across the whole turborepo, so a real `vite build` in that chain slowed down every backend-only iteration for a frontend build that wasn't needed yet — fits the timing and isn't evidence of some other blocking problem. `apps/web-app/package.json`'s `build` is now `tsc -b && vite build` directly; `build-old` removed.

**A vendor-chunking pass, done live during this same session, decided in scope for this Change rather than deferred.** Motivated by the stock Rollup chunk-size warning (`vite build` producing one 2,517 KB/778 KB-gzipped bundle) surfacing naturally once the build actually ran for the first time. Explicit user framing: caching benefit only (separately-cacheable vendor chunks so a deploy that only touches app code doesn't force everyone to re-download React/Monaco/etc.), deliberately **not** pursuing real lazy-loading (`React.lazy`/dynamic `import()`), which would additionally reduce initial-load bytes but requires real code changes and Suspense-boundary testing — out of scope, named as a real future option if ever wanted, not pursued now.

- **Config added**: `apps/web-app/vite.config.ts`'s `build.rollupOptions.output.manualChunks`, mapping `react`/`react-dom`/`react-dom/client`, `monaco-editor`/`@monaco-editor/react`, `@xyflow/react`, `dockview-react`, and `echarts`/`echarts-for-react` each to their own named chunk. Pure config, no application code touched.
- **Two real findings while verifying it actually worked, not assumed from the config alone:**
  - The first pass's `"react-dom"` entry matched nothing — the app only ever imports it via `react-dom/client` (`main.tsx`), a distinct module specifier from the bare `"react-dom"` Rollup resolves against. Fixed by adding `"react-dom/client"` explicitly; the `react` chunk grew from a bogus 11 KB to a real 192 KB once fixed.
  - `monaco-editor` itself is only ever imported as `import type * as monacoEditor` (`CodeEditor.tsx`) — a type-only import, fully erased, never reaching Rollup. The real Monaco runtime is already split out entirely independently, by `@monaco-editor/react`'s own internal loader, into separate worker chunks (`ts.worker` alone is 7 MB) — a mechanism that predates and is unrelated to this Change's config. The `monaco` chunk this config produces (15 KB) is just `@monaco-editor/react`'s thin wrapper; not a gap, Monaco's real weight was already being kept out of the main bundle before this Change touched anything.
- **Real post-fix chunk sizes** (minified/gzipped): `react` 192/60 KB, `monaco` 15/5 KB, `xyflow` 177/58 KB, `dockview` 363/83 KB, `echarts` 1,138/378 KB, `index` (app code + every other dependency not explicitly bucketed — Redux Toolkit, Radix/shadcn primitives, `zod`, `dnd-kit`, etc., not just hand-written code) 620/191 KB. Total bytes shipped is essentially unchanged from the original single-file bundle — splitting reorganizes, it doesn't shrink — the win is purely that these chunks now cache independently across deploys.
- **`chunkSizeWarningLimit` deliberately left untouched, the user's own call.** Two chunks (`echarts` at 1.1 MB, `index` at 620 KB) still exceed Rollup's stock 500 KB warning threshold after the split — `echarts` is genuinely that large as a self-contained library (real tree-shaking would mean switching to `echarts/core` + per-chart-type imports, a source-level change, not attempted here), and `index` will keep growing regardless. Confirmed the warning is purely informational: `vite build` exits 0 regardless, and `.github/workflows/ci.yaml`'s `build` job just runs `pnpm build` with no output-parsing or `--max-warnings`-equivalent step — nothing will fail CI over it. Kept as a live, useful signal rather than silenced.

**`baseUrl`/`paths` cleanup done, and one naming correction to the diagnosis above: "the root `tsconfig.json`" meant `apps/web-app/tsconfig.json` (the app's own TS-solution-style references root, `"files": []`, never compiles anything directly), not a monorepo-root file — the monorepo root has no `tsconfig.json` at all, only `tsconfig.base.json`, which never had a `baseUrl`/`paths` block to begin with.** With that resolved: `apps/web-app/tsconfig.json`'s entire `baseUrl`/`paths` block deleted outright (confirmed dead — nothing is ever compiled under a `"files": []` config, so it did nothing). `apps/web-app/tsconfig.app.json` is different — its `paths` (`"@/*": ["./src/*"]`) is real and load-bearing (mirrors `vite.config.ts`'s own `resolve.alias`), only `baseUrl` itself was dead weight — in modern TS, `paths` resolves relative to the tsconfig's own location once `baseUrl` is absent, which is exactly what `"baseUrl": "."` already meant here, so dropping it is a no-op, not a behavior change. Only `baseUrl` removed from that file, `paths` kept as-is. Verified both fixes together: a full `tsc -b && vite build` (the real `build` script now) succeeds, `@/*` imports resolve correctly, and a repo-wide `pnpm typecheck` (25/25 packages) stays clean.

**Also added along the way, not originally scoped but a direct and obvious follow-on from actually running these builds for real: a `build-packages` root script** (`turbo run build --filter='!./apps/*'`) — lets a backend-only iteration loop build just the 22 non-app packages without paying for `apps/web-app`'s now-real (and slower) `vite build`, the same tension that led to Change C201 disabling it in the first place, this time solved with a scoped command instead of disabling the app's build entirely. Verified: resolves to exactly the 22 `packages/*`/`packages/use-cases/*`/`examples/` packages, correctly excludes all 4 `apps/*`. Named with a hyphen (`build-packages`) rather than this repo's more common `:`-separated compound-script style (e.g. `test:e2e`) — a deliberate, acknowledged one-off, the user's own call, purely for easier typing on a command meant to be run often.

**ESLint activated for real on `packages/types` and `packages/ports`, both previously stubbed `"lint": "echo lint"`.** Flat `eslint.config.js` per package (`@eslint/js` + `tseslint.configs.recommended`, no React/browser plugins needed), `no-restricted-syntax` banning the runtime-emitting constructs discussed earlier, `@typescript-eslint/consistent-type-imports`, and `tsconfigRootDir: import.meta.dirname` pinned explicitly in both — needed once there were multiple sibling flat configs in the monorepo, since without it the user's editor's ESLint extension couldn't auto-resolve which package's tsconfig a given file belonged to (`consistent-type-imports` can opportunistically use type info even in non-type-checked mode, which is what triggers the lookup) and threw a real parse error; doesn't reproduce via plain CLI, only the editor's own project-discovery path. Same fix added there as well, confirmed clean.

**Zero findings from the custom `no-restricted-syntax` rule in either package** — confirms both really are pure types/interfaces today, no runtime code had snuck in. All real findings were baseline `typescript-eslint recommended` hygiene, never checked before since neither package had real lint:

**`localhost:3000` → `VITE_SERVER_URL` done.** Design settled first, since it had two real open questions: `dotenv` isn't needed at all (Vite already has built-in `.env`/`import.meta.env.VITE_*` handling — `dotenv` is the Node/backend pattern, irrelevant to client code that never runs in Node), and no `.env.*` file needed to be committed at all, sidestepping a real tension the user raised (this repo's habit of never committing real `.env` files, reserved for `.env.example` + gitignored real files, specifically so a real secret never accidentally lands in a committed file) — there's no secret here, so the simplest correct answer was a plain in-source fallback rather than inventing a file-based mechanism for a non-secret value.

- All 6 hardcoded call sites turned out to be one value, not six — every RTK Query API slice (`artifacts-api.ts`, `flows-api.ts`, `runs-api.ts`, `sims-api.ts`, `evals-api.ts`) does `fetchBaseQuery({ baseUrl: "http://localhost:3000/api/" })`, and `SseBootstrap.tsx` does `"http://localhost:3000/events"` — same origin, two path suffixes.

- New `apps/web-app/src/vite-env.d.ts` (didn't exist before), augmenting `ImportMetaEnv` so `VITE_SERVER_URL` is typed rather than falling through as `any`.
- `.gitignore` gains `.env.local`/`.env.*.local` (only the bare `.env` was covered before) — so if anyone ever does drop a real secret into a personal local override later, it's protected automatically, matching the user's standing habit without needing to remember it in the moment.
- Verified for real, not just typechecked: a cold `pnpm run build` with no override present bakes in the `localhost:3000` fallback (confirmed via `grep` on the built bundle); rebuilding with `VITE_SERVER_URL=https://example.test pnpm run build` correctly bakes in the override and the `localhost:3000` fallback is completely absent from that build's output. `pnpm run typecheck`/`pnpm run lint` both clean.
- **Explicitly not solving multi-target deployment** (the user's own correction, mid-discussion) — the initiative doc's original framing overstated this as being "for" the dual browser/Electron target; `docs/todo.md`'s already-designed Electron plan swaps the RTK Query `baseQuery` itself to route over IPC, not a different HTTP URL, so this change doesn't actually touch that path.

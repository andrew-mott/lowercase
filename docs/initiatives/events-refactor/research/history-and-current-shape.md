# History and current shape of `packages/events`

Pre-decision research: why `packages/events` (and the parts of `packages/types` it depends on) ended up the way it did, and what's confirmed-vs-aspirational in its current form. Organized by question. Nothing here is a decision yet — see `INITIATIVE.md` once anything is settled.

## Why the types are shaped the way they are

Hand-written from the start, and deliberately optimized for one thing above all else: real autocomplete on event `type` strings and their matching `data` payload, with no casting required at emit call sites. That goal was tested directly and repeatedly while writing it — "can I get autocomplete here?" was the actual design loop, not a retrospective justification. The type-generic techniques involved (conditional type dispatch, mapped types, indexed access chains) were also where the author cut their teeth learning TypeScript generics; the resulting complexity is real, and openly regretted in places (`EmitterFactory`'s and `BaseEmitter`'s own doc comments both call the class "currently in between being refactored"), but it also worked — the DX goal was achieved, and there's real pride in that alongside the dissatisfaction with how it grew.

Open question, raised directly and not yet answered: whether hand-maximizing autocomplete DX at this cost is still the right tradeoff "in the age of AI" — i.e. whether a future design should spend this much type-level effort on the same goal, given that AI-assisted tooling changes how much autocomplete actually matters day to day.

## The envelope: Cloud Events + a from-scratch OTel/W3C Trace Context alignment attempt

The envelope shape is the Cloud Events spec, adopted specifically to avoid inventing a custom envelope. On top of that, `docs/observability.md` (dated "Updated for `v0.1.0-alpha.12`", itself likely younger than the design it describes) documents a real, researched attempt to also align with OpenTelemetry and W3C Trace Context (`traceparent`/`tracestate` fields, per its own "Status" section: "an attempt to align event envelopes with Cloud Events and OpenTelemetry. Some design aspects are not yet implemented but documented for future use"). This was never just a retrofit story — it was written down as aspirational at the time.

**The same OTel-accessibility reasoning also explains why per-domain scope ids (`runid`/`stepid`/`jobid`/etc.) live on the envelope header rather than inside `data`.** OTel-adjacent tooling was understood to prefer flat, top-level fields for keying/filtering over reaching into nested payload structures — the same motivation behind the flat `domain`/`entity`/`action` fields below applies to the scope ids too, not just those three. This turned out to matter for a reason unrelated to its original motivation: the events-refactor initiative's span-derivation design (parent lookup by reference, using ids already on the envelope) only works because those ids are at the header level — see that initiative's `arcs/event-emission-core.md` for where this got tested directly against a real counter-example (`LimiterScope`, which keeps its ids in `data` instead, and needs fixing to match).

**The `domain`/`entity`/`action` flat header fields.** The event `type` string already encodes this (`domain.action` or `domain.entity.action` — confirmed via `DomainActionDescriptor` vs. `DomainEntityActionDescriptor` in `packages/types/src/events/shared/otel-attributes.ts`, e.g. `step.planned` has no entity, `job.mcp.queued` does). The fields are repeated flat on the envelope anyway, on the theory that OpenTelemetry-adjacent tooling (traceviewers, Datadog-style consoles, etc.) doesn't parse structured `type` strings and needs flat, sortable attributes to filter/group by. This was never validated against a real OTel backend or visualizer — explicitly described as "theoretical," an aspiration toward interop that's never actually been exercised, not a confirmed requirement.

## Span nesting: real infrastructure, wired end-to-end, but confirmed unused

The hardest unresolved design question, per direct discussion: how nested spans should work when one span starts inside another and needs to "jump back up" correctly when the inner one ends — no clear, articulable strategy exists yet (possibly: components each own their own span lifecycle rather than passing a parent id along; possibly a parent-span-id needs to ride along after all). Explicitly not solved, not just undocumented.

**Empirically confirmed while discussing this**: `parentspanid`/`parentSpanId` is fully wired through the stack — `CloudEvent`'s type (`packages/types/src/events/shared/cloud-event.ts`), the zod schema (`packages/events/src/schemas/cloud-context.schema.ts`), `BaseEmitter`'s envelope construction (`base.emitter.ts:42-44`), and even surfaced as a real field in the event-graph UI's detail panel (`apps/workbench/src/components/workbench/event-graph-panel/EventDetails.tsx`). But grep across `engine`/`worker`/`router`/`limiter` turns up no call site that ever actually sets a `parentSpanId` value — the only place it's ever assigned is a hand-written test (`packages/events/tests/step-emitter.test.ts`). It is not partially used or lightly used; it is fully plumbed and entirely inert.

This is also named as a genuinely-wanted feature, not dead weight to just delete: the event-graph panel currently shows events on a timeline (order on Y, time on X, zoomable) but doesn't correlate related events into spans — real nested-span data would let that panel show span relationships, which would be a real UX improvement if built. Whether that's worth doing by threading span ids through, or by inferring structure at read time the way the UI already reconstructs other relationships from the raw event log, is open.

**Clarification on how dead this actually is, direct from discussion**: it's not only that `parentspanid` never gets set. In practice the system never goes deeper than trace + one root span at all — nothing in the current code ever takes an existing span and starts a second, nested span underneath it during that event's lifecycle. The envelope/type layer has the _capability_ to represent arbitrarily nested spans (that's what `parentspanid` is for), but no component ever exercises even one level of that nesting today. The genuinely hard, unresolved problem is the strategy for going in and out of nested spans correctly — "start a span underneath a span, then correctly pop back up when it ends" — not just wiring a field through. Two rough directions floated, neither settled: components could each own their own span lifecycle independently, or a parent-span-id could ride along through the call chain; it's not yet clear one is even needed for the other to work.

## The `NewTrace`/`NewSpan`/`FromEvent` triplet explosion in `EmitterFactory`

Ties directly to the unresolved span-nesting question above: each domain emitter needs to be constructible from three different starting points — begin a brand new trace, begin a new span within a trace a caller already has, or resume from an inbound event's trace/span. That's the direct source of the `new<Domain>EmitterNewTrace`/`New<Domain>EmitterNewSpan`/`new<Domain>EmitterFromEvent` method triplet repeated per domain in `emitter-factory.ts`. It isn't arbitrary duplication — it's the same three-way construction concern, copy-pasted per domain because nothing currently abstracts "construct an emitter of domain X from starting-point Y" into one place.

## `EmitterFactory` / `BaseEmitter` / the ten domain emitter classes

Three separable problems, not one:

1. **Mixed concerns in one class.** `EmitterFactory`'s trace/span-id generation helpers (`generateTraceId`, `generateSpanId`, `makeTraceParent`, `makeNewSpan`, `startNewTrace`) are pure functions with no dependency on `bus` or any domain — they only live on this class because that's where they were needed, not because they belong there. A more robust OTel-handling piece would plausibly own these instead, though what that would look like isn't decided.
2. **The `NewTrace`/`NewSpan`/`FromEvent` method matrix is real but not uniform** — confirmed by reading the whole file: Limiter gets all three variants, Engine gets none (just a base constructor), Scheduler gets two but not `NewTrace`, Replay gets only `NewTrace`, Step gets a fourth, differently-named variant (`FromJobEvent`). This is evidence the class grew by "copy the nearest similar method when a new call site needed a new starting point," not from a systematic design — which is actually good news: a fix doesn't need to produce a full 3×10 grid, it needs one parameterized construction path any call site can reach for whichever starting point it actually needs.
3. **The two-step call site** (`factory.newXEmitterY(scope)` → `emitter.emit(type, data)`) is deliberate, not accidental: providing scope once and getting back a domain-scoped object is what makes `.emit()`'s `type`/`data` autocomplete narrow correctly, and the explicit goal throughout the whole emitter layer was zero casts anywhere. Not viewed as a problem in itself, separate from problems 1 and 2.

**The ten domain emitter classes (`run`/`job`/`tool`/`engine`/`system`/etc.) are almost character-for-character identical**, confirmed by reading five of them side by side: same constructor shape (destructure otel fields off `scope`, destructure domain scope fields, call `super()`, reassign `this.otel`, set the private scope field, set the domain's `OtelAttributesMap` field, set `bus`), same `emit()` body (spread envelope header + scope + data + type + domain/action/conditional-entity, `satisfies` check, look up `eventSchemaRegistry[type]`, `safeParse`, throw a domain-prefixed error, `publish`). The only things that vary per domain are which scope fields get destructured, the type parameter names, and the error-message prefix string — a strong candidate for one generic class parameterized by domain (scope shape + event map + otel-attributes map) instead of ten hand-written near-duplicates, without losing the autocomplete/no-cast goals since the type layer already has the generic machinery (`EventType`, `EventData<T>`, `OtelAttributesMap`) to support it.

**One real, load-bearing exception, confirmed via its actual caller**: `JobEmitter` alone splits `emit()` into `formEvent()` (builds and validates the event object) + `emitFormedEvent()` (publishes it) + `emit()` (does both). This isn't drift — `NodeRouter.queueJob()` (`packages/components/router/src/node.router.ts:38-41`) needs the concrete built event object to pass to `this.queue.enqueue()` _and_ the bus, not just the bus. That's a real, general capability (construct now, publish later/elsewhere) that happens to exist on only one of ten domain emitters today — worth carrying forward as something every domain emitter should get, not Job-specific scaffolding.

**Minor dead-code spotted in passing**: a stray commented-out `// console.log("event", ...)` line in `system.emitter.ts`'s `emit()` — leftover debug scaffolding, not a design choice.

## The registries (`packages/events/src/registries/`)

- **`event-schema.registry.ts`** — a ~300-line hand-written record literal pairing every event type string to `{ topic?, schema: { event, data } }` (the Zod schemas, imported from `../schemas/`). This is a runtime mirror of information the type layer already encodes in `EventMap` — the type side gets `EventType`/`EventData<T>` "for free" via generics, but runtime validation needs actual schema _objects_, so they're hand-paired per event type here. This is the single most direct overlap with `json-schema-migration`'s own stated rationale (hand-rolled Zod schemas).
- **`category.registry.ts` / `event-types.ts`** — a genuinely deliberate defensive pattern, confirmed directly: each hand-written array (`jobSubmittedTypes`, the master `eventTypes` list, `actionTypes`, `domainTypes`, `entityTypes`, etc.) is paired with an `Exclude<UnionType, (typeof array)[number]>` type that forces a compile error if the array and the type-level union ever drift apart — "I didn't have a clear way to ensure every event was covered, and didn't want to manually check." Not confirmed whether this was a reaction to an actual missed-event bug or just noticed as a gap; either way it's real, working exhaustiveness-checking, repeated by hand seven-plus times (same four-line trio each time) rather than generalized into one reusable `assertExhaustive<T>()` helper. One block (a commented-out `stepTypes` check) is dead and its reason for being cut isn't remembered — may just be a type that stopped being needed.
- **`otel-attributes.ts`** — the maximal case of the same redundancy: for every event type, hand-writes out `{ action, domain, entity }` — information already fully present in the dot-separated type string itself (e.g. `"job.mcp.submitted"` already _is_ domain `job`, entity `mcp`, action `submitted`). Explicitly named as something the author is willing to let go of ("not to have a clever emitter class parse a string... but literally" — done this way on purpose, not by oversight, but open to a cleverer approach now). Protected against typo-drift by `satisfies XOtelAttributesMap` (which pins the literal domain/action per key via `DomainActionDescriptor`), so this specific file doesn't need its own exhaustiveness check the way `category.registry.ts` does — the redundancy here is pure hand-typing effort with an available, working alternative already proven elsewhere in this same package: `job.parser.ts`'s `#getCapId()` (`parts = type.split("."); return parts[1]`) already derives the entity/capability id from the type string at runtime, for exactly this kind of purpose.
- **Why `category.registry.ts`'s job-specific groupings exist**: the job domain is the one place an event type has three dot-separated segments instead of two (`job.<capability>.<action>`), because the "entity" position holds which capability (`mcp`, `httpjson`) a job event is about — a deliberate design tension named directly: including that middle piece was good (needed to distinguish job payloads per capability) but multiplies the permutations that need covering (7 actions × N capabilities instead of 7 actions flat). `job.parser.ts` (`parseJobSubmittedType`/`parseJobDelayed`/etc., one pair of methods per action, mirroring `category.registry.ts`'s per-action grouping exactly) is the actual consumer this arrangement was built to serve — confirmed by reading it directly, not assumed. Whatever a redesign does with the entity/capability position needs to account for this being a real, deliberate three-segment case, not an inconsistency to flatten away.

## Open questions carried forward

- Whether the `domain`/`entity`/`action` flat envelope fields are worth keeping given they've never been exercised against a real OTel consumer, versus being redundant with the `type` string.
- What the actual nested-span strategy should be — genuinely unresolved, not just unbuilt.
- Whether solving nested spans "for real" is a precondition for cleaning up the `EmitterFactory` triplet explosion, or whether the construction-boilerplate problem and the span-nesting-design problem can be decoupled and solved separately.
- Whether the type-level effort behind `ScopeFor<T>`/`EventMap`-driven autocomplete is still the right tradeoff going forward, or whether AI-assisted development changes how much that specific DX investment is worth.
- Whether to generalize the `Exclude<>`-based exhaustiveness-check pattern into one reusable helper rather than the seven-plus hand-copied instances today, and whether it's still needed at all if schemas move to a single generated source (per `json-schema-migration`'s direction) rather than hand-maintained parallel arrays.
- Whether `otel-attributes.ts`'s hand-typed `{domain, entity, action}` maps should be replaced by runtime string-parsing (the same technique `job.parser.ts`'s `#getCapId()` already uses) or by codegen from the same source the type layer uses, rather than kept as hand-maintained data.
- Whatever replaces the job domain's per-action method pattern (`category.registry.ts`'s arrays, `job.parser.ts`'s `parseJobX`/`parseJobXType` pairs) needs to keep handling the three-segment `domain.entity.action` case as a real, deliberate shape — not flatten it away as if it were the same as every other domain's two-segment case.
- **Schema-format direction for `json-schema-migration`, surveyed but deliberately not decided here.** Real options and their actual tradeoffs, for whenever that initiative starts: (1) hand-authored JSON Schema + generated types — genuine schema-first, but a prior attempt at this (a different, earlier project, same purpose) was abandoned within about a week; raw JSON Schema authoring is a known, widely-felt pain point industry-wide, not just personal difficulty. (2) TypeBox — a schema/type _generator_, not a validator; still needs a separate validator (e.g. AJV) paired with it, and its own builder DSL (`Type.Object({...})`) means giving up plain-TypeScript authoring, same tradeoff Zod already makes today. (3) Plain `.ts` types + build-time JSON Schema extraction (`ts-json-schema-generator`/`typescript-json-schema`) + AJV as the runtime validator — keeps authoring as genuinely plain TypeScript (closest to how `packages/types` already reads today), and AJV is what Fastify already uses internally, so this would _unify_ validators across the system (one, not two) rather than adding a competing one. Real open risk: the existing hand-written generic-dispatch machinery (`ScopeFor<T>`, `EventMap`'s conditional-type chain) may not extract cleanly through a static-analysis tool built for "reasonably normal" TS types — may need simplifying first, which could be the same moment as a broader type-system rework, not a separate cost. **No option gets everything at once** (full plain-TS control, single source of truth, zero build lag, one validator, full constraint expressiveness) — every real path trades something off; this is a genuine, unresolved tension in the ecosystem, not a gap in the research. Hand-rolled Zod (the status quo) remains a legitimate, defensible choice under that framing, not a failure to find the "real" answer.
- **Data-vs-header field placement isn't applied consistently across the codebase, and isn't obviously wrong for that reason alone** — noted directly: during design, "include in data, or is the header enough?" was a real, researched question, and the answer landed differently in different places — sometimes duplicated deliberately as an experiment ("maybe that's the right way"), sometimes leaning on the header, sometimes leaning on `data` alone. `LimiterScope` keeping its ids in `data` (found while discussing span derivation) is a concrete instance of this inconsistency, not necessarily the only one. A real future goal: derive an actual principled answer for "what belongs where, and why," and align existing events to it — explicitly not scoped or started now, just named so it isn't lost.

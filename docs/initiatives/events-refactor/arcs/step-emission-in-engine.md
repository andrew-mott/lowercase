## Change C2 - Wire `step` emission in the engine onto the new core - merged (PR #348)

### Discussion

_Starting point, carried over from Change C1's arc doc:_

- **Real DX feedback from this decides whether `emit()` alone is enough**, or whether named variants (`emitFromEvent()` or similar) are actually needed — not designed ahead of finding real friction.
- **`source` field ergonomics, flagged in Change C1 as a question to raise here specifically**: typing a full CloudEvents-style URI (`"lowercase://engine/id"`) by hand at every call site is a real, separately-raised pain point. Open question: should `emit()` accept a simpler shorthand and build the full URI itself, or should the engine hold its own `source` as configured internal state (potentially including its own instance id) rather than re-typing it per call?

### How the engine actually handles `source` today, checked directly before deciding anything

No component-level identity config exists anywhere in the runtime — `runtime.ts:111` constructs exactly one `EmitterFactory(bus)` instance, shared across engine/worker/router/limiter/replay, and every call site across all of them just hardcoded a literal (`"lowercase://engine"`, `"lowercase://rm"`, five different shapes in `worker.ts` including one, `"lowercase://worker/" + workerId`, that's the only existing precedent for an instance embedding its own id). Within the engine specifically, `source` was set inconsistently even within one file: `step-planned.planner.ts` set it directly on the `scope` it built for step effects, while the same planner's job-submission effects carried no `source` in `scope` at all — it got bolted on later, redundantly, inside the effect handler.

One real, previously-unnoticed bug surfaced while tracing this: `run.requested`'s `source` is the one place in the system that already carries genuinely meaningful information (`apps/http-server/src/routes/runs/request.ts:36` sets `"lowercase://http-server"`, `apps/cli/src/commands/run/run.cmd.ts:16` sets `"lowercase://cli"` — which client triggered the run). `SqlRunProjectionSink.#updateState` (`packages/components/observability/src/sinks/sql-run-projection.sink.ts:79`) unconditionally overwrites `state.source` on _every_ event touching a run, not just the originating one, so by the time a run finishes, the persisted `Run.source` column is just whatever the last internal event's source happened to be (`"lowercase://engine"`) — the meaningful value is silently lost. Logged in `docs/todo.md`, folded into the existing `SqlRunProjectionSink` rework entry rather than a new item, since it's the same sink already flagged for a structural redo. Not fixed here — out of scope for this Change.

**Settled**: not worth resolving the format/scheme question now (considered shortening `"lowercase"` to `"lc"` purely to save bytes on the wire — rejected; the savings are negligible next to `data`/refs/hashes on the same envelope, and `lowercase` is more readable in raw event/replay dumps than a cryptic abbreviation is worth saving 7 bytes for). What _did_ get resolved: components should compute their own `source` once, as configured state, rather than re-typing a literal at every call site or having `emit()` manufacture it from a bare id. `EffectHandlerDeps` gained a `source: string` field, derived once in the `Engine` constructor (`` `lowercase://engine/${this.id}` ``) and threaded through `wireEffectHandlers(...)` — `Engine.id` itself stays hardcoded (`"internal-engine"`) for now, deliberately not wired to `RuntimeConfig`, since (unlike worker, which already supports multiple instances via `config.worker.id`) nothing today needs more than one engine instance; making it configurable would touch `EngineDeps`/`RuntimeConfig` for no live need yet.

### What actually landed (first slice — `step.planned`/`step.started`/`step.reused`, not the whole domain)

Deliberately partial, not a stopping point forced by a problem: these three were the ones this Change's own framing named (the normal path plus the short-span `step.reused` case), and real DX feedback was the actual goal — `step.completed`/`step.failed`, and everything outside `step`, stay on the old `EmitterFactory` path for now.

- **`EffectHandlerDeps`** (`engine.types.ts`) gained `bus: EventBusPort` alongside `source: string` — `emit()` takes the bus as an explicit argument rather than hiding it inside a constructed emitter, so every effect handler calling it needs direct access, not just the `Engine` class itself (which already held `this.bus` for topic subscription, unrelated to this change).
- **`EmitStepPlannedFx`/`EmitStepStartedFx`/`EmitStepReusedFx`'s `scope` type** narrowed from `StepScope & CloudScope` to `StepScope & Omit<CloudScope, "source">` — the effect handler owns `source` now, not the planner that constructs the effect. This mirrors an existing convention already established for job effects (`engine.types.ts:204/211` already omitted `source` from `CloudScope` for the same reason) — not a new pattern, bringing step in line with a precedent that already existed.
- **Four planners** (`run-started`, `step-finished`, `step-started`, `step-planned`) had their hardcoded `source: "lowercase://engine"` line removed from the step-effect scopes they build.
- **Three effect handlers** (`emit-step-planned`, `emit-step-started`, `emit-step-reused`) rewritten from `deps.ef.newStepEmitterNewSpan(scope, traceId).emit(type, data)` to `emit(deps.bus, type, data, { ...effect.scope, source: deps.source, traceId: effect.traceId })`.
- **`@lcase/events` added as a real dependency** of `packages/components/engine` (`package.json`, under `dependencies` not `devDependencies` — it's a runtime import, not type-only) — precedented by `worker`/`router` already depending on it directly; the engine had no direct dependency on it before this.
- **Tests**: two new effect-handler tests added where none existed before (`emit-step-started.effect.test.ts`, `emit-step-reused.effect.test.ts`), following the non-cast `EventBusPort` mock pattern from Change C1 rather than the package's older `as unknown as EmitterFactoryPort` style. These exercise the real `buildEvent()`/schema-validation path instead of mocking `EmitterFactory` away entirely — which is what caught a real, previously-invisible gap: the existing `emit-step-planned.effect.test.ts` fixture was missing `flowversionid` outright, invisible before because the old mock never validated anything against it. Two existing test fixtures (`run-started.planner.test.ts`, `step-planned.planner.test.ts`) updated to drop their now-removed `source` assertion.
- **Verified**: `pnpm typecheck`/`pnpm vitest run` clean inside `packages/components/engine` after each of the three migrations individually, and `pnpm -w typecheck` clean across all 26 packages each time — notably including `@lcase/runtime`, confirming a real prediction (that rewiring the engine's construction in `runtime.ts` would need changes) turned out false: `EngineDeps` already carried `bus` before this Change, for the unrelated reason of topic subscription, so nothing at the `runtime.ts` wiring boundary needed to change at all.

**A real, generalizable finding surfaced by doing this migration, not anticipated going in**: `EmitterFactory` bundling the bus internally, previously read as pure convenience, is a minor liability exactly where a caller already needs its own direct bus reference for something else — you don't end up with two buses, but the abstraction obscures that it's the same one. `emit()` taking `bus` as an explicit argument makes that dependency honest instead of hidden. Worth remembering as a data point for/against similar bundling choices elsewhere.

**Span-sharing is still unobserved, deliberately** — three isolated unit tests, each asserting one event's fields independently; none chain real sequential calls the way a live `step.planned`→`step.started` pair sharing one `spanid` would require. Change C1 already validated span derivation directly via its own dogfooding script, so this round intentionally didn't re-dogfood a still-unconnected single call site — the trigger for hand-running again is a real chained sequence, not any one more isolated call.

**Framing from the user, worth preserving**: this is a good direction, not a comprehensive one — expect real edge cases to surface as more of the system migrates onto it, and to possibly need extension or fixes as a result. That's separate from the still-undecided TypeScript/schema-format question (Zod vs. JSON Schema, tracked in this initiative's `Not yet scoped` and `research/history-and-current-shape.md`), and separate again from a broader engine hardening/refactor pass, already tracked as its own initiative (`docs/initiatives/engine-hardening/`) rather than folded in here.

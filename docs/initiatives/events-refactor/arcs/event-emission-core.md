# Events Package Refactor Initiative — Arc: Event-Emission Core (Change C1)

**Next:** [`step-emission-in-engine.md`](./step-emission-in-engine.md) (Change C2)

Part of the [`INITIATIVE.md`](../INITIATIVE.md) Change log, split out to keep that doc scannable. Originally scoped as "genericize the ten domain emitter classes" — a mechanical DRY-up of the existing `EmitterFactory`/`BaseEmitter` architecture. Discussion broadened it into a genuinely new event-emission core instead, superseding that narrower plan rather than incrementally cleaning it up. Full background on the current system this replaces: [`research/history-and-current-shape.md`](../research/history-and-current-shape.md).

## Change C1 - Event-emission core: single `emit()`, context propagation, span-per-entity model - merged (PR #347)

### Discussion

**Why this superseded the mechanical plan.** The original three tentative Changes (genericize the emitter classes, collapse `EmitterFactory`'s construction matrix, replace `otel-attributes.ts`'s hand-typed maps) turned out to be three symptoms of one architecture — per-domain classes, multi-variant construction, hand-typed derived data — not three independent problems. A single generic `emit()` plus a different approach to context removes the need for per-domain construction entirely, which dissolves what Change C2 and Change C3 would have fixed rather than requiring them as separate steps.

**The real DX floor, confirmed directly rather than assumed**: no casts required at any call site, and real autocomplete on `type`→`data`. The two-step factory/class shape was one way to achieve that, not the goal itself — confirmed the two-step-ness isn't sacred, and scope-reuse (the main thing motivating a stateful, class-based scope object) doesn't actually happen in practice: every place in the codebase where a variable holds a constructed emitter and calls `.emit()` more than once (e.g. `worker.ts:272-311`) turned out to be a branch-exclusive `if`/`else if` chain — only one call ever executes. `JobEmitter`'s `formEvent`/`emitFormedEvent` split stays a real, load-bearing requirement (`NodeRouter.queueJob()` needs the built event object before publishing) — generalized to every domain via plain functions, not kept Job-only.

**Internal casts are accepted, caller-facing casts are not.** TypeScript can't verify certain generic indexed-access correlations (`EventMap[T]["data"]` where `T` is a generic parameter) inside a function body even when provably correct by construction at every concrete call site — this is almost certainly why the original design became ten hand-written classes instead of one generic function. One or two well-placed internal casts inside a single shared `buildEvent()` implementation are accepted now, explicitly because `eventSchemaRegistry[type]`'s `safeParse` already runs on every emission regardless — an internal cast doesn't remove a safety net that exists independently of it.

**Settled shape: one function, origin folded into its options argument — no separate helper call, no named `emitFromEvent()`-style variants.** Explicitly chosen to avoid both a mandatory helper-call-before-every-emit and a proliferation of named functions — which of the three starting points (new trace / new span in a known trace / derived from an inbound event) applies is decided by which optional fields happen to be present, not by which function or preceding call you used:

```ts
await emit(bus, "step.completed", data, {
  ...stepScope,
  source,
  fromEvent: inboundEvent,
}); // derives trace/span from inboundEvent
await emit(bus, "run.requested", data, { ...runScope, source }); // no fromEvent/traceId -> starts a new trace
await emit(bus, "job.mcp.queued", data, {
  ...jobScope,
  source,
  traceId: knownTraceId,
}); // new span within a trace already held
```

Open, left for implementation: exact typing of the options argument (how `fromEvent`/`traceId` being mutually-exclusive-ish gets expressed), and whether any real verbosity that remains is actually the options-object shape or the underlying required-field list itself (a type-system question, not an API-sugar one — see below).

**`AsyncLocalStorage` was considered and dropped, not adopted.** It only propagates a value along one process's causal async chain (nested `await`s, promises, timers spawned within a `.run()` call) — it does **not** cross an event-bus hop, since `engine` publishing an event and `worker` reacting to it later via a subscription is a new, causally independent invocation, not a continuation of the same chain. That means explicit re-anchoring of context at the entry point of every subscriber (à la today's `FromEvent` constructors) is required either way — `AsyncLocalStorage` would only have saved threading a small scope object through the one or two call layers _within_ a handler, which isn't a real burden (confirmed: most `emit()` calls happen directly in a subscriber handler or one layer deep, not buried under many). Given its only real value is implicit propagation, and that value evaporates at exactly the boundary (`engine`↔`worker` over the bus) most likely to become a real process boundary later per `CLAUDE.md`'s stated runtime-decomposition direction, it isn't worth building foundational behavior on a mechanism that's weakest precisely where this system is headed. A plain `deriveTraceHeaderFields()`-style helper, passed explicitly, gets the same DX with no runtime-magic dependency, and behaves identically whether `worker` stays in-process or becomes its own service later. If a call site's internal threading ever gets deep enough to feel bad, that's a signal to flatten the handler, not a reason to reach for ambient state.

**The nested-span design question — previously flagged as genuinely unresolved and deliberately not blocking anything — has a real answer now, worked out directly in discussion:**

- **Span identity follows entity lifecycle, not a call stack.** Each entity (run, step, job, tool) owns exactly one span for its own lifetime — opened by its `*.planned`/`*.started`-equivalent event, closed by whichever terminal event actually fires for it. A sibling entity at the same level doesn't need to "pop back" to a parent span, because the parent's span was never overwritten — it's owned by the parent entity for its whole lifetime and any child just reaches back to it by reference.
- **Parent lookup is by reference, not coordination.** Every event already carries the id of its logical parent (a job event has `stepid`, a step event has `runid`), so a child can always find which span it belongs under. No stateful "span coordinator" component needed (an idea considered and set aside) and no ambient/`AsyncLocalStorage`-based lookup needed either, since this works across bus hops where ambient context wouldn't survive anyway.
- **The span key must be the full identity, not a bare entity id.** Confirmed directly: a reused step should get its own new span in the run that reused it, not reach back into the original run's step span — meaning the derivation key for a step's span has to be something like `(runid, stepid)`, not `stepid` alone, since the same step definition recurs across many runs and each occurrence needs its own distinct identity. Same logic likely extends further down (job/tool spans keyed on their full identity path).
- **Span id generation: deterministic derivation is a legitimate option, not a compromise.** W3C trace-context only constrains span-id _format_ (8 bytes / 16 hex chars), not how it's generated — a stable hash of the identity key, formatted to the right shape, is just as spec-compliant as `crypto.randomBytes` and requires no lookup or stored state anywhere. Whether to actually do this (vs. keep random generation plus a small explicit store) is still a real implementation choice, not settled — leaning toward derivation given it needs zero coordination and this system is bus-mediated and eventually multi-process.
- **Confirmed edge cases:**
  - **Retries** should produce two distinct spans, not one reused span across attempts — a real principle to remember, but not live work for this Change: confirmed there is no retry logic in the engine at all yet (the simplest, no-retry case was built first). Nothing to check or change now; revisit when retry logic actually gets built.
  - **Reused steps** get their own new span, not a reference back to the original run's step span (see identity-key point above).
  - **`step.reused`'s short-duration span is not a special case requiring an engine change** — verified directly in `packages/components/engine/src/planners/step-planned.planner.ts`: `step.planned` is unconditionally emitted first for every step, and only then branches to either `step.started`→...→`step.completed`/`failed` or directly `step.reused`. So `step.planned` is already, universally, the span-opening event; `step.reused` is just one more valid closing event alongside `completed`/`failed`. A short span is a normal thing for a trace to show (real APM tools render "cache hit" spans this way routinely) — nothing here needs engine changes.

**Type-system changes are in scope when they earn their keep for `emit()` specifically, not gated by "avoid touching the type system."** The default expectation is small and additive — an identity-key type for span derivation, whatever shape `deriveTraceHeaderFields()` returns — not a wholesale rework of `EventMap`/`ScopeFor<T>`/the existing generic machinery for its own sake. But if a specific type-level change would unlock a real DX or safety win for `emit()` itself, that's worth tracing through and taking, not avoided just because it touches the type layer. What's explicitly still out of scope is a speculative, general overhaul of the event type system unrelated to what this function actually needs — that's a real idea for someday, not this Change — see the research doc's open questions.

**Scope of this Change, narrowed**: build the new core only — `emit()`, `deriveTraceHeaderFields()`/context helpers, span derivation — as a self-contained addition to `packages/events`, with tests and hand-written/dogfooded usage to confirm the DX actually holds up in practice, not just types-check. No real call-site migration in this Change; proving the core out against a real usage (wiring `step` emission in the engine, specifically to exercise `step.reused`'s short-span case) is its own separate next Change — see `INITIATIVE.md`'s `Next up`.

**Adoption strategy beyond that proof, a real open strategic question, not yet decided**: whether to roll the new core out to the rest of the codebase (`worker`, `router`, `limiter`, etc.) as its own dedicated migration pass, or defer most of that adoption until each of those systems gets its own future refactor anyway (a broader refactor of `packages/*` beyond just `events` is a real, separately-intended future direction) — migrating a call site now that gets rewritten again later during that system's own refactor could just be redone work. Leaning toward deferring broad adoption and letting it happen naturally as part of each subsystem's own future work, but not settled. Related, also open: whether the helper surface beyond bare `emit()` needs its own named variants (`emitFromEvent()` or similar) or stays one function with options — a real design question that should be answered from actual friction found while proving this out on `step`, not designed speculatively ahead of that.

**Still explicitly deferred, unaffected by any of the above**: `event-schema.registry.ts`/`category.registry.ts`/`event-types.ts`'s hand-maintained schema/type wiring — real overlap with `json-schema-migration`, not resolved or required by this redesign.

**A real counter-example to the "derive span from envelope ids" pattern, found while checking it against a domain other than `step`**: `LimiterScope` is just `{ limiterid: string }` — the actual identifying ids (`runId`/`jobId`/`toolId`/`workerId`) live inside `LimiterSlotData` (the `data` payload), not on the envelope. Span derivation only looking at envelope-level fields (the whole appeal of the pattern) would have nothing to derive a parent span from for a slot request as things are shaped today. **Agreed fix, not yet done**: move those ids out of `data` and into `LimiterScope` itself, mirroring how every other domain already carries its ancestor ids at the envelope level — not special-casing span derivation to reach into `data` for one domain. Real, scoped work; not part of Change C1 (limiter isn't touched here), but the fix is decided, not just flagged.

**Clarified, not part of the control-plane question**: the `internal` flag already accepted by `EmitterFactory`/`LimiterEmitter`'s `bus.publish(type, event, { internal })` is unrelated to control-plane vs. data-plane — checked directly in `InMemoryEventBus`, it only gates whether an event gets forwarded to the observability topic. Separately, how span derivation should relate to control-plane events (start/quiesce/resume/shutdown) isn't answerable yet — `research/control-plane.md` (from `architecture-boundaries`) is explicit that it's a fragment with no settled event vocabulary, so there's nothing concrete to check span derivation against yet. Blocked on that doc's own status, not a gap in this discussion.

**`tool`/`job` span identity stays genuinely unresolved, and is now more uncertain, not less.** Beyond the earlier finding that `tool` and `job` events share identical identifying scope fields (no field uniquely `tool`'s own), `capid` itself may be semi-dead — the `mcp` step type already type-checks but its runtime reliability is doubted, and `httpjson` is the de facto primary/default step type. Not resolved here and not blocking Change C1 (only `step` is in scope), but a reason to actively avoid assuming `tool` deserves its own span identity when job/tool domains eventually get migrated, rather than letting the earlier "run, step, job, tool each own a span" framing stand unquestioned.

### What actually landed

Matches the plan closely, with two real deltas found during implementation, both small:

- **A third internal cast, not two.** `tsc` caught it immediately: `SpanIdentityConfig<StepScope>` isn't assignable to `SpanIdentityConfig<unknown>` when registering `stepSpanConfig` into `spanConfigByDomain`, since function parameters are contravariant — a function expecting the narrower `StepScope` can't safely substitute for one accepting arbitrary `unknown`. Cast at that registration point, same "correct by construction" justification as the other two.
- **`publishEvent` only passes a third argument to `bus.publish` when `publishOptions` is actually given**, rather than always passing an explicit `undefined` — a small correctness fix made while writing the emit tests, so `emit(bus, type, data, scope)` (the common case, no `publishOptions`) is observable as a plain two-argument call, not a three-argument one with a trailing `undefined`.

**New files, all additive, matching the plan exactly**: `core/{trace,span,scope,emit,index}.ts`, `registries/otel-attributes.registry.ts`, `examples/step-emit.dogfood.ts`, `tests/{span,scope,emit}.test.ts`, `tests/helpers/mock-bus.ts`. One-line addition to `src/index.ts`. Zero edits to `EmitterFactory`/`BaseEmitter`/the ten domain emitter classes/`otel-attributes.ts`/`event-schema.registry.ts` — confirmed via `git status` after implementation, matching the guardrail exactly.

**Tests deliberately departed from the existing package's conventions** where they were weak (explicit permission given): a shared, properly-typed `createMockBus()` helper instead of a repeated `as unknown as EventBusPort` cast per file; targeted property assertions computed from the module's own real exported functions (`deriveSpanId`, `makeTraceParent`) instead of hand-typed full-object literal equality; fixed (not copied) the existing `afterEach` import-from-`node:test`-instead-of-`vitest` bug. 23 tests pass total (17 new + 6 pre-existing, all pre-existing ones unaffected).

**Verified**: `pnpm typecheck`/`pnpm lint`/`pnpm vitest run` all clean inside `packages/events`; `pnpm -w typecheck` clean across all 26 typechecked packages (`apps/desktop` has no typecheck script, as already documented). The dogfooding script was hand-run and read directly — confirmed live: `step.planned`/`step.started`/`step.completed` for `(run-1, step-a)` all share one `spanid`; the same step reused under `run-2` gets a distinct `spanid`; `fromEvent` correctly inherits the fabricated inbound trace id; `buildEvent`/`publishEvent` correctly show nothing published between the build and the explicit publish call.

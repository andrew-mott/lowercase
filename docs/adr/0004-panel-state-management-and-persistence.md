# ADR-0004: Panel state management and persistence for the dockview-based workspace UI

Date: 2026-07-31
Status: Accepted

## Summary

Dockview owns workspace layout and panel identity. Redux owns durable panel UI/runtime state, keyed by dockview panel id and split by panel kind. Persistence stores dockview's serialized layout plus selected Redux panel-state slices together as one versioned workspace snapshot. Intentional panel removal deletes keyed state; route/host unmount does not.

## Context

`apps/workbench` is moving away from rigid, per-mode pages toward a dockview-based panel/tab workspace (currently prototyped under the `/explorer` route — that name is a throwaway spike label, not a settled product name, and this decision isn't about that route specifically). Content opens into panels a user can arrange, split, and close freely, rather than navigating between fixed pages.

The old page-based UI already used Redux for state that needed to survive route unmounts, with local `useState` reserved for state that was acceptable to lose. The dockview workspace reuses that general lesson, but adds requirements the old model never had to handle: **true multi-instance panels** (two different flow versions' graphs open side by side), **dockview owning the user-arranged layout itself** (a second state system with no fixed-page equivalent), and **cross-tab/reload/new-tab restoration** as load-bearing questions. The persistence work below is driven primarily by dockview's layout being torn down on reload with nothing to rebuild it from; keyed panel state is persisted alongside that layout because it makes restored work predictable, not because Redux alone had an unresolved route-survival gap.

The first, most-developed panel type (a flow version's graph, with run/param selection) was used as the concrete test case — validated by building it for real, not by planning it in the abstract. Full reasoning trail, including rejected alternatives and things learned only by building and testing, is in `docs/initiatives/ui-workspace/research/state-management.md`; this ADR is the distilled decision, not a replacement for that trail.

## Decision

**Durable panel UI/runtime state lives in Redux, keyed by panel id — one slice per panel kind, never a shared singleton.** A singleton-per-"current thing" slice (the old model's shape) breaks the moment two instances of the same panel kind are open at once, which is now a real, supported case. Each kind that needs state gets its own `Record<panelId, ...>` slice; there is no shared "common panel" slice, since no state has yet needed to exist across kinds. The panel id is sourced from dockview's own assigned id (`props.api.id`), not re-derived independently. The app supplies deterministic ids when creating panels (e.g. `flow-graph-${versionId}`), and dockview exposes that assigned id back to the panel — one source of truth, and the property that lets reopening the same content resolve to the same stored state after host unmount.

**Redux being a store singleton, independent of any component's mount lifecycle, is what makes this work at all — not anything added on top.** A panel's state survives switching tabs and an in-app route/host unmount with no explicit "restore" logic — it was simply never destroyed. If the same content is reopened after host unmount, its deterministic id finds the existing Redux state. The one thing that does need explicit handling is _deletion_: a panel's slot is only cleared when the user intentionally removes that panel (dockview's `onDidRemovePanel` event, wired centrally wherever the live `DockviewApi` is held — not per-panel-component, and not a generic React-unmount effect, since an unmount can also mean "navigated away," which should preserve state, not discard it).

**Persistence to survive a real reload uses two storage tiers, not one.** `sessionStorage` — physically isolated per browser tab, survives that tab's own reload, never seen by a new tab — is read first on mount and covers both in-app navigation and reload with zero cross-tab interference. `localStorage` — shared across tabs on the same origin — is the fallback, used only to seed a genuinely new tab from whichever tab most recently wrote. Both dockview's own serialized layout (`toJSON()`/`fromJSON()`) and the keyed Redux slice are written together as one versioned envelope, to both storages, on every write; only the keyed Redux slice is persisted from Redux as a whole — RTK Query's API caches are never included, since that cache is meant to be disposable and re-fetched, not frozen into a snapshot.

**Restoring the two halves is asymmetric on purpose, not symmetric for its own sake.** Redux panel state for a given panel is only used if dockview's own layout also restored successfully; dockview restoring is never conditioned on Redux state the other way. This was tried symmetric first and changed after tracing through what "layout missing, panel state kept" actually does: a panel manually reopened into an empty dockview host would get the same deterministic id and silently inherit old state, making it look restored when it wasn't. It should start clean unless the layout itself restored. The reverse direction has no equivalent problem — a restored panel's identity lives entirely in dockview's own params, so empty business state there is indistinguishable from a freshly opened panel. This is treated as a UI-behavior decision subject to iteration, not an architectural one — made once it was felt in practice, not argued to a conclusion in the abstract. If restoring layout without matching panel state later feels misleading in practice, this can be tightened into a fully symmetric restore rule; the architectural commitment is only that dockview layout and Redux panel state are persisted together and restored deliberately, not that this exact fallback behavior is permanent.

**Writes are debounced and dirty-tracked, not naive.** A pending write is flushed on unmount and on the page's `pagehide`/`beforeunload`, so a reload immediately after a change doesn't lose it. That flush is gated on an explicit dirty flag — an earlier, unconditional version of it caused a real bug: closing a stale, long-untouched background tab would re-persist that tab's old state and silently stomp a different, more-recently-active tab's newer write, purely because closing happened to trigger a write regardless of whether anything had actually changed.

## Consequences

- A panel kind gains real, working persistence (survives tab-switching, in-app navigation, reload, and an already-open tab is never disturbed by a different tab's edits) by adopting this same shape — keyed Redux slice, dockview-removal-triggered cleanup, the two-tier storage read/write pair — with no per-kind persistence code to invent.
- **Explicitly not solved, and not accidentally implied by anything above**: two tabs with genuinely simultaneous pending edits still resolve by write order (last one wins, non-destructively); a brand-new tab still seeds from whichever tab wrote most recently to `localStorage`; cross-_device_ sync has no answer at all yet, since `sessionStorage`'s isolation has no server-side equivalent. See `docs/initiatives/ui-workspace/research/state-management.md`'s "Cross-tab and cross-device coordination" section — real, wanted eventually, deliberately parked rather than guessed at.
- **Also explicitly deferred**: validating dockview's own serialized layout shape before calling `fromJSON()` on it (third-party, deeply recursive, not treated as a stable contract across library upgrades); signing or encrypting the persisted blob (no real secret can be kept client-side without a server to hold it, and today's data isn't sensitive enough to warrant it regardless); any of this surviving a future server-backed version's own trust boundary, which is a different, harder problem than anything solved here.
- Only the Flow Graph panel actually has this built today. Generalizing the pattern to other panel kinds, and building real cross-tab/cross-device coordination if it ever becomes a live pain point, are each their own future work — not blocked by this decision, but not included in it either.

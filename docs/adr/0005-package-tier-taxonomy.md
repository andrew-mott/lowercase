# ADR-0005: Package-tier taxonomy

Date: 2026-08-25
Status: Accepted

## Context

This initiative was a deliberate architectural audit, not primarily a placement-lookup problem. Several tiers already had homes that weren't fully satisfying: pure logic had no settled organizing tier of its own, it was unclear whether an exactly-one-port `Operations` shape was real or just a name, whether `services` was scoped and named correctly, and what `components` should be called and how it relates to `services`. The goal was to check each of these against the actual code already there — moving it, renaming it, removing what was dead — not just deciding on paper, though short of building anything new to really stress-test the boundaries; whether they hold is something only time will show. `docs/todo.md` had carried a growing, unresolved taxonomy sketch since before the `architecture-boundaries` initiative existed, itself replacing an earlier `use-cases` → `workflows`/`domains` reorg idea (from a since-deleted `ARCHITECTURE-NEXT.md`) that never sat right. A concrete secondary benefit, not the driving motivation: firmer boundaries also make it easier for new code — AI-authored or not — to land in the right place without guessing.

This ADR is not purely retroactive: the taxonomy was researched first (`docs/initiatives/architecture-boundaries/research/package-tier-taxonomy.md`), then checked against real code before being written down here — physical package moves (`functional-core/*`, `components/*`) and renames/dead-code removal (`services`→`app-services`, `web-app`→`workbench`, `packages/scheduler`, `packages/ui` deleted) were executed as their own PRs specifically because this initiative's own `Evolution` note found that discussion alone repeatedly misses things only real code surfaces. Seven of the eight tiers below were checked that way; the eighth (`Operations`) was not, and is marked accordingly.

## Decision

Eight tiers. `types`, `ports` (depends on `types`), and `functional core` (zero ports, zero I/O) form the shared foundation. `Operations` sits just one step below `functional core`, not as a peer of what depends on it — the same minimum-cost-above-zero, portable building-block role, just needing exactly one port, callable by whichever of `application services`, `components`, or the engine/worker already holds it. `specs`, `application services`, and `components` each depend on that foundation on their own terms — `ports`/`types` directly, `functional core`/`Operations` where useful — without depending on each other. `adapters` depend on that same foundation and nothing else — never imported by `application services`/`Operations`/`components`, only by `runtime`, the one composition root that wires a port to its concrete adapter:

- **`types`** — pure vocabulary: a shape a consumer can get without importing the package/library that produces it (an event payload's type without importing `zod`). Placement for a specific type, in order: does it cycle (needs a port or concrete class — disqualified), does it cross a boundary it shouldn't (`PrismaClient`, since `types` is deliberately Prisma-free), does the type define the reason a package exists (`StepArgs` stays in `specs` even though nothing forces it to), does any real consumer need only the type without the rest of its home package (if not, centralizing is ceremony).
- **`ports`** — interfaces depended-on-instead-of-the-concretion, verified by real usage as a type annotation outside `packages/ports` itself, not by an intent to someday swap implementations. Payoffs (build-graph decoupling via Turbo's per-package cache, test seams) hold even with a single implementation.
- **`specs`** — the flow-definition schema/parser, deliberately staying unsplit from its inferred types (unlike the `types`/`events` split already done): 9 of 10 cross-package consumers need the runtime Zod value, not just the shape, so the justification that earned the `events` split barely applies here. Also timing: `json-schema-migration` (the initiative right after this one) will restructure this relationship (schema generating types, not types manually kept in conformance) — splitting now risks doing structural work that gets reshaped almost immediately after.
- **`functional core`** (`packages/functional-core/*`) — zero ports, zero I/O, safe for anything to import directly. `flow-analysis`, `json-ref-binder` today. Naming convention for members: `<domain-word>-<agent-noun>`, not verb-object.
- **`application services`** (`packages/app-services`, classes unaffected — only the package name changed from `services`) — orchestrates one bounded, external, request/response-shaped interaction (an HTTP request, a CLI invocation) and is called directly by an app or `runtime`. Renamed specifically to stop "services" reading as "the event-driven, potentially-distributed pieces" — that's `components`, below.
- **`Operations`** — small units needing exactly one port to do one piece of work, never wired directly by `runtime`, never called by an app; whoever calls one (a service, `engine`, `worker`) already holds the port and threads it through. The one-port limit isn't arbitrary: needing more than one port at once means deciding a relationship between independent external capabilities, and that decision-making is what orchestration means — Operations exist specifically to stay below that line. **Status: speculative, included as a best-current-guess, not a proven tier.** `runFlow()` (`packages/use-cases/run-flow`) is the one clean real example, and it's small; no larger example exists yet. Every other multi-port candidate checked (`create-fork-spec.ts`'s `startForkedSim()`, `packages/artifacts`'s I/O-orchestration half once split from its pure logic) turned out to need decomposition rather than confirming the tier as-is — real evidence the boundary's diagnostic test works, not evidence a substantial Operation has actually been built. If this tier doesn't hold up once real code is built against it, the fix is a follow-up ADR superseding this section specifically — the other seven tiers are unaffected by that outcome.
- **`components`** (`packages/components/*`) — long-lived, self-driven by subscribing to the event bus (decides its own next action, rather than being called), and not infrastructure (real logic about how event flow should behave, not a swappable technology choice). `engine`, `worker`, `limiter`, `NodeRouter` (reclassified here from `adapters` — it self-subscribes to the bus and orchestrates across three ports at once, the same shape as `engine`/`worker`, not a thin single-port translator) sit in the critical path; `ObservabilityTap` passes the same test but taps the stream from outside the critical path. The system today is accurately described as **event-driven, structured as a modular monolith** — one process today, internal seams already shaped like a distributed system, deliberately not claiming any topology commitment it hasn't earned.
- **`adapters`** (`packages/adapters`, staying one package — no consumer outside `runtime` needs per-adapter build-cache decoupling, unlike `functional core`/`components`) — the inverse of `components`: implements exactly one port, no own lifecycle, not self-driven, called synchronously. Adapter logic is infrastructure mechanics only (how to open a file, run a query) — a decision about what data _means_ doesn't belong here, whatever concrete adapter it shows up in. May import `types`/`ports`/`functional core`; may not import another concrete adapter directly (checked, already clean). Whether an adapter could ever call an Operation is untested and more speculative than that — the intuition is that it'd be infrastructure reaching up into business logic, but nothing has actually required or ruled it out yet.

Also settled: `apps/web-app` → `apps/workbench` (the one naming outlier among `cli`/`desktop`/`http-server`, recovering the name already live throughout the actual source); a forward-looking, not-yet-needed convention that a `components` piece extracted into its own deployable belongs at `apps/<component-name>`; `packages/events` and `packages/db-prisma` are described precisely rather than forced into one tier — `events` genuinely straddles `functional core` (its Zod schemas) and `adapter` (`EmitterFactory`) and stays one package for the same cohesion reason `specs` does; `db-prisma` fits none of the eight tiers (deliberately Prisma-free `types` excludes it, it implements no port so isn't itself an adapter) and is better described than boxed. `packages/scheduler` and `packages/ui` are confirmed dead and removed.

Explicitly out of scope: `packages/tools` (governed by ADR-0006), `packages/replay`'s tier, the `packages/artifacts` I/O-orchestration split, `run-flow`'s internal decomposition, and the `components` tier's control-plane gap — see `docs/initiatives/architecture-boundaries/INITIATIVE.md`'s "Not yet scoped" section for current status on each.

## Consequences

- New code has an actual placement algorithm — a membership test per tier — instead of ad hoc judgment, the problem this ADR exists to solve.
- Seven tiers are validated by real execution — physical package moves and the renames/dead-code removal that followed — not just discussion. `Operations` is the one exception, included on its own explicit best-guess terms; expect it to be revisited once the relevant areas above actually get decomposed and a real example either confirms or breaks the one-port shape.
- Deliberately leaves real, already-identified work undone — see the out-of-scope list above.
- `packages/tools` stays outside this taxonomy entirely — its placement depends on ADR-0006, not this one.

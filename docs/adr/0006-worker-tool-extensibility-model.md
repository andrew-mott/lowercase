# ADR-0006: Worker/tool extensibility model — no tool registry

Date: 2026-08-25
Status: Accepted

## Context

The long-held intuition since early in this project was that tools are the extension point and something has to register them: a tool declares a capability, a registry tracks what's available, a step selects an implementation by name. That intuition was never pinned into a concrete, buildable shape, and `packages/tools`' own contract was left deliberately unclassified in ADR-0005's taxonomy pending this question (`research/package-tier-taxonomy.md`'s "Ambiguous packages" section).

Several concrete versions of "something has to register" were raised and pressure-tested against real scenarios, not just reasoned about abstractly: a tool declaring which existing step type's job-event envelope it can consume (a real, since-cut prior design from this project's own history); credential/secrets indirection as a reason to register; resource locality (GPU-bound local inference, grounded in a real earlier project — a hardcoded local speech-to-text → LLM → text-to-speech pipeline over a LAN) as a reason a tool might need to be "known" to a worker in advance. None held up. Checking `packages/tools/src/httpjson/httpjson.tool.ts` directly during this research retroactively invalidated the envelope-shape-registration idea specifically: the worker constructs an ordinary outbound HTTP request from a step's resolved args itself — the target never receives anything shaped by this project's internals, so there was never an envelope for a third party to declare support for.

## Decision

**There is no tool registry. The worker's fixed set of supported protocols is the entire extension mechanism.**

The worker owns all infrastructure coupling — the event bus, the queue, CAS, ref resolution, lifecycle. A protocol it speaks (`httpjson`, `mcp` today) is built into the worker, not a pluggable third-party-authored thing. Whatever's on the other end of a call is just the outside world — an existing HTTP API, an MCP server, written by someone who has never heard of this project. Extending the system = standing up a service that speaks a protocol the worker already supports; no registration step, no code shipped into or loaded by this repo, no plugin system. Extending the _set of protocols_ the worker itself speaks is this project's own work, not a third-party path.

A second, heavier path remains real without needing new design: running a separate worker instance, scoped to a specific tool's own hardware. This falls out of the existing per-tool-id job queue shape rather than requiring new mechanism, though it isn't available today as-is — `InMemoryQueue` is in-process-only and would need a distributed queue adapter first.

**Every registration justification raised was individually resolved without a registry:** secrets/credentials — a step can already carry auth headers to a credentialed endpoint via direct invocation; the actual fix for secrets safety (resolving a `secrets` ref scope at the worker level before dispatch, redacting the bus event) is orthogonal to whether anything is registered, and is out of scope for this ADR — a real, substantially-designed, not-yet-built future push (see `research/worker-tool-extensibility.md`'s "Open threads"). Resource locality — the tool deploys on the hardware; the worker, wherever it runs, reaches out over the network. Compute placement is solved by where the _service_ lives, not by the worker knowing about it in advance.

**"Tool" as a distinct concept is not settled vocabulary here** — it conflated "a protocol the worker speaks" with "whatever's on the other end of a call," and once separated there's nothing left for "tool" to denote on its own. This ADR does not retire, repurpose, or preserve that word; it names the worker's protocol/transport surface as the actual extension mechanism, whatever it ends up being called.

**Convenience step types are a first-party concern, not a third-party extension mechanism.** An opinionated, well-known-API-specific step (a Google Docs step, an OpenAI step) is real and worth having eventually, but it is the project's own accumulating library of shortcuts on top of protocols the worker already speaks — added the same way any feature is, consistent with flow-definition step types already being closed to third parties. Real, named cost: a convenience step hardcodes a specific external API's contract, which can drift silently as that API evolves; a generic protocol step degrades gracefully instead (a missing field fails cleanly).

**General principle governing the worker's posture: the system governs its own behavior toward the outside world, and never assumes the outside world's cooperation.** Retry, timeout, and backoff are the worker's own posture toward whatever it calls. A plain worker-side timeout (no completion within N seconds → treat as failed) is the settled v1 mechanism for a hung external call — not because heartbeating wouldn't be nicer, but because nothing entitles this system to assume a call target will proactively report its own health. A real heartbeat/liveness convention remains a legitimate, named, deliberately deferred future consideration.

**"The worker supports a protocol" requires a response-interpretability floor, not just wire connectivity.** `httpjson` is scoped to JSON specifically, and that scoping is deliberate, not incidental — it's the minimum structure the worker needs to turn a response into step outputs, a success/failure signal, and a storable CAS artifact at all. Every protocol the worker supports needs its own version of this floor; protocols differ in how expensive that floor is to establish (MCP carries its own discovery/negotiation; raw HTTP carries none, so the shape has to come from the flow author's own knowledge or a first-party convenience step).

**Explicitly unexercised, not confirmed:** the internal half of this decision — that `httpjson`/`mcp` already behave this way, and that the worker owning all infrastructure coupling while a tool owns none of it is how the system already works — is confirmed against real code, not asserted. The external half — that a genuine third party can stand up a service and extend this system with zero registration, zero coordination, and it just works — has never actually been tried against a real outside service. It is design intent, carried forward as a claim to validate the first time a real third-party integration is attempted, not a proven property of the system today.

## Consequences

- `packages/tools` is now classifiable relative to ADR-0005: it holds the worker's protocol bindings (`httpjson`, `mcp`), not a registry or a plugin surface — its contract is "the worker's fixed, first-party set of supported protocols," not an open extension point.
- No registry, plugin loader, or capability-declaration mechanism needs to be designed or built for third-party extension. Third-party extension guidance, if ever written, is "stand up a service that speaks a protocol this worker supports" — a short statement, not a guide substantial enough to be its own document (a previously-planned worker/tool extensibility guide was cut for this reason, and separately because the worker's own internal architecture — `packages/worker`'s known internal complexity — is itself a future rebuild target).
- The set of protocols the worker speaks remains this project's own, deliberate surface to grow (a generic HTTP transport beyond JSON, stdio/terminal, streaming — all real, named, not designed here).
- Secrets safety (the CAS/events leak surfaces, the `secrets` ref scope, encrypted-storage direction) is substantially designed but explicitly not built by this ADR — its own dedicated future push.
- If a real third-party integration attempt shows the "zero registration, it just works" claim doesn't hold, that's specifically the external half of this decision to revisit — a follow-up ADR, not a reason to doubt the internal half (worker owns infrastructure, protocols are first-party) that's already confirmed against real code.
